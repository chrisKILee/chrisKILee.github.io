01 — Root Cause

왜 단일 에이전트는 실패하는가

긴 코딩 작업을 AI 혼자 맡길 때 발생하는 두 가지 구조적 실패 원인입니다.

😰
문맥 불안 (Context Anxiety)
대화창이 꽉 찼다고 느끼는 순간, AI는 작업을 대충 마무리 지으려 합니다. 실제로 컨텍스트 한계에 도달하지 않았어도 "슬슬 마무리해야지" 증상이 나타납니다.
Claude Sonnet 4.5는 이 증상이 매우 강했으며, 컴팩션(대화 요약)으로는 해결되지 않았습니다. 완전한 컨텍스트 리셋이 필요했습니다.
🪞
자기 객관화 실패 (Self-Evaluation Bias)
자신이 만든 코드나 디자인을 스스로 평가하면, 아무리 형편없어도 "훌륭합니다"라고 답합니다. 특히 정답이 없는 디자인 영역에서 심각합니다.
해결책: 만드는 에이전트와 평가하는 에이전트를 분리합니다. 평가자를 까다롭게 튜닝하는 것이 생성자를 자기비판적으로 만드는 것보다 훨씬 쉽습니다.
💡 컴팩션(이전 대화를 요약하여 남기기)과 리셋(대화창을 완전히 비우고 다음 에이전트에게 상태 전달)은 다릅니다. 문맥 불안 해결에는 리셋만 효과가 있었습니다.
02 — Architecture

GAN에서 영감받은 3인조 구조

적대적 생성 신경망(GAN)의 핵심은 "만드는 놈"과 "평가하는 놈"을 분리하는 것입니다. 이 원리를 AI 에이전트 구조에 그대로 적용했습니다.

하네스 3인조 아키텍처 — GAN(적대적 생성 신경망)에서 영감받은 구조

P
Agent 01 — Planner
🗂️ 기획자
짧은 프롬프트를 상세한 제품 기획서로 확장합니다. 야심 차게 스코프를 잡도록 유도되며, 고수준 기술 설계에만 집중합니다.
1~4문장 입력을 전체 기능 스펙으로 확장
AI 기능을 스펙에 자연스럽게 엮을 기회 탐색
세부 구현 지시는 피함 (캐스케이딩 오류 방지)
프론트엔드 디자인 스킬로 비주얼 언어 정의
G
Agent 02 — Generator
⚙️ 생성자
기획서를 바탕으로 스프린트 단위로 코드를 작성합니다. 각 스프린트 종료 시 QA에 넘기기 전 자체 검토를 수행합니다.
스프린트별 기능 구현 (React, Vite, FastAPI, SQLite)
Git으로 버전 관리
평가자와 스프린트 계약 협상

E
Agent 03 — Evaluator

UI 기능, API 엔드포인트, DB 상태 검증
4가지 기준으로 점수 매기기
기준 미달 시 스프린트 실패 판정 + 상세 피드백
에지 케이스와 상호작용 흐름 적극 탐색
03 — Evaluation Criteria

주관적 디자인을 객관적으로 채점하는 법

"예쁘다"는 주관적인 기준을 평가자 프롬프트에 녹여넣기 위해 4가지 측정 가능한 기준을 정의했습니다.

기준 01
🎨 디자인 품질
색상, 타이포그래피, 레이아웃, 이미지가 결합해 일관된 분위기와 정체성을 만들어냅니까? 부품의 모음이 아닌 응집된 전체처럼 느껴지는가.
높은 가중치
기준 02
✨ 독창성
커스텀 의사결정의 흔적이 있습니까? 템플릿 레이아웃, 라이브러리 기본값, AI 특유의 패턴(흰 배경 위 보라 그라디언트 카드 등)은 감점 요소입니다.
가장 높은 가중치
기준 03
🔧 기술적 완성도
타이포그래피 계층, 여백 일관성, 색상 조화, 대비 비율 등 기본기 체크. 창의성 체크가 아닌 역량 체크입니다. 대부분 무난히 통과합니다.
낮은 가중치 (기본 통과)
기준 04
⚡ 기능성
미적 요소와 무관하게 사용성이 있습니까? 주요 기능을 찾아서 완료할 수 있습니까? 추측 없이 직관적으로 작동합니까?
낮은 가중치 (기본 통과)
🎯 독창성에 높은 가중치를 부여하자: AI는 뻔한 카드 레이아웃을 버리고, 체커보드 바닥이 있는 3D 공간에 미술 작품을 걸어놓은 CSS 퍼스펙티브 갤러리 룸을 만들었습니다. 10번째 반복에서 완전히 새로운 방향으로 피벗한 사례입니다.
04 — Sprint Contract

스프린트 계약: "뭘 만들고 어떻게 검증할지" 미리 합의

생성자와 평가자는 코드를 짜기 전에 반드시 이번 스프린트의 완료 기준에 합의합니다. 사람 개발팀의 스프린트 플래닝과 동일한 원리입니다.

01
생성자: 스프린트 제안서 작성
이번 스프린트에서 무엇을 구현할지, 성공 기준을 어떻게 검증할지 파일에 작성합니다.
02
평가자: 제안서 검토 및 수락/수정
파일을 읽고 기준이 검증 가능한지 확인합니다. 모호한 기준은 명확화를 요청합니다. 에이전트 간 통신은 파일로 합니다 (한 에이전트가 쓰면 다른 에이전트가 읽음).
03
생성자: 합의된 스펙대로 구현
계약된 기준을 염두에 두고 코드를 작성합니다. 스프린트 종료 시 자체 검토 후 QA 요청.
04
평가자: Playwright로 실제 테스트
브라우저를 직접 실행하고, 버튼을 클릭하고, API를 호출하며 계약 기준을 하나씩 검증합니다. 기준 미달 시 스프린트 실패 + 상세 원인과 수정 방법을 반환.

06 — Simplification

Opus 4.6이 나오자 하네스가 단순해졌다

"하네스의 모든 구성 요소는 '모델이 혼자서 못하는 것'에 대한 가정을 담고 있습니다. 그 가정이 맞는지 주기적으로 검증해야 합니다."

Opus 4.5 시절 하네스

01
컨텍스트 리셋 필수
문맥 불안 때문에 각 스프린트마다 새 에이전트로 완전히 교체해야 했음
02
촘촘한 스프린트 구조
작업을 잘게 분해해야만 에이전트가 완주할 수 있었음
03
매 스프린트 평가자 개입
스프린트마다 평가 루프를 돌려야 품질을 유지할 수 있었음

Opus 4.6 이후 하네스

01
자동 컴팩션으로 충분
Claude Agent SDK의 자동 컴팩션으로 컨텍스트 처리 — 리셋 불필요
02
스프린트 구조 제거
2시간 이상 스프린트 없이 연속 실행 가능 — 단순히 빌드하고 끝에 QA
03
필요할 때만 평가자 투입
모델 능력 범위 내 작업엔 평가자가 불필요 — 경계선 작업에만 투입
⚠️ 핵심 원칙: 새 모델이 출시되면 하네스를 처음부터 재검토하십시오. 불필요해진 구성 요소를 제거하고, 더 강력해진 모델로 새롭게 가능해진 조합을 찾아내십시오.

08 — Key Lessons

AI 엔지니어가 기억해야 할 3가지

Prithvi Rajasekaran이 정리한 하네스 설계의 핵심 원칙입니다.

🔬
모델에 맞게 실험하라
실제 문제에 대한 모델의 추적 데이터를 직접 읽고, 원하는 결과를 얻기 위한 성능을 조율하십시오. 추상적인 벤치마크가 아닌 당신의 실제 태스크를 기준으로.
✂️
복잡한 작업은 분해하라
문제의 각 측면에 특화된 에이전트를 투입하십시오. 전문화로 인한 여유 공간이 생깁니다. 기획자, 생성자, 평가자를 분리한 것이 핵심 설계 결정이었습니다.
🔄
새 모델이 나오면 하네스를 재검토하라
더 이상 필요 없는 구성 요소는 제거하고, 더 강력해진 모델로 이전에는 불가능했던 새로운 조합을 찾아내십시오. 하네스는 살아있는 시스템입니다.
"모델이 향상될수록 흥미로운 하네스 조합의 공간이 줄어드는 것이 아닙니다. 오히려 그 공간이 이동합니다. AI 엔지니어에게 앞으로도 계속되는 과제는 다음 새로운 조합을 찾아내는 것입니다."
— Prithvi Rajasekaran, Anthropic Labs
09 — Summary

한 눈에 보는 하네스 설계

핵심 개념 정리표입니다.
