01

왜 토큰이 이렇게 빨리 사라지나

코드 생성에 토큰이 쓰이는 게 아닙니다. 터미널 출력과 대화 기록 누적이 주범입니다.

Claude Code는 매 메시지마다 전체 대화 기록을 포함해서 API 요청을 보냅니다. 30분 세션에서 약 60개의 CLI 명령어를 실행하면, 터미널 출력만으로 약 21만 토큰이 소비될 수 있다는 주장이 있습니다 (단, 이 수치는 단일 사용자의 측정치로 독립 검증은 되지 않았습니다).

cargo test 한 번 실행 시 독립 측정 결과 약 4,800토큰이 소비됩니다. 에이전트에게 실제로 필요한 정보는 "262개 통과, 0개 실패" 한 줄인데도요.

02

도구 없이 지금 바로 — 5가지 방법

RTK 설치 전에 먼저 해볼 수 있는 방법들입니다. 비용 없고, 리스크 없습니다.

  1. 1
    /context 로 지금 상태 확인
    /context를 실행하면 시스템 프롬프트, MCP 도구, 메모리 파일, 스킬이 각각 얼마나 차지하는지 보입니다. 안 쓰는 MCP 서버는 연결만 돼 있어도 도구 목록이 컨텍스트에 들어갑니다. 불필요한 MCP/스킬을 끄면 시작 전 컨텍스트 사용률이 35%대에서 10%대로 낮아질 수 있습니다.
  2. 2
    CLAUDE.md 다이어트
    CLAUDE.md는 모든 세션에서 로딩됩니다. 장문의 프로젝트 설명은 별도 파일로 분리하고 필요할 때만 참조하게 하세요. 여기에 한 줄 추가하는 것만으로도 응답 토큰이 줄어듭니다: 가능한 한 간결하게 응답하고, 불필요한 인사나 부연을 생략해.
  3. 3
    주제가 바뀌면 /clear
    대화가 길어질수록 토큰이 기하급수적으로 늘어납니다. 인증 작업을 마치고 프론트엔드로 넘어가면 인증 관련 대화 기록이 계속 딸려갑니다. 주제 전환 시 /clear로 초기화하세요. 이것만으로도 체감 효과가 큽니다.
  4. 4
    정확한 프롬프트 작성
    모호한 프롬프트는 Claude가 더 많은 파일을 읽고 더 넓은 범위를 탐색하게 만듭니다.
    X "버그 고쳐줘" → O "app/auth.py의 로그인 함수에서 토큰 검증 로직을 수정해줘"
    파일 경로와 함수명을 특정하면 탐색 범위가 좁아집니다.
  5. 5
    Opus · Ultrathink는 필요할 때만
    Ultrathink는 복잡한 아키텍처 설계, 어려운 논리 추론에만 필요합니다. 단순 수정이나 테스트 실행에 켜두면 추론 토큰만 낭비됩니다. 간단한 편집이나 테스트 실행은 Sonnet으로 충분합니다.
03

RTK(Rust Token Killer)란

Claude Code와 터미널 사이에 앉는 CLI 프록시. Bash 훅으로 터미널 출력을 압축합니다.

RTK는 Claude Code의 PreToolUse Bash 훅을 이용해 에이전트가 실행하는 명령어를 투명하게 가로챕니다. 4가지 전략으로 출력을 압축합니다.

필터링
주석·공백·메타데이터 제거
프로그레스 바, 빈 줄, 주석 등 모델에게 불필요한 정보를 삭제합니다.
그루핑
디렉토리·오류 유형별 집계
47개의 .tsx 파일을 나열하는 대신 "components/ (47 .tsx files)"로 묶습니다.
절단(Truncation)
앞뒤 맥락만 보존
1,000줄 출력에서 앞뒤 N줄만 전달해 핵심 맥락을 유지합니다.
중복 제거
반복 메시지를 카운트로
"Error: timeout"이 347번 반복되면 "Error: timeout (×347)"으로 압축합니다.

⚠️ 작동 범위 제한: RTK는 Bash 훅으로만 작동합니다. Claude Code의 내장 도구인 Read, Grep, Glob은 Bash 훅을 통과하지 않으므로 RTK가 자동 적용되지 않습니다.

설치 명령어 (macOS/Linux):

brew install rtk-ai/tap/rtk
rtk init -g    # Claude Code 훅 자동 설치
04

RTK 주장 수치 — 팩트체크

공식 사이트와 마케팅 글에서 제시된 수치를 GitHub 이슈, 독립 블로거 측정, 공식 문서와 대조했습니다.

"수치는 대부분 테스트 성공 케이스 기준입니다. 실패 시나리오는 역효과가 날 수 있습니다."

GitHub rtk-ai/rtk 이슈 분석, 2026-03
주장 판정 근거
cargo test: 155줄 → 3줄 (98% 감소) 확인됨 독립 블로거(codestz.dev, rushis.com) 측정 수치에서 4,823 → 11 토큰(99%) 동일하게 보고. 단, 테스트 성공 시에만 해당. 실패 시 디버깅에 필요한 정보도 제거됨.
git status: 119자 → 28자 (76% 감소) 확인됨 여러 출처에서 일관되게 인용. 검증 가능한 단순 수치.
git push: 15줄 → 1줄 (95% 감소) 확인됨 공식 문서 수치. 성공 케이스 기준.
한 사용자 2주간 1,000만 토큰 절약, 89% 감소 미확인 Kilo-Org 디스커션에서 원저자 본인의 자가 보고. 독립 재현 없음. 공식 사이트는 "2,900개 이상의 실제 명령어에서 측정"이라 표기하지만 방법론 미공개.
30분 세션 15만 → 4만 5천 토큰 (70% 감소) 단일 사례 codestz.dev 블로거의 직접 측정. 단일 사례로 보편화 불가. 프로젝트 유형, 명령어 패턴에 따라 크게 다름.
10ms 미만 동작 미검증 GitHub README 명시. 단순 텍스트 파싱 특성상 합리적이나 독립 검증 없음.
의존성 제로 조건부 확인 MIT 바이너리 배포 기준 사실. Cargo로 소스 빌드 시에는 Rust 툴체인 필요.
총 60% 이상 토큰 절약 과장 가능성 최적 조건(성공 케이스, 특정 명령어 집중 사용)의 최대치. 실패 디버깅이 많은 세션에서는 오히려 토큰이 증가할 수 있음 (이슈 #690 사례 참조).
05

실제 사용자 후기 — 부정 사례

"AI가 오판을 하게 만든다"는 후기의 실체. 공개된 GitHub 이슈로 확인된 사례들입니다.

이슈 #690 — 해결됨 (PR #729, #730)
Playwright 테스트 과도한 압축 → 에이전트 디버깅 루프
RTK가 테스트 실패 시 DOM 스냅샷, 로케이터 상세, expected/received 차이, 재시도 타임라인을 "노이즈"로 간주해 모두 제거했습니다. 결과: 에이전트가 디버깅 루프에 빠져 170 도구 호출, 약 360만 토큰, 60분 소모. RTK 미적용 시 예상 약 20분/100만 토큰. 이것이 "지나치게 축약해서 AI가 오판하게 만든다"의 실제 사례입니다.
이슈 #923, #914 — 현재 미해결 (OPEN)
gh run view, dotnet build에서 불완전한 출력 생성
gh run view와 dotnet build 명령에서 잘못된 필터링으로 에이전트가 빌드 상태를 오판할 수 있는 false negative 케이스가 보고됐습니다. 현재 미해결 상태입니다.
이슈 #897 — P1-CRITICAL, 미해결
grep 하위 프로세스 메모리 누수 → macOS 커널 패닉
macOS 환경에서 grep 하위 프로세스의 메모리 누수가 커널 패닉을 유발하는 심각한 안정성 버그. 현재 미해결 상태입니다.

핵심 역설: 성공 케이스에서는 토큰을 절약하지만, 실패 케이스에서 에이전트가 필요한 정보를 잃어 디버깅 반복이 늘어나면 오히려 더 많은 토큰을 소모합니다. 이 역설이 "지나치게 축약" 후기의 본질입니다.

06

보안 우려사항 — 설치 전에 알아야 할 것

Claude Code가 의뢰한 자체 보안 리뷰(이슈 #640)에서 발견된 취약점들입니다. 공개된 사실입니다.

Critical
셸 인젝션 취약점 (C-1)
사용자 명령을 sh -c에 비살균 상태로 전달. RTK의 훅 재작성 특성상 LLM 프롬프트 인젝션 체인을 형성할 수 있어 특히 위험합니다.
High
동의 없는 텔레메트리 (H-1)
설치 시 사용자 동의 없이 호스트명+사용자명으로 파생된 영구 식별자와 함께 워크플로우 패턴을 외부 서버로 전송합니다. 세션 간 추적 가능한 행동 지문이 생성됩니다.
High
Claude Code 권한 우회 (이슈 #886)
RTK의 Bash 훅이 Claude Code의 ask/deny 권한 목록에 없는 명령을 사용자 확인 없이 실행합니다. Claude Code의 최소 권한 원칙을 훼손. 현재 미해결입니다.
Medium
시크릿 비마스킹 저장 (M-2)
SQLite DB에 민감 정보가 마스킹 없이 저장될 수 있습니다. API 키, 비밀번호 등이 포함된 명령어 출력이 로컬 DB에 남을 수 있습니다.
07

결론 — 누가 써도 되고, 누가 조심해야 하나

RTK의 토큰 절감 효과는 실재합니다. 하지만 마케팅 수치와 현실 사이에는 분명한 간극이 있습니다.

항목 평가
핵심 가치 제안 유효 — 성공 케이스에서의 토큰 절감은 측정 가능한 사실
마케팅 수치 부분적 과장 — 최적 조건(테스트 성공, 단일 측정) 기준. 실패 시나리오 미포함
성숙도 낮음-중간 — 184개 열린 이슈, P1-Critical 버그 미해결, 보안 취약점 다수
보안 위험 실재함 — 동의 없는 텔레메트리, Claude Code 권한 우회(미해결)
권장 대상
  • ✓ API 직접 과금(pay-per-token) 사용자
  • ✓ 대규모 자동화 파이프라인 운영자
  • ✓ 성공 케이스 위주의 CI/CD 작업
  • ✓ 개인 개발 환경, 보안 정책 유연한 경우
주의 대상
  • ✗ 보안 정책이 엄격한 팀/기업 환경
  • ✗ 복잡한 디버깅 세션이 많은 프로젝트
  • ✗ Playwright/E2E 테스트 집중 작업
  • ✗ 민감한 시크릿이 터미널에 자주 출력되는 환경

"RTK 설치 전에 먼저 /clear 습관, CLAUDE.md 다이어트, 불필요한 MCP 비활성화부터 하세요. 이것만으로도 상당한 효과가 있습니다."
