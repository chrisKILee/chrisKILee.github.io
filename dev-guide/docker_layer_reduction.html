Dockerfile 레이어 줄이기 — 8가지 실전 기법

레이어가 왜 이미지를 무겁게 만드는지 먼저 이해하고, RUN 합치기·멀티스테이지 빌드·캐시 정리로 더 작고 빠르게 pull 되는 이미지를 만드는 법.

난이도 · 중급 읽기 · 약 12분 업데이트 · 2026.07.23 대상 · Docker / Dockerfile

개요

Docker 이미지는 파일시스템 변경을 나타내는 읽기 전용 레이어(layer)가 쌓인 구조입니다. 레이어는 캐싱과 공유라는 강력한 이점을 주지만, 불필요하게 많아지면 이미지가 커지고, pull 이 느려지고, 디버깅이 복잡해집니다. 어떤 명령이 레이어를 만드는지, 그리고 그 수를 어떻게 줄이는지 이해하는 것이 효율적인 Dockerfile 작성의 핵심입니다.

TL;DR

핵심은 네 가지로 압축됩니다 — ① 여러 RUN을 &&로 합치고, ② 파일을 만든 같은 레이어에서 정리하고, ③ 멀티스테이지 빌드로 빌드 산출물을 통째로 버리고, ④ COPY를 캐시 효율에 맞게 통합합니다. 이 중 영향이 가장 큰 것은 멀티스테이지 빌드입니다.

레이어가 왜 중요한가 — 가산적(additive) 구조

가장 먼저 알아야 할 원리는 Docker 레이어가 가산적(additive)이라는 점입니다. 어떤 레이어에서 파일을 삭제해도 이미 하위 레이어에 저장된 데이터는 사라지지 않습니다. 삭제는 하위 레이어의 바이트를 지우는 것이 아니라, 새 레이어에 "이 파일은 없음"이라는 표시(whiteout)를 추가할 뿐이기 때문입니다. 그래서 "설치 후 다음 RUN에서 삭제"하면 이미지 크기는 전혀 줄지 않습니다.

어떤 명령이 레이어를 만드나

모든 Dockerfile 명령이 레이어를 만드는 것은 아닙니다. 실제 파일시스템을 변경하는 명령만 새 레이어를 생성하고, 메타데이터만 설정하는 명령은 레이어를 만들지 않습니다.

명령레이어 생성설명
RUN생성명령을 실행하고 그 결과를 저장
COPY생성빌드 컨텍스트에서 파일 복사
ADD생성파일 복사 (추가 기능 포함)
WORKDIR경우에 따라때때로 최소한의 엔트리 생성
FROM ENV EXPOSE안 함메타데이터만 설정 — 파일시스템 변경 없음
LABEL CMD ENTRYPOINT ARG안 함
그래서 레이어를 줄이는 작업의 대부분은 결국 RUN·COPY·ADD 세 명령을 어떻게 다루느냐로 귀결됩니다.

기법 1RUN 명령 합치기

각 RUN 명령은 별도의 레이어를 만듭니다. 아래처럼 설치를 여러 줄로 쪼개면 그만큼 레이어가 늘어납니다. &&와 줄바꿈(\)으로 하나의 RUN으로 합치면 5개 레이어가 1개로 줄어듭니다.

Before · 6 레이어
FROM ubuntu:22.04
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y git
RUN apt-get install -y wget
RUN rm -rf /var/lib/apt/lists/*
After · 1 레이어
FROM ubuntu:22.04

RUN apt-get update && \
    apt-get install -y --no-install-recommends \
      curl \
      git \
      wget \
    && rm -rf /var/lib/apt/lists/*
효과 5개 RUN이 1개로 줄고, 정리(rm -rf)가 같은 레이어 안에서 일어나 레이어 크기까지 함께 감소합니다. --no-install-recommends는 권장 패키지를 제외해 크기를 더 줄여줍니다.

기법 2파일을 만든 같은 레이어에서 정리

다른 레이어에서 삭제한 파일은 이미지 크기를 줄이지 못합니다(FIG.1). 레이어는 가산적이기 때문입니다. 빌드 도구처럼 임시로만 필요한 것은 설치·사용·삭제를 한 RUN 안에서 끝내야 합니다.

Bad · 별도 레이어에서 정리
RUN apt-get update && apt-get install -y build-essential
RUN make install
RUN apt-get purge -y build-essential && apt-get autoremove -y
# build-essential 은 첫 번째 레이어에 그대로 남아 있음
Good · 같은 레이어에서 정리
RUN apt-get update && \
    apt-get install -y --no-install-recommends build-essential && \
    make install && \
    apt-get purge -y --auto-remove build-essential && \
    rm -rf /var/lib/apt/lists/*
핵심 원칙 "설치했다가 나중에 지운다"가 아니라 "같은 명령 안에서 설치·사용·삭제를 모두 끝낸다"가 되어야 합니다.

기법 3멀티스테이지 빌드

멀티스테이지 빌드는 빌드 스테이지의 레이어를 최종 이미지에서 통째로 버리고, 마지막 스테이지의 레이어만 남깁니다. 컴파일러·개발 의존성·소스코드 등 런타임에 필요 없는 모든 것을 자연스럽게 제거하는 가장 강력한 방법입니다. 

# Stage 1: 빌드 (최종 이미지에서 폐기됨)
FROM node:20 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: 프로덕션 (최종 이미지)
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
영향 Node·npm·소스·빌드도구를 담은 builder 스테이지 레이어(10개 이상)가 완전히 사라지고, 최종 이미지에는 nginx 베이스 레이어 + COPY 레이어 1개만 남습니다.

기법 4COPY 명령 통합

각 COPY도 레이어를 만듭니다. 다만 무작정 하나로 합치기보다, 변경 빈도가 다른 것끼리 나눠 빌드 캐시 효율을 지키는 것이 정답입니다. 의존성 정의 파일은 자주 바뀌지 않으니 소스코드와 분리해 별도 COPY + RUN으로 캐싱합니다.

덜 최적 · 4개 COPY 레이어
COPY package.json /app/
COPY package-lock.json /app/
COPY tsconfig.json /app/
COPY src/ /app/src/
균형 · 캐시 효율 + 레이어 절감
WORKDIR /app

# 의존성은 덜 바뀜 — 따로 캐싱
COPY package.json package-lock.json ./
RUN npm ci

# 소스는 자주 바뀜
COPY . .
주의 레이어 수만 좇아 COPY를 전부 합치면 소스 한 줄만 바꿔도 npm ci가 매번 다시 도는 캐시 미스가 납니다. 레이어 절감과 캐시 효율의 균형이 핵심입니다.

기법 5.dockerignore 활용

.dockerignore는 레이어 수를 직접 줄이진 않지만, COPY 레이어에 불필요한 파일이 들어가는 것을 막아 레이어 크기를 줄입니다. .git, node_modules, 테스트·캐시 디렉터리, 시크릿 파일을 반드시 제외하세요. 

node_modules
.git
.gitignore
*.md
.env
.env.*
docker-compose*.yml
Dockerfile*
.dockerignore
coverage/
.nyc_output/
test/
__pycache__
*.pyc
.pytest_cache
보안 겸용 .env·시크릿·.git 히스토리가 이미지에 섞여 들어가는 사고를 막는 1차 방어선이기도 합니다.

기법 6Heredoc 으로 파일 인라인 생성

설정 파일 하나를 넣으려고 COPY 레이어를 추가하는 대신, Heredoc 문법으로 Dockerfile 안에서 파일을 바로 생성할 수 있습니다. 맨 위에 # syntax=docker/dockerfile:1 지시문이 필요합니다.

Before · 2개 COPY 레이어
COPY nginx.conf /etc/nginx/nginx.conf
COPY supervisord.conf /etc/supervisor/conf.d/supervisord.conf
After · 인라인 생성
# syntax=docker/dockerfile:1

COPY <<EOF /etc/nginx/nginx.conf
worker_processes auto;
events { worker_connections 1024; }
http {
    server {
        listen 80;
        location / { root /usr/share/nginx/html; }
    }
}
EOF
전제 Heredoc 문법은 BuildKit이 필요합니다. Docker Engine 23.0(2023-02)부터 BuildKit이 기본 빌더라 별도 설정 없이 동작하며, # syntax=docker/dockerfile:1 지시문은 이를 보장하는 표준 방법입니다.

기법 7--squash 플래그

docker build --squash는 새로 만들어진 빌드 레이어들을 하나로 합쳐 줍니다. 

docker build --squash -t myapp:squashed .
주의 · 실험적 기능 --squash는 실험적(experimental) 기능이며, 이미지 간 레이어 공유가 줄어드는 단점이 있습니다. 일반적으로 멀티스테이지 빌드가 더 나은 결과를 주므로 그쪽을 먼저 고려하세요.

기법 8패키지 매니저 캐시 최소화

패키지 매니저는 캐시를 남깁니다. "만들었다가 지우기"보다 애초에 캐시를 안 만드는 플래그(--no-cache 계열)를 쓰는 편이 깔끔합니다. 매니저별 관용구는 아래와 같습니다.

매니저관용구
apt (Debian/Ubuntu)rm -rf /var/lib/apt/lists/*
apk (Alpine)apk add --no-cache
pip (Python)pip install --no-cache-dir
npm (Node.js)npm ci --omit=dev && npm cache clean --force
dnf/yum (RHEL/Fedora)dnf clean all && rm -rf /var/cache/dnf

apt

RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*

apk · pip · npm · dnf

RUN apk add --no-cache curl

RUN pip install --no-cache-dir -r requirements.txt

RUN npm ci --omit=dev && npm cache clean --force

RUN dnf install -y curl && \
    dnf clean all && \
    rm -rf /var/cache/dnf

레이어 확인·측정

추측하지 말고 측정하세요. 레이어 수와 각 레이어 크기를 직접 확인하는 명령입니다.

# 레이어 개수 세기
docker inspect myapp:latest --format='{{len .RootFS.Layers}}'

# 각 레이어의 크기 보기
docker history myapp:latest --format "table {{.CreatedBy}}\t{{.Size}}"

# 두 버전의 총 크기 비교
docker history myapp:v1 --human=false --no-trunc --format "{{.Size}}" | paste -sd+ | bc
docker history myapp:v2 --human=false --no-trunc --format "{{.Size}}" | paste -sd+ | bc
팁 docker history의 각 행이 하나의 레이어입니다. 크기가 큰 행을 먼저 찾아 그 RUN/COPY부터 손보면 효과가 가장 큽니다.

Before / After 종합 예제

지금까지의 기법을 Python(Flask) 이미지 하나에 모두 적용해 보겠습니다.

Before · 최적화 이전
FROM python:3.11
RUN apt-get update
RUN apt-get install -y gcc
RUN apt-get install -y libpq-dev
RUN pip install flask
RUN pip install gunicorn
RUN pip install psycopg2
COPY requirements.txt /app/requirements.txt
COPY app.py /app/app.py
COPY config.py /app/config.py
COPY templates/ /app/templates/
WORKDIR /app
RUN apt-get remove -y gcc
RUN rm -rf /var/lib/apt/lists/*
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
After · 멀티스테이지 + 통합 + slim
FROM python:3.11-slim AS builder

WORKDIR /app
COPY requirements.txt .
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc libpq-dev && \
    pip install --no-cache-dir -r requirements.txt && \
    apt-get purge -y --auto-remove gcc && \
    rm -rf /var/lib/apt/lists/*

FROM python:3.11-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y --no-install-recommends libpq5 && \
    rm -rf /var/lib/apt/lists/*
COPY --from=builder /usr/local/lib/python3.11/site-packages/ /usr/local/lib/python3.11/site-packages/
COPY --from=builder /usr/local/bin/gunicorn /usr/local/bin/gunicorn
COPY . .
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
달라진 점 멀티스테이지 빌드 · RUN 통합 · python:3.11-slim 베이스 · COPY 정리 · 런타임엔 gcc 대신 libpq5만 남김 — 훨씬 작고 레이어가 적은 최종 이미지가 됩니다.

최적화 체크리스트

  • 연속된 RUN을 && + \로 하나로 합쳤는가
  • 임시 파일·빌드도구를 같은 레이어에서 삭제했는가
  • 빌드 산출물만 필요하면 멀티스테이지 빌드를 썼는가
  • 의존성 COPY와 소스 COPY를 캐시 목적에 맞게 분리했는가
  • .dockerignore로 불필요·민감 파일을 제외했는가
  • 패키지 매니저에 --no-cache 계열 플래그를 적용했는가
  • -slim/alpine 등 가벼운 베이스 이미지를 골랐는가
  • docker history로 큰 레이어를 실제로 확인했는가

요약

레이어를 줄이는 일은 결국 RUN 명령을 합치고, 파일을 만든 같은 레이어에서 정리하고, 멀티스테이지 빌드를 쓰고, COPY를 통합하는 것으로 귀결된다. OneUptime — How to Reduce the Number of Layers in a Dockerfile

가장 큰 효과는 멀티스테이지 빌드에서 나옵니다 — 빌드 스테이지 전체를 버리기 때문입니다. 그다음이 RUN 통합과 같은-레이어 정리입니다. 레이어 수 자체보다 "각 레이어에 무엇이 실제로 저장되는가"를 보는 관점이 핵심입니다.
