Knowledge Augmentation · 2026-08-30

RAG vs. CAG vs. MAG

원 논문(arXiv)과 Anthropic·OpenAI·Google 공식 문서를 직접 읽고 정리했습니다. 결론부터 말하면 세 약어는 대등하지 않고, 실무 분기선은 약어가 아니라 지식베이스 크기입니다.

근거: arXiv 원문 7편 + 벤더 공식 문서 10건 (2026-08-30 직접 확인) · 계기가 된 SNS 요약물은 08절에 참고로 수록
한 줄 결론

셋은 대등한 3대 패러다임이 아닙니다. RAG만 확립된 표준이고, CAG는 5쪽짜리 short paper의 신조어, MAG는 논문 한 편의 제목에만 등장한 약어입니다.

실무 분기선은 세 약어가 아니라 “지식베이스가 200K 토큰을 넘는가” 하나입니다 — 이건 Anthropic 공식 문서가 명시한 기준입니다. 넘지 않으면 통째로 컨텍스트에 넣고 prompt caching(=사실상 CAG), 넘으면 RAG. 세션을 넘는 사용자별 상태가 필요하면 그 위에 메모리 스토어를 얹습니다.

그리고 셋은 배타적 선택지가 아닙니다. CAG 논문 저자 본인이 결론에서 하이브리드를 권하고, Anthropic의 RAG 개선안(Contextual Retrieval)은 내부적으로 캐싱을 씁니다.

이 페이지의 근거 순위

본문의 모든 정의·수치는 ① 원 논문(arXiv) → ② 벤더 공식 문서 → ③ 프레임워크 공식 문서 순으로만 인용했습니다. 기술 블로그·유튜브·SNS 요약물은 근거로 쓰지 않았습니다.

이 주제를 파게 된 계기는 인스타그램에 널리 공유된 카드뉴스였지만, SNS 게시물은 신뢰도가 가장 낮은 축이라 근거가 아니라 검증 대상으로만 다룹니다. 해당 이미지는 08절에 참고 자료로 배치했고, 1차 출처와 어긋나는 두 지점은 03절에 따로 정리했습니다.

01먼저 — 세 약어는 같은 급이 아니다

비교표를 만들기 전에 확인해야 할 것은 “이 약어들이 실제로 통용되는가”입니다. 이 SNS 요약물은 셋을 나란히 놓지만, 1차 출처를 따라가면 무게가 전혀 다릅니다.

MAG에 대한 판정 — 자세히

(a) 이 약어를 쓰는 1차 출처가 있는가 → 있습니다. 창작은 아닙니다. 다만 실질적으로 논문 1편이 전부입니다. 저자들의 후속 확장판이 제목에서 약어를 뺀 것은, 저자 본인들도 이 약어를 밀지 않았다는 신호로 읽힙니다.

(b) 학계는 같은 개념을 뭐라 부르는가 → 압도적으로 agent memory / long-term memory for LLM agents입니다. Mem0 논문 제목은 “Scalable Long-Term Memory”, MemGPT는 “LLMs as Operating Systems”이고, LangGraph 공식 용어는 long-term memory·BaseStore, Anthropic 공식 용어는 memory tool입니다. 어느 쪽도 MAG를 쓰지 않습니다.

02세 방식이 실제로 하는 일

이름의 무게는 다르지만, 각 방식이 가리키는 기술적 실체는 셋 다 실재합니다. 지식을 모델에 넣는 위치가 각각 외부 인덱스 / 컨텍스트 KV 캐시 / 쓰기 가능한 메모리 스토어로 다릅니다.

Retrieval

RAG

Retrieval-Augmented Generation
arXiv:2005.11401 · NeurIPS 2020

확립된 표준

파라메트릭 메모리(모델 가중치)와 비파라메트릭 메모리(외부 dense 인덱스)를 결합. 원 논문 구성은 BART-large 400M + DPR, 코퍼스는 Wikipedia 2,100만 문서를 100단어 청크로 색인.

  • 규모 상한이 사실상 없음 — 외부 인덱스에 위임
  • 데이터가 바뀌면 인덱스만 갱신하면 됨
  • 출처 추적·인용이 구조적으로 가능
  • 검색 실패가 곧 답변 실패 — Anthropic 측정 baseline 실패율 5.7%(top-20)
  • 매 쿼리에 임베딩·조회·랭킹 왕복이 붙음
Cache

CAG

Cache-Augmented Generation
arXiv:2412.15605 · WWW ’25 short

신조어 · 벤더 미채택

검색을 우회하고 관련 자료 전체를 컨텍스트에 사전 로드한 뒤 KV cache로 고정. 3단계 — 사전 로딩 → 캐시로 추론 → 붙은 토큰을 truncate해 캐시 리셋. 논문 실험은 Llama 3.1 8B.

  • 매번 전체 문서를 넣는 방식(ICL) 대비 압도적으로 빠름
  • 검색 단계가 없어 파이프라인이 단순
  • 상용 API에서는 prompt caching으로 바로 구현됨
  • BM25 sparse RAG보다 느림 — 논문 표에서 확인 (아래 04절)
  • 지식이 커지면 “impractical”이라고 논문이 명시
Memory

MAG

Memory-Augmented Generation
arXiv:2505.22101 (제목 약어)

표준 용어 아님

MemOS는 메모리를 parametric(가중치) · activation(KV-cache) · plaintext(문서·프롬프트) 3종으로 나누고, MemCube라는 표준 단위로 스케줄링·접근제어·라이프사이클을 통일하자고 제안합니다.

  • 세션·스레드를 넘는 사용자별 상태 유지
  • Mem0 측정: full-context 대비 p95 지연 91%↓, 토큰 90%+ 절감
  • 상용 구현 존재 — Anthropic memory tool, LangGraph Store
  • 약어가 사실상 미통용 — 소통 시 “에이전트 메모리”가 안전
  • path traversal·파일 무한증식 등 운영 리스크가 문서에 명시됨

031차 출처와 대조 — 어긋나는 두 지점

널리 공유되는 SNS 요약물(08절에 원본 수록)이 가장 강조한 메시지는 “CAG는 가장 빠르고 RAG를 대체한다”입니다. 그런데 CAG 논문의 실제 표를 열어보면 논문 자신의 수치와 반대입니다. SNS 요약물을 근거로 삼으면 안 되는 이유를 보여주는 사례라 따로 정리했습니다.

SNS 요약물의 주장1차 출처가 말하는 것판정
CAG는 ≈0 ms TTFT, 세 방식 중 Fastest CAG 논문 Table(HotPotQA, large 85k): CAG 2.2631초 vs BM25 sparse RAG 0.6675초. CAG가 압도하는 상대는 RAG가 아니라 매번 전체 문서를 넣는 ICL(92.08초)입니다. 반대
CAG가 RAG를 대체하는 상위 방식 같은 논문 BERTScore, HotPotQA large: CAG 0.7407 < sparse top-5 0.7535. 논문 결론도 “hybrid approaches that combine preloading with selective retrieval”를 권합니다. 반대
MAG가 3대 패러다임의 하나 arXiv:2505.22101 제목에만 등장하는 약어. 저자들의 후속 확장판은 제목에서 뺐습니다. 근거 부족
RAG는 지연·복잡도가 높은 구식 방식 방향은 맞지만 정도가 과장. sparse(BM25) RAG의 검색 시간은 0.0008초로 무시할 수준입니다. 느린 것은 dense 검색(0.38~0.42초)입니다. 부분적
CAG 예시로 “Gemini 2.0 → 2M / Claude 3.5 → 200K” 게시 시점(2026-08) 기준으로 이미 지난 세대 모델을 인용하고 있습니다. 컨텍스트 상한은 모델 세대마다 바뀌므로 조회 시점을 명기해야 합니다. 시점 주의

05“롱컨텍스트 시대에 RAG는 죽었다”는 사실인가

아닙니다. “RAG는 끝났다”고 말한 1차 출처는 이번 조사에서 확인되지 않았습니다. 벤더 문서들의 실제 입장은 “죽었다”가 아니라 “임계값 이하에서는 쓰지 마라”입니다.

“If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt.”

Anthropic — Introducing Contextual Retrieval

주목할 것은 Anthropic이 실제로 한 일입니다. RAG를 버린 게 아니라 RAG를 개선했습니다 (Contextual Retrieval). 그리고 Google의 처방도 롱컨텍스트의 짝으로 RAG 제거가 아니라 context caching을 듭니다. Google 문서는 needle-in-haystack이 “많은 경우 최대 99% 정확도”라면서도, “여러 개의 needle을 찾는 경우에는 같은 정확도가 나오지 않는다”고 한계를 함께 명시합니다.

06실제로는 섞어 쓴다

1차 출처들이 명시적으로 혼합을 지시하거나, 이미 혼합 구조입니다.

  • RAG + caching — Anthropic Contextual Retrieval은 각 청크의 맥락을 생성할 때 prompt caching으로 원문 재처리 비용을 제거했고, 그 결과 비용이 문서 100만 토큰당 $1.02(Claude 3 Haiku 기준). RAG 파이프라인 안에 캐싱이 이미 들어 있습니다.
  • CAG 논문 결론 — “hybrid approaches that combine preloading with selective retrieval”. 제목(Don’t Do RAG)과 결론의 온도차가 큽니다.
  • MemOS — 3종 메모리 중 activation memory가 곧 KV-cache(CAG의 재료), plaintext memory가 RAG의 재료입니다. 애초에 셋을 통합하는 프레임으로 제안됐습니다.
  • Anthropic memory tool + context editing — 공식 문서가 함께 쓰라고 권장합니다: “compaction keeps the active context small… and memory preserves the information that must survive summarization.”

상황별 선택

Scenario 01

사내 규정·FAQ 챗봇

문서가 수십~수백 페이지고 분기에 한 번 바뀝니다. 질문은 하루 수천 건.

→ 전체 주입 + prompt caching
Scenario 02

법무·컴플라이언스 검색

수백만 파일, 법령이 수시로 갱신, 답변마다 정확한 출처 인용이 필수.

→ RAG + Contextual Retrieval
Scenario 03

키워드가 잘 맞는 대량 로그 검색

에러 코드·식별자처럼 lexical 매칭이 강한 도메인. 지연이 중요.

→ BM25 sparse RAG
Scenario 04

고객 계정 자동화 에이전트

사용자별 이력·선호·티켓을 세션을 넘어 기억하고 갱신해야 합니다.

→ 장기 메모리 스토어
Scenario 05

단일 코드베이스 QA

레포 전체를 넣고 깊이 이해시켜야 하고, 코드는 자주 바뀌지 않습니다.

→ 전체 주입 + caching
Scenario 06

장기 실행 코딩 에이전트

수 시간짜리 작업. 컨텍스트가 압축돼도 진행 상태는 살아남아야 합니다.

→ 메모리 + context editing
