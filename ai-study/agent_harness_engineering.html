01

핵심 공식: Agent = Model + Harness

에이전트는 모델 단독이 아니다. 모델을 둘러싼 모든 코드, 설정, 실행 로직이 합쳐질 때 비로소 에이전트가 된다.

원본 (English)
한글화
Model
모델이 하는 것
  • 자연어 추론 및 생성
  • 코드 이해 및 작성
  • 패턴 인식 및 계획 수립
  • 도구 호출 결정
Harness
하네스가 하는 것
  • 모델이 단독으로 할 수 없는 것을 보완
  • 실패로부터 학습한 규칙을 영구 저장
  • 안전한 실행 환경(샌드박스) 제공
  • 장기 작업의 컨텍스트 유지 및 조율

"평범한 모델과 훌륭한 하네스의 조합이, 훌륭한 모델과 나쁜 하네스의 조합을 이긴다."

02

하네스의 7가지 구성 요소

하네스는 단일 컴포넌트가 아니다. 모델 주변을 감싸는 7가지 레이어가 협력하여 에이전트를 구성한다.

[01]
프롬프트 & 스킬 파일
시스템 프롬프트, AGENTS.md를 통한 행동 규칙 정의. 모든 요청의 최우선 컨텍스트.
[02]
도구 & MCP 서버
Bash, 파일시스템, Git, 웹 검색 등 실행 능력 확장. MCP로 외부 서비스 통합.
[03]
샌드박스 & 기본 환경
격리된 실행 환경, 위험 명령 화이트리스트, 헤드리스 브라우저 포함.
[04]
오케스트레이션 로직
Ralph 루프, 계획 수립, 자체 검증. 장기 실행 작업의 흐름 제어.
[05]
훅 & 미들웨어
도구 호출 전·후에 실행되는 스크립트. 타입체크, 린트, 위험 명령 차단.
[06]
메모리 & 검색
AGENTS.md 지속성 학습, 웹 검색으로 컷오프 극복, 코드베이스 탐색.
[07]
관찰성
이벤트 버스, 배경 실행기, 성능 추적, 로깅. 에이전트 동작 가시성 확보.
[∑]
7가지의 합
각 컴포넌트는 "모델이 단독으로 할 수 없는 것"에 대한 가정을 인코딩한다. — Addy Osmani
03

래칫 원칙 (Ratchet Principle)

하네스 엔지니어링의 가장 강력한 설계 철학. 모든 실수는 되돌릴 수 없는 개선의 계기가 된다.

"모든 실수가 규칙이 된다. 모든 실패가 하네스를 한 단계 더 나아가게 한다."

래칫 원칙 — Addy Osmani

04

핵심 하네스 컴포넌트 상세

각 컴포넌트는 독립적으로 존재하지 않는다. 상호 보완하며 에이전트의 실행 능력을 구성한다.

파일시스템 & Git
에이전트의 외부 기억
모델이 컨텍스트 밖의 중간 작업을 저장하는 공간. 작업 진행 상황을 영속적으로 추적하고, 오류 시 간단한 롤백을 지원한다. 여러 에이전트 간 조율 매체 역할도 수행한다.
Bash & 코드 실행
ReAct 루프의 실행 엔진
범용 도구로서 에이전트가 필요한 도구를 동적으로 구성할 수 있게 한다. 추론 → 행동 → 관찰 → 피드백의 ReAct 사이클을 구동하는 핵심 메커니즘.
컨텍스트 관리
3가지 컨텍스트 로트 해결책
  • 압축(Compaction): 오래된 컨텍스트를 지능형 요약으로 교체
  • 도구 아웃로딩: 대용량 출력을 파일시스템으로 이동
  • 점진적 공개: 필요할 때만 도구·지시사항 노출
훅 (Hooks)
"성공은 침묵, 실패는 크게"
  • 모든 편집 후 → 타입체크, 린트, 테스트
  • 위험 Bash 명령 → 실행 전 차단
  • 커밋 전 → 테스트 스위트 자동 실행
  • 자동 포맷팅 적용

Ralph 루프 — 장기 실행 작업

컨텍스트가 가득 차도 원본 의도를 잃지 않는 메커니즘. 에이전트가 종료를 시도할 때 원본 프롬프트를 새 컨텍스트에 재주입한다.

세션 1: [원본 프롬프트] + [초기 작업 실행]
          ↓ (컨텍스트 소진)
세션 2: [원본 프롬프트 재주입] + [이전 진행 상황 요약]
          ↓ (컨텍스트 소진)
세션 3: [원본 프롬프트 재주입] + [누적 진행 상황]
          ↓
         ... (무한 반복 가능, 원본 의도 유지)

06

모델-하네스 학습 루프

하네스와 모델은 독립적으로 존재하지 않는다. 서로를 강화하는 공진화(Co-evolution) 사이클이 작동한다.

원본 (English)
한글화

"Claude Code의 Opus 4.6은 동일 모델을 다른 하네스에 배치하면 더 낮은 성능을 보인다. 하네스와 모델은 공생 관계다."

Addy Osmani — 모델-하네스 공진화

이 사이클이 의미하는 바: 하네스의 패턴이 모델 학습에 피드백되고, 개선된 모델이 더 고급 하네스 설계를 가능하게 한다. 하네스 수준의 혁신이 모델 버전 업그레이드만큼 중요한 이유다.

07

HaaS — Harness-as-a-Service

업계가 LLM API 제공에서 하네스 API 제공으로 전환 중이다. 사용자는 이제 도메인별 프롬프트와 도구 설계에만 집중할 수 있다.

이전 패러다임
LLM API
API 호출 → 텍스트 완성(completion) 반환. 루프, 도구, 컨텍스트 관리를 사용자가 직접 구현해야 했다.
// 직접 구현 필요
const completion = await llm.complete(prompt);
// 루프, 도구 호출, 컨텍스트 관리...
// 모두 수작업
현재 패러다임
Harness API
API 호출 → 런타임(runtime) 반환. 루프, 도구, 컨텍스트 관리가 내장된 하네스를 그대로 활용.
// 하네스가 내장됨
const agent = await harness.create({
  tools: [...],
  rules: 'AGENTS.md',
  // 나머지는 자동 처리
});
플랫폼제공사내장 하네스 요소
Claude Agent SDKAnthropic루프, 도구 통합, 컨텍스트 관리, 서브에이전트
OpenAI Agents SDKOpenAI도구 체인, 상태 관리, 핸드오프
Codex SDKGitHub / OpenAI코드 생성 특화 하네스, 저장소 컨텍스트
08

미래 방향

하네스 엔지니어링이 해결해야 할 3가지 미결 문제. 각각이 에이전트 패러다임 전환의 핵심이다.

방향 01
병렬 다중 에이전트 조율
공유 코드베이스에서 여러 에이전트가 동시에 협력. 에이전트 A는 버그 수정, 에이전트 B는 테스트 작성, 에이전트 C는 문서화 — 충돌 없이 병렬 진행.
방향 02
하네스 자동 최적화
에이전트가 자신의 실행 추적(trace)을 분석하여 AGENTS.md 규칙을 자동 생성. 수동 설정에서 자율 개선으로의 전환.
방향 03
동적 도구 조립
사전 고정된 도구 세트 대신, 주어진 작업에 맞게 도구를 실시간으로 구성. 하네스가 정적 설정에서 컴파일러에 가까운 것으로 진화.

"하네스는 정적 설정에서 컴파일러에 가까운 것으로 진화할 수 있다."

Addy Osmani — 미래 방향
