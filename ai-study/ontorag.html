Abstract — 한 단락 요약

이 데모는 OntoRAG(온톨로지 기반 그래프 DB에서의 의미론적·확률적 추론)와 ontorag-flow(자동 규칙 + 인간 승인 게이트를 갖춘 적응형 사례관리)를 결합해, 제조 공정에서 불량률이 왜 올랐는지를 단순 집계가 아니라 인과적으로 분리한다. 600개 합성 제품·151개 실패 데이터 위에서 다중홉 SPARQL로 용의 로트(LOT-0047, 실패율 83%)를 좁히고, 베이지안 네트워크의 do-calculus로 개입 효과를 계산한 결과 — 공정 조건 개입(−0.134)이 공급사 개입(−0.067)보다 약 2배 효과적이라는, 상관만 봐서는 알 수 없는 결론에 도달한다.
큐레이터 노트

이 데모가 흥미로운 이유는 결과 수치보다 질문의 전환에 있다. “어느 공급사가 문제냐(상관)”가 아니라 “무엇을 바꿔야 불량이 줄어드냐(인과)”를 묻고, 그 둘이 전혀 다른 답을 준다는 것을 한 화면에서 보여준다.

제조 현장의 RCA(근본 원인 분석)는 보통 “실패가 몰린 로트·공급사를 찾는다”에서 멈춘다. 이 데모는 거기서 한 발 더 나아가 Pearl의 인과 사다리(see → do → counterfactual)를 실제 데이터 파이프라인으로 구현해 보인다.

3-bullet TL;DR

  • What. 온톨로지(그래프) + 베이지안 네트워크 + do-calculus + 사례관리 + 감사추적을 하나의 RCA 루프로 통합.
  • Why it matters. “SUP-B가 범인처럼 보이지만”, 개입 효과를 계산하면 진짜 지렛대는 공정 압력이다 — 상관 ≠ 인과를 정량으로 증명.
  • Caveat. 데이터는 합성(synthetic)이며, 생성기와 추론기가 같은 CPT를 공유하므로 “정합성 검증” 용도이지 실측 일반화는 아니다.

1. 먼저, 온톨로지(Ontology)란 무엇인가

온톨로지는 한마디로 “어떤 도메인에 무엇이 존재하고, 그것들이 서로 어떻게 연결되는지를 기계가 읽을 수 있게 적어둔 약속”이다. 엑셀 표가 “행과 열”이라면, 온톨로지는 “개념(클래스)과 개념 사이의 관계(프로퍼티)”로 세상을 기술한다.

온톨로지는 보통 두 층으로 나뉜다. TBox는 스키마(개념 정의)이고, ABox는 그 스키마를 따르는 실제 사실(인스턴스)이다. 이 데모의 TBox는 제조 도메인을 7개 클래스 · 12개 프로퍼티로 정의하고, 데이터는 RDF 트리플(Turtle 형식)로 저장된다.

트리플 = ( 주어 Subject ) — [ 술어 Predicate ] → ( 목적어 Object ) RDF

예를 들어 (Product-014) —[isMadeIn]→ (ProcessRun-007) 처럼, 하나의 사실을 “주어–술어–목적어” 한 줄로 쓴다. 이런 트리플을 쌓으면 표가 아니라 그래프가 되고, 그래프이기 때문에 “제품 → 공정 → 부품 → 로트 → 공급사”처럼 여러 단계를 거슬러 올라가는 추적(multi-hop)이 자연스럽게 가능해진다. 바로 이 다중홉 추적 능력이 제조 traceability(이력 추적)의 핵심이다.

설계 디테일 하나가 인상적이다. ProcessRun의 조건(온도·압력 등)을 숫자가 아니라 이산 문자열("normal"/"high"/"low")로 저장한다. 이렇게 하면 뒤에 올 베이지안 네트워크가 별도의 구간화(binning) 전처리 없이 그래프 값을 그대로 소비할 수 있다 — 즉 온톨로지 스키마를 추론 엔진의 입력 포맷에 맞춰 미리 설계한 것이다.

2. OntoRAG vs ontorag-flow — 두 개의 엔진

이 데모는 성격이 다른 두 시스템을 의도적으로 분리하고 결합한다. 하나는 “생각하는” 엔진, 다른 하나는 “행동하는” 엔진이다.

구분OntoRAGontorag-flow
역할Semantic + Dynamic 추론Kinetic / Adaptive Case Management
하는 일그래프 다중홉 쿼리 + 확률적 추론자동 규칙 엔진 + 인간 승인 게이트로 의사결정 실행
핵심 산출“원인은 무엇이고 개입 효과는 얼마인가”“그래서 무엇을 했고, 누가 승인했는가”
비유진단하는 의사처방·시술하고 차트를 남기는 시스템

OntoRAG가 “LOT-0047을 격리하면 불량이 X만큼 준다”를 계산하면, ontorag-flow는 그 추천을 받아 자동 단계 → 인간 승인 게이트 → ABox write-back(격리 플래그 기록) → 반사실 재실행 → 종료의 사례(case)를 굴리고, 모든 활동을 PROV-O 감사 추적으로 남긴다. 추론만으로는 “책임 추적”이 불가능하다는 문제를, 사람의 승인과 활동 로그로 메우는 구조다.

3. 베이지안 네트워크와 인과추론

그래프가 “무엇이 무엇과 연결됐나”를 말한다면, 베이지안 네트워크는 거기에 확률을 입힌다. 이 데모의 베이지안 네트워크는 7개 노드로 구성되며, 합성 데이터 생성기와 추론 엔진이 동일한 CPT(조건부 확률표)를 공유한다 — 이것이 “정답을 아는 상태에서 추론이 그 정답을 맞히는가”를 검증할 수 있게 하는 트릭이다.

3.1 Pearl의 인과 사다리 (Ladder of Causation)

인과추론의 핵심은 “본다(see)”와 “한다(do)”의 구분이다. 유다 펄(Judea Pearl)의 사다리 3단을 이 데모는 그대로 단계로 옮긴다.

4. RCA 파이프라인 — 좁히고, 의심하고, 증명한다

L1. 다중홉 SPARQL 추적 — 범위 좁히기

먼저 그래프를 거슬러 올라가 실패가 어디에 몰렸는지 센다. LOT-0047은 12개 제품 중 10개가 실패 — 약 83%로, 전체 평균 25.2%의 3배가 넘는다. 공급사별 실패 건수도 SUP-B(46) > SUP-D(32) > SUP-E(28) > SUP-A(24) > SUP-C(21) 순으로 집계된다. 중요한 점은 이 SPARQL 카운트가 합성 데이터의 ground truth와 100% 일치한다는 것 — 추적의 신뢰성이 검증된다.

L2. 관찰 확률 — “SUP-B가 범인처럼 보인다”

이제 확률로 본다. see(SupplierQuality=bad)를 조건으로 걸면 P(실패)=0.467. baseline 0.265의 거의 두 배다. 여기서 멈추면 “SUP-B 공급사가 원인”이라는 흔한 결론으로 직행한다. 하지만 이것은 상관일 뿐, 공급사를 바꾼다고 불량이 그만큼 준다는 보장은 없다.

L3. 인과 개입 — 진짜 지렛대를 찾는다

do-calculus로 개입을 시뮬레이션한다. do(SupplierQuality=good)의 효과는 −0.067에 그친다. 반면 do(AssemblyPressure=normal)은 −0.134 — 거의 2배다. 표면적으로 가장 의심스러웠던 공급사보다, 공정 압력을 정상화하는 편이 훨씬 효과적이라는 뜻이다. 두 개입을 함께 하면(do(both)) −0.200으로, 두 단일 효과의 합(0.067+0.134=0.201)과 거의 같다 — near-additive.

시나리오유형P(실패)Δ vs baseline
baseline—0.265+0.000
see(나쁜 공급)관찰(L2)0.467+0.202
do(좋은 공급)개입(L3)0.197−0.067

5. 데모의 결과물과 성과

이 데모의 “성과”는 화려한 정확도 수치가 아니라, 전체 RCA 루프가 검증 가능하게 닫힌다는 것 자체다. 합성이지만 ground truth를 알기에, 각 단계가 정답을 재현하는지 일일이 대조할 수 있다.

6. 제작자가 고민한 부분 (Challenges)

이 데모의 진짜 가치는 “무엇을 만들었나”보다 “무엇을 고민했나”에 있다. 제작자가 워크스루·구현 노트에서 드러낸 설계 난제 6가지를 정리한다.

1

상관(Correlation) vs 인과(Causation) 구분

문제: L1 추적·L2 관찰만으로는 “SUP-B가 원인”이라고 단정할 수 없다(관찰일 뿐). 해결: 베이지안 DAG + do-calculus로 개입 효과를 분리해, “공정(−0.134) > 공급사(−0.067)”라는 반직관적 결론을 정량으로 증명.
2

다중 원인의 상호작용

문제: 불량이 공급사 + 공정 조건의 상호작용으로 생길 수 있다. 모델링: 7개 노드 중 상호작용을 1개 명시적으로 설정. 검증: do(both) 효과 −0.200 ≈ 단일 개입 합(0.201) → near-additive임을 확인.
3

휴리스틱 라벨의 함정

문제: 생성기의 “attributed cause” 분류가 불완전(오염 로트 3건으로 표시했지만 실제 LOT-0047 영향은 10건). 명시: “이 카테고리는 지배적 원인만 표시” — 최종 판단은 휴리스틱이 아니라 SPARQL + do() + 반사실 결과만 신뢰.
4

운영 의사결정의 감사 가능성

문제: 자동 추론만으로는 “누가 왜 그 조치를 했는가”의 책임 추적이 불가. 해결: 인간 승인 게이트(Phase 2) + PROV-O 활동 로그 → 추천 → 승인 → write-back → 반사실 replay의 완전한 추적 체인 확보.
5

온톨로지 설계의 실용성 (이산 vs 연속)

문제: 공정 조건을 연속값으로 둘지 이산값으로 둘지. 선택: ProcessRun에 조건을 이산 문자열로 저장. 이유: pgmpy(베이지안 라이브러리)가 별도 binning 없이 직접 소비 가능 → 스키마를 추론기 입력에 맞춰 설계.
6

플랜과 구현의 격차

문제: 계획서(plan §6)는 ontorag-flow를 MCP 클라이언트 + HTTP 서비스로 설계했으나, 데모는 커스텀 Python API로 직접 호출. 이점: 단일 uv run으로 전체 루프 실행. 확장성: MCP로 전환하려면 build_domain_actions()를 with_triple_actions(client)로 교체하면 됨 — 격차를 숨기지 않고 마이그레이션 경로로 문서화.

7. 비판적 평가

강점

  • 온톨로지·베이지안·인과·사례관리·감사를 하나의 닫힌 루프로 통합한 드문 레퍼런스.
  • 생성기와 추론기가 같은 CPT를 공유 → 각 단계 정확성을 ground truth로 검증 가능.
  • “상관 ≠ 인과”를 추상 설명이 아니라 실행되는 수치로 보여줌.
  • 설계 결정·플랜 격차를 숨기지 않고 노트로 명시.

한계

  • 데이터가 합성이며, 생성·추론이 같은 모델 → 실제 공정 일반화는 별개 과제.
  • DAG 구조(인과 그래프)를 사람이 미리 정의 — 현실에선 구조 학습 자체가 난제.
  • 7노드 소규모 — 대규모·시계열 공정으로의 확장성은 미검증.
  • 휴리스틱 라벨 불일치가 보여주듯, “원인 귀속”은 여전히 해석 여지가 큼.

실무 시사점 — 5가지

  1. RCA를 “실패가 몰린 곳 찾기(L1/L2)”에서 멈추지 말고, “무엇을 바꿔야 주는가(L3)”까지 밀어붙일 것.
  2. 관찰 확률이 큰 변수 ≠ 개입 효과가 큰 변수 — 현장 개선 우선순위는 do() 효과로 정렬.
  3. 온톨로지 스키마는 처음부터 다운스트림 추론기(베이지안 등)의 입력 포맷에 맞춰 설계하면 전처리가 사라진다.
  4. 자동 추론에 인간 승인 게이트 + PROV-O 감사로그를 붙여야 운영 의사결정으로 쓸 수 있다.
  5. 합성 데이터 + 공유 CPT는 “정합성 검증” 도구로 강력하지만, 일반화 주장과는 구분해야 한다.

유다 펄의 개입 연산. do(x)는 x로 들어오는 인과 화살표를 끊고 x를 강제 고정해 순수 인과 효과를 계산한다(L3).
Counterfactual 반사실
“만약 그때 x가 달랐다면?”을 개별 사례 단위로 묻는 추론. Pearl 사다리 최상단.
PROV-O 프로브-오
W3C 표준 provenance 온톨로지. 누가·무엇을·언제 했는지 활동 이력을 그래프로 기록해 감사 추적을 가능케 한다.
ACM Adaptive Case Management
정해진 워크플로가 아니라, 상황에 따라 단계를 적응적으로 구성하는 사례 관리 방식. ontorag-flow가 담당.
