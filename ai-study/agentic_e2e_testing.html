01 — 패러다임의 차이

"경로를 강제"하던 테스트에서 "목표를 검증"하는 테스트로

전통적 E2E는 클릭·입력의 정확한 순서를 스크립트로 고정한다. 에이전틱 테스팅은 목표만 주고, 에이전트가 화면을 관찰·추론하며 스스로 경로를 찾는다. 같은 결과에 도달하는 길이 여러 개라는 점이 핵심 차이다.

결정론적 E2E
정해진 여정을 강제
click → type → click → assert 순서를 사전에 스크립트로 박는다. 빠르고 저렴하며 재현 가능하지만, UI가 바뀌면 깨지고 "다른 경로의 성공"은 보지 못한다.
에이전틱 테스팅
목표 달성 가능성을 검증
goal → 관찰·추론 → 행동 → 결과 검증. 사람이 쓰듯 다양한 경로로 목표에 도달한다. 유연하지만 느리고($15–30/회) 비결정적이라 CI 반복엔 부적합하다.
02 — 실험 설계

Slack은 무엇을, 어떻게 측정했나

200건 이상의 자동화 실행을 3가지 실행 모델 × 5가지 구성(각 20회 반복)으로 돌려 신뢰성·실행시간·비용을 정량 비교했다. 실행은 비대화형 Claude Code(claude -p)로 수행.

실행 모델구동 방식사용 모델
Playwright MCP구조화된 브라우저 프리미티브를 도구 호출로 통합Claude Sonnet 4.5
Playwright CLI에이전트와 브라우저 사이에 CLI 레이어 추가Claude Sonnet 4.5
Generated Tests에이전트가 Playwright 테스트 코드를 생성 후 실행Claude Opus 4.6
  • 대상 시나리오 — Thread Reply(단순, ≈15–20단계) vs Search Discovery(중복잡도, ≈25–30단계)
  • 입력 형식 — 자연어(NL)와 구조화된 YAML을 비교
  • 경로 측정 — action signature를 정규화해 도구 호출·UI 동작 순서를 비교
03 — 데이터

신뢰성 · 속도 · 비용, 숫자로 보기

가장 또렷한 결론: 신뢰성과 비용은 모델보다 실행 환경(인프라)이 좌우한다. MCP는 단순 흐름에서 0% 실패, 복잡한 흐름에서도 12% 이내로 가장 안정적이었다.

신뢰성 — 실패율(낮을수록 좋음)

접근 방식Thread Reply (단순)Search Discovery (복잡)
Playwright MCP0%~12%
Playwright CLI~12%~20%
Generated Tests~8%~48%

속도 · 비용

접근 방식평균 실행시간턴 수토큰(복잡 흐름)
Generated Tests~3분~70~7M
Playwright MCP~5–8분~40–60~3.5–3.8M
Playwright CLI~9–11분~85~6M

생성 테스트는 코드 생성(1회) + 실행(5회)을 포함한 수치다. 순수 실행만 보면 Thread Reply 32초, Search Discovery 45초로 가장 빠르다. 반면 에이전트 실행은 회당 $15–30이 든다.

"신뢰성·속도·비용은 모델뿐 아니라 실행 환경이 얼마나 안정적이고 잘 설계됐는지에 달려 있다."

Slack Engineering

CLI가 불안정했던 이유는 에이전트와 브라우저 사이의 추가 레이어 때문이다 — 인증 처리, 네비게이션 타이밍, 세션 불안정, 순차 실행 제약. MCP는 브라우저 프리미티브를 도구 호출에 긴밀히 통합해 이 마찰을 줄였다.

04 — 비용의 정체

왜 회당 $15–30이나 드는가

비용은 모델의 출력이 아니라, 매 턴 컨텍스트가 얼마나 빨리 쌓이고 에이전트가 몇 턴을 도는지가 결정한다. Stateless API라 매 턴마다 지금까지의 내용을 통째로 다시 보낸다.

비용의 대부분은 "이미 본 내용의 재전송"이다. 턴마다 새로 추가되는 정보는 극히 일부고, 전체 시스템 프롬프트 · 누적 대화 이력 · 브라우저 스냅샷이 반복 전송되면서 토큰이 불어난다.
  • 전체 시스템 프롬프트 재전송 — 매 턴 동일 프롬프트가 다시 청구된다
  • 대화 이력 누적 — stateless API 특성상 히스토리가 매번 재전송
  • 브라우저 스냅샷 누적 — MCP/CLI는 화면 상태가 컨텍스트로 쌓임
  • 에러·어설션 추적 — 생성 테스트는 실패 추적이 토큰을 늘림

따라서 비용 최적화의 핵심은 출력 단축이 아니라 컨텍스트 관리다 — prompt caching, context compaction, 스냅샷 빈도 축소가 직접적인 절감 수단이 된다.

05 — 위치

테스트 피라미드에서 에이전트의 자리

에이전틱 테스팅은 기존 계층을 대체하지 않는다. 피라미드 맨 위에 새 층으로 얹혀 탐색 · 디버깅 · 복잡한 동작 검증을 맡는다. 아래 단단한 결정론 계층이 CI를 떠받친다.

06 — 가장 합리적인 방법

하이브리드: 결정론적 토대 + 에이전틱 탐색

결론은 명확하다. 둘 중 하나를 고르는 게 아니라 역할을 나눈다. 결정론적 테스트로 CI를 빠르고 싸게 지키고, 에이전틱 테스팅은 위층에서 사람이 손대기 어려운 탐색·디버깅을 맡긴다.

CI / 회귀 — 결정론적
기본 안전망
단순·반복 흐름은 생성/스크립트 테스트로(≈3분, 저비용). 매 PR·매 머지마다 빠르게 돌린다. Thread Reply 같은 단순 흐름의 실패율은 8% 수준으로 충분히 실용적.
탐색 / 디버깅 — 에이전틱
타깃 투입
복잡한 UI 동작 탐색, flaky 워크플로 디버깅, 프로덕션 버그 재현에 한해 투입. 인프라는 CLI보다 MCP를 우선(신뢰성·속도 우위).
실무 지침. 에이전트 기반 테스트는 현재 고빈도 CI보다 표적 디버깅·탐색 테스트에 더 적합하다. 비용이 부담되면 prompt caching · context compaction · 스냅샷 빈도 축소부터 적용한다. 
# 권장 운영 모델 (요약)
CI 단계        →  결정론적 E2E (생성/스크립트)   # 빠름·저비용·매번 실행
릴리스 전 점검  →  에이전틱(MCP) 핵심 시나리오 탐색  # 회귀 스크립트가 못 잡는 경로
버그 재현/조사  →  에이전틱(MCP) 1회성 실행        # flaky·프로덕션 이슈 추적
07 — 도구 변화 & 전망

툴체인은 어디로 가는가

이번 실험이 보여준 도구 지형의 변화는 분명하다. Playwright는 여전히 실행 기반이지만, 그 위에 MCP(Model Context Protocol)가 에이전트–브라우저를 잇는 표준 인터페이스로 부상했다. "어떤 모델을 쓰느냐"보다 "브라우저 제어를 어떻게 도구화하느냐"가 신뢰성을 가른다.

  • 실행 계층 — Playwright(결정론) + Playwright MCP(에이전트) 병행이 현재 가장 안정적
  • 비용 곡선 — 모델 효율·prompt caching 개선으로 점진 하락 여지. 지금은 저빈도 사용이 합리적
  • 미탐색 영역 — 멀티세션 · 크로스 워크스페이스 워크플로, 병렬화·프롬프트 최적화

"미래의 가장 효과적인 테스트 전략은 둘을 결합한다. 결정론적 테스트가 CI의 안정적 토대를 제공하고, 에이전틱 테스팅이 피라미드 최상단에서 탐색·디버깅·복잡한 동작 검증의 층을 더한다."
