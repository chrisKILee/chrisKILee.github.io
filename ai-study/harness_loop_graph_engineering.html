01하네스 엔지니어링 — 모델 밖의 전부

하네스(harness)는 세 용어 중 Anthropic 공식 문서에 그 단어 그대로 등장하는 개념입니다. 다만 harness engineering이라는 합성어를 먼저 쓴 곳은 Anthropic이 아니라 OpenAI와 Thoughtworks입니다.

“The agentic loop is powered by two components: models that reason and tools that act. Claude Code serves as the agentic harness around Claude: it provides the tools, context management, and execution environment that turn a language model into a capable coding agent.”

Claude Code 공식 문서 — How Claude Code works

“An agent harness is the software scaffolding around a model: the loop, tools, context management, and guardrails that turn raw intelligence into a working agent.”

Anthropic 블로그 — Lance Martin, Agent Harness Design (2026-04-02)
인스타 요약과 공식 문서가 일치하는 지점 위 카드뉴스의 9개 요소는 Anthropic Agent SDK 문서의 Capabilities 표(Built-in tools / Hooks / Subagents / MCP / Permissions / Sessions / Skills·commands·memory / Plugins)와 거의 그대로 대응합니다. 용어만 한글화됐을 뿐 창작된 항목이 아닙니다.

Anthropic이 하네스를 정의하는 두 가지 범위

같은 회사 문서 안에서도 하네스의 범위가 넓게도, 좁게도 정의됩니다. 인용할 때 어느 쪽인지 밝히는 편이 안전합니다.

넓은 정의

스캐폴딩 전체

루프 + 툴 + 컨텍스트 관리 + 가드레일. Claude Code 문서와 Agent Harness Design 블로그가 이 범위를 씁니다.

좁은 정의

루프 + 툴 라우팅

“the loop that calls Claude and routes Claude’s tool calls to the relevant infrastructure”. Managed agents 문서는 Session·Harness·Sandbox 3분할에서 하네스를 이렇게 좁힙니다.

외부 프레이밍

Agent = Model + Harness

Thoughtworks Birgitta Böckeler: 하네스 = “everything in an AI agent except the model itself”. Guides(사전 조종) vs Sensors(사후 관찰) 2축, 각각 Computational vs Inferential로 분화.

컨텍스트 관리 — 하네스의 핵심 축

Anthropic은 context engineering을 “LLM 추론 중 최적의 토큰 집합을 큐레이팅·유지하는 전략의 총체”로 정의하고, 프롬프트 엔지니어링(지시문 작성법)과 명확히 구분합니다. 장기 태스크용으로 문서가 제시하는 기법은 네 가지입니다.

  • Compaction — 오래된 메시지를 요약으로 대체
  • Structured note-taking — 컨텍스트 밖 파일에 진행 상태 기록
  • Sub-agent architectures — 서브에이전트가 보통 1,000–2,000 토큰의 요약만 반환
  • Just-in-time context retrieval — 파일 경로·쿼리·링크 같은 가벼운 식별자만 유지하고 필요할 때 로드
Context rot “As the number of tokens in the context window increases, the model’s ability to accurately recall information from that context decreases.” — 컨텍스트를 많이 넣을수록 좋아지는 게 아니라는 것이 공식 입장입니다. (Effective context engineering)

가드레일은 프롬프트가 아니라 훅으로

“An instruction like ‘never edit .env’ in CLAUDE.md or a skill is a request, not a guarantee. A PreToolUse hook that blocks the edit is enforcement.”

가장 중요한 함정 — 하네스에는 유통기한이 있다

“Every component in a harness encodes an assumption about what the model can’t do on its own, and those assumptions are worth stress testing.”

Anthropic Engineering — Harness design for long-running application development

실제 사례가 문서에 있습니다. Sonnet 4.5는 컨텍스트 한계가 다가오면 작업을 조기 종료하는 경향 (context anxiety)이 있어 하네스에 context reset을 넣었는데, Opus 4.5에서 그 현상이 사라져 reset이 그대로 “dead weight”가 됐습니다. 그래서 Agent Harness Design의 세 패턴은 이렇게 요약됩니다.

  1. Lean on the model, not the harness — 모델이 이미 아는 것을 쓴다
  2. Strip your agent harness down — 주기적으로 “무엇을 그만할 수 있는가”를 묻는다
  3. Set boundaries carefully — 경계는 신중하게 설계한다

02루프 엔지니어링 — 정지 조건의 설계

세 용어 중 Anthropic이 공식 채택한 유일한 “~ engineering”입니다. Claude Code Agent SDK 문서가 이 이름의 블로그를 본문에서 직접 링크합니다.

“For a practical guide to designing loops in Claude Code, from turn-based to goal-based and proactive loops, see Loop engineering: getting started with loops on the blog.”

Claude Code — How the agent loop works

공식 블로그(2026-06-30)의 정의는 한 줄입니다 — 루프란 “정지 조건이 충족될 때까지 작업 사이클을 반복하는 에이전트”. 즉 루프 엔지니어링의 실체는 반복 그 자체가 아니라 무엇을 ‘완료’로 볼 것인가를 설계하는 일입니다.

공식 문서가 명시한 루프 5단계

단계내용방출 메시지
1. Receive prompt프롬프트 + 시스템 프롬프트 + 툴 정의 + 대화 이력SystemMessage(subtype:"init")
2. Evaluate and respond텍스트 / 툴 호출 요청 / 둘 다AssistantMessage
3. Execute toolsSDK가 툴 실행·결과 수집. 훅으로 가로채기·수정·차단 가능—
4. Repeat한 사이클 = 1 turn. 툴 호출이 없는 응답이 나올 때까지 반복—
5. Return result최종 응답 + 토큰·비용·세션 IDResultMessage

정지·제어 수단 (공식)

  • max_turns / maxTurns — 툴 사용 왕복 상한. 초과 시 error_max_turns
  • max_budget_usd — 비용 상한. 서브에이전트 지출도 총액에 포함(v2.1.217+)
  • effort — low / medium / high / xhigh / max
  • 종료 상태: success, error_max_turns, error_max_budget_usd, error_during_execution, error_max_structured_output_retries

Agent SDK — 루프 제어 (공식 문서 예시)

async for message in query(
    prompt="Find and fix the bug causing test failures in the auth module",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Edit", "Bash", "Glob", "Grep"],
        setting_sources=["project"],
        max_turns=30,       # Prevent runaway sessions
        effort="high",
    ),
): ...

루프 4종 — 무엇이 시작시키고 무엇이 멈추는가

유형시작 트리거정지 조건적합한 작업
Turn-based사용자 프롬프트Claude가 완료 판단짧고 반복되지 않는 작업

Proactive이벤트/스케줄, 실시간 사람 개입 없음—버그 리포트, 이슈 트리아지, 마이그레이션, 의존성 업그레이드
/goal의 내부 구현 — 공식 문서 원문

“/goal is a wrapper around a session-scoped prompt-based Stop hook.”

매 턴이 끝나면 조건과 대화를 small fast model(Claude API 기본값 Haiku)에 보내 Not yet met / Met / Impossible 3판정을 받습니다. 평가자는 툴을 호출하지 않으므로, 조건은 “Claude 자신의 출력으로 증명 가능한 것”으로 써야 합니다. 조건 최대 4,000자.

무한 루프 방지 장치 (문서 명시)

· /goal: 툴 사용 없이 여러 턴 연속 답만 하면 루프를 멈추고 경고를 출력합니다.

· Auto-compaction thrashing: 단일 파일·툴 출력이 너무 커서 요약 직후 컨텍스트가 다시 차면, 몇 번 시도 후 auto-compact를 중단하고 에러를 표시합니다.

공식 블로그가 든 루프 운영 주의사항 5가지입니다.

  • 코드베이스를 깨끗하게 유지 — Claude는 기존 패턴을 그대로 따른다
  • 코드 리뷰는 별도 에이전트에게 — 신선한 컨텍스트의 리뷰어가 메인 에이전트의 추론에 덜 편향된다
  • 개별 이슈를 그때그때 고치지 말고 시스템에 인코딩하라
  • 프리미티브와 모델을 적정 선택 — 작은 작업에 다중 에이전트·루프는 불필요
  • 큰 실행 전 파일럿 — dynamic workflows는 수백 개 에이전트를 스폰할 수 있다

03그래프 엔지니어링 — 흐름을 코드에 맡기기

먼저 짚을 것 — 이건 공식 용어가 아닙니다

조사 범위(anthropic.com · claude.com · code.claude.com) 어디에서도 “graph engineering”이라는 표현을 찾지 못했습니다. LangGraph 공식 문서조차 이 명칭을 쓰지 않습니다(Graph API, StateGraph라고 부름).

LangGraph를 만든 LangChain은 자사 공식 블로그에서 이 용어를 이렇게 규정했습니다 — “the latest term to come out of X’s AI content factory”. 다만 같은 글에서 “these terms exist and emerge for a reason: they do describe real challenges and design decisions builders face”라고 덧붙입니다. (3 Years of Graph Engineering with LangGraph, 2026-07-22)

즉 개념은 실재하되 이름이 비공식입니다. Anthropic은 같은 것을 workflow, orchestrator-workers, dynamic workflows라고 부릅니다.

LangGraph — 그래프 개념이 실제 API로 구현된 곳

LangGraph는 3년 전 구축돼 월 6,500만 회 이상 다운로드되며, DAG가 아니라 사이클을 지원합니다(retry·validation·human input pause).

StateGraph사용자 정의 State 객체로 파라미터화되는 주 그래프 클래스. 사용 전 컴파일 필요
State + ReducerTypedDict/dataclass/Pydantic 스키마 + reducer 함수. 키마다 독립 reducer, 미지정 시 덮어쓰기
Node“Functions encoding agent logic. They receive state as input, perform computation, and return updated state”

Send APImap-reduce용. 엣지나 state 변형을 미리 알 수 없을 때
Commandstate 업데이트 + 제어 흐름을 하나의 반환값으로 결합
Checkpointer단기·thread 범위 메모리 — 대화 연속성, human-in-the-loop, time travel, 장애 복구

Anthropic의 대응물 — Dynamic workflows

Claude Code에도 같은 문제를 푸는 기능이 있습니다. 다만 선언적 그래프가 아니라 명령형 JavaScript 스크립트이며, 해당 문서에는 “graph”·“DAG”·“node”·“edge”라는 단어가 한 번도 나오지 않습니다.

“A dynamic workflow is a JavaScript script that orchestrates many subagents at once. Claude writes the script for the task you describe, and a runtime executes it in the background.”

Claude Code — Dynamic workflows

공식 문서 예시 스크립트

export const meta = {
  name: 'audit-routes',
  description: 'Audit every route handler for missing auth checks',
}

const found = await agent('List every .ts file under src/routes/.', {
  schema: { type: 'object', required: ['files'],
            properties: { files: { type: 'array', items: { type: 'string' } } } },
})

const audits = await pipeline(found.files, file =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }),
)

return audits.filter(Boolean)
런타임 제약문서가 밝힌 이유
실행 중 사용자 입력 불가스테이지별 승인이 필요하면 각 스테이지를 별도 워크플로로 분리
스크립트의 파일시스템·셸 직접 접근 불가에이전트가 읽고 쓰고 실행. 스크립트는 조율만
모듈 로딩 불가 (import() 포함 시 실행 전 실패)스크립트 본문은 plain JavaScript
동시 에이전트 최대 16개로컬 자원 사용 제한
parallel()/pipeline() 호출당 최대 4,096 항목조용한 상한은 작업 일부를 말없이 누락시키므로
실행당 총 1,000 에이전트Prevents runaway loops
결정성 강제 “Claude Code makes Date.now(), Math.random(), and a no-argument new Date() throw inside the script, so that a relaunched run repeats the same agent() calls.” — 재실행이 같은 결과를 내도록 비결정성을 아예 막아 둡니다.
실패 시 재실행 폭발 fan-out 중간에 하나가 실패하면 그 이후 시작된 이미 완료된 에이전트들까지 재실행됩니다. “If a script starts A, B, C, and D in that order and B fails, relaunching returns A from cache and runs B, C, and D again.”

Anthropic 멀티에이전트 문서의 수치 — 그래프는 공짜가 아니다

Opus 4(lead) + Sonnet 4(subagents) 멀티에이전트가 단일 Opus 4 대비 내부 평가에서 90.2% 우수. 그러나 토큰은 채팅 대비 에이전트가 약 4배, 멀티에이전트는 약 15배입니다. 브라우징 태스크 성능 분산의 80%를 토큰 사용량이 설명합니다.

잘 맞지 않는 경우(문서 명시): “모든 에이전트가 같은 컨텍스트를 공유해야 하거나 에이전트 간 의존성이 많은 작업”, 그리고 대부분의 코딩 작업(병렬화 가능한 부분이 제한적).

실무 판단 6원칙 — 모두 공식 문서 문장

01

먼저 만들지 마라

“finding the simplest solution possible… This might mean not building agentic systems at all.”

02

예측 가능하면 그래프, 아니면 루프

workflow = “predefined code paths”. agent = “dynamically direct their own processes”. 단계 수를 예측할 수 없을 때만 에이전트.

03

하네스의 모든 부품은 가정이다

“Every component in a harness encodes an assumption about what the model can’t do on its own.” 모델이 좋아지면 그 가정은 만료된다.

04

“무엇을 그만할 수 있는가”

Agent Harness Design 패턴 2. Sonnet 4.5용 context reset이 Opus 4.5에서 dead weight가 된 실제 사례가 있다.

05

멀티에이전트는 공짜가 아니다

약 15×채팅 대비 토큰. 컨텍스트 공유가 필요하거나 의존성이 많은 작업, 대부분의 코딩 작업에는 부적합.

06

가드레일은 훅·권한·샌드박스로

“A real guardrail needs to be deterministic.” 프롬프트에 적은 금지는 요청이지 강제가 아니다.

그래서, 새 아키텍처인가 새 어휘인가

어휘 쪽에 가깝습니다. 세 개념이 가리키는 문제 — 도구·권한·컨텍스트를 갖춰주는 일(하네스), 언제 멈출지 정하는 일(루프), 무엇을 병렬로 돌리고 어디서 합칠지 정하는 일(그래프) — 은 ReAct(2022)·Reflexion(2023)부터 LangGraph(3년 전 구축)까지 이미 있던 문제입니다.

다만 하나는 실제로 달라졌습니다. LangChain의 표현대로 “노드 안에 넣을 수 있는 것”이 바뀌었습니다 — 예전엔 노드가 결정론적 코드나 LLM 호출 하나였다면, 지금은 노드 하나가 온전한 에이전트 실행일 수 있습니다. 이름이 셋으로 갈라진 건 그 변화에 붙은 라벨입니다.
