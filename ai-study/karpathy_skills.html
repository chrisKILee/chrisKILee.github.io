02 핵심 원칙

4가지 행동 원칙 (원문 기반)

CLAUDE.md에 명시된 4가지 원칙입니다. 각 원칙에는 원문 핵심 문장이 함께 수록되어 있습니다.

🧠
Think Before Coding
코딩 전 먼저 생각하기

가정을 명시적으로 진술하라. 불확실하면 묻거나 여러 선택지를 제시하라. 침묵 속에 가정하지 말고 혼동과 트레이드오프를 수면 위로 드러내라.

"State your assumptions explicitly. If uncertain, ask."
모호성 해소
✂️
Simplicity First
단순함 우선

문제를 해결하는 최소한의 코드만 작성하라. 요청하지 않은 기능 추가, 섣부른 추상화, 불필요한 에러 핸들링을 금지한다. 200줄을 50줄로 줄일 수 있다면 그렇게 하라.

"Minimum code that solves the problem. Nothing speculative."
과잉 엔지니어링 방지
🔬
Surgical Changes
정밀한 변경

반드시 필요한 부분만 수정하라. 무관한 코드를 개선하지 말고, 자신이 만든 변경이 불필요하게 만든 코드만 정리하라. 기존 스타일과 일치시켜라.

"Touch only what you must. Clean up only your own mess."
부작용 방지
🎯
Goal-Driven Execution
목표 기반 실행

요청을 검증 가능한 성공 기준으로 변환하라. 명확한 목표와 검증 단계를 먼저 정의한 후 구현한다. AI는 명확한 목표까지 반복하는 데 뛰어나다.

"Define success criteria. Loop until verified."
자율 반복 실행
03 작동 원리

왜 65줄짜리 파일이 성능을 높이는가

CLAUDE.md는 단순한 텍스트 파일이지만, Claude Code가 세션을 시작할 때 자동으로 읽어 모든 API 호출의 시스템 프롬프트에 주입됩니다. 규칙이 명확할수록 AI는 가정을 줄이고 의도에 맞게 동작합니다.

CLAUDE.md → 시스템 프롬프트 주입 → 전 세션 규칙 적용 흐름

핵심 인사이트: "Harness Engineering"
AI 모델 자체를 개선하는 것이 아니라, AI를 어떻게 조종하는가에 초점을 맞추는 패러다임 전환입니다. 명확한 제약이 오히려 성능을 끌어올립니다 — 모호한 자유보다 잘 정의된 한계가 더 좋은 결과를 만듭니다.
왜 짧아야 하는가?
CLAUDE.md가 길수록 규칙 준수율이 낮아집니다. 200줄 이하를 권장하며, 짧고 명확한 문장이 긴 설명보다 더 잘 지켜집니다. AI는 명확한 제약 조건을 선호합니다.
04 문제와 해결책

AI 코딩의 3가지 반복 문제

Karpathy가 AI 에이전트를 실제로 사용하면서 반복적으로 마주친 문제들과, CLAUDE.md의 해결 방식입니다.

반복 문제 증상 CLAUDE.md 해결 원칙 적용 방법
무언의 가정
Silent Assumptions		 AI가 당신의 의도를 추측하고 그대로 진행. 질문 없이 코드 완성. Think Before Coding 불확실할 때 묻거나 복수 선택지 제시 — 침묵 가정 금지
과잉 엔지니어링
Over-Engineering		 간단한 요청에도 복잡한 추상화, 인터페이스, 에러 핸들링을 추가. Simplicity First 요청한 것만 최소한으로 — 추측성 기능 추가 금지
의도치 않은 부작용
Unwanted Side Effects		 관련 없는 코드도 수정·삭제·리팩토링. 원하지 않은 변경이 동반됨. Surgical Changes 요청과 직접 관련된 코드만 수정 — 무관한 정리 금지
성공 지표 (원문 기준)
CLAUDE.md 적용 후 기대할 수 있는 변화: 불필요한 diff 변경 감소 · 과잉 복잡화로 인한 재작업 감소 · 실수 후가 아닌 코드 작성 전에 명확화 질문이 선행됨.
05 원본 내용

CLAUDE.md 핵심 규칙 (원문)

GitHub에 공개된 실제 파일의 핵심 내용입니다. 4개 섹션으로 구성되며, 각 섹션은 문제 상황과 해결 목표를 명시합니다.

CLAUDE.md (markdown) 
## Think Before Coding

When starting a task:
- State your assumptions explicitly
- If uncertain about intent, ask clarifying questions or present
  multiple options before implementing
- Surface confusion and tradeoffs rather than making silent decisions

Goal: Resolve ambiguity before writing code, not after making mistakes.

---

## Simplicity First

Write the minimum code that solves the problem:
- No unrequested features
- No speculative abstractions
- No unnecessary error handling for cases that can't happen
- If you can solve it in 50 lines instead of 200, do it

Goal: Prevent over-engineering.

---

## Surgical Changes

When editing existing code:
- Only modify what's directly required by the request
- Don't "improve" unrelated code you notice
- Don't remove existing dead code unless your changes made it obsolete
- Match the current code style, even if imperfect

Goal: Prevent unintended side effects.

---

## Goal-Driven Execution

Before implementing:
- Transform the request into verifiable success criteria
- Define what "done" looks like concretely
- Provide a test loop so the model can iterate autonomously

Goal: LLMs excel at iterating toward specific targets.
Clear goals = more effective independent execution.

---

Note: Apply judgment to trivial tasks.
Speed vs caution — the tradeoff is real.
These rules trade speed for fewer rewrites.
