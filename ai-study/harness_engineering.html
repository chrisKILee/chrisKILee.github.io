Harness Engineering
AI가 잘 일하는 환경을 설계하는 기술

프롬프트만으로는 부족하다. "말을 잘 하는 것"에서 "일하는 방법을 설계해주는 것"으로. AI가 혼자서도 잘 일할 수 있는 작업 환경을 만드는 6가지 축을 정리한 발표 자료입니다.

04 구조 (Scaffolding)

프로젝트 구조, 도구 배치, 경계 설정

한 번 해두면 계속 쓰는 것. 프로젝트 구조를 잘 설계하면, AI는 그 구조에 맞춰 따라간다.

권장 프로젝트 구조

folder 
my-project/
├── src/        # 비즈니스 로직
├── docs/       # AI의 참고 문서
├── tests/      # 검증 인프라
├── .dev/       # 개발 도구/스크립트
├── .claude/    # AI 설정
├── out/        # 빌드 산출물
└── CLAUDE.md   # 프로젝트 지도

AI가 "테스트 작성해줘"→tests/, "문서 업데이트"→docs/에 자동으로 찾아간다

사람의 문서 vs AI의 문서

docs/ — 사람이 관리
  • 비즈니스 룰·도메인 정의
  • 체크리스트·온보딩 가이드
  • ADR·API 스펙·외부 연동 규격
.dev/ — AI가 남기는 기록
  • learnings·troubleshooting 기록
  • 작업 로그·디버깅 히스토리
  • 실험 결과·스크래치패드

경계 설정 — AI가 뭘 알고, 뭘 할 수 있고, 뭘 하면 안 되는지

구분파일역할예시
뭘 알려줄까 CLAUDE.md · rules/ 프로젝트 규칙, 코딩 스타일, 금기사항 기술 스택, 컨벤션, 중요 제약
어디까지 허용할까 settings.json Permission Mode로 자동 허용 범위 설정 plan / auto / bypass 모드
뭘 막을까 .claude/hooks/ 위험한 명령을 실행 전에 자동 차단 git push --force 차단, rm -rf 차단

05 맥락 (Context Engineering)

CLAUDE.md, 규칙, 점진적 노출

AI가 뭘 알고 일하는가. "한꺼번에 다 주면 AI도 헷갈린다."

설정 파일 상속 구조

하위가 상위를 덮어쓴다
USER(~/.claude/CLAUDE.md) → PROJECT(my-app/CLAUDE.md) → FOLDER(src/auth/CLAUDE.md)
가장 좁은 범위가 우선. 예: User에 "camelCase", Project에 "snake_case" → 이 프로젝트만 snake_case

CLAUDE.md 실전 가이드

U
User CLAUDE.md
내 작업 습관, 선호하는 코딩 스타일, 공통 규칙
P
Project CLAUDE.md
이 프로젝트의 기술 스택, 컨벤션, 중요한 제약. 팀 공유, Git 커밋.
F
Folder CLAUDE.md
특정 모듈의 특수한 규칙. 이 폴더 작업 시만 자동 로드.
팁
최대 200줄 정도를 유지하며 계속 업데이트하라. 너무 길어지면 AI 성능이 급격히 저하된다.

Progressive Disclosure

내용을 다 때려넣지 말고, "이런 상황에서는 이걸 참고해"라고 안내해서 필요한 것만 읽게 한다.

CLAUDE.md 
코드 작성 시 → references/code-style.md 참고
테스트 시   → references/testing-guide.md 참고
API 설계 시 → references/api-convention.md 참고
배포 시     → references/deploy-checklist.md 참고

세션 맥락 관리

사용량명령상황
~50%/compact오래된 대화 요약·압축. 같은 주제 이어갈 때.
~80%/clear컨텍스트 완전 초기화. 다른 주제로 전환할 때.
전환 전handoff현재 세션의 맥락을 파일로 저장 → 새 세션에서 이어받기.
06 계획 (Planning)

AI에게 일을 시키기 전에, 무엇을 할지 함께 정하기

"해줘"가 아니라 "같이 계획 세워보자". 계획과 실행을 분리하면 검수 횟수가 줄고, 결과의 예측 가능성이 올라간다.

❌ 안티패턴: "해줘"
1
"이거 만들어줘"
2
AI가 알아서 만듦
3
검수 → "아닌데..."
4
다시 시킴 → 검수 → 다시... 시간만 낭림
✅ 올바른 방법: 같이 계획부터
1
"~~할 건데 같이 계획 세워보자"
2
AI가 계획 작성 + AskUserQuestion으로 모호한 점 질문
3
사람이 검토 → 수정 → 승인
4
승인된 계획대로 실행 → 높은 성공률
AskUserQuestion 활용
스킬 프롬프트에 "이해한 것을 미러링하고, 모호한 점을 질문해서 명확하게 해줘"를 넣으면 AI가 자동으로 AskUserQuestion을 사용해 모호한 점을 물어본다. "해줘"가 아니라 "물어봐" — AI가 스스로 맥락을 채우게 하기.
07 실행 (Orchestration)

혼자, 부하 파견, 팀 — 상황에 맞는 실행 패턴

90%는 단일/서브에이전트로 충분하다. 팀 모드는 토큰 비용이 ~7배다.

👤
혼자 · Single

단순 작업, 대부분의 일상. AI 하나가 순차적으로 처리.

예: "블로그 글 조사 → 초안 작성 → 퇴고까지 순서대로"

TaskCreate로 체크박스
🔀
부하 파견 · Subagent

병렬/전문화. 위임 → 종합. 독립적인 작업에 서브에이전트 3개 spawn.

예: "A사, B사, C사 랜딩 페이지를 각각 에이전트 파견해서 동시에 분석해줘"

Agent 3개 spawn
👥
팀 협업 · Team Mode

다관점·복잡. 에이전트 간 소통. PM, 개발, 디자인, QA 역할 분리.

예: "Team 커서 설계자, 구현자, 리뷰어 3명으로 팀 꾸려줘"

TeamCreate · 토큰 ~7×

Ralph Loop — 될 때까지 반복

완료 기준을 정하고, 충족할 때까지 AI가 알아서 돈다. "뭐가 되면 끝인지"만 정해주면 AI가 될 때까지 계속 돈다.

1
완료 기준 합의
측정 가능한 조건으로 작성. "테스트 통과 + 빌드 성공 + 카피 3번 이상 퇴고"
2
AI가 작업
기준을 향해 자율적으로 실행
3
기준 충족? → 완료, 미달 → 2번으로
기준이 명확하면 자동 반복이 가능해진다

Auto Research — 자율 실험 루프

사람은 방향만 정하고, AI가 밤새 실험을 돌린다. karpathy/autoresearch 패턴.

패턴 
코드 수정 (train.py 변경)
    ↓
실행 (5분간 학습)
    ↓
평가 (성능 비교)
    ↓
판단 (유지 / 폐기)
    ↓ 자동 반복
다음 실험

시간당 ~12개 실험 자율 수행, 밤새 무인 운영

08 검증 (Verification)

결과물을 어떻게 믿을 것인가

기준이 있어야 검증이 가능하다. "뭐가 되면 끝인가"를 작업 시작 전에 정한다.

📋
원칙 01 · Sprint Contract

작업 전에 "뭘 만들고 어떻게 검증할지" 합의. 기준 없이 시키면 AI가 끝없이 하거나 대충 끝냈다고 한다.

  • 완료 조건을 먼저 정한다
  • 조건을 측정 가능하게 쓴다
  • 미달이면 다시 돌린다
Ralph Loop와 연동
⚖️
원칙 02 · Generator vs Evaluator

만든 AI와 확인하는 AI를 분리. 같은 컨텍스트에서 만들고 평가하면 quality가 mediocre해도 자신있게 칭찬한다.

Generator
결과물 생성
→ 분리 →
Evaluator
결과물 평가
컨텍스트 물리적 분리
🧪
원칙 03 · 모델도 역할도 나눈다
  • Codex — 코드 리뷰 (로직 오류, 보안 취약점)
  • Gemini — 문서 리뷰 (일관성, 정확성)
  • Opus/Sonnet — 성능별 분업
"Out of the box, Claude is a poor QA agent." — 검증 에이전트도 튜닝이 필요하다.
교차 검증
👁️
원칙 04 · 에이전트에게 눈을 달아주기

코드만 검증하는 게 아니라, 화면도 직접 보고 확인할 수 있어야 한다.

  • Browser Agent — Chrome CDP, DOM 탐색, 스크린샷, UX 직접 검증
  • Computer Use — 스크린샷 + 마우스/키보드로 모든 앱 제어
  • 시각 검증 루프 — 만든다 → 스크린샷 → 보고 판단 → 수정
chrome-cdp · computer-use MCP

안전장치 — "실수해도 괜찮은 구조"를 만드는 것이 핵심

09 개선 (Compound)

어떻게 계속 나아질 것인가

관측하기

세션 분석

10 자가 진단

잘 가고 있나? — Harness 건강 체크

복잡해지고 있다면 뭔가 잘못된 것. 좋은 Harness는 점점 단순해진다.

✅ 잘 가고 있다는 신호

  • +
    같은 말을 두 번 하지 않는다
    맥락 전달이 잘 되고 있다
  • +
    실수가 규칙이 된다
    개선 루프가 돌고 있다
  • +
    차단 장치가 뭔가를 막고 있다
    사고가 구조적으로 예방되고 있다
  • +
    불필요한 것이 줄어든다
    복잡해지는 게 아니라 단순해지고 있다

❌ 실패하고 있다는 징후

  • −
    검수에 시간이 더 오래 걸린다
    검증 자동화가 필요하다는 신호
  • −
    시켰는데 원하는 결과가 안 나온다
    맥락 전달 또는 계획 단계가 부족
  • −
    스킬·에이전트가 많은데 잘 안 쓴다
    context pollution + 제대로 동작 안 함
  • −
    가이드 파일이 길어지고 관리 안 된다

구조(Scaffold) — 환경을 설계하고 유지
  • 비즈니스 요구사항이 바뀔 때마다 코드베이스 구조 발전시키기
  • 새 도구/서비스 도입 시 폴더링과 경계 재설계
  • AI가 따라올 수 있는 아키텍처 유지
🧠
맥락(Context) — AI가 아는 것을 최신으로 유지
  • CLAUDE.md와 docs/를 코드와 함께 갱신
  • 새 컨벤션이 생기면 rules/에 추가
  • 오래된 규칙은 정리 — 가비지 컬렉션
📈
개선(Compound) — AI Slop이 나오지 않도록 점검
  • AI 산출물의 품질을 지속적으로 모니터링
  • 반복되는 실수 → 규칙으로, 반복 작업 → 스킬로
  • 안 쓰는 건 치우고, 쓰는 건 날카롭게
