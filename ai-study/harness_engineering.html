하네스 엔지니어링이란

핵심 정의 "AI가 잘 일하는 환경을 설계하는 기술" — 모델의 능력 자체가 아니라, 모델이 작동하는 구조와 환경을 최적화하는 것.

프롬프트 엔지니어링이 AI에게 무엇을 말할지를 다루고, 컨텍스트 엔지니어링이 무엇을 알려줄지를 다룬다면, 하네스 엔지니어링은 AI가 어떤 환경에서 작동하는가를 다룹니다.

"하네스(Harness)"는 말에 마차를 연결하는 마구(馬具)를 의미합니다. 말의 능력 자체를 바꾸지 않아도, 마구를 잘 설계하면 더 먼 거리를 더 안전하게 갈 수 있습니다. AI 개발에서도 마찬가지입니다.

진화 흐름

AI와 함께 일하는 방식은 세 단계를 거쳐 진화해왔습니다. 각 단계는 이전 단계를 포함하며, 더 높은 레이어를 추가합니다.

왜 중요한가

AI 도구가 범람하는 시대에 중요한 것은 "어떤 도구를 쓰는가"가 아니라 "AI가 어떤 환경에서 작동하는가"입니다.

6개 축 개요

하네스 엔지니어링은 6개의 축으로 구성됩니다. 각 축은 독립적이지만 서로 연결되어 하나의 생태계를 이룹니다.

FIG.2 · Harness Engineering 6개 축 구조

축 1
구조
Scaffolding
AI가 독립적으로 프로젝트를 파악할 수 있는 파일/폴더 구조. 네이밍 규칙, 역할 분리, 진입점 문서.
축 2
맥락
Context
시스템 프롬프트, CLAUDE.md, 규칙 파일, 외부 시스템 연결. 정보를 점진적으로 노출하는 설계.
축 3
계획
Planning
복잡한 작업을 실행 전에 먼저 계획하게 하는 구조. 스펙 문서, 태스크 분해, 의존성 파악.
축 4
실행
Execution
도구 호출, 반복 루프, 병렬 처리, 에이전트 오케스트레이션. AI가 완료 기준까지 스스로 실행.
축 5
검증
Verification
자동 테스트, 린터, 위험 작업 차단 훅. 생성 AI와 검증 AI를 분리하는 이중 구조.
축 6
개선
Compounding
AI의 반복 실수를 규칙으로 전환하고 자동화하는 피드백 루프. 사용할수록 나아지는 시스템.

① 구조 (Scaffolding)

AI가 세션을 새로 시작해도 프로젝트를 독립적으로 파악할 수 있도록 하는 구조 설계입니다.

핵심 원칙 "새 팀원이 설정 파일만 읽고 개발을 시작할 수 있다면, AI도 마찬가지다."
1

역할이 드러나는 디렉토리 구조

폴더 이름만 봐도 각 모듈의 역할을 알 수 있어야 합니다. src/auth/, src/payments/처럼 기능 단위로 구성.

2

CLAUDE.md — AI 진입점 문서

프로젝트 설명, 코딩 규칙, 금지 사항, 중요 파일 경로를 담는 AI 전용 가이드. 세션 시작 시 자동 로드.

3

도메인별 규칙 분리

전체 규칙은 루트 CLAUDE.md에, 도메인별 세부 규칙은 각 폴더의 규칙 파일로 분리. 관련 작업 시에만 자동 로드.

4

민감 파일 보호

.env, 시크릿 파일, 운영 DB 설정 등을 AI가 함부로 수정하지 못하도록 명시적으로 제한.

project/
├── CLAUDE.md          ← AI 진입점 (전체 규칙)
├── src/
│   ├── auth/
│   │   └── CLAUDE.md  ← 도메인 규칙 (인증 관련만)
│   └── payments/
├── .env.example       ← 실제 .env는 gitignore
└── docs/              ← 긴 맥락은 별도 분리

② 맥락 (Context)

AI가 작업에 필요한 정보를 정확하게, 적시에 받을 수 있도록 설계합니다.

점진적 노출 (Progressive Disclosure)

모든 정보를 한꺼번에 주입하면 컨텍스트 창이 낭비됩니다. 필요한 맥락을 필요할 때만 로드하는 설계가 핵심입니다.

범위위치내용
전체 프로젝트루트 CLAUDE.md코딩 컨벤션, 금지 사항, 주요 파일 경로
프로젝트 도메인폴더별 CLAUDE.md도메인 특화 규칙, 용어 정의
외부 시스템MCP / API 연결Jira, Confluence, Google Sheets 실시간 조회
작업별 컨텍스트HANDOFF.md / SPEC.md현재 진행 상황, 결정 사항, 다음 단계
주의 CLAUDE.md가 너무 길어지면 역효과. 핵심만 남기고, 상세 내용은 별도 문서로 분리한 뒤 참조하는 구조를 사용하세요.

③ 계획 (Planning)

복잡한 작업을 실행 전에 먼저 계획하게 하는 구조. "코드부터 짜봐"가 아닌 "먼저 계획을 세워봐".

효과 계획 단계를 명시적으로 강제하면 AI의 실행 품질이 크게 향상됩니다. 계획 없이 바로 코딩하면 중간에 방향을 바꾸거나 재작업이 발생합니다.
1

Plan 모드

Claude Code에서 Shift+Tab으로 Plan 모드 토글. 실행 없이 계획만 수립하고 사용자 승인 후 진행.

2

SPEC.md 작성

변경 목적, 영향 범위, 성공/실패 케이스를 문서화. 구현 전에 스펙부터 합의하는 SDD 방식.

3

Task 분해

큰 작업을 독립적인 작은 태스크로 분해. 의존성을 파악하고 병렬 처리 가능한 것을 식별.

4

HANDOFF.md

장시간 작업 시 세션 간 인수인계 문서. 다음 세션에서 컨텍스트를 즉시 복원할 수 있게 구조화.

④ 실행 (Execution)

AI가 도구를 호출하고, 반복하고, 병렬 처리하며 완료 기준까지 스스로 작업을 완수하는 구조.

오케스트레이션 패턴

작업 규모실행 방식예시
소형 (단순 반복)AI 단독 실행코드 포맷팅, 주석 추가
중형 (복잡한 단일 작업)Plan 모드 + 실행새 기능 구현, 버그 수정
대형 (복수 파일/시스템)서브에이전트 파견리팩토링, 아키텍처 변경
복합 (독립 태스크)병렬 에이전트 실행멀티 파일 동시 수정
자율 실행 구조 AI가 완료 기준까지 스스로 반복 시도하는 구조를 만드세요. "한 번만 실행하고 결과 보고"가 아닌 "기준을 충족할 때까지 계속 시도"가 목표입니다. 
## 실행 원칙 (CLAUDE.md에 명시)
- 테스트가 통과할 때까지 수정을 반복한다
- 빌드 에러는 자동으로 수정 시도한다
- 완료 기준: 테스트 Green + 린트 통과 + 타입 체크 통과

⑤ 검증 (Verification)

AI의 실수를 자동으로 감지하고, 위험 작업을 차단하며, 되돌릴 수 있는 구조를 만듭니다.

자동 검증린터, 포맷터, 타입 체커를 훅으로 자동 실행. AI 작업 후 즉시 품질 게이트 통과 여부 확인.
위험 작업 차단삭제, 배포, 민감 파일 수정을 자동으로 차단하는 가드레일. 시뮬레이션→확인→실행 흐름.

이중 검증 구조

1

생성 AI와 검증 AI 분리

코드를 작성한 에이전트가 직접 검증하면 실수를 놓칩니다. 별도 에이전트가 검증하는 이중 구조를 사용하세요.

2

격리 환경 E2E 테스트

메인 환경에 영향 없이 격리된 환경(브랜치, 도커)에서 End-to-End 검증 가능한 구조.

⑥ 개선 (Compounding)

AI와 협업하면서 발견한 패턴을 규칙으로 전환하고, 반복 작업을 자동화하는 피드백 루프입니다.

복리 효과 하네스는 사용할수록 나아지는 시스템입니다. AI의 실수 패턴 → 규칙 추가 → 다음 세션부터 자동 적용. 이것이 "Compounding(복리)"의 의미입니다.
1

실수 패턴 → 규칙화

AI가 같은 실수를 반복하면 즉시 CLAUDE.md에 규칙으로 추가. 다음 세션부터 자동으로 적용.

2

반복 작업 → 스킬(Skill)화

3회 이상 반복하는 작업 패턴을 인식하고, 슬래시 커맨드(Skill)로 자동화합니다.

3

작업 관찰 및 추적

AI 작업의 토큰 사용량, 성공/실패 패턴, 재작업 횟수를 추적. 개선 방향을 데이터로 파악.

4

정기 정리 (Pruning)

미사용 자동화, 오래된 규칙, 더 이상 유효하지 않은 연결을 정기적으로 정리. 시스템의 신선도 유지.

4가지 실습 스킬

team-attention/harness 리포지토리는 Claude Code 플러그인으로 설치할 수 있는 4가지 스킬을 제공합니다.

/check-harness
하네스 성숙도 진단
현재 프로젝트의 AI 최적화 수준을 5축 35개 항목으로 진단합니다. L1/L2/L3 성숙도 점수와 개선 우선순위를 제시.
/scaffold
AI 친화적 구조 생성
신규 프로젝트에 CLAUDE.md, 규칙 파일, 폴더 구조, Hook 템플릿 등 AI 최적화 스캐폴딩을 자동으로 생성합니다.
/specify
스펙 문서 작성
목표를 입력하면 상세한 구현 계획(spec.md)으로 변환합니다. 영향 범위, 성공/실패 케이스, 태스크 분해를 포함.
/deep-interview
요구사항 인터뷰
소크라테스 방식의 질문으로 요구사항의 불명확성을 해소합니다. "무엇을 왜 어떻게"를 구조화하는 심층 인터뷰.
설치 방법 Claude Code에서 /install-plugin https://github.com/team-attention/harness 실행 후 /scaffold로 현재 프로젝트에 AI 친화적 구조를 즉시 적용할 수 있습니다.

축 1

준비 (Scaffolding) — AI가 독립적으로 프로젝트를 파악할 수 있는 구조

L1디렉토리 구조만 보고 프로젝트의 역할 구분을 알 수 있다
L1AI에게 프로젝트 설명을 전달하는 파일이 있다 (CLAUDE.md 등)
L1긴 맥락은 별도 문서로 분리하고, 메인 파일에서 참조한다
L1민감 파일(.env, 시크릿 등)을 AI가 함부로 수정하지 못하게 보호
L2도메인별 규칙 파일 분리, 관련 작업 시에만 자동 로드
L2프로젝트 전용 자동화(Skill, Hook 등) 1개 이상 보유
L2AI 행동 범위를 명시적으로 제한 (샌드박스, 경로 제한, 권한)
L3새 팀원이 설정 파일만 읽고 개발 시작 가능
축 2

맥락 (Context) — 문서, 규칙, 정보의 점진적 노출

L1반복 지시 내용을 설정 파일에 기록
L1설정 파일이 간결함 (핵심만, 길면 분리)
L1AI 예상 외 행동 시 암묵지를 명시지로 기록
L2정보 범위를 구분해서 배치 (전체/프로젝트/폴더 설정)
L2도메인 용어, 정책, 장애 기록 등을 문서화
L2외부 시스템을 AI가 직접 조회 가능하게 연결
L3필요한 맥락을 "필요할 때만" 로드 (Progressive Disclosure)
축 3

실행 (Orchestration) — 계획 수립, 위임, 조율 체계

L1배경, 목적, 제약을 함께 전달
L1위임 시 완료 기준을 명시
L2복잡한 작업 전 계획을 먼저 세우게 함
L2작업 규모별로 혼자/부하 파견/팀 구성 구분
L2장시간 작업 시 세션 인수인계 문서 남김
L3AI가 완료 기준까지 스스로 반복 시도하는 구조
L3커스텀 계획 프로세스 보유 (인터뷰→스펙→실행)
L3독립 작업을 병렬 동시 실행 구조
축 4

검증 (Verification) — 테스트, 코드 리뷰, 품질 관리

L1AI 작업 후 테스트 가능한 환경 구축
L1코드 포맷터/린터가 자동으로 적용
L1위험 작업(삭제, 배포, 민감파일 수정)을 자동 차단
L2되돌릴 수 있는 구조 (브랜치, 격리 환경)
L2시뮬레이션→확인→실행 흐름 적용
L2AI 실수 자동 감지 및 재시도 복구 구조
L2격리 환경에서 E2E 검증 가능
L3생성 AI와 검증 AI 분리
축 5

개선 (Compounding) — 학습 및 피드백 루프

L1반복 실수 패턴 발견 시 규칙으로 전환
L13회 이상 반복하는 작업 인식
L2반복 작업을 자동화로 구현 (Skill 등)
L2AI 작업 관찰/추적 가능 (토큰, 로그 분석)
L3미사용 자동화, 규칙, 연결을 정기 정리
