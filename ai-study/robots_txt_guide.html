역사와 표준화

robots.txt는 1994년 Martijn Koster가 고안한 웹 크롤러 제어 프로토콜이다. 초기에는 비공식 신사협정으로 WebCrawler, Lycos, AltaVista 등이 자발적으로 준수하기 시작했으며, 약 25년간 공식 RFC 없이 de facto 표준으로만 유지됐다.

시점사건
1994년 6월Martijn Koster가 Robots Exclusion Protocol 창안. 초기명 "RobotsNotWanted.txt"
1994~2019년~25년간 공식 RFC 없이 de facto 표준으로 유지. 주요 검색 엔진 대부분 자발적 준수
2019년 7월Google이 IETF에 공식 표준화 제안 (Martijn Koster와 공동 저술)
2022년 9월RFC 9309 공식 발표 (IETF Proposed Standard Track)
💡

RFC 9309의 핵심 기여

오류 처리(5xx → 차단, 404 → 허용) 명확화 · 캐싱 지침 표준화 · Percent-Encoding 처리 규칙 · 최소 500 KiB 처리 용량 요구

파일 구조

robots.txt는 UTF-8 텍스트 파일로 웹사이트 루트(https://example.com/robots.txt)에 위치해야 한다. 기본 구조는 User-agent 그룹들의 집합이다.

# 기본 구조
User-agent: Googlebot        # 적용 대상 크롤러
Disallow: /private/          # 차단할 경로
Allow: /private/public/      # 예외적으로 허용

User-agent: *                # 모든 크롤러
Disallow: /admin/

Sitemap: https://example.com/sitemap.xml
⚠️

중요: 각 User-agent 그룹은 빈 줄로 구분되어야 한다. 한 그룹의 규칙은 다른 그룹에 자동으로 상속되지 않는다.

지시어 완전 정리

User-agent

규칙이 적용될 크롤러를 지정한다. *는 모든 크롤러를 의미하는 와일드카드다. 대소문자를 구분하지 않으며, 영문자·언더스코어·하이픈만 사용 가능하다.

Disallow

접근을 차단할 경로를 지정한다. 경로는 대소문자를 구분한다(case-sensitive). 빈 값(Disallow:)은 모든 경로를 허용하는 것과 같다.

Disallow: /private/      # /private/ 이하 전체 차단
Disallow: /admin/        # /admin/ 이하 전체 차단
Disallow: /temp.html     # 특정 파일만 차단
Disallow: /              # 사이트 전체 차단
Disallow:                # 모든 경로 허용 (= 차단 없음)

Allow

Disallow와 충돌할 때 특정 경로를 예외적으로 허용한다. 더 구체적인(긴) 경로가 우선한다. 빈 값은 무시된다.

Disallow: /temp/
Allow: /temp/public/     # /temp/ 전체 차단이지만 /temp/public/은 허용

Crawl-delay

다음 요청까지 대기할 시간(초)을 지정한다. RFC 9309 비표준 지시어다.

크롤러Crawl-delay 지원
Googlebot❌ 무시 — Google Search Console에서 개별 설정 필요
Bingbot✓ 지원
Yandex, Baidu✓ 지원
AI 크롤러들대부분 무시

Sitemap

XML 사이트맵의 절대 URL을 지정한다. 여러 개 선언 가능하며, 반드시 완전한 URL을 사용해야 한다(상대 경로 불가).

Sitemap: https://example.com/sitemap.xml
Sitemap: https://example.com/sitemap-images.xml

와일드카드

RFC 9309 표준에 포함되지 않지만 Google, Bing, 주요 AI 크롤러가 모두 지원한다.

* — 0개 이상의 임의 문자

Disallow: /*.php$         # .php로 끝나는 모든 URL
Disallow: /search*        # /search로 시작하는 모든 URL
Disallow: /*?             # 쿼리 파라미터가 있는 모든 URL
Disallow: /development/*  # /development/ 하위 전체

$ — URL 끝 앵커

Disallow: /example$       # 정확히 /example로 끝나는 URL만 차단
                          # /example-page, /examples 는 차단 안 됨
Disallow: /*.pdf$         # .pdf로 끝나는 모든 URL
💡

조합 예시: Disallow: /*.php$는 *와 $를 결합해 ".php로 끝나는 모든 경로"를 차단한다.

우선순위 결정 방식

RFC 9309는 경로 길이(Specificity) 기반 최장 일치(Longest Match) 우선 원칙을 정의한다.

기본 원칙

상황규칙결과
경로 길이 다름긴 경로 vs 짧은 경로긴 경로 우선
동일 길이 Allow+Disallow 충돌동등한 두 규칙 경합Allow 우선 (덜 제한적)
매칭 규칙 없음-Allow (기본값)

실전 예시

# 예시 1: 길이 기반 우선순위
User-agent: *
Disallow: /admin/            # 길이 7
Allow: /admin/public/        # 길이 14 ← 더 길어서 우선

GET /admin/public/file.html  → ALLOW  ✓
GET /admin/private/data.json → DISALLOW ✗

# 예시 2: 동일 길이 — Allow 우선
User-agent: *
Disallow: /test/
Allow: /test/

GET /test/page.html → ALLOW (길이 같을 때 Allow 우선)

# 예시 3: 여러 User-agent 그룹
User-agent: Googlebot
Disallow: /private/

User-agent: *
Disallow: /temp/

# Googlebot → /private/ 적용, /temp/ 도 적용(*)
# Bingbot → /temp/ 만 적용 (Googlebot 그룹 미해당)
⚠️

User-agent 그룹 상속 없음

특정 User-agent 규칙은 * 그룹 규칙을 자동으로 포함하지 않는다. Googlebot에 대한 규칙이 있으면 * 그룹 규칙과 독립적으로 평가된다.

크롤러 실제 동작 방식

HTTP 상태코드별 처리 (RFC 9309)

상태코드처리 방식효과
200 OK파일 파싱규칙 적용
404 Not FoundEMPTY_RULES 가정모든 경로 허용
401/403UNAVAILABLE모든 경로 허용 (접근 불가 → 허용으로 처리)
5xxUNREACHABLE모든 경로 차단 (서버 장애 중 보수적 처리)
30x리다이렉트 추적최종 URL의 robots.txt 적용

캐싱 정책 (Google 기준)

  • 기본 캐시 TTL: 최대 24시간
  • Cache-Control: max-age 헤더가 있으면 해당 값 따름
  • 타임아웃/연결 실패 시: 마지막 알려진 버전 사용
  • 지속적 5xx 장애 시: 최후 작동 버전 유지하며 재시도

파일 크기 제한

RFC 9309는 크롤러가 최소 500 KiB를 처리할 수 있어야 한다고 규정한다. 이를 초과하는 부분은 크롤러가 무시할 수 있다.

5가지 핵심 허점

허점 1 — 법적 구속력 없음 (신사협정)

robots.txt는 법적으로 강제되지 않는 자발적 프로토콜이다. 미국 Ninth Circuit 항소법원 판례 hiQ Labs v. LinkedIn (2022)에 따르면, 공개된 데이터에 대한 접근은 CFAA(Computer Fraud and Abuse Act) 위반이 되지 않는다. CFAA는 사용자명/비밀번호 같은 기술적 인증 우회에만 적용된다.

기술적 차단 (강제 가능)

  • • HTTP 401/403 인증
  • • IP 차단
  • • WAF/Cloudflare 규칙
  • • Rate Limiting

robots.txt (신사협정)

  • • 법적 구속력 없음
  • • 착한 크롤러만 따름
  • • 실제 접근은 막지 못함
  • • 위반 시 제재 수단 없음

2024년 영국 뉴스 사이트를 대상으로 한 연구에서 AI 크롤러의 72%가 robots.txt 지시를 무시한 것으로 확인됐다.

Anthropic 봇 3분류 문제

ClaudeBot만 차단해도 불완전하다. Claude-User(사용자가 Claude에서 링크 방문)와 Claude-SearchBot(검색 기능)은 별도로 차단해야 한다. ChatGPT-User처럼 인터랙티브 접근은 robots.txt로 제어 자체가 불가능하다.

정보 누출 역설 (robots.txt Leakage)

robots.txt는 크롤러를 막기 위해 경로를 나열한다. 그런데 이 파일 자체가 공개 URL(/robots.txt)에 위치해 있기 때문에, 악의적 행위자에게 공격 지도(attack map)를 제공하는 역설이 발생한다. 

# 이 robots.txt는 공격자에게 다음을 알려준다:
Disallow: /admin/           # → 관리자 패널 위치
Disallow: /backup/          # → 백업 파일 위치
Disallow: /api/v1/users/    # → API 구조
Disallow: /.git/            # → Git 저장소 위치
Disallow: /database/backup.sql  # → 직접 DB 파일 경로!
⚠️

이중 모순

선의의 크롤러(Google, Bing)는 차단되지만, 악의적 행위자는 robots.txt를 읽고 오히려 공격 대상을 파악한다. 정말 민감한 경로는 robots.txt에 노출하는 대신 기술적 인증(401/403, IP 차단)으로 보호해야 한다.

나머지 허점 요약

  • 동적 콘텐츠 차단 불가 — JavaScript SPA, GraphQL 쿼리는 robots.txt로 차단 불가
  • 기술적 차단이 아님 — robots.txt는 "팻말"이고, HTTP 403은 "울타리"다. 파일은 실제로 접근 가능한 상태다
  • User-Agent 위조 가능 — curl -A "Googlebot/2.1"으로 누구나 크롤러를 흉내 낼 수 있다

대안 및 보완책

X-Robots-Tag HTTP 헤더

페이지 수준에서 인덱싱을 제어한다. HTML뿐 아니라 PDF, 이미지 등 모든 파일 타입에 적용 가능하다.

# Nginx 설정 예시
location /private/ {
    add_header X-Robots-Tag "noindex, nofollow";
}

# HTTP 응답 헤더
X-Robots-Tag: noindex, nofollow
X-Robots-Tag: noindex          # 인덱싱만 금지 (크롤링은 허용)
X-Robots-Tag: none             # 모든 것 금지
비교robots.txtX-Robots-Tag
적용 범위경로 전체개별 페이지/파일
동작크롤링 차단인덱싱 제어
파일 타입모든 리소스HTML, PDF, 이미지 등
강제 여부신사협정신사협정

Cloudflare Bot Management (기술적 강제)

robots.txt와 달리 실제로 요청이 서버에 도달하지 않도록 기술적으로 차단한다.

  • Managed Robots.txt — Cloudflare가 자동 생성·관리, AI 크롤러 자동 차단 (Pro 플랜 이상)
  • AI Crawl Control — robots.txt 무시하는 봇도 WAF 레벨에서 강제 차단
  • Rate Limiting — 특정 User-Agent의 요청 속도 제한

llms.txt (신규 제안)

2024년 Jeremy Howard가 제안한 새로운 프로토콜이다. robots.txt가 "무엇을 차단할지"를 알려준다면, llms.txt는 "AI가 무엇을 읽어야 하는지"를 안내하는 Markdown 문서다. 공식 RFC는 아니지만 초기 채택 단계에 있다. 

# /llms.txt 예시 (Markdown 형식)
# My Company

My company is a SaaS platform for project management.

## Key Features
- Real-time collaboration
- AI-powered task prioritization

## Licensing
Creative Commons Attribution 4.0

## API Docs
- [REST API](https://docs.example.com/api)

계층화된 방어 전략 (Defense in Depth)

1

robots.txt

선의의 크롤러 차단 — 신사협정

2

X-Robots-Tag / noindex

페이지 수준 인덱싱 제어

3

Authentication / Authorization

HTTP 401/403 기술적 접근 제어

4

Cloudflare / WAF

기술적 강제 차단 — IP/User-Agent 레벨

5

Rate Limiting / IP 화이트리스트

대량 요청 차단, 공식 크롤러 IP만 허용

✅

핵심 요약

robots.txt는 선의의 크롤러에 대한 1차 방어선일 뿐이다. AI 크롤러가 이를 무시하는 시대에는 Cloudflare AI Crawl Control과 같은 기술적 강제 수단을 반드시 병행해야 한다. 민감한 데이터는 반드시 기술적 인증으로 보호하고, robots.txt에 절대 경로를 노출하지 말 것.
