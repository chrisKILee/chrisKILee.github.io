2. 현행 아키텍처 주요 한계 및 이슈

MM2 복제 구조와 DMZ 구간 통신 제약 — 2가지 핵심 문제

Issue 01
데이터 복제 구조의
강-결합 (Tight-Coupling)
MirrorMaker2 기반 클러스터 간 복제
현황 거점 Kafka ↔ GCP Kafka 간 MM2 기반 복제 운영 중
문제 두 클러스터 간 상태 동기화로 인한 운영 오버헤드 및 장애 전파 위험
요구 MM2를 대체할 수 있는 유연한 데이터 복제 방안 검토 필요
Issue 02
DMZ 구간
통신 제약
방화벽 정책으로 인한 직접 전송 불가
현황 지역 DMZ 서버 내 Alloy에서 내부망의 GCP Kafka로 직접 전송 불가
문제 DMZ 방화벽 정책 및 네트워크 단절로 인한 통신 제약 발생
요구 거점 내에서 데이터를 중계(Proxy)해 줄 수 있는 서버 아키텍처 필요
3. 차세대 모니터링 데이터 파이프라인 (TO-BE)

3-Step 아키텍처 — 엣지 수집 → 거점 버퍼 → 클라우드 통합

Step 1  ·  수집 / 전달
엣지 & 게이트웨이 구성

DMZ 서버군은 Alloy Gateway 또는 REST Proxy를 통해 HTTP/OTLP 기반으로 안전하게 내부 거점으로 데이터를 전송합니다.

Alloy Gateway REST Proxy HTTP/OTLP
Step 2  ·  완충 / 로컬 저장
거점 허브 — 버퍼 풀

각 지역 거점 Kafka/Alloy가 데이터를 1차 취합하여 네트워크 단절에 대비한 버퍼 풀(Buffer Pool) 역할을 수행합니다.

거점 Kafka Buffer Pool Local Alloy
Step 3  ·  전송 / 통합
클라우드 통합 전송

MM2 강결합을 탈피하여 GCS 기반 우회 전송 또는 비동기 Connect를 활용해 GCP Kafka로 최종 통합합니다.

GCS 우회 Async Connect GCP Kafka
