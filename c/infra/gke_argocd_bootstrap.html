01 — Overview

부트스트랩 전체 흐름

Phase 0~E의 5단계 수동 절차로 ArgoCD를 부트스트랩하고 이후 GitOps 자동 운영 체계로 전환. 각 Phase는 클러스터당 최초 1회만 실행하며, 이후 모든 변경은 Git PR을 통해 ArgoCD가 자동 반영한다.

주의: Phase 0~D의 수동 명령은 클러스터당 최초 1회만 실행한다. 반복 실행하면 ArgoCD auto-sync와 충돌하여 drift가 발생하므로 절대 재실행하지 않는다.

핵심 순서 결정 근거

Phase 0
런북 진입점 — context 검증
잘못된 context에서 실행되는 kubectl apply / helm install은 운영 클러스터를 오염시킨다. Phase 0은 "런북 진입점"이자 "각 Phase 시작 직전 재확인 지점"이다.
Phase A
ComputeClass 선배포 (닭과 달걀 방지)
ADR-018 dedicated infra 노드 격리 정책에 따라 플랫폼 Pod은 computeclass=e2-on-demand + dedicated=infra toleration을 가진다. ComputeClass 리소스가 없으면 Phase B/C의 Pod가 오래 Pending으로 남는다.
Phase B
sealed-secrets controller 선기동
ArgoCD의 configs.secret.createSecret: false 설정상 helm install은 argocd-secret을 생성하지 않는다. helm install 이전에 평문 argocd-secret이 클러스터에 있어야 ArgoCD Pod이 정상 기동하며, 이를 위해 sealed-secrets controller가 먼저 기동해 SealedSecret을 복호화해야 한다.
Phase C
SealedSecret 선배포 → helm install argocd
helm install 직전에 sealedsecret-*.yaml만 먼저 apply해 controller가 평문 Secret을 생성하도록 한다. AppProject / ApplicationSet은 argoproj.io/v1alpha1 CRD가 argocd helm chart로부터 설치된 후에만 apply 가능하므로 Phase D로 분리한다.
Phase D
self-management 전환 — GitOps 시작점
잔여 매니페스트(AppProject·ApplicationSet 4종·HTTPRoute)를 apply하여 ArgoCD가 자기 자신과 다른 모든 서비스를 GitOps로 관리하기 시작하는 전환점이다.

04 — Phase A

ComputeClass 선배포

ADR-018 dedicated infra 노드 격리 정책에 따라 플랫폼 Pod은 computeclass=e2-on-demand toleration을 가진다. ApplicationSet이 본 리소스를 자동 생성하기까지 기다리면 닭과 달걀 문제가 발생하므로, Phase A에서 ComputeClass만 단독으로 직접 apply한다.

bashLAB
kubectl --context lab apply -f infra/k8s/lab/compute-class/manifests/
bashDEV INFRA
kubectl --context dev-infra apply -f infra/k8s/dev-infra/compute-class/manifests/

검증

bash
kubectl --context lab get computeclass        # Lab
kubectl --context dev-infra get computeclass  # Dev Infra
# e2-on-demand, e2-spot 두 ComputeClass가 표시되면 성공
참고: namespace가 없는 cluster-scoped CRD 인스턴스이므로 별도의 namespace 선생성은 불필요하다. Phase D에서 ApplicationSet이 <cluster>-compute-class-manifests Application을 자동 생성해 동일 매니페스트를 desired로 등록하므로, 이후 ComputeClass 변경은 Application을 통해서만 반영한다.
05 — Phase B

sealed-secrets 부트스트랩

controller가 fresh keypair를 자동 생성하면 기존에 커밋된 SealedSecret 전부가 복호화 불가능해지므로, Secret Manager에 사전 저장된 마스터 키를 선주입한 뒤 helm install한다.

5.1 namespace 생성

bash
kubectl --context lab create namespace sealed-secrets      # Lab
kubectl --context dev-infra create namespace sealed-secrets # Dev Infra

5.2 Secret Manager 마스터 키 → cluster apply

yq 사용 이유: Secret Manager 저장본이 kubectl get secret -o yaml 결과 그대로일 경우 runtime 필드(resourceVersion / uid / creationTimestamp / managedFields)가 포함되어 apply 시 경고·오류가 발생한다.
bashLAB
gcloud secrets versions access latest \
    --secret=lab-gke-sealed-secret-master-key \
    --project=vntg-rnd-lab-dev \
  | yq 'del(.metadata.resourceVersion, .metadata.uid, .metadata.creationTimestamp, .metadata.managedFields)' \
  | kubectl --context lab apply -f -
bashDEV INFRA
gcloud secrets versions access latest \
    --secret=dev-infra-gke-sealed-secret-master-key \
    --project=vntg-nfw-common-dev \
  | yq 'del(.metadata.resourceVersion, .metadata.uid, .metadata.creationTimestamp, .metadata.managedFields)' \
  | kubectl --context dev-infra apply -f -

5.3 helm install sealed-secrets (최초 1회)

금지: helm uninstall은 master key Secret까지 제거할 위험이 있다. 이후 chart 업그레이드는 ArgoCD Application을 통해서만 반영한다.
bash
helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
helm repo update sealed-secrets
bashLAB
helm --kube-context lab install lab-sealed-secrets sealed-secrets/sealed-secrets \
    --version 2.18.0 \
    --namespace sealed-secrets \
    --values infra/k8s/lab/sealed-secrets/values.yaml
bashDEV INFRA
helm --kube-context dev-infra install dev-infra-sealed-secrets sealed-secrets/sealed-secrets \
    --version 2.18.0 \
    --namespace sealed-secrets \
    --values infra/k8s/dev-infra/sealed-secrets/values.yaml

5.4 검증

bashLAB
# 1) Controller Pod Running
kubectl --context lab -n sealed-secrets get pod

# 2) 선주입된 마스터 키가 active로 등록됐는지 확인
kubectl --context lab -n sealed-secrets get secret \
    -l sealedsecrets.bitnami.com/sealed-secrets-key

# 3) Controller 로그 확인
kubectl --context lab -n sealed-secrets logs deploy/lab-sealed-secrets \
  | grep -E "registered private key|Searching for existing"

# 4) 공개 cert 대조 (kubeseal은 --context 미지원, use-context 먼저)
kubectl config use-context lab
kubeseal --fetch-cert \
    --controller-namespace sealed-secrets \
    --controller-name lab-sealed-secrets \
  > /tmp/new-pub.pem
diff infra/k8s/lab/sealed-secrets-pub.pem /tmp/new-pub.pem  # 빈 출력이면 일치
06 — Phase C

ArgoCD SealedSecret 선배포 → helm install

SealedSecret만 먼저 apply → helm install argocd → 잔여 매니페스트 apply (Phase D)의 3단계로 분리. 일괄 apply 시 발생하는 두 가지 실패 패턴을 방지한다.

시도 패턴 실패 원인
A. helm install 이전 일괄 apply AppProject / ApplicationSet CRD 부재 → silent skip되어 누락이 늦게 발견됨
B. helm install 이후 일괄 apply 평문 argocd-secret 부재 → Pod CrashLoopBackOff. SealedSecret 복호화 후에도 Pod 자동 회복 안 됨

6.1 argocd namespace 생성

bash
kubectl --context lab create namespace argocd      # Lab
kubectl --context dev-infra create namespace argocd # Dev Infra

6.2 SealedSecret만 먼저 apply

bashLAB
cat infra/k8s/lab/argocd/manifests/sealedsecret-*.yaml \
  | kubectl --context lab apply -f -
# Lab: argocd-secret / argocd-redis / repo-rnd-infra / repo-creds-github-vntgcorp

# Secret 생성 확인
kubectl --context lab -n argocd get secret argocd-secret argocd-redis repo-rnd-infra repo-creds-github-vntgcorp
bashDEV INFRA
cat infra/k8s/dev-infra/argocd/manifests/sealedsecret-*.yaml \
  | kubectl --context dev-infra apply -f -
# Dev Infra: 위 4개 + cluster-dev-service / cluster-idc

kubectl --context dev-infra -n argocd get secret \
    -l argocd.argoproj.io/secret-type=cluster

6.3 helm install argocd

주의: chart 버전 9.5.2는 infra/k8s/<cluster>/argocd/config/external-helm.yaml의 chartVersion과 정확히 일치해야 한다. 일치하지 않으면 adopt 직후 Application이 OutOfSync로 표시된다.
bash
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update argo
bashLAB
helm --kube-context lab install lab-argocd argo/argo-cd \
    --version 9.5.2 \
    --namespace argocd \
    --values infra/k8s/lab/argocd/values.yaml
bashDEV INFRA
helm --kube-context dev-infra install dev-infra-argocd argo/argo-cd \
    --version 9.5.2 \
    --namespace argocd \
    --values infra/k8s/dev-infra/argocd/values.yaml

self-management 전환

잔여 매니페스트를 apply하여 AppProject·ApplicationSet이 생성되게 함으로써 ArgoCD가 자기 자신과 다른 모든 서비스를 GitOps로 관리하기 시작하는 전환점이다.

7.1 잔여 매니페스트 apply

bashLAB

08 — Phase E

검증

부트스트랩 완료 여부를 Application 상태 / Cloud DNS record / UI 접근 / auto-sync의 4단계로 검증한다.

8.1 모든 Application Synced / Healthy

bash
kubectl --context lab -n argocd get application -o wide
kubectl --context dev-infra -n argocd get application -o wide

8.2 Cloud DNS A record 자동 생성 확인

bashLAB
gcloud dns record-sets list \
    --zone=lab-terroir-vntgcorp-com \
    --project=vntg-nfw-infra-common \
    --filter="name:argocd.lab.terroir.vntgcorp.com"
기대 결과: argocd.<cluster-domain>. A record + _externaldns.argocd.<cluster-domain>. TXT record가 함께 존재. external-dns의 policy: upsert-only 설정 때문에 record 삭제는 자동 발생하지 않는다.

8.3 UI 접근 (페이지 미표시 시 순서대로 확인)

① DNS resolve
dig argocd.lab.terroir.vntgcorp.com 또는 dig argocd.dev.terroir.vntgcorp.com
② Gateway 외부 IP
kubectl --context lab -n gateway-system get gateway
③ Certificate Manager
인증서가 ACTIVE 상태인지 확인
Google OAuth: @vntgcorp.com 도메인 계정으로 로그인. admin 이메일 목록 계정은 role:admin, 그 외는 policy.default: role:readonly.

8.4 Git push로 auto-sync 검증 (선택)

사소한 non-destructive 변경(예: 주석 한 줄)을 commit·push·merge한 뒤 timeout.reconciliation 주기(Lab: 30s / Dev Infra: 60s) 내에 Application 상태가 Synced를 유지하는지 관찰한다.

09 — Operations

운영 원칙 (부트스트랩 이후)

helm upgrade 금지
ArgoCD의 auto-sync가 helm이 남긴 변경을 다시 desired로 덮어쓰거나 drift가 발생한다. 버전 업그레이드는 infra/k8s/<cluster>/<service>/config/external-helm.yaml의 chartVersion을 PR로 변경한다.
kubectl edit 금지
selfHeal=false로 즉시 되돌리지는 않지만 Application이 OutOfSync로 누적되어 추적이 어려워진다. 실험이 필요하면 임시 리소스를 ArgoCD 관리 범위 밖 namespace에 만들어 검증한다.
변경 경로는 Git만
values.yaml, manifests/*.yaml, config/*.yaml 수정 → Pull Request → merge → ArgoCD가 timeout.reconciliation 주기 내 감지하여 sync.
신규 서비스 추가
infra/k8s/<cluster>/<service>/에 config/*.yaml, manifests/, values.yaml을 커밋하면 ApplicationSet이 다음 scan 주기에 Application을 자동 생성한다. 런북 재실행 불필요.
수동 sync
selfHeal=false이므로 sync 실패 후 재시도는 ArgoCD UI의 SYNC 버튼 또는 argocd app sync <application-name>으로 수동 트리거한다.
--context 명시 필수
운영 단계의 ad-hoc kubectl / helm 명령에도 항상 --context <cluster>를 붙인다. 전역 default context에 의존하면 다른 클러스터 운영 중인 동료의 context가 우연히 일치하지 않을 때 사고가 발생한다.
10 — Troubleshooting

트러블슈팅

부트스트랩 과정에서 발생할 수 있는 주요 장애 상황과 원인·해결 방법.

11.1 SealedSecret이 복호화되지 않음 (argocd-secret NotFound)
원인 1 controller가 fresh keypair를 생성해 기존 봉인 cert와 어긋났다. Phase B §5.2의 Secret Manager 마스터 키 apply가 helm install 이전에 수행됐는지 재확인.
원인 2 controller 기동 시 master-key Secret label(sealedsecrets.bitnami.com/sealed-secrets-key=active)과 namespace가 올바른지 확인.
원인 3 argocd ns가 SealedSecret apply 시점에 존재하지 않았다. Phase C §6.1에서 ns를 선생성했는지 확인.
11.2 argocd-server / argocd-redis Pod이 CrashLoopBackOff
원인 Phase C §6.2의 SealedSecret apply가 누락되어 helm install 시점에 평문 argocd-secret / argocd-redis가 없었다.
bash
kubectl --context lab -n argocd get secret argocd-secret argocd-redis
# 없다면 §6.2 SealedSecret apply 후 Pod 재기동
kubectl --context lab -n argocd rollout restart deploy/lab-argocd-server
11.3 <cluster>-argocd Application이 OutOfSync 상태로 남음
원인 infra/k8s/<cluster>/argocd/config/external-helm.yaml의 chartVersion과 Phase C §6.3의 helm install --version 값이 다르다. UI에서 SYNC를 수동 실행하거나 config의 chartVersion을 helm install 값과 일치시킨다.
11.4 repo-rnd-infra로 Git clone이 실패
원인 1 sealedsecret-repo-rnd-infra.yaml 봉인 당시의 평문 값(App ID / Installation ID / Private key PEM)이 잘못됐거나 현재 GitHub App 설정과 어긋났다.
원인 2 이전 클러스터의 sealed-secrets 마스터 키로 봉인되어 현재 클러스터의 키쌍과 맞지 않는다. controller 로그에서 failed to unseal 메시지 확인.
11.5 Gateway HTTPS listener가 Degraded
원인 Certificate Manager map이 아직 wildcard 인증서를 발행하지 않았거나 DNS authorization 검증이 완료되지 않았다. Terraform apply 완료 후 수 분~수십 분 대기. 인증서 ACTIVE가 되면 Gateway가 자동 회복.
11.6 Google OAuth 로그인 시 redirect_uri_mismatch
원인 Google OAuth Client의 Authorized redirect URIs에 https://argocd.<cluster>.terroir.vntgcorp.com/api/dex/callback이 등록되어 있지 않거나 HTTP/HTTPS scheme이 다르다. Cloud Console → APIs & Services → Credentials에서 redirect URI 추가. hostedDomains는 argocd values.yaml에서 설정.
11.7 external-dns가 record를 만들지 않음
원인 1 Workload Identity 바인딩 누락 → external-dns Pod이 Cloud DNS API 호출 시 401. Pod 로그에서 Error getting zones 확인.
원인 2 HTTPRoute hostname이 domainFilters: - lab.terroir.vntgcorp.com에 포함되지 않는 도메인이다.
원인 3 sources: [service, gateway-httproute] 외 리소스 타입에서 hostname 선언 중. values.yaml에 source 추가 또는 HTTPRoute로 변경.
11.8 Pod이 Pending 상태로 남아 ComputeClass 미스 의심
원인 Phase A의 ComputeClass 선배포가 누락되어 sealed-secrets / argocd Pod의 nodeSelector / toleration을 만족하는 노드가 없다.
bash
kubectl --context lab get computeclass        # Lab
kubectl --context dev-infra get computeclass  # Dev Infra
# e2-on-demand / e2-spot 없다면 §4.1 apply 실행 후 Pending Pod를 delete해 재스케줄
11.9 Dev Infra — dev-service-* Application이 cluster-not-found로 실패
원인 1 §6.2에서 sealedsecret-cluster-dev-service.yaml apply가 누락되어 cluster Secret 미생성.
원인 2 cluster Secret의 label이 누락 — argocd.argoproj.io/secret-type=cluster가 포함되어야 한다.
원인 3 cluster Secret의 name 필드와 ApplicationSet의 destination.name이 불일치. dev-service ApplicationSet은 destination.name: dev-service를 기대한다.
