핵심 결정: 군산·포항 등 VM이 있는 지역에는 지역 Kafka를 직접 배치하고, VM이 없는 순천·창원은 상암 IDC를 경유하여 GCP로 전송한다. 이미 구성이 완료된 상태이며, 대체할 명확한 사유가 없어 현행 유지.
🎯 지역 Kafka 배치의 이유/필요성
단순히 이미 설치됐기 때문이 아닙니다. 지역 Kafka는 운영 현실의 네 가지 문제를 구조적으로 해결합니다.
✅

이미 구성 완료

  • 🖥️ 지역별 Kafka 서버가 이미 설치·운영 중
  • 🌐 각 지역 Kafka마다 개별 도메인 URL 생성 완료
  • 🔒 대체해야 할 명확한 사유가 현재로서는 없음
이미 구성이 완료된 상태 → 유지가 기본값
🔔

회선 장애 알림 집약

  • ❌ 지역 Kafka 없을 때: 서버 수십~수백 개에서 알림 동시 발생
  • ✅ 지역 Kafka 있을 때: Kafka 1개 알림으로 집약
  • 🎯 장애 포인트(회선 vs 서버)를 즉시 식별 가능
알림 100개 → 1개로 줄어 원인 파악이 빨라짐
🔀

GCP 경로 변경 시 단일 수정

  • 📡 GCP 업로드 경로가 바뀌어도 지역 Kafka 1곳만 수정
  • 🚫 하위 서버 수십~수백 대 Config 수정 불필요
  • ⚡ 변경 반영 시간·공수 대폭 절감
말단 서버를 건드리지 않고 단일 포인트에서 경로 제어
🌐

도메인 기반 유연한 전환

  • 🔗 각 지역 Kafka는 개별 도메인으로 식별됨
  • 🔄 지역 Kafka 철수 시 해당 도메인만 GCP Kafka로 변경
  • 🛡️ 하위 서버는 아무것도 수정할 필요 없음
Kafka 유무와 관계없이 하위 구성은 그대로 유지
💥 회선 장애 시나리오 비교
지역 Kafka 유무에 따라 회선 장애 시 알림 구조와 수신처 변경 방식이 달라집니다.
⚖️ 있을 때 vs 없을 때
지역 Kafka 유무에 따른 실질적인 차이입니다.
❌ 지역 Kafka 없이 GCP 직접 연결
  • 회선 장애 시 해당 지역 서버 수십~수백 개에서 각각 알람 발생
  • 장애 원인이 회선인지 서버인지 즉시 구분 불가
  • GCP 수신처 변경 시 모든 서버 Config를 일일이 수정해야 함
  • 회선 단절 시 데이터 유실 위험 (버퍼 없음)
  • ping/Port 체크 결과가 분산되어 집약 관제 어려움
✅ 지역 Kafka 배치 시
  • 회선 장애 시 Kafka 1개 알람만 발생, 즉시 장애 포인트 파악
  • 지역 내 모든 서버 데이터의 단일 집약·프록시 포인트
  • 수신처 변경은 Kafka 1대의 Config만 수정으로 완료
  • 메시지 큐 버퍼로 회선 단절 시에도 데이터 보존
  • 도메인 기반 구성으로 나중에 GCP Kafka로 전환도 용이
📍 지역별 구성 현황
VM 유무에 따라 데이터 전송 경로가 다르게 구성됩니다.
지역 VM 유무 데이터 경로 비고
제강 군산 ✅ VM 있음 서버 → 지역 Kafka → 상암 IDC → GCP 지역 Kafka 직접 운영
제강 포항 ✅ VM 있음 서버 → 지역 Kafka → 상암 IDC → GCP 지역 Kafka 직접 운영
제강 순천 ❌ VM 없음 서버 → 상암 IDC Kafka → GCP 상암 IDC Kafka 경유
제강 창원 ❌ VM 없음 서버 → 상암 IDC Kafka → GCP 상암 IDC Kafka 경유
상암 IDC ✅ 상암 IDC 상암 IDC → GCP 중앙 집약 포인트
※ 가용성 확보를 위해 홀수(3~5개) 구성이 권장되나, 현재는 지역별 1대로 운영 중. 향후 증설 검토.

🎯 결론 요약

  • 지역 Kafka는 알람 집약·데이터 버퍼·경로 유연성의 세 가지 역할을 동시에 수행한다.
  • 이미 구성이 완료됐고, 대체할 명확한 대체 솔루션에 대한 검토가 없었으므로 현행 유지가 합리적이다.
  • VM 없는 지역(순천·창원)은 상암 IDC를 경유하는 방식으로 동일한 효과를 얻는다.
  • Alloy Aggregator는 대안으로 존재하나, 현재 Kafka 효용성이 충분히 높아 병행 검토만 유지한다.
  • 향후 수신처 변경이나 Kafka 철수 시에도 도메인 단위 전환으로 유연하게 대응 가능하다.
