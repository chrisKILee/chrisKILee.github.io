인프라 도구
역할·사용 범위 정의

terraform, ansible, argocd, github actions, backstage, KMM 등 현재 사용 중인 인프라 관리 도구에 대한 역할과 사용 범위를 채팅 토론 및 ADR 문서 기반으로 정리합니다. 추가 조사 없이, 팀 논의 내용의 적절여부를 함께 표기합니다.

Terraform Ansible ArgoCD GitHub Actions Backstage (IDP) KMM GCP / IDC
Section 01

도구별 역할 정의

Terraform
IaC · GCP
GCP 클라우드 인프라 리소스 관리. VPC, GKE 클러스터, IAM, 스토리지 버킷 등 GCP API로 제어 가능한 논리적 리소스를 선언적으로 관리한다.
  • IDC의 물리적 서버, 디스크, 네트워크 장비는 관리 대상 아님
  • 클라우드 리소스의 생성/변경/삭제 이력 관리
종원 확인

"Terraform의 IDC에서의 역할 - 없음! terraform 관리 대상은 IDC에 있는 물리적인 서버, 디스크 등이 아니다."

✓ 적절
Ansible
Config Mgmt
OS / 미들웨어 단 configuration 관리 도구. 현재 환경은 k8s로 대부분 관리되어 있어 Ansible이 제어할 대상 자체가 없음.
  • GCP 환경에서의 역할 없음 (k8s declarative config로 대체)
  • IDC 베어메탈 서버 OS 설정 등에서만 의미 있음
종원 확인

"Ansible은 OS/미들웨어 단 configuration 도구이므로, 현재 k8s로 대부분 관리된 환경에서는 관리할 대상조차 없음."

✓ 적절
ArgoCD
CD · GitOps
Continuous Deployment — GitOps 방식의 k8s 배포. Git 리포지터리의 상태를 클러스터에 지속적으로 동기화한다. IDP(Backstage)에서 CD 관련 개발자 경험 향상이 필요한 경우 IDP에서 추가 기능을 개발한다.
✓ 적절
GitHub Actions
CI · Automation
Continuous Integration — 빌드, 테스트, 패키징 자동화. CI의 대부분을 담당. 필요 시 Jenkins 등으로 교체 가능성을 열어둠. IDP에서는 개발자 경험 향상에 필요한 부분에 한해 추가 기능 개발.
✓ 적절
Helm
k8s Packaging
Kubernetes 애플리케이션 패키지 관리. k8s 매니페스트의 템플릿화 및 버전 관리. ArgoCD와 함께 사용.
✓ 적절
Section 02

IDP (Backstage) 설계 기준

Backstage 요청 UI + 카탈로그
셀프서비스를 요청하는 UI 포탈. 소유권과 발견가능성을 시각화하는 카탈로그 역할.
  • 개발 진입점 (프로젝트 생성, 서비스 등록)
  • CI/CD, Observability 등 다른 생태계의 포탈 역할
  • 생태계 Plugin 우선 활용, 필요 시 확장 개발
KMM 실행 컨트롤러
셀프서비스를 실행하는 컨트롤러. 매니페스트 변환 + Git 커밋이라는 실제 인프라 조작 담당.
  • DevOps Engineer의 반복 작업 자동화
  • Backstage와 상호보완적 관계
  • 최소 기능 원칙 유지
  • 1
    Backstage 생태계 충실 활용 ✓ 적절
    IDP는 Backstage를 기준으로 충실하게 운영한다. 생태계의 활성화 정도에 따라 유용한 Plugin을 우선 사용하고, 개발자 경험 향상에 필요한 경우에만 직접 확장 개발한다.
  • 2
    IDP = 다른 생태계의 Portal ✓ 적절
    각 영역의 주도구는 외부 생태계에서 담당하고, IDP는 Portal로서 통합된 접근점 역할을 한다.
    CI → GitHub Actions / Jenkins 주관 + IDP 경험 향상
    CD → ArgoCD 주관 + IDP 경험 향상
    Observability → Grafana 주관 + IDP 경험 향상
  • 3
    Backstage Plugin vs KMM 선택 기준 논의 필요
    특정 인프라 조작을 KMM이 전담할지, Backstage Plugin으로 처리할지에 대한 기준이 아직 명확하지 않다는 의견이 있었다. 현재 사용 사례 기반의 팀 피드백이 추가로 필요한 영역.
    종원 의견

    "서비스를 위한 manifest 등 인프라 단 제어를 KMM이 전담하기보다, 어떤 특정 상황에서는 backstage plugin으로도 제어가 가능하니 해당 기능이 더 나을 수도 있지 않나?"

Section 03

KMM 설계 원칙 (다윈 가이드라인)

  • 1
    최소 기능 원칙 ✓ 적절
    DevOps Engineer의 역할을 기준으로, IDP → CI/CD 흐름 속 자동화에 필요한 것만 개발한다. 기준 없이 기능을 확장하지 않는다. 기능 제약이 있을 경우 ADR로 명시하고 진행한다.
  • 2
    장애 허용성 (수동 조치 가능) ✓ 적절 (중요)
    KMM에 장애가 생기거나 배포 중단이 발생하더라도, CI/CD 과정은 수동 개입으로 문제가 없어야 한다. KMM은 단일 장애 지점(SPOF)이 되어서는 안 된다.
    왜 중요한가

    서비스 배포가 내부 플랫폼 도구의 가용성에 의존하면 운영 위험이 높아진다. 수동 fallback이 가능한 설계는 안정적인 플랫폼 운영의 기본 원칙이다.

  • 3
    툴체인 중립성 ✓ 적절
    KMM은 Backstage, GitHub Actions, ArgoCD에 대해 중립적으로 기능해야 한다. 특정 영역이 다른 도구로 교체되더라도 (GitHub Actions → Jenkins, ArgoCD → Flux 등) KMM의 구조적 변경이 최소화되어야 한다.
  • 4
    프로젝트 생성 이후 CI/CD 독립성 ✓ 적절
    프로젝트 생성 이후 개발이 진행되는 단계에서는 IDP와 KMM의 장애가 서비스 배포를 막아서는 안 된다. 또는 수동 조치가 명확하게 가능해야 한다.

Section 05

토론 결론 — 적절여부 요약

  • ✓
    Terraform = GCP 전용, IDC 물리 서버 관리 아님
    적절. IaC 도구는 API 기반 클라우드 리소스를 다루는 것이 본래 역할이다. IDC 물리 장비는 다른 접근법(IPMI, 직접 provisioning 등)이 맞다.
  • ✓
    Ansible = GCP 환경에서 역할 없음
    적절. k8s 환경에서는 Pod/Deployment 단 선언적 관리가 Ansible의 역할을 대체한다. 관리 대상이 없는 도구를 억지로 쓰는 것은 불필요한 복잡성을 더한다.
  • ✓
    IDP = Backstage 기반 Portal 역할
    적절. IDP가 모든 기능을 직접 구현하기보다, 검증된 생태계 도구(ArgoCD, GitHub Actions, Grafana)의 Portal로 통합하는 방향은 유지보수 비용을 줄이고 생태계 발전을 활용하는 현명한 접근이다.
  • ✓
    KMM 장애 시 수동 fallback 보장
    매우 적절 (필수 원칙). 내부 플랫폼 도구가 서비스 배포의 단일 장애 지점이 되면 안 된다. 이 원칙은 KMM 설계의 핵심 안전망이다.
  • ✓
    KMM 툴체인 중립성
    적절. CI/CD 도구는 조직 상황에 따라 교체될 수 있다. KMM이 특정 도구에 강하게 결합되면 교체 비용이 KMM에까지 전파된다. 중립성 유지는 장기적으로 유리하다.
  • △
    Backstage Plugin vs KMM 경계 기준
    논의 필요. "어떤 인프라 조작을 KMM이 하고, 어떤 것은 Backstage Plugin으로 하는가"에 대한 구체적 기준이 아직 정의되지 않았다. ADR에 결정 기준을 명문화하는 것이 필요하다.
    권장 조치

    실제 사용 사례(현재 KMM 사용 패턴) 기반으로 경계를 구체화하고 ADR에 기준을 추가할 것.

  • ✓
    AI 화룡점정 — 1단계 기반 정의 후 진행
    적절 (단계적 접근). 도구 역할과 범위가 불명확한 상태에서 AI 자동화를 얹으면 복잡성이 증폭된다. 1단계(역할 정의) 완료 후 AI 활용 검토하는 순서가 맞다.
종합 판단

팀 토론에서 합의된 방향은 전반적으로 적절하다. 특히 Terraform/Ansible 역할 명확화, KMM 장애 허용성 원칙, 툴체인 중립성은 실용적이고 검증된 설계 기준에 부합한다. 보완이 필요한 부분은 Backstage Plugin vs KMM 선택 기준 명문화이며, 현재 사용 사례 기반의 팀 피드백을 수렴해 ADR에 구체적 기준을 추가하는 것을 권장한다.
