개요

왜 Twelve-Factor인가

소프트웨어를 서비스로 제공(SaaS)하는 앱을 만들 때 반복적으로 마주치는 문제들을 해결하기 위한 방법론입니다. 시간이 지나면서 앱이 성장해도 유지보수 비용이 폭증하지 않도록 설계 단계부터 올바른 구조를 잡는 것이 목표입니다.

"Twelve-Factor App은 선언적 형식으로 설정을 자동화하고, OS에 의존하지 않으며, 클라우드 플랫폼 배포에 적합하고, 개발과 운영의 차이를 최소화하며, 도구나 아키텍처 변경 없이 수평 확장할 수 있는 앱을 만들기 위한 방법론이다."

— 12factor.net
적용 대상
모든 언어·플랫폼
Ruby, Python, Java, Go, Node.js 등 어떤 언어로 작성된 앱에도 적용됩니다. 백엔드 서비스(DB, Queue, Cache)도 무관합니다.
배경
Heroku 팀의 실무 경험
수백만 개의 앱 배포 경험에서 도출된 원칙입니다. 현대 클라우드 네이티브 아키텍처(Kubernetes, 컨테이너)의 기초이기도 합니다.
Factor I

코드베이스

버전 관리되는 하나의 코드베이스, 다양한 배포

앱과 코드베이스는 항상 1대1 관계입니다. 하나의 코드베이스에서 개발, 스테이징, 운영 환경으로 배포됩니다.

  • 01앱 : 코드베이스 = 1 : 1 — 앱이 여러 개라면 저장소도 여러 개여야 합니다.
  • 02여러 앱이 동일 코드를 공유하면 12-Factor 위반. 공유 코드는 라이브러리화하여 종속성 매니저로 관리합니다.
  • 03하나의 코드베이스에서 개발·스테이징·운영 등 여러 환경으로 배포할 수 있습니다.
Factor II

종속성

명시적으로 선언되고 분리된 종속성

시스템에 특정 패키지가 암묵적으로 존재한다고 가정하지 않습니다. 모든 의존 라이브러리를 manifest 파일에 명시하고, 실행 환경과 격리합니다.

Ruby
Bundler
Gemfile로 선언 + bundle exec로 격리 실행
Python
Pip + Virtualenv
requirements.txt로 선언 + virtualenv로 격리
Node.js
npm / yarn
package.json으로 선언 + node_modules로 격리

"Twelve-Factor App은 전체 시스템에 특정 패키지가 암묵적으로 존재하는 것에 절대 의존하지 않는다."

— 12factor.net / II. 종속성
  • 01ImageMagick, curl 같은 시스템 도구도 명시적으로 선언합니다. "설치돼 있겠지"는 금물.
  • 02격리 덕분에 새 개발자가 팀에 합류해도 코드 체크아웃 후 빌드 명령 하나로 실행 환경을 구성할 수 있습니다.
Factor III

설정

환경(environment)에 저장된 설정

"설정"이란 배포마다 달라질 수 있는 모든 것입니다. DB 접속 정보, 외부 서비스 인증 키, 배포별 호스트명 등이 해당합니다. 이것들은 코드가 아닌 환경 변수에 저장해야 합니다.

❌ 위반 예시
코드나 설정 파일에 포함
Rails의 config/database.yaml처럼 버전 관리 시스템에 등록된 파일에 접속 정보를 담는 것. 환경마다 별도 파일이 필요하고, 실수로 저장소에 커밋될 수 있습니다.
✅ 올바른 방법
환경 변수(ENV) 사용
OS와 언어에 무관한 표준 방식. 코드 변경 없이 배포마다 다른 값 주입 가능. 저장소에 실수로 올라갈 위험 없음.
# ❌ 금지: 코드에 하드코딩
DATABASE_URL = "postgres://user:pass@prod-db.example.com/mydb"

# ✅ 올바른 방법: 환경 변수로 주입
DATABASE_URL = os.environ["DATABASE_URL"]

간단한 검증 방법: "지금 당장 코드베이스를 오픈 소스로 공개해도 어떤 인증 정보도 유출되지 않는가?" 이 질문에 Yes라면 설정이 올바르게 분리된 것입니다.

Factor IV

백엔드 서비스

백엔드 서비스를 연결된 리소스(attached resource)로 취급

앱이 네트워크를 통해 이용하는 모든 서비스(DB, 메시지 큐, 메일, 캐시)는 교체 가능한 리소스로 다뤄야 합니다. 코드 수정 없이 로컬 서비스를 서드파티 서비스로 바꿀 수 있어야 합니다.

유형로컬 예시서드파티 예시교체 방법
데이터 저장소로컬 MySQLAmazon RDS설정(ENV)의 URL만 변경
메시지 큐로컬 RabbitMQAmazon SQS코드 수정 없이 URL 교체
메일로컬 PostfixPostmark, SendGridSMTP 설정만 교체
캐시로컬 MemcachedAmazon ElastiCache접속 URL만 변경
스토리지로컬 파일시스템Amazon S3설정 교체, 코드 무수정

"Twelve-Factor App의 코드는 로컬 서비스와 서드파티 서비스를 구별하지 않는다."

— 12factor.net / IV. 백엔드 서비스
Factor V

빌드, 릴리즈, 실행

철저하게 분리된 빌드와 실행 단계

코드베이스는 3단계를 거쳐 배포로 변환됩니다. 각 단계는 엄격하게 분리되며, 실행 중인 앱에서 코드를 직접 변경하는 것은 불가능해야 합니다.

  • 빌드코드 저장소를 실행 가능한 번들로 전환. 지정 버전의 코드, 의존성 획득, 바이너리·에셋 컴파일을 포함합니다.
  • 릴리즈빌드 결과물과 현재 설정(환경 변수)을 결합합니다. 각 릴리즈는 고유 ID(타임스탬프 또는 증가 번호)를 가지며, 수정 불가능합니다.
  • 실행선택된 릴리즈로 애플리케이션을 기동합니다. 실행 중에는 코드 변경 불가. 변경이 필요하면 새 빌드 → 새 릴리즈.
  • 롤백이전 릴리즈 ID로 언제든지 복원 가능해야 합니다.
Factor VI

프로세스

무상태(stateless) 프로세스로 애플리케이션 실행

앱은 하나 이상의 무상태 프로세스로 실행됩니다. 프로세스 간 상태를 공유하지 않으며, 보존이 필요한 데이터는 반드시 DB·캐시 같은 백엔드 서비스에 저장합니다.

허용
단기 캐싱
단일 요청(트랜잭션) 안에서 메모리·파일시스템을 임시 캐시로 쓰는 것은 허용됩니다. 예: 파일 수신 후 처리.
❌ 금지
Sticky Session
사용자 세션을 프로세스 메모리에 저장하는 방식은 절대 금지. 세션 데이터는 Redis·Memcached 같은 외부 저장소에 보관해야 합니다.

무상태 설계 덕분에 프로세스를 자유롭게 추가·제거할 수 있습니다. 어떤 요청이 어떤 프로세스 인스턴스로 라우팅되어도 동일하게 동작해야 합니다.

Factor VII

포트 바인딩

포트 바인딩을 사용한 서비스 공개

앱은 Apache·Tomcat 같은 외부 웹서버 컨테이너에 의존하지 않습니다. 웹서버 라이브러리를 의존성에 포함하고, 앱 스스로 포트를 바인딩하여 HTTP 요청을 수신합니다.

Python
Tornado / Gunicorn
앱 코드 안에서 HTTP 서버를 직접 기동합니다.
Ruby
Thin / Puma
외부 웹서버 없이 Ruby 프로세스가 직접 포트를 열어 요청을 받습니다.
Java/JVM
Jetty / Undertow
WAR 배포 방식 대신 임베디드 서버로 JAR 안에 HTTP 서버를 내장합니다.

개발 환경에서는 http://localhost:5000으로 접근하고, 운영 환경에서는 라우팅 레이어가 외부 호스트명의 요청을 포트로 전달합니다. HTTP뿐 아니라 Redis 프로토콜, XMPP 등 다양한 프로토콜에도 적용됩니다.

Factor VIII

동시성

프로세스 모델을 사용한 확장

확장은 수직(단일 VM 증설)이 아닌 수평(여러 머신에 프로세스 분산)으로 합니다. 서로 다른 작업 유형을 별도 프로세스 타입에 할당하는 것이 핵심입니다.

프로세스 타입 예시
Web 프로세스
HTTP 요청 처리 담당. 트래픽에 따라 인스턴스 수를 늘립니다.
프로세스 타입 예시
Worker 프로세스
백그라운드 작업, 큐 소비, 이메일 발송 등 시간이 오래 걸리는 작업 담당.
  • 금지프로세스를 데몬화(daemonize)하거나 PID 파일을 직접 작성하는 것. OS의 프로세스 매니저(systemd, Foreman)에 위임합니다.
  • 확장VI. 무상태 프로세스 원칙 덕분에 인스턴스를 몇 개든 추가해도 공유 상태로 인한 충돌이 없습니다.
Factor IX

폐기 가능

빠른 시작과 안정적 종료를 통한 안정성 극대화

프로세스는 언제든지 시작·종료될 수 있어야 합니다. 빠른 시작(Fast Startup)과 우아한 종료(Graceful Shutdown)가 핵심입니다.

빠른 시작
수 초 내 요청 처리 준비
짧은 시작 시간은 릴리즈 작업과 스케일 아웃을 민첩하게 만듭니다. 프로세스 매니저가 쉽게 다른 머신으로 이동할 수 있습니다.
Graceful Shutdown
SIGTERM 신호 처리
웹 프로세스: 포트 수신 중지 → 진행 중인 요청 완료 후 종료. Worker: 현재 작업을 큐에 반환(NACK)하고 종료.
  • 재입력모든 작업은 멱등(idempotent)하거나 트랜잭션으로 래핑되어, 중간에 종료되어도 다시 실행하면 동일한 결과가 나와야 합니다.
  • 설계Crash-only design — 예기치 않은 하드웨어 에러로 갑자기 종료되어도 견고하게 복구되는 구조를 권장합니다.
Factor X

Dev/Prod 환경 일치

개발·스테이징·운영 환경을 최대한 비슷하게 유지

전통적으로 세 가지 격차가 존재했습니다: 시간의 차이(개발 코드가 운영에 반영되기까지 수 주), 담당자의 차이(개발자 ≠ 배포자), 도구의 차이(로컬 SQLite vs 운영 PostgreSQL). 이 모든 격차를 줄이는 것이 목표입니다.

항목전통적 앱Twelve-Factor
배포 간격몇 주 ~ 몇 달몇 시간 ~ 매일
코드 작성/배포 담당다른 사람 (개발자 / 운영자)같은 사람 (DevOps)
개발/운영 환경 도구불일치 (SQLite / PostgreSQL)최대한 동일하게 유지

"로컬에서는 SQLite를, 프로덕션에서는 PostgreSQL을 쓰고 싶은 충동에 저항하라."

— 12factor.net / X. dev/prod 일치

Docker, Vagrant, Homebrew 등 현대적 도구로 로컬 환경에서도 운영과 동일한 종류·버전의 백엔드 서비스를 쉽게 구성할 수 있습니다. 어댑터(ActiveRecord, Django ORM 등) 추상화를 과신하지 마세요 — 미묘한 동작 차이가 예측 불가능한 버그를 만듭니다.

Factor XI

로그

로그를 이벤트 스트림으로 취급

앱은 로그 파일을 직접 관리하지 않습니다. 각 프로세스는 이벤트를 버퍼링 없이 stdout에 출력하고, 나머지는 실행 환경이 처리합니다.

앱의 역할
stdout으로 출력만
로그 파일 경로, 로테이션, 보관 기간을 앱이 신경 쓰지 않습니다. 그냥 표준 출력으로 내보냅니다.
실행 환경의 역할
수집·라우팅·저장
Logplex, Fluentd, Logstash 같은 로그 라우터가 스트림을 수집하여 Splunk, Elasticsearch, S3 등으로 전달합니다.
  • 형태가공되지 않은 텍스트, 하나의 이벤트 = 하나의 라인. 고정된 시작과 끝이 없는 연속 스트림입니다.
  • 활용로그 분석 시스템(Splunk), 범용 데이터 보관소(Hadoop/Hive), 알림 시스템(오류율 임계값 초과 시 알림) 등에 활용합니다.
Factor XII

Admin 프로세스

일회성 관리 작업을 일회성 프로세스로 실행

DB 마이그레이션, 콘솔 접속, 일회성 스크립트 등 관리 작업은 일반 앱 프로세스와 동일한 환경에서 실행되어야 합니다.

마이그레이션
DB 스키마 변경
Rails: rake db:migrate
Django: manage.py migrate
릴리즈 시 자동 실행.
콘솔(REPL)
라이브 DB 조회
운영 환경 모델을 직접 조회하거나 수정. Rails console, Python shell 등을 사용.
일회성 스크립트
데이터 수정/정리
잘못된 레코드 수정 같은 단발성 작업. 저장소에 코드와 함께 관리하여 동기화 문제를 방지합니다.
