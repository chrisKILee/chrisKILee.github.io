01

왜 Route to Terroir인가?

현재 시스템은 세 가지 구조적 문제를 안고 있다. 이 문제들이 Route to Terroir 프로그램의 출발점이다.

레거시 고착
.NET/SIS 기반 시스템이 현대화 없이 유지되고 있다. 기술 부채가 누적되고 새로운 역량 추가가 어렵다.
데이터 사일로
시스템 간 데이터가 단절되어 있어 AI 활용이 불가능하다. 데이터를 통합하거나 의미 있는 인사이트를 도출하기 어렵다.
이중 운영 부담
신규 서비스와 레거시 시스템이 혼재해 운영 복잡도가 증가한다. 두 환경을 동시에 유지하는 비용이 크다.

"하나의 프로그램, 세 가지 경로. 모든 서비스가 Terroir를 거치되, 출발점에 따라 경로가 다르다."

Route to Terroir 핵심 원칙
02

세 가지 경로 개요

서비스의 출발 상태에 따라 세 가지 경로 중 하나를 선택한다. 경로가 달라도 최종 목적지는 Terroir 생태계다.

Nouvelle Cuvée
신규 프로젝트
  • 새로 시작하는 서비스
  • Terroir 5대 역량 Day 1 탑재
  • SDD 기반 SPEC 주도 개발
  • 레거시 없음 — 최단 경로
핵심 결과: Terroir Native 서비스 출시
Vinification
완전 재구축
  • 레거시를 완전히 새로 만드는 과정
  • Harvest → Fermentation → Bottling
  • 레거시와 신규 병행 후 전환
  • 완료 후 레거시 retire
핵심 결과: 레거시 → Terroir 완전 전환
Élevage
시맨틱 강화
  • 레거시를 retire 하기 어려운 경우
  • Semantic Layer를 씌워 AI 역량 확보
  • 레거시 데이터 위에 영속적 인터페이스
  • 추후 Vinification 브리지 가능
핵심 결과: 레거시 위 Semantic + DX/AX 확보
03

Nouvelle Cuvée

새로운 서비스는 처음부터 Terroir 생태계 위에서 시작한다. 레거시 제약 없이 5대 역량을 Day 1부터 탑재한다.

01
Domain SPEC 작성
SDD 기반으로 도메인 SPEC 먼저 작성. Claude Code와 함께 인터페이스 정의.
02
Day 1 인프라 구성
K8s + GCP/IDC 하이브리드. CI/CD GitOps 파이프라인 즉시 구성.
03
Observability 내장
LGTM 스택 + OTel + Kafka를 서비스 시작과 동시에 탑재.
04
IDP 등록 & 출시
Backstage 서비스 등록, API 문서 자동화, 온보딩 가이드 완비.
적용 조건
  • →기존 시스템이 없는 신규 프로젝트
  • →그린필드 개발 환경
  • →Terroir 역량 Full 적용 가능한 리소스
Terroir 활용도
DevDeploy InfraOpsIDP
04

Vinification

레거시를 완전히 재구축한다. 와인의 발효 과정처럼 원재료(레거시)를 새로운 형태로 전환한다.

Crush
레거시 역추출
기존 코드에서 도메인 로직 추출. 비즈니스 규칙을 SPEC으로 문서화.
Harvest
SPEC 전환
추출된 로직을 SDD SPEC으로 재구성. 이중 환경 운영 준비.
Ferment
신규 서비스 개발
Terroir Native로 신규 개발. 레거시와 병행 운영 (Strangler Fig).
Bottle
전환 완료 & Retire
트래픽 완전 전환 후 레거시 retire. 단일 Terroir 환경 완성.
적용 조건
  • →레거시가 존재하고 retire 가능한 서비스
  • →재구축 리소스(인원, 시간)가 확보된 경우
  • →이중 운영 감당 가능한 시기
핵심 패턴
Strangler Fig Pattern — 레거시를 즉시 제거하지 않고 신규가 완성되면 트래픽을 점진적으로 이전
05

Élevage

레거시를 retire하기 어렵거나 유보해야 할 때. 와인의 숙성처럼, 레거시 위에 Semantic Layer를 덧씌워 새로운 가치를 만든다.

01
데이터 매핑
레거시 데이터 구조 분석. Ontology 기반 시맨틱 매핑 설계.
02
Semantic Layer 구축
Data to Semantic Mapper + Adapter 개발. 레거시 DB 위에 직접 연결.
03
Semantic API 제공
Ontology 기반 통합 API. AI Agent 인터페이스로 활용 가능.
04
DX / AX 확보
기존 서비스에 AI 기반 검색·분석·자동화 기능 추가. IDP Catalog 연동.
적용 조건
  • →레거시 retire가 어려운 서비스
  • →재구축 리소스가 부족하거나 시기상조
  • →당장 AI 역량 확보가 필요한 경우
장기 전략
Élevage 완료 후 → Vinification 전환 가능.
Ontology가 이미 완성되어 Crush 단계를 단축.
06

Terroir 역량 활용 매트릭스

5개 Terroir Layer가 각 트랙에서 어느 수준으로 활용되는지 정리한다.

Terroir Layer Nouvelle Cuvée Vinification Élevage
Dev SDD 기반 SPEC → Claude Code 코드 생성. Coder IDE 전면 활용 Full 레거시 역추출 → SPEC 전환 → SDD 재구축. 역공학 + SDD Full Semantic Mapper, Adapter 개발. connector 개발 시 부분 활용 Partial
Deploy Day 1 CI/CD + GitOps. 컨테이너 기반 파이프라인 전체 Full 이중 환경 운영 후 점진적 전환 (Strangler Fig) Full Semantic Layer만 배포. 레거시 배포 기존 유지 Light
Infra GCP/IDC 하이브리드, K8s, VPN 풀 활용 Full 전환기 이중 인프라 → 완료 후 단일화 Full 최소 인프라. Semantic Layer 호스팅만 Light
Ops LGTM 전면 적용. OTel, Kafka Day 1 내장 Full 신규에 LGTM + 레거시 대비 비교 대시보드 Full 데이터 파이프라인 모니터링. 레거시 Ops 기존 유지 Partial
IDP Backstage 서비스 등록, API 문서, 온보딩 Full 마이그레이션 트래커(Cuvée Card), 전환 대시보드 Full Data Catalog, Semantic Registry 중심 Partial

Full 전면 활용    Partial 부분 활용    Light 최소 활용

08

경로 간 관계 — Élevage는 Vinification의 브리지

공유 역량 Data to Semantic은 세 트랙 모두에서 발생하지만 목적과 결과가 다르다.

Nouvelle Cuvée
Data to Semantic 역할

SDD Domain SPEC 작성 시 시맨틱이 자연 내장.
별도 작업 불필요.

Vinification
Data to Semantic 역할

재구축을 위한 수단. 역추출 → SPEC 전환 과정.
완료 후 레거시 데이터 retire.

Élevage
Data to Semantic 역할

그 자체가 목적. 영구적 시맨틱 인터페이스.
레거시 데이터 위에 영속.

Élevage → Vinification 브리지 패턴
재구축 리소스가 부족한 서비스는 Élevage로 시맨틱 가치를 먼저 확보한다.
이후 여건이 되면 Vinification으로 전환 — Élevage에서 만든 Ontology가 Crush 단계를 단축시킨다.
(이미 도메인의 의미 구조가 파악되어 있기 때문)
