🗄️ Database

DB 운영 가이드 — 로컬 개발 → 운영 배포 플로우

Terroir 가이드 문서 (Beta) · R&D실

PostgreSQL + Prisma 기반 DB 운영 가이드. 로컬 개발부터 운영 배포까지.

이 문서는 "DB에 직접 접속해서 SQL을 실행"하는 방식을 다룹니다.

⚠️ Prisma Migrate와 혼용 금지
이 방식은 _prisma_migrations 이력 테이블을 관리하지 않습니다.
동일 DB에서 prisma migrate dev/deploy를 섞어 쓰면 이력 불일치(drift)로 충돌이 발생합니다.
팀 단위로 이 방식을 일관되게 사용합니다.

1. 로컬 개발 플로우

'로컬'의 범위: 이 섹션은 개발자 PC의 로컬 DB를 대상으로 합니다.

1.1 전체 흐름

Step 1: app.prisma 수정
       │
       ▼
Step 2: prisma migrate diff로 SQL 초안 생성
       │
       ▼
Step 3: 초안 검토 + 수정 → manual-migrations/<ts>_<name>/migration.sql 저장
       │       ← 반드시 확인 (예상치 못한 DROP 주의)
       ▼
Step 4: DB 도구(DBeaver 등)로 로컬 DB에 SQL 실행
       │
       ▼
Step 5: prisma generate (TypeScript Client 갱신)
       │
       ▼
기능 개발 + 테스트
       │
       ▼
Step 6: PR 생성 (migration.sql 반드시 포함)

1.2 단계별 설명

Step 1 — app.prisma 수정

// apps/db-postgres/src/api-server-db/prisma/app.prisma
model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?            // ← 추가
  createdAt DateTime @default(now())
}

Step 2 — migration.sql 초안 생성

prisma migrate diff로 현재 로컬 DB 상태와 수정된 app.prisma의 차이를 SQL로 뽑습니다.

cd apps/db-postgres            
pnpm db:migrate-diff > /tmp/init.sql
cat /tmp/init.sql

출력 결과가 다음 단계에 저장할 SQL 초안입니다.

Step 3 — 초안 검토 + migration.sql로 저장

초안을 그대로 쓰지 말고 반드시 눈으로 검토합니다. 특히 예상치 못한 DROP이 있는지 확인합니다.

/tmp/diff.sql 내용을 검토한 뒤, manual-migrations/ 아래에 타임스탬프 + 이름 폴더를 직접 만들고 migration.sql로 저장합니다.

src/api-server-db/prisma/manual-migrations/
└── {타임스탬프}_{변경 내용}/   예) 20260414120000_add_user_name
    └── migration.sql

저장 결과 예시:

apps/db-postgres/src/api-server-db/prisma/manual-migrations/
└── 20260414120000_add_user_name/
    └── migration.sql
            │
            └─ 내용 ──────────────────────────────────
               BEGIN;

               ALTER TABLE "User" ADD COLUMN "name" TEXT;

               COMMIT;
               ──────────────────────────────────────

migration.sql은 반드시 BEGIN; ... COMMIT;으로 감쌉니다.

PostgreSQL DDL은 대부분 트랜잭션 안에서 동작합니다. 트랜잭션으로 감싸면 실패 시 자동 롤백되어 DB가 부분 적용된 중간 상태로 남는 일을 막을 수 있습니다.

⚠️ 트랜잭션 안에서 실행할 수 없는 DDL 예외
다음은 PostgreSQL 규칙상 트랜잭션 바깥에서 실행해야 하므로, BEGIN/COMMIT을 빼고 파일 상단에 주석으로 이유를 명시합니다.

  • CREATE INDEX CONCURRENTLY / REINDEX CONCURRENTLY

  • ALTER TYPE ... ADD VALUE (ENUM 값 추가)

  • VACUUM, CLUSTER

폴더명을 타임스탬프로 시작하는 이유: 여러 migration이 쌓였을 때 운영 DB 적용 순서를 타임스탬프로 판단하기 위함.

한 번 커밋한 migration.sql은 절대 수정하지 않습니다 (이미 배포된 SQL은 불변).

Migration 이름 컨벤션

# 좋음
add_user_name
add_post_table
drop_old_notification_table
make_user_phone_not_null

# 나쁨
migration_1
update
fix

Step 4 — 로컬 DB에 SQL 실행

편한 DB 도구로 로컬 DB에 접속해서 migration.sql을 실행합니다.

  • GUI: DBeaver, DataGrip, pgAdmin, TablePlus 등

  • CLI: psql

Step 5 — prisma generate

DB 스키마와 schema.prisma가 일치하는 상태에서 TypeScript Client를 재생성합니다.

pnpm -F db-postgres db:generate

Client는 schema.prisma를 기반으로 생성됩니다. Step 4에서 DB를 schema.prisma와 동일한 상태로 만들었으므로, 이 시점에 generate하면 DB / Client / 코드가 모두 같은 스키마를 바라봅니다.

Step 6 — PR에 migration.sql 포함

manual-migrations/ 하위 파일은 소스 코드와 함께 커밋합니다.

GitHub Actions CI

       ▼
완료 확인

2.2 운영 DB에 SQL 수동 실행

실행 전: 반드시 배포 대상 브랜치로 체크아웃

로컬의 manual-migrations/ 파일이 실행 재료이므로, 브랜치가 맞지 않으면 잘못된 migration이 적용될 수 있습니다.

# dev 환경
git checkout develop && git pull

# prod 환경
git checkout main && git pull

실행 절차

DB 도구(DBeaver, psql 등 편한 것)로 운영 DB에 접속해서 적용 안 된 migration을 타임스탬프 순서로 하나씩 실행합니다.

  1. manual-migrations/ 폴더에서 운영 DB에 적용할 폴더를 식별

    • 이 방식은 _prisma_migrations 테이블로 이력을 추적하지 않습니다.

    • 팀에서 마지막으로 적용한 migration 폴더명을 별도로 기록해두고, 그 다음 타임스탬프부터 적용합니다.

  2. 각 폴더의 migration.sql을 하나씩 순서대로 실행

  3. 각 SQL 실행 후 성공을 확인한 뒤 다음 SQL로 넘어갑니다

manual-migrations/
├── 20260413120000_add_user_name/       ← 이미 적용됨
│   └── migration.sql
├── 20260414090000_add_post_table/      ← 적용 대상 (1)
│   └── migration.sql
└── 20260414150000_add_post_index/      ← 적용 대상 (2)
    └── migration.sql

한 SQL 파일 단위로 실행 성공을 확인한 뒤 다음 파일로 넘어갑니다.
여러 파일을 한 번에 붙여서 실행하면 실패 지점을 파악하기 어렵습니다.

적용 결과 확인

실제 테이블/컬럼이 의도대로 생성되었는지 DB 도구에서 직접 확인합니다.

2.3 배포 체크리스트

  • migration.sql이 PR에 포함되어 있는가?
  • migration.sql 내용을 눈으로 검토했는가?
  • 배포 대상 브랜치로 체크아웃했는가?
  • 운영 DB에 접속한 세션이 **맞는 환경(host, DB명)**인지 재확인했는가?
  • 각 migration.sql을 순서대로 실행하고 하나씩 성공을 확인했는가?
  • 적용 결과를 DB에서 직접 확인했는가? (테이블/컬럼 실제 생성 여부)
  • 데이터 손실 가능성이 있는 변경이면 DB 백업을 했는가?
  • 데이터 변경·삭제를 포함하는 변경이면 down SQL(롤백용 역방향 SQL)을 사전에 준비했는가?
