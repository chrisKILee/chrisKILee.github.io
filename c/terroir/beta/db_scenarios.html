DB 운영 가이드 — 시나리오별 가이드

Terroir 가이드 문서 (Beta) · R&D실

PostgreSQL + Prisma 기반 DB 운영 가이드. 시나리오별 상세 절차.
이 문서는 "DB에 직접 접속해서 SQL을 실행"하는 방식을 다룹니다.

⚠️ Prisma Migrate와 혼용 금지
이 방식은 _prisma_migrations 이력 테이블을 관리하지 않습니다.
동일 DB에서 prisma migrate dev/deploy를 섞어 쓰면 이력 불일치(drift)로 충돌이 발생합니다.

공통 규칙: migration.sql은 BEGIN; ... COMMIT;으로 감쌉니다. 실패 시 자동 롤백으로 부분 적용을 막기 위함입니다.
단, CREATE/DROP INDEX CONCURRENTLY, ALTER TYPE ... ADD VALUE, VACUUM, CLUSTER는 트랜잭션 바깥에서 실행해야 하므로 BEGIN/COMMIT을 빼고 별도 파일로 관리합니다.

1. 초기설정

1.1 새 프로젝트

IDP로 프로젝트를 생성하면 Prisma 기본 구조가 이미 세팅된 상태로 나옵니다.

apps/
└── db-postgres/                  ← Prisma 전용 라이브러리
    └── src/api-server-db/prisma/
        ├── schema.prisma         ← DB 연결 + Client 설정 (SSoT)
        ├── app.prisma            ← 모델 정의 (여기에 테이블 작성)
        ├── libs.prisma           ← 공통 모델
        └── manual-migrations/   ← 실행한 SQL 파일 (Git 관리)
            └── <timestamp>_<name>/
                └── migration.sql

개발자가 할 일은 모델 정의 → 첫 migration.sql 생성 → 로컬 DB에 실행입니다.

Step 1 — app.prisma에 첫 모델 작성

// app.prisma
model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  createdAt DateTime @default(now())
}

위 코드는 예시입니다. 실제 모델명과 필드는 프로젝트에 따라 다릅니다.

Step 2 — 로컬 인프라 실행

make infra-up   # PostgreSQL 등 인프라 컨테이너 시작

Step 3 — init migration.sql 초안 생성

빈 DB 기준으로 app.prisma 전체를 SQL로 뽑습니다.

cd apps/db-postgres
pnpm db:migrate-diff > /tmp/init.sql
cat /tmp/init.sql

Step 4 — migration.sql 저장 (BEGIN/COMMIT 래핑)

/tmp/init.sql 내용을 검토한 뒤, manual-migrations/ 아래에 타임스탬프 폴더를 직접 만들고 migration.sql로 저장합니다.

src/api-server-db/prisma/manual-migrations/
└── {타임스탬프}_init/   예) 20260414120000_init
    └── migration.sql
-- migration.sql
BEGIN;

-- /tmp/init.sql 내용 검토 후 붙여넣기
CREATE TABLE "User" (
  "id"        SERIAL PRIMARY KEY,
  "email"     TEXT NOT NULL UNIQUE,
  "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP
);

COMMIT;

위 SQL은 예시입니다. 실제 내용은 /tmp/init.sql에서 생성된 SQL을 검토 후 붙여넣습니다.

Step 5 — 로컬 DB에 SQL 실행

DB 도구(DBeaver, psql 등)로 로컬 DB에 접속해서 migration.sql을 실행합니다.

Step 6 — prisma generate

pnpm -F db-postgres db:generate

1.2 이미 설정된 프로젝트 셋업

Step 1 — 저장소 클론 + 브랜치 체크아웃 + 의존성 설치

git clone <repo-url>
cd <repo>

# 셋업할 환경의 브랜치로 체크아웃
git checkout develop   # dev 환경
# git checkout main    # prod 환경

pnpm install

브랜치가 맞지 않으면 app.prisma가 의도한 환경의 스키마와 다를 수 있습니다.

Step 2 — 로컬 인프라 실행

cd projects/<project-name>
make infra-up   # PostgreSQL, Redis, Kafka 시작

Step 3 — 로컬 DB 스키마 생성

현재 스키마의 SSoT이므로, 현재 상태를 한 번에 적용합니다.

cd apps/db-postgres

# .env 의 DB_URL 을 사용해 schema → DB 동기화
pnpm prisma db push --schema=./src/api-server-db/prisma

manual-migrations/의 파일들은 변경 이력/감사 용도입니다. 새 환경 셋업에서는 사용하지 않습니다.

Step 4 — Client 생성 + 전체 앱 실행

pnpm -F db-postgres db:generate
make all-up

Step 5 — 정상 동작 확인

DB 도구(DBeaver 등)로 로컬 DB에 접속해서 테이블이 정상 생성됐는지 확인합니다.

예시 — 컬럼 추가

model User {

}

cd apps/db-postgres

--from-schema-datasource: 현재 DB 상태를 읽어 비교 기준으로 삼습니다.

BEGIN;

ALTER TABLE "User" ADD COLUMN "phone" TEXT;

DB 도구(DBeaver, psql 등)로 로컬 DB에 접속해서 migration.sql을 실행한다.

PR 머지 후 운영 DB에 동일한 migration.sql을 실행합니다.

⚠️ 표시 변경은 DB 적용 전 반드시 down SQL을 사전 작성해 둡니다. (→ 3.2 롤백)

3. 문제 대응

3.1 마이그레이션 실패 복구

migration.sql이 BEGIN; ... COMMIT;으로 감싸져 있으면 실패 시 자동 롤백되므로 복구가 단순합니다.

복구 절차

1. migration.sql 실행
       │ (실패 → 자동 롤백)
       ▼
2. 에러 메시지에서 실패 원인 파악
       │
       ▼
3. DB 상태 확인 (자동 롤백 되었는지 = 변경이 반영 안 됐는지)
       │
       ▼
4. migration.sql 원인 수정
  • 아직 운영에 한 번도 적용 안 된 파일이면 → 파일 직접 수정 가능
  • 이미 다른 환경(예: dev)에 적용된 파일이면 → 새 migration으로 보정
       │
       ▼
5. 수정된 SQL 재실행

Step 1 — migration.sql 실행

DB 도구(DBeaver, psql 등)로 대상 DB에 접속해서 migration.sql을 실행합니다.

Step 2 — 원인 파악

DB 도구의 쿼리 콘솔 로그 또는 psql 출력에서 에러 메시지를 확인합니다.

ERROR:  column "phone" contains null values

Step 3 — DB 상태 확인

트랜잭션 래핑 덕분에 실패하면 DB에는 아무 변경도 없습니다.

Step 4 — migration.sql 수정

  • 아직 운영/공유 환경에 적용 안 된 파일이면 파일을 직접 수정합니다.

  • 이미 다른 환경에 적용된 파일이면 절대 수정하지 말고, 보정용 새 migration을 만듭니다.

-- 예) 백필을 먼저 하는 보정 migration 추가
-- 20260414yyyyyy_backfill_then_not_null/migration.sql
BEGIN;

UPDATE "User" SET "phone" = '' WHERE "phone" IS NULL;
ALTER TABLE "User" ALTER COLUMN "phone" SET NOT NULL;

COMMIT;

Step 5 — 재실행

DB 도구(DBeaver, psql 등)로 수정된 migration.sql을 다시 실행합니다.

⚠️ BEGIN/COMMIT을 뺀 예외 SQL(CONCURRENTLY, ENUM ADD VALUE, VACUUM, CLUSTER)은 자동 롤백이 안 됩니다.
실패 시 어느 지점까지 적용됐는지 DB에서 직접 확인하고, 필요하면 수동 DROP/정리 후 재실행합니다.

3.2 롤백

이미 성공한 마이그레이션을 자동으로 되돌리는 기능(undo)은 없습니다. 역방향 SQL(down.sql)을 실행하는 것이 롤백입니다.

3.1절의 "자동 롤백"은 실행 중 에러 발생 시 트랜잭션이 취소되는 것입니다. 여기서 말하는 "롤백"은 이미 성공 적용된 마이그레이션을 되돌리는 것으로, 별개의 개념입니다.

사전 준비 — down.sql을 migration.sql과 같은 폴더에 미리 작성

변경을 만들 때 migration.sql(up)과 함께 down.sql을 같은 폴더에 미리 준비해 둡니다.
긴급 상황에서 폴더 하나만 찾으면 up/down 둘 다 바로 실행 가능합니다.

manual-migrations/
└── 20260414120000_add_user_phone/
    ├── migration.sql   ← up: 실행된 변경
    └── down.sql        ← 사전 준비된 역방향 SQL
-- down.sql 예시 (phone 컬럼 추가를 되돌림)
BEGIN;

ALTER TABLE "User" DROP COLUMN "phone";

COMMIT;
