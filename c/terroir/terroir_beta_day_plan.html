Executive Summary
Terroir Beta — Development Readiness Validation

Terroir는 기존 SIS(.NET/TFS) 환경을 대체하는 차세대 AI-Native 개발 플랫폼이다. Nx Monorepo · NestJS/React · GitHub Actions + ArgoCD(GitOps) · GKE · Kafka · LGTM · Backstage IDP를 축으로 5월 Beta Release를 앞두고 있으며, 6월 Chapter 3에서 Vinification/Élevage 실전 프로젝트가 본격 진입한다.

본 Beta Day는 Chapter 3 진입 전에 "플랫폼 자체가 개발 환경으로 완결되어 있는가"를 플랫폼 개발자들 본인이 1일 동안 집중적으로 실증하는 이벤트다. Production 서비스 검증이 아니라 Development Readiness 확정이 목표다.

R&D실 플랫폼 개발자들이 본인이 만든 플랫폼을 직접 써서 개발·배포·관측까지 완주한다. 모든 주제는 SDD 사이클을 따른다 — ① SPEC 작성 ② Cursor/Claude Code로 구현 ③ 테스트 ④ 배포 ⑤ LGTM 확인.

Chaos 계열 (장애·경계 조건) — 플랫폼의 회복성 검증
ID주제의도적 시나리오완료 정의 (DoD)
C1 의도적 배포 실패 & 롤백 의도적으로 빌드는 되지만 런타임에 크래시 나는 이미지를 배포. ArgoCD 자동 회귀 또는 수동 Revert가 5분 내에 가능한지. Pod Running 복원 · Revert Commit · LGTM에 이상 감지 기록
C2 Secret/Config 오설정 DB 비밀번호 틀림, 잘못된 Kafka 토픽 이름 등 흔한 실수 3종. 오류 메시지가 개발자 친화적인지, LGTM으로 원인 추적 가능한지. 세 오류 모두 로그/트레이스에서 원인 5분 내 식별
C3 멀티 테넌시 격리 두 팀이 같은 네임스페이스 이름을 선점 시도, 동일 DB 스키마 이름 충돌. 충돌 감지 및 명확한 가드레일 작동 · 가드레일 없으면 이슈로
C4 LGTM 없이 디버깅 불가 증명 의도적으로 난이도 있는 버그(비동기 경합, 간헐적 Kafka 소비 누락)를 심음. LGTM만으로 15분 내에 원인 식별 가능한지. Trace 또는 Log 기반 원인 식별 스크린샷 제출
Chaos 주제의 역할

Chaos 주제는 "플랫폼이 좋은 날 돌아간다"가 아니라 "나쁜 날 개발자를 구해주는가"를 검증한다. C1~C4는 모두 실제로 Chapter 3 Vinification/Élevage에서 재현될 가능성이 높은 시나리오다. 팀 자체 진행뿐 아니라 16:30 Bug Bash 시간에 타 팀 산출물에 대해 교차 실행하는 공격 시나리오로도 재활용.

SDD 검증의 결정적 질문
  • Q1. SPEC 작성 시간이 전체의 몇 %였는가? (너무 적으면 SDD가 아니라 AI 자유 코딩)
  • Q2. SPEC을 얼마나 자주 고쳤는가? (0회면 검증 부족, 10회 이상이면 SPEC 훈련 부족)
  • Q3. Cursor와 Claude Code를 어떻게 나눠 썼는가? (역할 분담 실패 패턴 파악)
  • Q4. 팀이 가장 많이 반복한 프롬프트 3개는? (향후 재사용 템플릿 자산)
  • Q5. 기존 방식(AI 없이) 대비 추정 시간 단축률은? (참가자 주관 평가, 허위 숨김 주의)

Dogfooding의 함정 회피 규칙
  • ① 자기 영역 자기 검증 금지 — Backstage 담당자는 Backstage를 직접 검증하는 팀에 배정하지 않는다.
  • ② "이건 원래 이래" 금지 — 평소 우회한 패턴도 이번엔 이슈로 올린다. 우회가 정당화되면 Service Dev는 쓸 수 없다.
  • ③ Contestant가 자기 컴포넌트 Fix 시 — PR은 반드시 On-Call 리뷰를 통과해야 하며, 구현 시간은 Contestant 시간에 포함 (공정성 유지).
  • ④ 성취감 > 완결 — 완주 압박으로 DoD를 낮추지 않는다. DoD 미달 시 솔직 공개가 시상 가산점.

Live Fix 루프
1
제보: Jira BETA-DAY + Google Chat #terroir-bugs 동시 포스트 (봇 자동 연동)
2

3
Claim: On-Call이 Claim → 상태 Fixing (해당 컴포넌트 Owner가 Contestant여도 On-Call이 우선 처리)
4
Fix: 동시 P0/P1 병렬 최대 2건 — 과부하 방지
5
Hotfix 배포: PR → 2명 리뷰 → CI → Beta 테넌트 반영 (목표 30분)
6
Verify: 원 제보자가 재현 불가 확인 → Done
7
공지: Done 전환 시 Google Chat #terroir-beta 자동 공지

10 Commandments · 컴포넌트별 검증 중점 · SDD 기록 양식
Terroir Beta Day — 10 Commandments
  1. 1.본인이 만든 플랫폼을 본인이 쓴다. 친절하지 말고 솔직하라.
  2. 2.SPEC은 AI가 아니라 사람이 먼저 쓴다. 이건 타협 없다.
  3. 3."원래 그래요"는 금기어. 원래 그런 것이 Service Dev에게 통할 리 없다.
  4. 4.자기 영역 자기 검증 금지. 자기 컴포넌트 이슈는 타 팀이 낸 것을 우선 신뢰.
  5. 5.Hotfix는 Feature Flag 뒤에. 18:15 이후 Freeze.
  6. 6.P0 1건이라도 남으면 No-Go. Chapter 3는 No-Go 위에 세울 수 없다.
  7. 7.실데이터 반입 금지. 위반 즉시 Disqualify + CISO 보고.
  8. 8.On-Call은 로테이션. 번아웃은 더 큰 장애를 낳는다.
  9. 9.Dogfooding은 경쟁이 아니라 증언이다. Honest Dogfooder가 Best Team과 동급.
