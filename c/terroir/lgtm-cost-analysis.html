요구사항 정의 — 본 리포트의 기준점

본 리포트가 제시하는 아키텍처 트랙은 다음 필수 요구사항과 기준 시나리오를 전제로 평가된다. 모든 수치와 비교는 이 기준 위에서만 유효하다.

필수 요구사항 — 운영 환경이 반드시 충족해야 할 조건

섹션 1

배경: 왜 본 리포트가 필요한가

vntg R&D실은 각 그룹사의 데이터센터(IDC)와 공장에 있는 서버·데이터베이스를 중앙에서 통합 모니터링할 수 있도록 테루아 플랫폼을 구축해 운영하고 있다. 그룹사의 서버에서 발생하는 메트릭(수치 측정값), 로그(텍스트 기록), 트레이스(요청 추적 기록)를 수집 에이전트(Alloy)가 모아 중앙 테루아 플랫폼의 저장소로 보내고, 대시보드 도구 Grafana에서 각 그룹사 담당자가 모니터링 결과를 조회하는 구조이다.

현재 22개 그룹사의 서버 108대가 테루아 플랫폼에 연결되어 모니터링을 받고 있다. 앞으로 상암 IDC 전체 확대와 지역 공장 7개 거점(세아제강 포항·군산·순천·창원, 세아베스틸 군산·창녕, 세아창원특수강 창원) 온보딩이 진행되면서 모니터링 대상 서버 수가 크게 늘어날 예정이다.

그룹사가 테루아 플랫폼의 통합 모니터링을 공동 사용하기 때문에, 월 운영 비용을 각 그룹사에 어떤 기준으로 얼마씩 청구할지에 대한 근거 수치가 필요하다. 현재는 "그룹사별·서버 1대당 모니터링 비용이 얼마인지"에 대한 수치 환산이 존재하지 않아 비용 분담 논의를 진행할 근거가 없는 상황이다.

비교 대상 아키텍처 3가지

통합 모니터링 파이프라인의 비용을 3가지 아키텍처 트랙으로 나누어 추산한다. 각 트랙은 규모·안정성·보관 기간이 다르며 비용도 달라진다.

트랙 A — 참고용 (운영 부적합)
현재 구조 · 복제본 1개 · MinIO 내장
Mimir / Loki / Tempo 각 역할 복제본 1개. 저장 백엔드 MinIO 내장 PVC. 보관 7일/7일/24시간.

합계 요청: 6.15 vCPU · 19.33 GiB · 135 GiB PVC.

필수 요구사항 미충족 — 보관·HA·확장성·캐시 모두 부족. 현재 개발 모드 비용 하한선.
트랙 B-Mimir 요구사항 충족
고가용성 + Mimir 유지 + Google Cloud Storage
핵심 역할 복제본 3개. 메트릭 원본 GCS Standard 30일 + Recording Rule 집계본 365일. Mimir가 저장 등급 전환을 지원하지 않아 수명 주기 정책은 메트릭에 미적용. 로그는 수명 주기 적용.

합계 요청: 15.85 vCPU · 65.25 GiB · 50 GiB PVC + GCS.
트랙 B-Prometheus 요구사항 충족
고가용성 + Prometheus + Thanos 전환
Mimir 대신 Prometheus + Thanos 사용. Thanos 다운샘플링으로 원본 14일 + 5분 90일 + 1시간 365일 보관.

Mimir가 다운샘플링을 지원하지 않는 것이 이 경로를 별도 옵션으로 포함시킨 핵심 이유.

합계 요청: 10.6 vCPU · 98 GiB · 570 GiB PVC + GCS.

핵심 인사이트 6가지

인사이트 1
GKE Autopilot에서 Standard로 전환하면 컴퓨트 비용이 약 12~15% 절감된다
Autopilot vCPU $0.0571/시간, Standard N2 vCPU $0.0406/시간. Standard가 기본 40% 저렴하지만 시스템 오버헤드 15% 가산 시 실질 차이 12~15%. 메모리 단가 차이는 1%에 불과하므로 Prometheus처럼 메모리 중심 워크로드는 Standard 전환 이득이 작다.
인사이트 2
트랙 A → 트랙 B 전환 시 비용 증가의 대부분은 고가용성 확보 컴퓨트
복제본 1개 → 3개 + 캐시 활성화로 컴퓨트 리소스 약 2.5배 증가. GCS 저장 비용은 호스트 1대당 월 약 $0.17로 매우 작다. GCS 전환 자체는 비용을 거의 안 올린다.
인사이트 3
트랙 B-Mimir와 트랙 B-Prometheus 비용 차이는 미미하나 장기 메트릭 품질은 크게 다르다
B-Mimir × ST × Managed $8.48 / B-Prometheus × ST × Managed $8.82. 서버 1대당 차이 $0.34 수준. Mimir는 다운샘플링 미지원으로 raw 30일 + 집계본 365일만. Prometheus+Thanos는 raw 14일 + 5분 90일 + 1시간 365일 자동 보관으로 품질 우수.
인사이트 4
Managed Kafka는 Self-Managed 대비 약 3.3배 비싸나 운영 부담 0
Self-Managed 3 broker $77 vs Managed 3 DCU $271. 차이 $194/월. Managed Kafka는 Internal LB 비용 $72/월도 절약. 적극 시나리오에서 비용 차이 $527는 운영 인력 0.1명 미만 수준.
인사이트 5
Windows 호스트 집중 그룹사가 시계열 82%를 생성. 단순 서버 수 기반 청구는 불공정
Windows 1대 평균 5,000 시계열, Linux 1대 1,500. 약 3.3배 차이. 중앙값 1,492, 최대 13,426. 단순 서버 수 과금은 Windows 비중 낮은 그룹사에 불리. 장기적으로 데이터량 기반 또는 혼합 과금 공정.
인사이트 6
호스트 수가 늘어날수록 서버 1대당 비용은 감소 (경제 규모 효과)
고정 비용(VPN + Internal LB + Kafka 기본 + Grafana egress + GKE 분담 = $211)은 호스트 수와 무관. 트랙 B-Prom × ST × Managed 기준 현재(108) $12.13 → 적극(2,000) $8.82. 약 $3.3 감소. 그룹사·호스트 확장에 따른 단가 경쟁력 증가.
섹션 7

업계 레퍼런스 비교 — 상용 SaaS vs vntg 자체 운영

유사 워크로드(서버 1대 + 메트릭 + 로그 + 트레이스 + 대시보드)에 대한 주요 상용 SaaS 요금과 vntg 자체 운영 원가를 비교한다. vntg 자체 운영 원가는 상용 SaaS 대비 약 13% 수준으로, 자체 인프라 구축이 비용 측면에서 압도적 우위를 가진다.

솔루션서버 1대당 월 비용계산 기준
Datadog Infrastructure + Logs + APM약 $70Infrastructure $31 + Logs $0.10/GB × 1.3 GB/일 × 30일 + APM $36
New Relic One Full Platform약 $40~60Full Platform User + 100 GB ingest
Grafana Cloud Pro약 $655k active series × $10/1k + 로그 1.3 GB/일 × $0.50/GB
vntg 자체 운영 원가 (트랙 B-Prom × ST × Managed Kafka, 적극)$8.82본 리포트 산출. 상용 SaaS 대비 약 13% 수준

자체 운영이 저렴한 구조적 이유: 상용 SaaS 요금에는 벤더 개발·영업·지원 인력 비용과 마진이 포함되지만, 자체 운영은 GCP 인프라 원가만 지불한다. 단 자체 운영은 개발·운영 인력 비용이 별도로 발생하므로 "총 소유 비용(TCO)" 관점에서는 호스트 수가 일정 이상(약 500대 이상)일 때 상용 SaaS 대비 유리하다. vntg는 기대 시나리오(750 호스트) 도달 시점부터 자체 운영의 TCO 우위가 명확해진다.

섹션 8

그룹사 청구 단가 설계 — 원가 + 마진

예상 비용 면책 조항
  • 본 리포트의 모든 비용 수치는 설계 단계 예상 원가이며, 실제 운영 시 측정되는 비용과 차이가 있을 수 있다.
  • 실제 GCP 청구는 스크랩 빈도·쿼리 패턴·트래픽 급증 등 운영 중 실측 데이터에 따라 달라진다.
  • 그룹사 계약 시 "3개월 또는 6개월 실측 기반 단가 재조정" 조항 포함 권장.
  • 본 리포트 원가 모델은 이후 실측 데이터와 주기적으로 대조해 보정해야 한다.

원가에 마진을 추가해야 하는 이유

본 리포트의 원가(예: 적극 시나리오 $8.82/호스트·월)는 순수 GCP 인프라 비용만 반영한다. 그룹사 청구 단가는 다음 요소를 원가 위에 마진으로 얹어야 지속 가능한 운영이 가능하다.

마진 구성 요소원가 대비 비중근거
운영 인력 간접비약 10~20%SRE · 플랫폼 엔지니어 인건비 분담 (월 $8,000 × 0.5 FTE)

혼합 모델 (기본 + 사용량)

주요 가정과 실측 근거

  • 실측Mimir 메트릭 일 저장량 8.4 GiB/일은 카운터 역산(8.6 GB)과 MinIO PVC 실사용량(59 GiB / 7일) 교차 검증. 편차 2% 이내.
  • 실측Loki 로그 일 저장량 3.7 GiB/일은 MinIO PVC 실사용량(26 GiB / 7일) 기준. Loki 압축 설정 chunk_encoding: gzip 약 13배 압축.
  • 실측Tempo 트레이스 일 저장량 1.2 GiB/일은 PVC 실사용량 기준. 외부 IDC는 현재 트레이스 미수집.
  • 실측Classic VPN Gateway + Tunnel $74/월: vntg-nfw-network-hub 프로젝트 hub-idc-vpn 조회.
  • 실측Internal LB 3개 × $24/월 = $72/월: Kafka 브로커별 forwarding-rule 실사.
  • 실측Managed Kafka DCU $83.77/월: Cloud Billing Catalog SKU 0027-FE69-7D73.
  • 실측GKE 공통비 분담 73%: dev-infra 클러스터 네임스페이스별 vCPU 요청 실측 (monitoring+kafka+grafana = 10.69 vCPU / 워크로드 총 14.64 vCPU).
  • 가정Windows 서버 1대당 평균 시계열 5,000은 실측 분포 평균. 실제 편차 1,000~13,000.
  • 가정GKE Standard 시스템 오버헤드 15% 가산은 일반적 추정치.
  • 가정모든 비용 항목이 호스트 수에 선형 비례. 대규모에서는 비선형 요소 존재.
  • 가정Kafka broker 1개당 처리량 약 3.5 MB/s는 Snappy 압축 기준 업계 평균.
  • 가정Grafana 외부 egress 월 100 GiB는 대시보드 사용 패턴 추정값.
  • 가정마진 30%는 내부 공유 서비스 표준 비율. 실제 운영 3~6개월 후 실측 기반 재조정 필요.

Kafka 운영 옵션 비교 — Self-Managed vs Managed

본 파이프라인에서 Kafka는 IDC 수집 데이터의 중앙 버퍼 역할을 담당한다. 현재는 자체 구축 운영 중이며, 향후 운영 환경은 Managed Kafka 전환 예정.

옵션 1 (현재 운영)
GCP K8s Self-Managed Kafka
구성: GKE StatefulSet 3 broker + Internal TCP LB 3개.

장점: 비용 최저, 세부 설정 통제.

단점: R&D실이 패치·백업·장애 대응 직접 담당.

현재 구성: 3 broker × (0.5 vCPU + 1 GiB + 30 GiB PD).
옵션 2 (운영 전환 예정)
GCP Managed Service for Apache Kafka
구성: Google broker 관리, bootstrap endpoint 자동 제공.

장점: 운영 부담 0.

단점: Self-Managed 대비 약 3.3배.
