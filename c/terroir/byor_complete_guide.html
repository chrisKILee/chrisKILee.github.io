🍾 BYOR란?

BYOR (Bring Your Own Repo)는 VntgCorp org 내 기존 레포지토리를 KMM IDP에 연결하는 온보딩 패턴입니다. 레포를 이전하거나 새로 만들 필요 없이, 기존 레포 그대로 Terroir 배포 파이프라인에 연결됩니다.

온보딩 패턴 3가지

Pattern 1
Greenfield

Terroir 템플릿에서 처음부터 신규 개발

Pattern 2
Migration

기존 코드를 Terroir 템플릿에 이관·덮어쓰기

Pattern 3
BYOR [바이오아]

VntgCorp org 기존 레포를 IDP에 연결 (레포 이동 없음)

🤖 Claude Code 개발 워크플로우

Terroir init 후 Claude Code를 활용한 SDD(Spec-Driven Development) 파이프라인으로 개발합니다. 대규모 기능은 스펙 → 태스크 → 실행 순서로 컨텍스트를 분리해 진행합니다.

⚠️
작은 프로젝트 vs 대형 프로젝트
소규모 기능은 SDD 전체 파이프라인이 과할 수 있습니다. 대형 프로젝트는 스펙 주도 플로우가 품질 관리에 효과적입니다.

SDD 파이프라인 전체 흐름

1
PRD 작성 — /sdd-prd
심층 인터뷰를 통해 요구사항 정리 → docs/features/{feature}/prd.md 생성. PRD 리뷰어가 자동 검증 (Critical / Major 이슈 리포트).
2
Spec 확정 — /sdd-spec
PRD를 기반으로 API 스펙·DB 스키마·UI 스펙 작성. spec.md 생성 후 Self-Correction 품질 검증 자동 실행.
3
문서 검증 Gate — /sdd-doc-review
prd.md + spec.md 검증. G3 게이트 통과 시 다음 단계 진행. Critical 0건이어야 통과.
4
Task 분해 — /sdd-task
spec.md를 분석해 구현 가능한 단위로 Task 파일 생성. Task 1개 = 독립적으로 실행 가능한 최소 작업 단위.
docs/features/roulette/tasks/ ├── 001-project-init.md ├── 002-db-schema-seed.md ... └── 012-gcp-deployment.md
5
Task 실행 — /sdd-execute
Task 1개 = /clear 후 새 세션에서 실행. 개발(backend-developer-agent) + QA(qa-agent) + 코드리뷰(code-reviewer) 병렬 에이전트 실행.
6
커밋 & PR — /sdd-commit-pr
Task 완료 후 자동 커밋·PR 생성. reports/ 폴더에 리포트 작성.
💡
TDD 원칙 (Kent Beck)
"테스트가 없으면 구현하지 않는다." — 반드시 Red → Green → Refactor 순서로. 구현 코드 먼저 작성 금지.

📋 terroir.json 설정

프로젝트 루트에 위치하는 배포 설정 파일. CI가 이 파일을 읽어 빌드 대상과 배포 환경을 결정합니다.

🚨
version 변경 필수!
코드를 변경해도 version을 올리지 않으면 CI가 빌드를 스킵합니다. 모든 배포 시 반드시 version bump 후 커밋하세요.

chris-fun 실제 예시

terroir.json
{ "schema": "1", "environments": { "DEV": "main" }, "apps": [ { "name": "chris-fun", "root": ".", "group": "chris-fun", "version": "0.1.8", "type": "FE" }, { "name": "chris-fun-db", "group": "chris-fun", "type": "DB", "engine": "postgres" } ] }

필드 설명

필드 필수 설명 예시
schema 필수 스키마 버전 — 현재 "1" 고정 "1"
environments 필수 환경명 → 브랜치 매핑. 키는 대문자 환경명 {"DEV": "main"}
apps[].name 필수 앱 이름. 소문자 + 하이픈만 허용 "chris-fun"
apps[].type 필수 BE / FE / DB "FE"
apps[].group 필수 프로젝트 그룹명. AR 레포({group}-{env}-images) 및 KMM 프로젝트명으로 사용 "chris-fun"
apps[].root BE/FE 필수 Dockerfile 위치. DB는 커스텀 빌드 시에만 필요 "."
apps[].version BE/FE 필수 앱 버전. 변경 시에만 CI 트리거 "0.1.8"
apps[].engine DB 필수 DB 엔진 종류. 현재 postgres만 지원 "postgres"

DB 시나리오 3가지

시나리오설명terroir.json
KMM 기본 DB ✅ KMM이 제공하는 기본 이미지(postgres:16-alpine)로 배포. root 없음 → Docker 빌드 스킵 name, type, engine, group
커스텀 DB 🚧 사용자 Dockerfile로 DB 이미지 빌드 (현재 미지원) + root, version
외부 DB 🚧 CloudSQL 등 외부 관리형 DB (현재 미지원). terroir.json에 DB 선언 안 함 DB 선언 없음 → IDP에서 직접 입력

🐳 Dockerfile (Next.js 기준)

Next.js의 output: 'standalone' 모드를 활용한 멀티스테이지 빌드입니다. FE 앱은 COPY .env* 로 빌드 타임 환경변수를 수용합니다.

Dockerfile
FROM node:20-alpine AS base # deps 단계 FROM base AS deps WORKDIR /app COPY package.json package-lock.json ./ RUN npm ci # builder 단계 FROM base AS builder WORKDIR /app COPY --from=deps /app/node_modules ./node_modules COPY . . COPY .env* ./ # FE 빌드 타임 환경변수 RUN npx prisma generate RUN npm run build # runner 단계 (프로덕션) FROM base AS runner WORKDIR /app ENV NODE_ENV=production COPY --from=builder /app/.next/standalone ./ COPY --from=builder /app/.next/static ./.next/static COPY --from=builder /app/public ./public EXPOSE 3000 CMD ["node", "server.js"]

next.config.ts 필수 설정

// next.config.ts const config: NextConfig = { output: 'standalone', // 필수 — standalone 빌드 활성화 } export default config

🗄️ KMM IDP — DB 앱 환경변수

KMM IDP에서 DB 앱(chris-fun-db)에 입력하는 환경변수입니다. 이 값들은 PostgreSQL 컨테이너 설정에 사용됩니다.

⚠️
시크릿 vs 일반 환경변수
DB명·유저명은 평문(ConfigMap)으로, 비밀번호는 반드시 Secret으로 등록하세요.
환경변수타입설명예시
DATABASE_DB 일반값 데이터베이스 이름 postgres
DATABASE_USER 일반값 DB 유저명 postgres
DATABASE_PASSWORD Secret DB 비밀번호 — (Secret 등록)

🔧 KMM IDP — FE 앱 환경변수

FE 앱(chris-fun)에 DB 접속 정보를 주입합니다. DB 앱에 입력한 정보와 동일한 값을 사용합니다.

💡
왜 FE에도 DB 정보가 필요한가?
Next.js App Router는 서버 컴포넌트에서 DB에 직접 접근합니다. Prisma는 FE 앱(Next.js 서버) 안에서 실행되므로 DB 접속 정보가 필요합니다.
환경변수타입설명
DATABASE_HOST 일반값 KMM이 생성하는 DB 서비스 호스트명
DATABASE_DB 일반값 DB 앱에 설정한 것과 동일
DATABASE_USER 일반값 DB 앱에 설정한 것과 동일
DATABASE_PASSWORD Secret DB 앱에 설정한 것과 동일
⚠️
환경변수 없을 때 앱 저장 안 됨
DB 환경변수가 없으면 FE 앱이 시작되지 않습니다. 배포 후 즉시 환경변수를 확인하고, 누락 시 IDP에서 입력 후 재배포하세요.

lib/prisma.ts — 환경변수 폴백 패턴

DATABASE_URL 단일 형태 또는 개별 변수 형태 모두 지원하도록 코드 레벨에서 처리합니다.

function createPrismaClient(): PrismaClient { const connectionString = process.env.DATABASE_URL ?? `postgresql://${process.env.DATABASE_USER}:${process.env.DATABASE_PASSWORD}@${process.env.DATABASE_HOST}:5432/${process.env.DATABASE_DB}` if (!connectionString.includes('@')) { throw new Error('DATABASE_URL 또는 HOST/USER/PASSWORD/DB 환경변수 필요') } const adapter = new PrismaPg({ connectionString }) return new PrismaClient({ adapter }) }

🔍 트러블슈팅

① 버전 변경 없이 배포 → 빌드 스킵

terroir.json의 version을 변경해야 CI가 트리거됩니다.

- "version": "0.1.7" + "version": "0.1.8"

② 배포 후 404 — 앱 크래시

모듈 로드 시점에 DB 환경변수 없으면 즉시 크래시. Prisma를 lazy init으로 변경해야 합니다.

// ❌ 모듈 로드 시 즉시 초기화 — 환경변수 없으면 크래시 export const prisma = new PrismaClient() // ✅ Proxy 패턴으로 lazy init — 첫 사용 시점에 초기화 export const prisma = new Proxy({} as PrismaClient, { get(_target, prop) { return (getPrisma() as any)[prop] }, })

③ Next.js 빌드 타임 API 라우트 크래시

Next.js가 빌드 시 API 라우트를 pre-render 시도 → DB 접근으로 크래시 발생.

// DB를 사용하는 모든 API route 파일 최상단에 추가 export const dynamic = 'force-dynamic'

④ fe-build.yml 없을 때

FE 앱은 ci.yml(300 workflow)이 아닌 fe-build.yml(301 workflow)로 배포합니다. 누락 시 IDP에서 배포 불가.

⚠️
Confluence 배포 가이드 댓글에서 fe-build.yml 템플릿을 다운로드하여 .github/workflows/에 추가하세요.

⑤ DATABASE_DB / DATABASE_USER 값 문제

KMM IDP에서 DATABASE_DB와 DATABASE_USER를 일반 환경변수(Secret이 아닌 ConfigMap)로 설정하는 것은 정상입니다. DB명과 유저명은 민감한 정보가 아닙니다. 비밀번호(DATABASE_PASSWORD)만 Secret으로 등록하면 됩니다.

⑥ SSH 터널 포트 충돌

로컬 GCP SSH 터널(5433)과 로컬 Docker PostgreSQL 포트 충돌 시 docker-compose에서 포트 변경.

services: db: ports: - "5434:5432" # 5433 → 5434 (SSH 터널 충돌 방지)
