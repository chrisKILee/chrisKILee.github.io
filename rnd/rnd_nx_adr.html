레거시 ADR

docs/adr/ (루트 · 4개)

초기 구조에서 루트에 직접 작성된 ADR. 현재는 global/ 하위로 이전하는 방식으로 통일.

Context — 문제 상황
  • 여러 백엔드 앱이 PostgreSQL, Redis, Kafka 등 공통 인프라를 중복 정의
  • 서비스마다 docker-compose 파일이 달라 유지보수 어려움
  • 개발자마다 선호 워크플로우가 다름 (로컬 실행 vs Docker 실행)
  • 새 앱 추가 시 인프라 설정을 처음부터 다시 작성해야 하는 문제
Decision — 결정 내용

Docker Compose를 Base(공통 인프라)와 App(앱 전용)으로 분리

  • infra/local/docker/docker-compose.base.yml — PostgreSQL, Redis, Kafka
  • projects/{app}/docker/docker-compose.app.yml — 앱별 컨테이너
  • Profile 전략: db, cache, kafka, infra, all
Consequences — 결과
  • ✅ 공통 인프라 한 번만 정의, 모든 앱에서 재사용
  • ✅ 필요한 서비스만 선택적 실행 가능
  • ✅ 새 앱 추가 시 인프라 설정 즉시 재사용
  • ⚠️ Base/App 두 파일 관계 이해 필요

Context — 문제 상황
  • ADR-001 Base/App 분리 이후 시나리오별 선택적 실행 메커니즘 필요
  • DB만 필요한 개발자 / 전체 인프라 필요 개발자 혼재
  • 특정 서비스만 실행하려 해도 명령어가 복잡하고 휴먼 에러 발생
  • 신규 팀원이 서비스 조합을 파악하기 어려움
Decision — 결정 내용

Docker Compose Profile로 논리적 서비스 그룹화

  • db — PostgreSQL만
  • cache — Redis만
  • kafka — Kafka만
  • infra — 전체 인프라 (DB+Cache+Kafka)
  • app — 앱 컨테이너만
  • all — 인프라 + 앱 전체
Consequences — 결과
  • ✅ --profile db 한 줄로 필요한 서비스만 실행
  • ✅ 표준화된 프로파일 이름으로 팀 전체 통일
  • ✅ 로컬 리소스 최적화 (불필요한 컨테이너 미실행)
  • ⚠️ Profile 개념 이해 필요 (신규 멤버 온보딩 비용)

Global ADR

docs/adr/global/ · 11개

전체 모노레포 또는 여러 프로젝트에 공통 적용되는 기술 결정.

Context — 문제 상황
  • 프로젝트마다 개별 .eslintrc.json 파일 존재 → 규칙 중복 정의
  • 공통 규칙 변경 시 n개 파일 모두 수정 필요
  • 신규 프로젝트 추가 시 규칙 누락 가능성
  • 각 project.json에 수동 lint 타겟 정의 → 설정 복잡도 증가
Decision — 결정 내용

모든 ESLint 규칙을 루트 eslint.config.mjs 하나에 집중

  • @nx/eslint/plugin 자동 추론으로 lint 타겟 자동 생성
  • Glob 패턴으로 프로젝트 타입별 규칙 자동 적용
  • 개별 .eslintrc.* 원칙적 금지 (예외 시 팀 리뷰 필수)
  • NX: 실행 시점·캐싱 / ESLint: 규칙 정의 역할 명확 분리
Consequences — 결과
  • ✅ 규칙 1개 변경 = 파일 1개만 수정
  • ✅ 신규 프로젝트 추가 시 규칙 자동 적용
  • ✅ NX 캐싱으로 불필요한 린트 재실행 방지
  • ⚠️ 전체 영향 범위 확대 (규칙 변경 시 모든 프로젝트 영향)

Multi-stage Docker build + Nginx 리버스 프록시

  • ✅ Gzip 압축, 캐싱, 보안 헤더 (Nginx)

Decision — 변환 규칙

변환 규칙: project.json {a}/{b} → package.json @{a}/{b}

  • project.json name → Nx CLI, buildTarget, dependsOn에 사용
  • package.json name → tsconfig paths, import 구문에 사용
적용 예시
폴더: projects/tech-blog/be-api-server
project.json: tech-blog/be-api-server
package.json: @tech-blog/be-api-server

폴더: libs/be/auth
project.json: libs/be-auth
package.json: @libs/be-auth
Consequences — 결과
  • ✅ Nx CLI vs import 경로 명확히 구분
  • ✅ 프로젝트마다 네이밍 패턴 통일
  • ✅ buildTarget 참조 오류 방지
  • ⚠️ 기존 프로젝트 마이그레이션 시 import 경로 일괄 변경 필요

Decision — 3단계 문서 체계
  • PRD — "뭘 만들거야?" (기획자 관점, 비개발자 언어, 사용자 시나리오)
  • SPEC — "어떤 형태로?" (개발 아키텍처 관점, Input/Output, 예외 케이스)
  • PLAN — "어떻게 만들거야?" (개발 리더·아키텍트, 구체적 구현 계획)

기능별 디렉토리 구조 + 인덱스 파일로 일관성 확보

  • 개발 과정에서 생성되는 문서들의 체계적 관리 방안 필요
  • 문서 템플릿 표준화로 팀 전체 일관성 확보
  • PRD·SPEC·PLAN 역할 명확히 분리하여 문서 중복 방지
Consequences — 결과
  • ✅ 기획·설계·구현 단계 문서 역할 명확화

├── schema.prisma  # generator + datasource
├── app.prisma     # 프로젝트 전용 모델
└── libs.prisma    # 공유 라이브러리 모델
