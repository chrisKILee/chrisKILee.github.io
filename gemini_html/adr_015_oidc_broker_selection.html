내부 운영 도구 전용
OIDC 브로커로 dex 채택

Grafana·ArgoCD·신규 내부 관리 콘솔을 하나의 Google Workspace 연동 OIDC 브로커 아래 묶는다. Keycloak·Authentik 등 풀스택 IAM 대신, 경량·stateless·GitOps 친화 설계의 dex를 채택. 엔드유저 인증(축 B)과는 완전 분리된 내부 운영자 전용 결정이다.

배경

통일된 인증 체계가 없는 내부 운영 도구

R&D실이 사용하는 운영 도구(Grafana, ArgoCD, 향후 내부 대시보드·관리 콘솔)에 현재 통일된 인증 체계가 없다. RDDP-456(Grafana 인증 체계 도입)을 계기로, 개별 서비스마다 Google OAuth Client를 발급·관리하는 분산 구조 대신 내부 운영 도구 전용 공용 OIDC 브로커를 한 곳에 두는 방향이 유리하다는 판단이 섰다.

현재 상황 (AS-IS)
인증이 각자 따로 운영되는 상태
· Grafana: auth.anonymous.enabled=true — 누구나 Editor 권한 접근 가능
· ArgoCD: bundled dex에 Google OAuth 연동 (ArgoCD 전용으로만 사용)
· 신규 서비스: 각자 Google OAuth Client를 별도 발급하는 구조 → 관리·정책 분산
목표 상태 (TO-BE)
공용 OIDC 브로커 한 곳에 수렴
· Google Workspace OAuth Client 1개를 공용 dex 전용으로 발급
· 신규 내부 서비스는 dex staticClient에 YAML 등록만으로 온보딩
· 단일 관리 지점, 단일 정책 집행, GitOps 완전 호환
추가 배경 — GKE 재구축 내성
GKE Autopilot → Standard 마이그레이션이 임박해 있어 (ADR-008), 어떤 OIDC 브로커를 선택하든 모든 설정이 GitOps·IaC로 코드화되어 클러스터 재생성 후 ArgoCD sync 한 번으로 복구되는 것이 전제다.
관리 대상 범위

두 개의 인증 축 — 본 ADR은 축 A만 다룬다

회사 전체의 인증은 목적이 완전히 다른 두 축으로 분리된다. 두 축은 상호 독립이며, 이 ADR은 내부 운영자 축(축 A)만 결정한다.

구분 축 A: 내부 운영자 SSO (본 ADR) 축 B: 서비스 엔드유저 인증
대상 사용자 R&D실 구성원 (수십 명) 고객사 최종 사용자 (수천~수만 명)
인증 대상 도구 Grafana, ArgoCD, 향후 내부 대시보드/관리 콘솔 ERP, MES, B2B 포털 등 서비스 애플리케이션
Upstream IdP Google Workspace (vntgcorp.com) 확정 Google / Kakao / Naver 등 다수 또는 자체 IdP
사용자 DB 없음 — upstream IdP에 완전 위임 필요 — 서비스별 사용자 테이블, 가입, 권한
커스텀 요구사항 거의 없음 — 도메인 제한, 역할 매핑 정도 많음 — 비밀번호 정책, 계정 잠금, 감사 로그 등
운영 주체 인프라 팀 (GitOps) 서비스 팀 (애플리케이션 코드·DB)
본 결정 dex 채택 (이하 비교) 별도 결정 (RDDP-343, Keycloak 추천 상태)
결정 요인

축 A에 특화된 7가지 핵심 드라이버

일반 풀스택 IAM 선택 기준과는 다르다. "비밀번호 정책·자체 사용자 DB"는 축 B에서만 필요하며 축 A에서는 의도적으로 드라이버에서 제외했다.

드라이버 01
Upstream IdP 완전 위임
자체 사용자 DB·가입·세션 관리 기능이 필요 없다. Google Workspace가 ID/MFA/계정 라이프사이클을 전담한다.
드라이버 02
K8s 네이티브·Stateless
외부 RDBMS 의존 없이 GKE 안에서 in-cluster 저장소로 동작하고, Helm values + SealedSecret으로 전부 GitOps 관리.
드라이버 03
staticClients의 코드화
신규 내부 서비스를 Git 커밋 한 번으로 OIDC 클라이언트 등록 가능해야 한다. 관리 콘솔 클릭 의존 금지.
드라이버 04
부트스트랩 독립성
공용 브로커 장애가 ArgoCD 로그인까지 막는 닭-달걀 상황이 없어야 한다. ArgoCD는 복구의 최후 보루이므로 외부 IdP 의존 금지.
드라이버 05
운영 부담 최소
수십 명 규모 내부 도구 SSO에 메모리 GB 단위·JVM 스타트업 수십 초·DB 마이그레이션이 있는 풀스택 IAM은 과잉이다.
드라이버 06
GKE 재구축 내성
PVC·외부 DB에 상태가 없어야 클러스터 재생성 후 ArgoCD sync만으로 복구된다. (ADR-008 요구사항)
드라이버 07
도메인 제한
vntgcorp.com 외부 Google 계정의 접근을 IdP 설정 한 곳에서 차단할 수 있어야 한다.
hostedDomains: vntgcorp.com

후보별 제외 사유 요약
Keycloak: 풀스택 IAM으로 기능은 충족하나, PostgreSQL 필수·JVM 메모리 1GB+·자체 사용자 DB import로 설계 철학이 반대편. 축 B에서는 유효하나 축 A에는 과잉.
Authentik: Keycloak과 유사한 이유로 과잉. 일부 고급 기능의 Enterprise tier 전환 추세도 장기 리스크.
Authelia: forward-auth 게이트웨이 카테고리 — Google을 upstream으로 federate하는 표준 기능이 없어 범주 자체가 다름.
Ory Hydra: headless OAuth2 서버 — dex가 즉시 해주는 federation broker 동작을 직접 개발해야 함. 축 A에 부적합.
결정 2

dex 채택 — 공용 OIDC 브로커

내부 운영 도구 전용 공용 OIDC 브로커로 dex를 채택한다. dex의 설계 의도와 본 축의 요건이 1:1 대응한다.

"upstream IdP에 위임하고 downstream 서비스에 OIDC로 중개하는 경량 broker"가 곧 dex의 존재 이유다. 이 영역에서 dex는 대체가 거의 없다.

ADR-015 Rationale
구체적 결정 내용
6가지 구현 지침
  • D-01infra/k8s/services/dex/ 디렉터리를 신설하고 dexidp/dex Helm chart를 ArgoCD Application으로 배포한다.
  • D-02Google Workspace OAuth 2.0 Client 1개를 공용 dex 전용으로 신규 발급. client_id/secret은 SealedSecret으로 봉인. hostedDomains: vntgcorp.com으로 도메인 제한 강제.
  • D-03storage: kubernetes 모드로 in-cluster CRD에 상태를 저장한다 — 외부 RDBMS·PVC 사용 금지.
  • D-04downstream 내부 서비스(Grafana 최초, 이후 추가될 내부 도구들)는 dex의 staticClients 항목에 YAML로 등록. 각 staticClient secret도 SealedSecret으로 봉인.
  • D-05Gateway API HTTPRoute로 dex.infra.nfw.vntgcorp.com 공개.
  • D-06본 결정은 내부 운영자 축(축 A)에만 적용된다. 서비스 엔드유저 축(축 B)은 RDDP-343의 결과를 따른다.
ArgoCD 예외 — 영구 적용
ArgoCD는 자체 bundled dex를 그대로 유지하며, 공용 dex의 staticClient로 이관하지 않는다.

이유 ①: 부트스트랩 닭-달걀 문제 — 공용 dex가 ArgoCD로 GitOps 관리될 예정. ArgoCD 로그인이 공용 dex에 의존하면 신규 클러스터 부트스트랩·공용 dex 장애 시 복구 경로가 단절된다.
이유 ②: 장애 격리 — 공용 dex가 죽더라도 ArgoCD 로그인은 살아 있어야 관리자가 dex를 복구할 수 있다.
이유 ③: 운영 비용 0 — ArgoCD bundled dex는 ArgoCD Helm chart가 lifecycle을 책임진다.
결과 및 영향

긍정적 효과와 신규 운영 책임

dex 채택으로 생기는 이점과, 새롭게 감수해야 하는 운영 부담을 균형 있게 정리한다.

긍정적 영향
  • +단일 IdP 통합점: Google OAuth Client 1개, 도메인 제한 1회 설정, 신규 서비스 온보딩이 staticClients 추가로 끝남
  • +GitOps 완전 호환: Helm values + SealedSecret만으로 모든 설정이 코드화 → PR 리뷰·감사 가능
  • +GKE 재구축 내성: 외부 DB·PVC 없음 → 클러스터 재생성 후 ArgoCD sync 한 번으로 복구
  • +경량: ~100Mi/Pod, HA는 replica 증설만으로 달성
  • +책임 분리: 인프라 팀 운영자 SSO와 서비스 팀 엔드유저 SSO가 완전 분리
부정적 영향 / 신규 운영 책임
  • −가용성·관찰성 운영 책임 신설: LGTM 관측 스택에 dex 로그·메트릭 반드시 수집
  • −보안 패치 SLA 운영 루틴 필요: 메인테이너 풀이 Keycloak 대비 작음 → CVE 모니터링 정책 필수
  • −관리 UI 부재: 디버깅은 전적으로 로그·메트릭 의존 → 런북으로 보완
  • −Google Groups claim 시 DWD 필요: 그룹 기반 권한 도입 시 Workspace 관리자 협조 필요 (초기 범위 외)
운영 정책

5가지 운영 정책 — 의사결정 동반 사항

dex 채택과 함께 정의되어야 하는 운영 기준들. 별도 런북에 세부 절차 유지.

정책 1
신규 내부 서비스 OIDC 등록 절차
신규 서비스 추가는 전적으로 Git 커밋으로 처리한다. 관리 콘솔 클릭으로 등록하는 것은 금지.
  1. 신규 서비스용 client_secret을 랜덤 생성 (openssl rand -hex 32)
  2. 공용 dex의 dex-secrets SealedSecret에 <SERVICE>_CLIENT_SECRET 키로 봉인 추가
  3. dex-values.yaml의 staticClients에 해당 서비스 항목(id, name, redirectURIs, secretEnv) 추가
  4. 서비스 측 Helm values에서 dex issuer URL과 동일한 client_id/secret을 SealedSecret으로 주입
  5. PR 리뷰 → 머지 → ArgoCD sync → 검증. 등록 체크리스트를 infra/k8s/services/dex/README.md에 유지
정책 2
Break-glass 로컬 계정 — dex staticPasswords 미사용
dex에 로컬 사용자를 두면 "upstream 위임" 원칙이 희석된다. break-glass는 각 downstream 서비스 자체의 로컬 admin 계정(Grafana admin, ArgoCD admin 등)으로 처리한다. 해당 패스워드는 SealedSecret으로 봉인.
정책 3
Google OAuth Client Secret 관리·회전
공용 dex 전용 Google OAuth Client는 다른 용도와 공유하지 않는다. Client Secret은 SealedSecret으로만 저장. 회전 주기: 최소 연 1회, 또는 운영자 인력 변동·의심 이벤트 발생 시 즉시.
정책 4
보안 패치 SLA
dex 릴리스 노트와 CVE 알림을 정기 확인. Critical: 72시간 이내, High: 2주 이내, Medium 이하: 분기 단위 정기 업그레이드에 포함.
정책 5
관찰성 — LGTM 스택 연동
  • Ldex Pod 로그를 Loki로 수집. 인증 실패·에러 로그에 대한 기본 알림 설정
  • Mdex Prometheus 메트릭(/metrics)을 Mimir로 수집. 로그인 성공/실패율, 토큰 발급 레이턴시 모니터링
  • Uhttps://dex.infra.nfw.vntgcorp.com/.well-known/openid-configuration 가용성을 Uptime 체크에 추가

# 항목 대응 / 결정 필요 시점
R-1 dex 메인테이너 풀이 작아 보안 패치 지연 가능성 운영 정책 "보안 패치 SLA"로 대응. 6개월 주기로 프로젝트 활동성 재평가
R-2 Google Groups claim 사용 시 GSuite DWD + 서비스 계정 셋업 필요 RDDP-456 초기 범위에서 Groups claim 미사용. 향후 그룹 기반 권한 필요 시 별도 티켓
R-3 관리 UI 부재로 장애 시 초기 대응 속도 저하 가능성 런북(infra/k8s/services/dex/README.md) + LGTM 대시보드 + kubectl 명령 정리로 보완
R-4 break-glass 로컬 admin 패스워드의 물리적 접근성 SealedSecret 복호화 권한자 최소화 + 회전 정책. 필요 시 외부 vault(1Password 등) 병행 검토
R-5 향후 축 B(Keycloak)와의 통합 유혹 본 ADR "관리 대상 범위" 섹션을 근거로 거부. 통합이 정말 필요하면 별도 ADR로 재검토
R-6 ArgoCD bundled dex도 Google OAuth Client를 사용하므로 Client가 2개가 됨 의도된 결정. Client 간 결합을 끊어 ArgoCD 복구 경로 독립성 확보
R-7 공용 dex 자체의 HA replica 2+ 배포. 수십 명 규모에서 HPA 오버헤드가 더 크므로 HPA 미적용
R-8 dex 업그레이드 시 CRD 스키마 변경 가능성 릴리스 노트 사전 검토. 중요 업그레이드는 dev 클러스터 먼저 검증 후 prod 반영
