선행 ADR-016이 남긴 미결 사항

ADR-016은 Grafana 배포 패턴(Helm chart 선택, PVC SQLite 영속성, 단일 인스턴스 운영)을 확정했다. 대시보드에 한해 코드/UI 이원 관리 원칙을 세웠으나, 나머지 17개 설정 범주의 관리 주체와 방법은 미결 상태였다.

ADR-016 확정 사항
Grafana 배포 패턴
· grafana-community/grafana Helm chart 사용
· Kubernetes PVC에 SQLite 영속화
· 단일 인스턴스 + R&D 운영팀 중앙 관리
· 대시보드만 코드/UI 이원 분리 원칙 수립
ADR-016 미결 사항
나머지 17개 설정 관리 방법
· Datasources 변경 권한 정책 없음
· Alert Rules / Contact Points 혼재 생성 가능
· Organizations, Teams, Users 관리 절차 미명시
· Notification Policies 예외 처리 정책 없음

분류 기준 — 6개 차원 정의

각 설정을 코드 관리 / UI 관리 계층에 배정할 때 사용하는 판정 기준. 차원 6(기술적 제약)이 UI 관리를 강제하면 나머지 차원은 무시된다. 차원 6이 코드 관리를 허용하면 차원 1~5를 종합하되, 차원 1(관리 주체)이 가장 큰 가중치를 가진다.

차원 1 — 가중치 최고
관리 주체
책임이 플랫폼 엔지니어인가, 사용자인가, 조직 관리자인가.
플랫폼 → 코드 관리 / 사용자 → UI 관리
차원 2
영향 범위
변경이 Grafana 전체에 영향을 미치는가, 개인/팀에만 미치는가.
전체 영향 → 코드 관리 / 개인 영향 → UI 관리
차원 3
변경 빈도 · 검증 필요성
거의 변경 안 되는가, 업무 흐름 중 수시로 변경되는가.
낮은 빈도 + 엄격 검증 → 코드 / 높은 빈도 + 즉시 반영 → UI

실수 비용
변경 실수 시 복구 비용이 얼마나 큰가. Datasource 오타 = 전체 장애.

차원 5
거버넌스 요구
변경 이력 감사 추적, 롤백, 승인 절차가 필요한가.
감사 추적 필요 → 코드 관리(Git 히스토리)
차원 6 — 최우선 적용
기술적 제약
Grafana가 파일 프로비저닝을 지원하는가. Notification Policies처럼 공존이 구조적으로 불가능한 경우도 포함.
프로비저닝 불가 → UI 관리 강제 (다른 차원 무시)

"Datasources에 k8s-sidecar를 쓰지 않는다. Helm values 단일 파일 관리로 변경 원자성을 확보하고, 운영 사고 추적 단계를 최소화한다."

— 결정 3, Datasource에 k8s-sidecar를 쓰지 않는 근거

Datasources에 editable: false 적용 근거

Datasource는 Loki, Mimir, Tempo의 클러스터 내부 엔드포인트를 가리킨다. 잘못 변경하면 전체 대시보드와 알림이 동작하지 않는다. editable: false 설정 시 Grafana UI에 "This data source was provisioned and cannot be modified" 메시지가 표시되어 실수로 인한 변경을 차단한다.

결정 4

베이스 대시보드 편집 권한 세분화

strict / flexible 이원 분리

코드 관리 계층의 대시보드를 UI 편집 허용 여부에 따라 두 카테고리로 분리한다. 기본값은 strict.

strict 카테고리
allowUiUpdates: false
· Grafana UI에서 저장 불가
· "Cannot save provisioned dashboard" 메시지 표시
· 변경은 Git PR만 인정
· 실험 필요 시 "Save As"로 사용자 폴더에 복사
· 대상: SLO, 인프라 장애 감지, 회사 표준 개요 대시보드
flexible 카테고리
allowUiUpdates: true
· Grafana UI에서 저장 가능
· 단, 다음 sidecar reconcile 시점에 Git 버전으로 덮어씀
· 임시 실험/파라미터 조정 용도
· 영구 반영은 Git PR로
· 대상: 탐색용, 팀별 커스터마이징이 빈번한 대시보드

strict = k8s-sidecar + 라벨 watch ConfigMap. flexible = dashboardsConfigMaps로 ConfigMap 직접 마운트 + 별도 dashboardProviders entry. 두 카테고리 간 대시보드 uid 중복 금지 — 중복 시 한 쪽이 무효화됨.

직접 작성 금지 — 공개 표준 대시보드 JSON 복사 방식 채택

kube-prometheus-stack 번들 + grafana.com 커뮤니티 표준 대시보드를 조합한 23개를 Day-1 베이스 세트로 선정한다. 전체를 strict 카테고리로 시작하며, 명시적 요청 시에만 flexible로 재분류한다.

결정 6

작성 방식 — Raw JSON + Git

베이스 대시보드를 Git 저장소에 Raw JSON으로 커밋한다. ConfigMap으로 프로비저닝하고 k8s-sidecar 또는 직접 마운트로 delivery한다.

인지하는 단점 (채택 상태로 감수)

  • 단점 1JSON diff 가독성 저하 — 패널 하나 변경이 200줄 diff로 보임. PR 리뷰가 rubber-stamp화되기 쉬움.
  • 단점 2ConfigMap 1 MiB etcd 한계 — "대시보드 하나당 ConfigMap 하나" 패턴으로 회피.
  • 단점 3수동 UID 관리 — strict/flexible 간 uid 중복 금지. 실수 시 대시보드 로드 실패.
  • 단점 4공유 패널 재사용 불가 — 동일 패널을 여러 대시보드에 복사-붙여넣기 해야 함.
대안결과사유
Grafana Foundation SDK미채택2026-04 public preview 상태. 공식 SLA 없음. 결정 9 재평가 대상.
Grafonnet미채택"experimental" 상태. Jsonnet 학습 곡선. 현 규모에서 비용 대비 이점 부족.
grafanactl미채택v0.1.9 preview. Grafana 12 이상 필요. 안정 릴리스 대기.
Grizzly미채택2025-01 DEPRECATED. grafanactl로 흡수 예정.
Terraform grafana provider미채택GitOps와 이중 reconciliation loop 발생. split brain 상태.
Raw JSON + Git채택단점 감수 가능한 현재 규모. 업계 공통 포맷. Foundation SDK 등 상위 도구도 최종 JSON 생성.
결정 7

Grafana 폴더 컨벤션 — Core

코드 관리 계층의 대시보드는 Grafana UI 내 Core 폴더에 배치한다. 사용자 관리 계층 대시보드는 폴더 강제 규칙 없이 사용자 자율.

Core 폴더 이름 선정 근거
중립성과 지속성
선행 ADR-016 제안 이름 Platform은 팀/역할 주어를 포함하여 조직 변경 시 부정확해질 수 있다. Core는 "표준 제공 기본 대시보드"의 의미를 조직 변경과 무관하게 유지한다.
00-readme 워크어라운드
폴더 설명 대체
Grafana 12.x는 폴더 description 필드를 미지원한다. 대신 각 코드 관리 폴더에 00-readme 이름의 Markdown 텍스트 패널 대시보드를 배치한다. 00- 접두사로 알파벳 정렬 시 상단 고정.

00-readme 대시보드 본문: 폴더 목적, 편집 정책(strict/flexible), 변경 절차(Git PR → ArgoCD sync → sidecar reconcile), 담당(R&D 인프라 팀). 00-readme도 strict 카테고리이므로 UI 수정 차단됨.

결정 8

Notification Policies 특수 처리

Notification Policies는 라우팅 트리 전체가 단일 리소스다. 파일 프로비저닝 시 사용자가 UI에서 생성한 정책까지 모두 덮어쓴다. 플랫폼 정책과 사용자 정책의 공존이 구조적으로 불가능하다.

"Since the policy tree is a single resource, provisioning it will overwrite all policies in the notification policy tree."

— Grafana 공식 문서 / Alerting File Provisioning
  • 결정Notification Policies를 파일 프로비저닝하지 않는다. 전체를 Grafana UI와 HTTP API로만 관리한다.
  • 초기초기 기본 라우팅 트리는 플랫폼 엔지니어가 UI에서 구성. 이후 사용자는 본인 Alert Rule에 대한 라우팅을 UI에서 추가.
  • 권장Alert Rule의 simplified notification routing 사용 권장 — Contact Point를 직접 지정하여 라우팅 트리를 우회. 플랫폼 정책과 독립적으로 알림 경로 구성 가능.

위험심각도완화
flexible 대시보드 수정이 sidecar reconcile에 덮어써져 사용자 혼란 Medium 00-readme 대시보드에 동작 명시. 초기 flexible 0개로 시작.
strict/flexible 간 대시보드 uid 중복 시 로드 실패 Low 향후 CI lint 스크립트로 uid 유일성 검증. 초기엔 수동 리뷰.
Foundation SDK GA 도달 시 Raw JSON 작업이 재작업 부담 Low 결정 9 트리거. Raw JSON → SDK 전환은 점진적으로 가능.
kube-prometheus-stack 번들 대시보드 업그레이드 부담 Low 버전 pin + Renovate 자동 PR. 대시보드 독립이므로 전체 교체 불필요.
Notification Policies 플랫폼/사용자 혼재로 라우팅 꼬임 Medium 초기 라우팅 트리 플랫폼 엔지니어 설정. 사용자는 simplified routing 권장.
GKE Standard 전환 후에도 control-plane 대시보드 공란 Low GKE control-plane metrics 옵션 활성화 필요. 별도 티켓 분리.
Terroir 확장 시점과 재평가 시점 불일치로 프로젝트 분리 요구 누적 Low 결정 9에 Terroir 확장 조건 명시. 분기 1회 주기적 리뷰.

채택 후 실행 작업

신규 Grafana 매니페스트 변경
namespace=grafana, Helm release=grafana
· Datasources (Loki, Mimir, Tempo) Helm values 인라인 선언 (editable: false)
· sidecar.dashboards.provider.allowUiUpdates → false (strict)
· flexible provider 구조만 준비 (Day-1 엔 strict만 사용)
· 23개 베이스 대시보드 JSON → dashboards/ 경로 추가
· 00-readme.json Markdown 대시보드 작성
· provisioning/alerting/ 디렉터리에 Alert Rules, Contact Points, Templates, Mute Timings YAML 추가
기존 Grafana 마이그레이션
namespace=monitoring, chart 8.15.0
· 사용자 생성 대시보드 11개: 사용자가 HTTP API로 JSON export → 신규 Grafana에 import
· 플랫폼 엔지니어는 이관 방법 안내만 담당
· 세아제강 Alert Rule, Google Chat Contact Point 분류: 팀 리뷰 후 공용이면 provisioning YAML 이관, 사용자 소유이면 UI 재생성

운영 규칙 요약

  • 베이스신규 베이스 대시보드 추가: Git PR → JSON + ConfigMap 추가 → 리뷰 → 머지 → ArgoCD sync → sidecar reconcile. 기본값 strict.
  • 사용자사용자 대시보드 / Alert Rule은 사용자 본인 책임. 플랫폼 엔지니어 관여 없음. Grafana UI에서 자유 생성.
  • Corestrict 대시보드 편집 시도 → "Cannot save provisioned dashboard" 차단. flexible → 저장되나 다음 reconcile에 덮어씌워짐. 00-readme에 동작 고지.
  • 알림Notification Policies는 UI 전용. 사용자는 Alert Rule의 Contact Point 직접 지정(simplified routing) 사용 권장.
