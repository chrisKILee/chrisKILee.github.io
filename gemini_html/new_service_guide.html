소개

이 가이드는 권남(kwonnam) 개발자가 실무 경험을 바탕으로 정리한 신규 웹 서비스 개발 체크리스트입니다. 기술 환경과 경험의 변화에 따라 지속적으로 업데이트되는 살아있는 문서입니다.

💡
모든 원칙에는 그 가치와 이유를 함께 명시해야 합니다. 이유를 모르는 규칙은 지켜지지 않고, 환경 변화 시 적절하게 개정될 수도 없습니다.

핵심 원칙

프로그래밍 언어 선택

  • ✅ 정적 타입 언어 선호 — 동적 언어는 초반 개발 속도는 빠르지만, 서비스 성장 후 리팩토링 단계에서 발목을 잡는 경향이 있다. 타입 힌팅을 지원하는 언어도 고려 가능.
  • 🔍 신기술 선택 시 충분한 검토 — 단점, 주의사항, pitfall을 반드시 사전에 파악한다. 커뮤니티 성숙도와 장기 지원 여부도 확인.

용어 통일

  • 📖 한국어 ↔ 영어 매핑 명확화 — 같은 개념을 가리키는 용어를 통일하고, 약자 사용을 금지한다. 예: "고객" = Customer = Member 중 하나로 통일.
  • 📖 정확한 의미 정의 — 팀원 간 용어의 의미 해석이 달라지지 않도록 사전 합의 후 문서화.

영웅 의존성 제거

⚠️
특정 개발자 한두 명에게만 의존하는 시스템 구조를 만들지 않는다. 버스 팩터(bus factor): 핵심 인원이 빠지면 프로젝트가 멈추는 구조는 위험하다. 문서화, 코드 리뷰, 지식 공유를 통해 버스 팩터를 높여야 한다.

아키텍처

프로젝트 구성

🗂️ 단일 프로젝트 멀티 모듈
  • 업무 도메인 단위로 모듈 분화
  • 인터페이스(interface) 기반 개발로 모듈 간 결합도 낮추기
  • MSA 전환이 필요할 때 분리 용이
  • 초기부터 MSA 구성은 과도한 복잡도 유발
📐 계층 분리 원칙
  • 상위 계층 → 하위 계층으로만 의존
  • Web Context(HttpServletRequest 등)를 비즈니스 레이어까지 끌고 가지 않기
  • 비즈니스 로직은 저장소(DB, 캐시)에 두지 않기
  • 서비스 레이어에서 트랜잭션 관리

API Gateway

  • 🚪 내부 API 직접 노출 금지 — 외부 요청은 반드시 API Gateway를 통해 라우팅.
  • 🔐 외부용 API는 별도 인증·권한 검사 — 내부 서비스 간 통신과 외부 클라이언트 통신의 보안 정책을 분리.

데이터베이스

Primary Key 설계

항목 권장 금지/비권장 이유
PK 타입 Long (BigInt) Integer (Int) Integer는 21억 근처에서 오버플로우 발생
PK 종류 인공키(surrogate key) 자연키(natural key) 자연키는 변경 가능성이 있어 연결된 FK 모두 업데이트 필요
자연키 처리 별도 Unique Index 설정 PK로 사용 비즈니스 식별자는 변경될 수 있음
금액/가격 타입 BigDecimal 또는 Long Double, Float 부동소수점 오차로 금융 계산 오류 발생 가능

ORM 활용 원칙

  • ✅ ORM 사용 권장 — 직접 SQL 작성보다 ORM이 유지보수와 DB 변경 대응에 유리.
  • 🚫 저장소에 비즈니스 로직 금지 — Stored Procedure, Trigger에 비즈니스 규칙을 넣으면 로직이 분산되어 테스트와 이해가 어려워짐.
  • 🚫 SQL 내 데이터 생성 로직 금지 — now(), password() 등 SQL 함수로 데이터를 생성하면 애플리케이션에서 제어 불가능.
  • 🚫 서로 다른 도메인 테이블 간 JOIN 금지 — 도메인 경계를 코드 레벨에서 유지. 필요하면 Application Join으로 처리.
  • 📦 선형·지수적 증가 데이터 저장소 분리 — 로그, 이벤트성 데이터는 메인 DB와 분리하여 보관.
⚠️
Stored Procedure는 절대 금지합니다. DB에 비즈니스 로직이 숨으면 버전 관리, 테스트, 디버깅이 모두 어려워집니다.

페이징

대용량 데이터 조회 시 페이징 방식에 따라 성능이 크게 차이납니다.

방식구현성능추천 여부
커서 기반(더보기) WHERE id > :lastId LIMIT :size O(1) — 항상 일정 권장
오프셋 기반 LIMIT :size OFFSET :page * :size O(n) — 뒷 페이지일수록 느림 비권장
💡
OFFSET이 커질수록 DB가 앞쪽 데이터를 모두 읽고 버리기 때문에 성능이 선형으로 저하됩니다. "더보기" UI에서는 커서 기반 페이징이 항상 빠르고 일관됩니다. 
-- ❌ offset/limit: 100만 번째 페이지에서 느려짐
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;

-- ✅ cursor 기반: 항상 빠름
SELECT * FROM orders WHERE id > :lastId ORDER BY id LIMIT 20;

보안

🌐 네트워크 접근 제어
  • 사내 직원용 서비스는 사내망 또는 VPN에서만 접근 가능하도록 제한
  • 내부 API는 외부에 직접 노출 금지
  • 도메인 기반 내부 통신 (IP 하드코딩 금지)
🔑 인증 정보 관리
  • 암호화 키, API 키, 비밀번호를 소스코드에 포함시키지 않기
  • 환경 변수 또는 Secret Manager 사용
  • 공용 계정으로 서버 접근 금지 — 개인 계정 사용 필수
✅ 입력값 검증
  • 클라이언트 검증을 믿지 않고 서버에서 반드시 재검증
  • Whitelist 방식 적용 (허용 목록 기반, Blacklist 금지)
  • SQL Injection 방지 — 파라미터화된 쿼리(PreparedStatement) 사용
🛡️ 설정 관리
  • 설정 변경 시 무배포 적용 시스템 구축 (Feature Flag, Config Server 등)
  • 운영 서버 직접 접속 이력 감사(audit) 기록
  • 시크릿 로테이션(rotation) 절차 수립
🚨
공용 계정 서버 접근 절대 금지. 누가 무엇을 했는지 추적이 불가능해집니다. 모든 운영 접근은 개인 계정 + 접근 로그 기록이 필수입니다.

운영 관리

로깅

  • 📝 Slf4j 사용 (Java 기준) — 구현체와 분리된 로깅 퍼사드 사용으로 로깅 라이브러리 교체 용이.
  • 📡 중앙 집중형 비동기 로그 수집 — ELK Stack, Loki 등 중앙 집계 시스템 구축. 로컬 파일 저장만으로는 검색·분석 어렵다.
  • 🚫 예외 먹기(swallowing) 절대 금지 — catch 블럭에서 예외를 무시하거나 빈 블럭으로 처리하면 장애 원인 파악 불가.
  • 📋 요청 파라미터 포함 예외 메시지 — 어떤 입력으로 예외가 발생했는지 메시지에 담아 디버깅 시간 단축. 
// ❌ 예외 먹기 — 절대 금지
try {
    someOperation();
} catch (Exception e) {
    // 아무것도 안 함
}

// ✅ 예외 기록 + 상위 전파
try {
    someOperation();
} catch (Exception e) {
    log.error("작업 실패: param={}", param, e);
    throw new ServiceException("처리 중 오류 발생: " + param, e);
}

배포 전략

  • 🔵 Blue/Green 배포 설계 — 무중단 배포를 위해 초기부터 Blue/Green 전환 가능한 구조 준비.
  • 📦 프로젝트별 독립 배포 스크립트 — 공통 배포 스크립트가 아닌 각 프로젝트에 특화된 스크립트로 배포 신뢰성 확보.
  • 🏷️ 배포 프로필 전사 통일 — local, dev, qa, staging, prod 프로필명을 팀 전체가 동일하게 사용.

모니터링

  • 📊 초기부터 모니터링 강화 — 런칭 후가 아닌 개발 단계부터 메트릭·알림 구성. 나중에 추가하면 항상 늦다.
  • 🖥️ 서버/VM 수준 모니터링 — CPU, Memory, Disk, Network 기본 지표 확인. Prometheus + Grafana 조합 일반적.
  • 💻 언어·프레임워크 수준 모니터링 — JVM 힙 사용량, GC 현황, Thread Pool 포화도 등 언어 특화 지표도 수집.

개발 환경

Local 개발 환경 자동화

  • 🐳 Docker/docker-compose로 필수 서비스 구축 — DB, MQ, Cache 등 인프라 서비스를 코드로 관리하여 팀원 누구나 동일한 환경 구성.
  • 🚫 Embedded DB 사용 금지 — H2 같은 임베디드 DB는 실제 운영 DB와 동작 차이가 발생. 로컬에서도 실제 DB 엔진 사용.

IaC (Infrastructure as Code)

🗃️ DB 스키마 관리
  • Flyway 또는 Liquibase로 DB 마이그레이션 버전 관리
  • 스키마 변경 이력을 코드로 추적 가능
  • 롤백 절차 사전 계획
🏗️ 인프라 관리
  • Terraform으로 클라우드 인프라 코드화
  • Ansible로 서버 설정 자동화
  • 수동 변경 금지 — 모든 변경은 코드로

조직 구성

신규 개발 조직 시작 시 우선순위

  • 🔐 OAuth/SSO 솔루션 구축 — 여러 서비스의 인증을 단일화. 나중에 추가하면 모든 서비스를 수정해야 하므로 초기에 구성.
  • 📦 의존성 저장소(Nexus) 구성 — 내부 라이브러리 배포 및 외부 의존성 캐싱. 인터넷 단절 시에도 빌드 가능.
  • 🐳 Docker Registry 구축 — 내부 컨테이너 이미지 저장소. 운영 배포 시 외부 Registry 의존 제거.
  • 🗄️ 내부 소스코드 저장소 — GitLab 등 자체 Git 서버. 코드 보안 및 접근 제어.
  • 📜 기술 선언서 및 Ground Rule 수립 — 팀이 따를 기술 원칙을 문서화. 정기적으로 회고하며 개정.

Git 전략

  • 🚫 git rebase + push --force 금지 — 공유 브랜치의 커밋 이력을 변경하면 팀원 모두의 로컬 저장소가 꼬인다.
  • ✅ Squash merge 권장 — PR 단위로 커밋을 합쳐 메인 브랜치의 이력을 깔끔하게 유지.

배치 작업

  • 🔌 DB 커넥션 최소 유지 — 배치 작업이 DB 커넥션을 과도하게 점유하면 운영 서비스에 영향. 작업 단위로 커넥션 반납.
  • 📊 시작 여부 모니터링 필수 — 배치가 실행되지 않아도 알림이 없으면 모른다. "배치가 시작됐는가"부터 모니터링.
  • 🔗 Job 간 의존관계 명확화 — A 배치가 성공해야 B 배치가 실행되는 구조라면 이를 명시적으로 설계하고 문서화.
  • 🕐 시간/날짜 범위 명시 — "지난 달", "이번 주" 같은 상대적 표현 대신 일(day) 수로 명시. 월/년 경계는 계산 오류 발생 가능.

기타 원칙

부하 대비

  • ⚡ 크리티컬하지 않은 기능 일시 차단 옵션 — 트래픽 급증 시 주요 기능 보호를 위해 부가 기능을 Feature Flag로 끌 수 있게 설계.
  • 🔄 언어·프레임워크 업그레이드 대비 테스트 커버리지 — 테스트가 없으면 메이저 업그레이드 시 회귀 여부 확인 불가.

도메인 기반 통신

  • 🌐 IP 기반 내부 통신 금지 — 서비스 간 호출 시 IP 대신 도메인명 사용. IP는 서버 이전 시 모두 변경해야 하므로 유지보수 비용 폭증.
