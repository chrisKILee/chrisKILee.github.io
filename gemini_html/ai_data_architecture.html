Doc 01 — Strategic Analysis Report · Vol. 01 · 2026

Data Architecture 2026
From Storage to Meaning

데이터 웨어하우스에서 시맨틱 온톨로지까지 — 30년의 진화, 2026년의 합의, 그리고 여섯 벤더가 그리는 서로 다른 미래에 대한 종합 조사

Chapter I — 진화의 계보

데이터 아키텍처의 30년은 한 줄로 요약된다 — 무게중심이 저장(Storage)에서 의미(Meaning)로 이동해 온 역사다. 각 세대는 이전 세대가 풀지 못한 한계에서 출발했고, 새로운 한계를 남기며 다음 세대를 촉발했다.

처음 30년의 질문은 "데이터를 어떻게 더 잘 저장하고 쿼리할 것인가"였다. 2025년 이후의 질문은 "데이터가 무엇을 의미하며 어떤 행동으로 연결되는가"다.

💡
"You can't scale AI until you re-architect the data beneath it."
— Matt Turck, MAD Landscape 2026
1990s구조화 시대

Data Warehouse — 구조화된 진실의 단일 원천

ETL → Star/Snowflake schema → OLAP cubes. 분석과 운영을 분리한 첫 번째 아키텍처. 일관된 비즈니스 리포팅과 historical trend 분석을 가능하게 했다.

OLAP/BI 확립 Historical trend Schema-on-write 경직 비정형 불가 Teradata · Oracle DW · IBM Netezza
2000s부서별 시대

Data Mart — 부서별 맞춤 뷰

Warehouse에서 도메인별로 추출한 주제 중심 저장소. 부서별 성능 최적화에는 성공했지만, Mart 간 silo와 데이터 중복이라는 새 문제를 만들었다.

부서별 최적화 Silo 심화 Cross-domain 불가 SSAS Cubes · MicroStrategy · Cognos
2010s원시 시대

Data Lake — Schema-on-read, 원시 데이터를 있는 그대로

Hadoop과 저비용 Object Storage 위에 정형/비정형/반정형 데이터를 원시 형태로 저장. ML/AI 학습 데이터의 주요 소스가 되었지만, 거버넌스 부재로 "Data Swamp"화 위험이 있었다.

비정형 수용 저비용 대규모 Data Swamp화 ACID 없음 Hadoop HDFS · AWS S3 · ADLS
2020s통합 시대

Data Lakehouse — Lake 유연성 + Warehouse 성능/거버넌스

Open Table Format(Delta·Iceberg·Hudi) 위에 ACID 트랜잭션, 스키마 진화, 타임 트래블. 2025년에는 "Lakehouse는 단일 제품이 아닌 layered architecture pattern"이라는 합의 형성.

Lake+Warehouse 통합 Iceberg 표준화 의미 계층 부재 Databricks · Apache Iceberg · Snowflake
2024+번역 시대

Semantic Layer — 물리 데이터 위의 비즈니스 의미

Metrics·Dimensions·Entities를 YAML/DSL로 정의하는 번역 계층. "매출"이 무엇인지 한 곳에서 정의하면 모든 소비자가 동일하게 해석한다. LLM이 SQL을 생성할 때 신뢰할 수 있는 기반.

Metric 일관성 LLM→SQL 신뢰 기반 정적 정의 — 맥락 적응 불가 dbt Semantic · Cube.dev · Snowflake Semantic Views
2025+관계 시대

Ontology + Knowledge Graph — 엔티티 간 관계와 규칙

Entity-Relationship-Rule을 그래프로 표현. Palantir의 Ontology, Microsoft Fabric IQ가 대표 사례. GraphRAG가 LLM의 hallucination을 줄이는 핵심 인프라로 부상.

관계 기반 추론 Cross-domain entity resolution 수동 구축 비용 Palantir Foundry · Fabric IQ · Neo4j
Now→에이전트 시대

AI-Native Data Fabric — 데이터가 살아있는 의미·거버넌스 메모리 시스템

AI Agent가 데이터의 발견·매핑·문서화·통합·전달·감시를 자율 수행. 데이터의 가치는 양이 아니라 "얼마나 잘 이해되고 행동으로 연결되는가"에서 나온다.

Agent memory 자율 운영 Agent governance — 새 과제 Databricks Agent Bricks · Snowflake Cortex · Palantir AIP
⚠️
Gartner: "Data Mesh vs Data Fabric 논쟁은 끝났다." 가장 강력한 아키텍처는 Lakehouse(플랫폼) + Data Fabric(통합/거버넌스) + Data Mesh(소유권 모델)를 결합하는 하이브리드다. 2026~2028년까지 자율 데이터 제품의 약 80%가 이 하이브리드에서 등장할 전망이다.
Chapter II — 2026년의 합의: 7-Layer Reference Stack

2025년이 끝날 무렵, 데이터 아키텍처의 큰 그림에 대해 산업이 합의에 도달했다. 하위 계층(L1~L4)에서는 Apache Iceberg가 사실상의 표준이 되었고, 진짜 차별화는 상위 계층 — Semantic Layer, Ontology, Agent Layer — 에서 일어나고 있다.

📐
두 가지 의미: ① 하부 계층의 상품화(Commoditization) — Storage와 Table Format은 더 이상 차별화 포인트가 아니다. ② 상위 계층의 전쟁 — L4~L7에서 누가 가장 풍부한 비즈니스 맥락을 제공하느냐가 미래를 결정한다.

네 가지 수렴 벡터
① Warehouse ↔ Lake ↔ OLTP

Lakehouse가 표준이 된 후, Databricks Lakebase와 Snowflake Postgres가 OLTP까지 통합. 분석 + 트랜잭션 + AI가 하나의 거버넌스 하에 동작하는 "Full-spectrum Data Platform"이 형성되고 있다.

② Structured ↔ Unstructured

Snowflake Cortex AISQL이 SQL로 문서/이미지를 분석하듯, 정형과 비정형의 경계가 소멸하고 있다. McKinsey: "모든 데이터 주도 기업은 비정형+반정형 데이터의 관계를 쿼리하고 이해해야 한다."

③ Analytics ↔ Ontology

Semantic Layer(Metrics/KPIs)와 Ontology(Entity-Relationship-Rule)가 동일 플랫폼 위에서 결합되기 시작. Microsoft Fabric IQ가 대표 사례. "Ontology is the contract between chaos and understanding" — Palantir.

④ Human ↔ Agent

AI Agent가 데이터 파이프라인 구축, 쿼리 실행, 품질 모니터링을 자율 수행. Agent의 행동을 관찰·감사·평가하는 "Agent Observability"가 새로운 거버넌스 영역으로 부상.

Chapter III — 세 부족의 데이터 플랫폼

Ontology 핵심
원시 데이터를 비즈니스 객체(Employee, Aircraft, Purchase Order)로 매핑. Object Type + Properties + Links + Actions + Functions = 기업의 "디지털 트윈". 단순 스키마가 아닌 Data + Logic + Action 통합 모델.

Action

Chapter V — 최적 조합 시나리오

단일 벤더로는 7-layer stack을 모두 풀 수 없다. 조직의 핵심 과제에 따라 4가지 조합이 가능하다.

① 조합 A — "Managed Everything" (Cloud-first 중소 조직)

AWS Sagemaker Lakehouse + Redshift + Glue Catalog + dbt Semantic + AtScale

Storage/Compute/Catalog는 AWS로 통합. Semantic Layer는 dbt+AtScale로 보강. AI는 SageMaker. 인프라 관리 최소화가 핵심. Ontology/KG는 별도 투자 없이 시작.

② 조합 B — "Open Core + Semantic" (데이터 엔지니어링 강한 조직)

Databricks (Delta+Unity Catalog) + dbt Semantic Layer + Databricks Agent Bricks

오픈소스 DNA. Delta Lake로 Storage/Compute/Catalog 통합. dbt가 Semantic Layer 담당. AI는 Agent Bricks. ML/AI 워크로드 최강이지만 Ontology는 외부 도구 필요.

③ 조합 C — "SQL-First + AI-in-SQL" (SQL 중심, 빠른 Time-to-Value)

Snowflake (Virtual Warehouse + Semantic Views) + Cortex AISQL

운영 부담 최소. SQL이 모든 것의 인터페이스 — AI까지 SQL 안에. Semantic Views로 Metric 정의. 학습 곡선이 가장 낮고 Quick Win 가능성 최고. 단 Ontology/Deep ML은 약함.

④ 조합 D — "Decision-Centric" (의사결정 자동화가 핵심인 대기업)

Snowflake or Databricks (인프라) + Palantir Foundry (Ontology+Action)

인프라는 기존 클라우드 플랫폼 유지. 그 위에 Palantir를 올려서 Ontology, Action, AIP 활용. 분석→행동의 루프를 폐쇄하는 유일한 조합. 비용과 전문 인력이 관건.

✦ Claude의 분석 의견

이 보고서는 2026년 현재의 벤더 전략을 사실 기반으로 잘 정리했다. 단, 한 가지 중요한 관점이 빠져 있다 — 벤더 없이 범용 LLM + MCP로 이 스택을 얼마나 대체할 수 있는가의 문제다. DOC 02(Unified LLM Agentic)가 바로 이 질문에 답한다.

내 판단: 조합 D(Palantir)의 Action 기능은 현재 LLM 자동화로 완전 대체하기 어렵지만, L4(Semantic) ~ L6(Agent)의 많은 기능은 Claude + MCP Protocol로 상당 부분 구현 가능하다. 특히 중소 조직의 경우 Palantir 없이도 DOC 02~04의 접근으로 80%+ 커버가 가능하다는 것이 나의 판단이다.

Core Insight: LLM의 진화 = 전체 파이프라인의 진화
특화 도구 10개를 쓸 때, 각 도구의 진화는 별개다. 하지만 범용 LLM을 중심으로 하면, Claude가 업그레이드될 때 Schema Matching도, Meta Data 생성도, Ontology 구축도 동시에 좋아진다.
2. 아키텍처: 6 Data Agents

전체 아키텍처는 3개 레이어로 구성된다. Reasoning Layer(LLM이 하나이므로 Schema를 분석하면서 얻은 컨텍스트가 Meta Data 생성에 자연스럽게 흐른다.

2.2 6개 Data Agent 정의
🔍 Scout L0→L1
Data Discovery & Profiling

DDL/샘플 데이터를 분석하여 각 컬럼의 의미, DMS Level(L0–L5), 품질 이슈를 JSON으로 추출. 모든 Data Lifecycle 작업의 시작점.

초기 L2_confirm → 목표 L4_autonomous

Schema Matching & Entity Resolution

서로 다른 시스템의 Schema 간 대응 관계를 추론. 신뢰도 0.7 미만은 Human Review 자동 라우팅. Cross-context Reasoning으로 정확도 향상.

초기 L1_suggest → 목표 L2_confirm
✍️ Scribe L1→L2
Meta Data 생성 & Catalog 관리

Scout/Mapper 결과로 Tier 1~3 Meta Data 자동 생성. Business Glossary 초안, Catalog 업데이트. Cascading Context로 ORD_DT → "주문일자" 정확히 추론.

초기 L1_suggest → 목표 L3_notify
🕸️ Weaver L2→L3
Ontology & Knowledge Graph 구축

DDL에서 Domain Ontology 자동 추출 (RIGOR Pattern). 3단계: CQ 생성 → Relation 추출 → KG 구축. 기존 RDB DDL에 이미 도메인 지식이 암묵적으로 내재.

초기 L1_suggest → 목표 L2_confirm
📢 Herald L3→L4
Data Serving & Query Agent

자연어 질의 → SQL 생성 및 실행 → 결과 해석. Metadata-Grounded SQL: Scribe의 Business Meta로 의미 파악, Weaver의 Ontology로 JOIN 경로 추론.

초기 L2_confirm → 목표 L3_notify
🛡️ Warden 전체
Governance & Quality

Quality Guard(품질 검증) + Policy Guard(권한/PII) + Change Guard(Schema 변경 감지 → 관련 Agent 자동 트리거). 보안/품질 감시는 자동화가 필수.

초기 L2_confirm → 목표 L4_autonomous

3. MCP 기반 Connection Layer

MCP(Model Context Protocol)는 LLM과 외부 시스템을 연결하는 표준 프로토콜이다. 특화 도구 대신 MCP Server를 통해 기존 시스템에 접근한다.

MCP Server접근 대상사용 Agent권한
DB MCP ServerPostgreSQL, MSSQL, Oracle 등 운영 DBScout, Mapper, HeraldRead-only (Scout/Herald) / Read-Write (Migration)
Catalog MCP ServerData Catalog (OpenMetadata 등)ScribeRead-Write
KG MCP ServerNeo4j, RDF Store 등WeaverRead-Write
Git MCP ServerSchema DDL, dbt Model, Config 버전 관리전체Read-Write
Slack MCP Server알림 및 Human Review 요청Warden, OrchestratorWrite
File System MCP문서, CSV, JSON 등 파일 접근전체Read-Write
💡
MCP의 전략적 의미: MCP는 단순한 기술 연결이 아니라, Tool Sprawl을 방지하는 아키텍처 원칙이다. 특화 AI 도구를 도입하는 대신, 기존 시스템에 MCP Server를 붙이고 LLM이 직접 접근하면, 벤더 종속성 없이 모든 기능을 확보할 수 있다. 도구를 교체하는 것이 아니라 MCP Server를 교체하는 것이므로 교체 비용이 근본적으로 낮다.
6. Progressive Autonomy: 점진적 자율성 확대

AI Agent에게 처음부터 전체 자율성을 부여하지 않는다. 신뢰가 축적될수록 점진적으로 권한을 확대한다.

4. State Management: Agent Memory 설계

Agentic 시스템의 핵심 과제는 상태 관리다. LLM은 본질적으로 Stateless이므로, Agent의 결과물을 지속적으로 저장하고 참조하는 체계가 필요하다.

4.2 Agent Artifact 표준 형식

Agent 간 결과물은 표준화된 JSON Schema로 전달된다 — 이것이 계약이자 인터페이스:

• Scout Artifact:  { table, columns[], dms_level, quality_issues[], profile_stats }
• Mapper Artifact: { mappings[{source, target, confidence, transform_rule}], unmatched[] }
• Scribe Artifact: { catalog_entries[{column, tier1, tier2, tier3}], glossary_terms[] }
• Weaver Artifact: { ontology_triples[], kg_entities[], competency_questions[] }
• Herald Artifact: { query, sql, result_summary, confidence }
• Warden Artifact: { quality_score, policy_violations[], change_impacts[] }

2. Agent Spec YAML Format

Agent Spec은 각 Agent를 완전히 정의하는 단일 파일이다. 이 파일만으로 Agent를 생성하고, 테스트하고, 운영할 수 있어야 한다.

2.1 Agent Spec YAML Schema
agent:
  name: string          # Agent 식별자 (scout, mapper, scribe...)
  version: string       # Spec 버전 (semver)
  description: string   # 한 줄 설명
  dms_scope: string     # 담당 DMS 전환 구간 (e.g., "L0 → L1")

reasoning:
  system_prompt: string # LLM System Instruction (전문)
  output_format: enum   # json | yaml | markdown | sql
  temperature: float    # 0.0–1.0 (default: 0.1)
  max_tokens: int

input:
  required: []          # 필수 입력 목록
    - name / type / source / schema_ref
  optional: []

output:
  artifact:
    schema_ref: string  # 출력 JSON Schema $ref
    storage: enum       # git | session | both
    path_template: string

mcp_tools: []           # 사용 가능한 MCP Server 목록
  - server / operations / permission

quality_gate:
  pass_criteria: []     # metric / operator / threshold
  on_fail: enum         # retry | escalate | block
  max_retries: int

autonomy:
  initial_level: enum   # L1_suggest | L2_confirm | L3_notify | L4_autonomous
  target_level: enum
  promotion_criteria:
    min_accuracy / min_executions / min_duration_days
2.2 Scout Agent Spec — 전체 예시
# agent-specs/scout.yaml
agent:
  name: scout
  version: "1.0.0"
  description: "Data Discovery & Profiling. 데이터 현황 파악 및 DMS Level 진단"
  dms_scope: "L0 → L1"

reasoning:
  system_prompt: |
    너는 Data Discovery 전문가다. 주어진 DDL/샘플 데이터를 분석하여:
    (1) 각 컬럼의 추정 의미와 비즈니스 역할
    (2) 데이터 타입과 패턴 (DATE인데 VARCHAR 저장 등)
    (3) DMS Level 평가 (L0–L5)
    (4) 품질 이슈 (NULL률, 타입 불일치, PII 감지)
    결과는 반드시 scout-artifact.json Schema에 맞는 JSON으로 출력하라.
    한국어 컬럼명 약어를 이해하고 비즈니스 맥락을 추론하라.
  output_format: json
  temperature: 0.1
  max_tokens: 8000

input:
  required:
    - name: ddl
      type: mcp_query
      source: db-mcp-server
    - name: sample_data
      type: mcp_query
      source: db-mcp-server

mcp_tools:
  - server: db-mcp-server
    operations: [query, get_schema, get_tables, get_sample]
    permission: read

quality_gate:
  pass_criteria:
    - metric: column_coverage
      operator: gte
      threshold: 0.95      # 95%+ 컬럼에 의미 분석 완료
    - metric: dms_level_assigned
      operator: eq
      threshold: true
  on_fail: retry
  max_retries: 2

autonomy:
  initial_level: L2_confirm
  target_level: L4_autonomous
  promotion_criteria:
    min_accuracy: 0.95
    min_executions: 50
    min_duration_days: 30

4. 핵심 설계 원칙 & Quality Gates
1.3 핵심 설계 원칙
원칙설명
Spec-FirstAgent를 코드로 구현하기 전에 YAML Spec으로 정의한다. Spec이 곧 문서이며, 문서가 곧 실행 가능한 코드이다.
Contract-DrivenAgent 간 경계는 JSON Schema로 정의된 Artifact가 계약이다. Schema 검증을 통과해야 다음 Agent로 전달된다.
Gate-Guarded모든 Phase 전환에 Quality Gate가 존재한다. Gate를 통과하지 못하면 다음 Phase로 진행할 수 없다.
Progressive TrustAgent Autonomy는 점수화된 신뢰도 기반으로 점진적으로 확대된다. 자동 승격은 없다.
Git-Native State모든 Artifact, Semantic Layer, Scorecard는 Git에 저장된다. 변경 이력 = Audit Trail.
LLM-AgnosticAgent Spec의 System Prompt는 LLM 벤더에 의존하지 않는다. Claude/GPT/Gemini 간 전환 가능.
✦ Claude의 분석 의견

Spec-First 원칙이 ADLF의 핵심 기여다. DOC 02가 "무엇을 만들어야 하는가"를 정의했다면, ADLF는 "어떻게 만들 것인가"를 YAML이라는 실행 가능한 형태로 규명한다. 이것은 단순한 문서화가 아니다 — TDD(테스트 주도 개발)를 AI Agent 세계로 가져온 것이다.

Quality Gate의 Gate-Guarded 원칙도 중요하다. 자동화가 실패했을 때 어디서 멈춰야 하는지를 명시적으로 정의함으로써, Agentic 시스템이 "조용히 틀리는" 가장 위험한 실패 모드를 차단한다. Progressive Trust와 결합하면 실제 운영 가능한 안전한 자동화 시스템을 만들 수 있다.

단, ADLF가 Terroir 플랫폼 특화 문서인 만큼, 다른 조직에서 그대로 적용하기 위해서는 MCP Binding과 CLAUDE.md를 환경에 맞게 커스터마이징해야 한다.

2. Semantic Layer: AI와 Service의 공통 기반

Semantic Layer는 Raw Schema와 Business Logic 사이의 번역 계층이다. AI가 정확한 SQL을 생성하려면, 컬럼명이 아닌 비즈니스 개념으로 데이터를 이해해야 한다.

2.1 Semantic Layer의 4가지 구성 요소
구성 요소정의예시AI에게 주는 가치
Entities & RelationsBusiness Object와 관계 정의고객 → 주문 → 상품. JOIN 경로 포함AI가 JOIN을 추론할 필요 없이 정확한 관계 파악
Metrics & Time LogicKPI 산출식과 시간 로직매출 = SUM(amount) WHERE status='completed', YTD/MTD/RollingAI가 Metric을 재발명하지 않고 기정의 활용
Governance PoliciesAccess Control, Masking, 품질 규칙RLS/RBAC/ABAC, PII 마스킹AI가 권한 범위 내에서만 작동
NL MetadataSynonym, 설명, 비즈니스 용어 매핑'GM%' = 'Gross Margin %', '매출액' = 'revenue'AI가 자연어 → Semantic 개념 변환

2.3 Unified LLM Agentic에서의 Semantic Layer 구축
  • Entities & Relations: Weaver의 Ontology에서 직접 추출. Object Type, Relation, Cardinality 포함
  • Metrics: Scribe의 Business Meta(Tier 3)에서 KPI 산출식 추출. LLM이 SQL로 변환
  • NL Metadata: Scribe의 Business Glossary에서 Synonym/설명 추출
  • Governance: Warden의 정책에서 RLS/RBAC 규칙 추출
  • 출력 형식: YAML/JSON으로 코드화하여 Git 버전 관리
3. Text-to-Mutation: 읽기를 넘어 쓰기로

Text-to-SQL(Query)은 읽기 전용이다. 하지만 서비스에서 진정한 가치를 발휘하려면 자연어로 데이터를 수정(INSERT/UPDATE/DELETE)할 수 있어야 한다. 이것이 Text-to-Mutation이다.

3.1 Mutation의 근본적 차이
구분Text-to-Query (Read)Text-to-Mutation (Write)
위험도낮음 (데이터 변경 없음)높음 (비가역적 변경)
오류 비용재실행으로 복구복구 불가 또는 고비용
Guardrail 수준권한 검증 정도Transaction + Validation + Rollback 필수
인간 개입결과 확인 수준실행 전 승인 필수 (Progressive)
3.2 5-Phase Mutation Safety Model
1
Intent Parsing
자연어에서 의도(Create/Update/Delete) 및 대상 Entity 추출
→ Reject + 명확화
2
Semantic Validation
Semantic Layer의 Business Rule과 충돌 여부 검증
→ 규칙 위반 설명
3
SQL Generation
Validated Intent 기반 Parameterized SQL 생성
→ Retry (max 3)
4
Preview & Confirm
Dry-run으로 영향 범위(affected rows) 표시. 사용자 승인 대기
→ Timeout → Rollback
5
Execute & Audit
Transaction 내 실행 + Audit Log 기록
→ Rollback + 알림
3.3 Operation Class별 안전 수준
OperationRisk LevelGuardrail 전략Progressive Autonomy
INSERT (Create)중간Schema 검증 + 필수값 확인 + Constraint CheckL2 → L3
UPDATE (Modify)높음WHERE 필수 + Affected Rows 제한 + PreviewL1 → L2
DELETE (Remove)매우 높음Soft Delete 우선 + 사용자 2회 확인 + RetentionL1 유지
Bulk Operation위험Batch 제한(max N건) + Dry-run 필수 + Admin 승인L1 유지
Schema Change (DDL)최고자동화 불가. 제안만 생성 → DBA 승인Agent 범위 밖
🔒
Parameterized SQL 원칙: Mutation SQL은 반드시 Parameterized Query로 생성해야 한다. LLM이 생성하는 것은 SQL Template이고, 실제 값은 Parameter로 분리하여 SQL Injection을 근본적으로 차단한다.

4.1 AI Data Gateway 아키텍처

4.2 Service에서의 3가지 활용 패턴
Pattern A: Natural Language API

서비스가 자연어 문장을 AI Data Gateway에 전송하고, 결과를 받는 패턴. 사용자가 직접 자연어 입력(Chatbot, 내부 툴)에 적합.

POST /api/data/query
{ "text": "지난달 비즈니스팀의 매출 합계" }
→ { "result": [...], "sql": "SELECT ...", "confidence": 0.95 }

POST /api/data/mutate
{ "text": "고객 A의 등급을 VIP로 변경", "confirm": true }
→ { "affected_rows": 1, "preview": {...} }
Pattern B: Structured Intent API

서비스가 구조화된 Intent를 전송. Herald가 Semantic Layer를 참조하여 SQL 생성. 자연어 파싱 오류를 줄이고 정확도가 더 높다.

POST /api/data/intent
{ "action": "query", "entity": "Order", "metrics": ["revenue"],
  "filters": { "period": "last_month", "team": "biz" } }
Pattern C: Schema-Aware MCP (Terroir 플랫폼)

Application이 MCP Client로 Herald Agent에 직접 연결. Terroir 플랫폼의 NestJS 서비스가 MCP로 Herald에 접속하여 AI Data Access를 직접 활용. 최소 레이턴시, 가장 유연.

  • NestJS 서비스가 MCP Client로 Herald Agent에 접속
  • Herald는 Semantic Layer를 참조하여 SQL/Mutation 생성
  • Warden이 정책 검증 후 DB MCP Server로 실행
  • Application은 MCP 응답으로 결과 수신
패턴적합한 상황장점주의점
A: NL API사용자가 직접 자연어 입력 (Chatbot)유연하고 직관적자연어 파싱 오류 가능성
B: Intent API서비스가 프로그래마틱하게 호출정확도 높고 예측 가능Entity/Metric 사전 정의 필요
C: MCP Direct플랫폼 내부 서비스최소 레이턴시, 최대 유연성MCP Protocol 이해 필요

8. 결론: 자연어가 데이터와 서비스를 잇는 세계
🎯

첫째, Semantic Layer가 모든 것의 기반이다. AI가 정확한 SQL을 생성하고, Service가 일관된 결과를 받으려면 Business Logic이 코드화된 Semantic Layer가 전제된다.

둘째, Mutation은 Query와 근본적으로 다른 안전 모델이 필요하다. 5-Phase Safety Model(Intent Parsing → Semantic Validation → SQL Generation → Preview & Confirm → Execute & Audit)을 통해 안전하게 쓰기 작업을 허용한다.

셋째, Service Integration은 3가지 패턴으로 접근한다. Terroir 플랫폼의 NestJS Service가 MCP로 Herald Agent에 직접 연결하는 Pattern C가 장기적으로 가장 강력하다.

결국, 우리가 만들고자 하는 것은 자연어가 데이터와 서비스를 잇는 세계다. Data 전문가만 할 수 있었던 작업을 비즈니스 담당자가, 서비스 개발자가, 그리고 서비스 자체가 자연어로 수행한다.

✦ Claude의 종합 분석 의견 — 4개 문서 통합 관점

4개 문서는 하나의 연속적인 아키텍처 논증을 형성한다. DOC 1이 "why the landscape matters", DOC 2가 "what to build", DOC 3이 "how to build", DOC 4가 "how to connect to production"이다. 이 순서가 단선적으로 읽혀야 한다.

가장 중요한 발견은 DOC 4의 Semantic Layer 정확도 데이터(20% vs 92.5%)다. 이 숫자는 단순 통계가 아니라 아키텍처 결정의 근거다. Scribe와 Weaver에 투자해야 하는 이유가 여기에 있다.

단, 한 가지 우려: DOC 2~4는 모두 "클로드 중심" 세계관을 전제한다. 실제 구현에서는 LLM 벤더 간 Prompt 호환성, 컨텍스트 윈도우 한계, 비용 최적화를 현실적으로 고려해야 한다. LLM-Agnostic 설계(DOC 3의 원칙)를 지키는 것이 장기적으로 옳다.
