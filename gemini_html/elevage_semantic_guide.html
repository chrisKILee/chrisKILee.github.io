Élevage — 3개 경로 모두의 공통 기반

레거시를 retire하기 어려울 때 선택하는 경로. 기존 시스템을 유지한 채 Semantic Layer를 씌워 AI 역량을 즉시 확보합니다.

브리지 패턴 (Bridge Pattern)
레거시 DB 위에 Data to Semantic Mapper + Adapter를 덧씌워 AI 역량을 즉시 확보합니다.
Ontology 기반 통합 API로 AI Agent 인터페이스를 제공하고 DX/AX를 구현합니다.
Élevage 완료 후 조건이 갖춰지면 Vinification으로 전환 가능 — 이것이 브리지 패턴의 핵심입니다.

3개 경로 모두에서 Élevage가 공통으로 자리잡는 이유

NC · Nouvelle Cuvée
Élevage의 역할

그린필드 신규 구축 경로에서도 Semantic Layer를 처음부터 설계에 포함합니다.
SDD Domain SPEC 작성 시 시맨틱이 자연 내장.

VIN · Vinification
Élevage의 역할

완료 후 레거시 데이터 retire.

Élevage의 역할

그 자체가 목적. 영구적 시맨틱 인터페이스.
레거시 데이터 위에 영속. 조건 충족 시 VIN 전환.

01

왜 시멘틱/온톨로지가 안 와닿는가

개발자가 체감하지 못하는 이유, 그리고 이미 하고 있다는 사실.

컬럼명 속 의미
테이블명을 orders로, 컬럼을 status로 짓는 순간 이미 시맨틱 행위를 한 것입니다. 문제는 그 "의미"가 기계가 읽을 수 없는 곳에 숨어있다는 점입니다.
코드 속 의미
if status == 'VIP' — VIP 기준이 뭔지는 비즈니스 로직에 흩어져 있습니다. 신규 개발자는 코드를 뒤져야 합니다. 퇴사하면 사라집니다.
ERD 속 의미
customer_id → customers.id — "연결"만 있고 "왜" 연결인지 없습니다. 온톨로지는 그 구두 설명을 기계가 읽을 수 있게 체계화한 것입니다.

"이 amount 컬럼이 정확히 뭐에요?" — 선임이 구두로 설명하는 그 모든 것이 바로 시맨틱입니다.

시맨틱/온톨로지는 그 구두 설명을 기계가 읽을 수 있게 체계화한 것

의미가 숨어있는 장소

숨어있는 곳예시문제
컬럼명price라고 쓰면 끝VAT 포함인지? 원화인지? 할인 전인지?
코드의 if문if status == 'VIP'VIP 기준이 뭔지는 비즈니스 로직에 흩어져 있음
개발자의 머리"아 그 테이블은 환불 건도 포함이에요"퇴사하면 사라짐
위키/노션 문서데이터 사전 문서업데이트 안 되고, 코드와 동기화 안 됨
ERD의 FKcustomer_id → customers.id"연결"만 있고, "왜" 연결인지 없음
02

같은 데이터, 4개 수준의 표현

"고객이 상품을 주문했다"는 하나의 사실을 각 수준에서 어떻게 다루는지 봅니다.

① 데이터
값 그 자체
{ customer_id: 42, product_id: 7, amount: 35000 }
"42번이 7번을 35000에 샀다" — 숫자만 있음
② 메타데이터
데이터에 대한 데이터
amount: { type: DECIMAL, nullable: false, created_at: 2024-01-15 }
"amount는 소수점 숫자고, 비어있으면 안 되고, 1월 15일에 만들어졌다"
③ 시멘틱
비즈니스 의미
amount: { meaning: "VAT포함_소비자가", currency: "KRW", includes: ["상품가","배송비"], excludes: ["쿠폰할인"] }
"이 금액이 정확히 무엇을 포함하고 무엇을 제외하는지"
④ 온톨로지
개념 간 관계 체계
주문 → (결제를_발생시킨다) → 결제 → (정산에_반영된다) → 정산
"주문이라는 개념은 결제, 정산, 배송, CS 티켓과 어떤 관계인지"

같은 SQL, 다른 깊이

전통적 접근 — 개발자가 알아야 쿼리 가능
-- "VIP 고객의 반품률"을 구하려면
-- 1) VIP 기준이 뭔지? → 코드 뒤져야 함
-- 2) 반품이 뭔지? → 취소? 교환? 환불?
-- 3) 어느 테이블? → 3개 서비스 DB 조인

SELECT c.id,
  COUNT(CASE WHEN o.status = 'returned'
    THEN 1 END)::float / COUNT(*) as return_rate
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE c.grade = 'VIP'  -- 이 'VIP'가 정확히 뭔데?
  AND o.status IN ('returned', 'refunded')
GROUP BY c.id;
시맨틱 + 온톨로지 기반 — 의도만 전달
-- 시맨틱 레이어 질의 (Metric Query)
SELECT * FROM metrics.return_rate
WHERE customer.tier = 'VIP'
  AND period = 'last_30_days';

-- 이 한 줄 뒤에서 시스템이 자동으로:
-- ✓ VIP = 온톨로지 정의 참조
--   (최근 6개월 구매 100만원 이상
--    AND 반품률 10% 미만)
-- ✓ return_rate = 사전 정의된 메트릭
--   (returned + refunded + exchanged)
--   / total_completed
-- ✓ 데이터 소스 자동 라우팅
--   (주문DB + CS DB + 정산DB)
03

서비스 설계 시 구체적으로 뭘 다르게?

아래 5가지를 기존 설계 과정에 추가하면, 시맨틱과 온톨로지는 자연스럽게 축적됩니다.

① 컬럼 설계: 타입 + 의미 주석

기존 DDL
CREATE TABLE orders (
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  amount      DECIMAL(10,2),
  status      VARCHAR(20),
  created_at  TIMESTAMP
);
시맨틱 선언 추가 (YAML 병행)
# order-schema.yaml (시맨틱 선언)
entity: Order
domain: commerce
owner: order-team

properties:
  amount:
    business_name: "결제요청금액"
    definition: "쿠폰 할인 적용 후, VAT 포함 최종 결제 요청 금액"
    unit: KRW
    includes: [product_price, shipping_fee]
    excludes: [coupon_discount, point_used]

  status:
    business_name: "주문상태"
    type: enum
    values:
      PLACED: "주문 접수 (결제 전)"
      PAID: "결제 완료"
      SHIPPED: "배송 중"
      RETURNED: "반품 접수"
      REFUNDED: "환불 완료"
    lifecycle: PLACED → PAID → SHIPPED → DELIVERED
    terminal_states: [REFUNDED, DELIVERED]

  customer_id:
    references: Customer
    relationship: "placed_by"     # ← FK가 아니라 '의미'
    cardinality: "many-to-one"
핵심 변화
DDL 자체는 바뀌지 않습니다. 옆에 YAML 한 장이 추가될 뿐입니다. 이 YAML이 시맨틱 메타데이터이고, 이것이 쌓이면 온톨로지가 됩니다.

② FK에 관계의 의미를 부여하라

기존 — 연결만 있음
-- ERD에는 선만 있음
orders.customer_id → customers.id
orders.product_id  → products.id
shipments.order_id → orders.id
변경 — 관계에 의미 부여
# ontology/commerce-relations.yaml
relationships:
  - from: Order
    to: Customer
    type: placed_by
    inverse: has_orders

  - from: Order
    to: Product
    type: contains
    inverse: ordered_in

  - from: Shipment
    to: Order
    type: fulfills
    inverse: fulfilled_by
    constraints:
      - "1 Order → N Shipments (분할배송)"
      - "Shipment.created_at > Order.paid_at"

③ 이벤트 발행 시 비즈니스 컨텍스트 포함

기존 — 기술적 이벤트
{
  "event": "order.status.changed",
  "order_id": 1234,
  "old_status": "PAID",
  "new_status": "SHIPPED",
  "timestamp": "2024-03-15T10:00:00Z"
}
시맨틱 인식 이벤트
{
  "event": "order.status.changed",
  "order_id": 1234,
  "transition": {
    "from": "PAID",
    "to": "SHIPPED",
    "business_meaning": "fulfillment_started",
    "triggers": [
      "shipment_creation",
      "inventory_deduct",
      "customer_notification"
    ],
    "reversible": false
  },
  "context": {
    "domain": "commerce",
    "aggregate": "Order",
    "caused_by": "warehouse_scan"
  }
}

④ API 응답에 타입 힌트 추가

기존 API 응답
{
  "customer_id": 42,
  "total": 150000,
  "items": [...]
}
시맨틱 힌트 포함 (JSON-LD 스타일)
{
  "@type": "Order",
  "@context": "https://your-co.com/ontology/commerce",
  "customer": {
    "@type": "Customer",
    "@id": "/customers/42",
    "tier": "VIP"
  },
  "total": {
    "@type": "MonetaryAmount",
    "value": 150000,
    "currency": "KRW",
    "includes": ["product_price", "shipping_fee", "vat"]
  },
  "items": [...]
}

⑤ 용어 사전(Glossary)을 코드와 동기화

# glossary/commerce.yaml — 이것이 온톨로지의 씨앗
terms:
  주문:
    english: Order
    definition: "고객이 하나 이상의 상품을 구매 의사 표시한 트랜잭션"
    distinguished_from:
      - term: 결제
        difference: "주문은 의사표시, 결제는 돈의 이동"
      - term: 배송
        difference: "주문은 논리적 단위, 배송은 물리적 단위"
    states: [PLACED, PAID, SHIPPED, DELIVERED, RETURNED, REFUNDED]
    metrics:
      - 주문전환율: "주문수 / 장바구니생성수"
      - 반품률: "(RETURNED + REFUNDED) / DELIVERED"
    related_entities:
      - entity: Customer
        relation: placed_by
      - entity: Product
        relation: contains
      - entity: Payment
        relation: triggers
5가지 실천의 공통점
기존 코드를 바꾸지 않습니다. YAML 선언 파일을 "옆에 두는 것"만으로 시맨틱 레이어가 점진적으로 형성됩니다. 이 파일들이 모이면 자연스럽게 온톨로지 그래프가 됩니다. Palantir가 고객사에서 하는 일의 핵심도 이것입니다.
04

시멘틱/온톨로지가 있을 때 구체적으로 뭐가 달라지나

4가지 실제 시나리오로 비교합니다.

시나리오 1 · 신규 개발자 온보딩
없을 때
온보딩 2-3주 소요
"이 amount가 뭐에요?" → 선임 찾아서 물어봄 → "아 그건 쿠폰 빠진 거고 VAT 포함이야" → 위키에 있다는데 2년 전 문서 → 실제로는 코드 까봐야 확실함
있을 때
온보딩 3-5일로 단축
"이 amount가 뭐에요?" → 스키마 레지스트리 조회 → 정의, 포함/제외 항목, 계산식, 관련 엔티티 즉시 확인 → 코드와 항상 동기화
시나리오 2 · 크로스 도메인 데이터 질의
비즈니스 질문
"반품이 잦은 VIP 고객이 CS 문의도 많은지 확인해줘"

없을 때: 개발자가 해야 하는 일

1VIP 기준 확인 → 마케팅팀에 문의 (반나절)
2반품 정의 확인 → CS팀에 문의 (반나절)
33개 DB 접속 권한 요청 (1-2일)
4각 DB 스키마 파악 + 조인 키 확인 (반나절)
5쿼리 작성 + 결과 검증 (반나절)
= 총 3-4일, 3개 팀 협조 필요

있을 때: 시스템이 하는 일

1"VIP" → 온톨로지에서 Customer.tier = 'VIP' 정의 자동 해석
2"반품" → 시맨틱 레이어에서 return_rate 메트릭 자동 매핑
3"CS 문의" → Ticket 엔티티 자동 연결 (Customer ← placed_by → Order ← relates_to → Ticket)
4데이터 소스 자동 라우팅 + 조인 실행
= 총 30초, 셀프서비스
시나리오 3 · AI 에이전트 활용
없을 때
AI가 할 수 있는 게 없음
AI에게: "매출 분석해줘"

AI: "어떤 테이블에 매출 데이터가 있나요? amount 컬럼이 매출인가요? 환불은 빼야 하나요? 어떤 DB에 접속하면 되나요?"

컨텍스트가 없으니까.
있을 때
AI가 즉시 정확한 분석
AI에게: "매출 분석해줘"

AI: 온톨로지 조회 → "매출"은 revenue 메트릭 → SUM(Order.amount) WHERE status IN (DELIVERED, SHIPPED) → 자동 쿼리 생성 및 실행
AI 시대의 결정적 차이
온톨로지는 AI 에이전트의 "업무 매뉴얼"입니다. 사람에게는 구두 설명으로 충분하지만, AI에게는 기계가 읽을 수 있는 시맨틱 정보가 필수입니다. 이것이 LLM 시대에 온톨로지의 가치가 폭발적으로 증가하는 이유입니다.
시나리오 4 · 임팩트 분석 (변경 영향도)

orders.status 컬럼에 새 상태값 'PARTIALLY_RETURNED'를 추가하려 합니다.

없을 때
"다 바꾼 줄 알았는데" 🔥
이 컬럼 쓰는 서비스 찾기 (grep? 수동?) → 반품률 계산 로직 어디있지? → 대시보드에 영향? → 정산 로직에 영향? → 발견은 배포 후
있을 때
변경 전에 전체 파악
Order.status → 영향 메트릭: [return_rate, completion_rate, revenue]
영향 서비스: [settlement, analytics, cs-dashboard]
영향 이벤트: [order.status.changed → 5개 컨슈머]
05

팔란티어가 실제로 하는 일

Palantir의 독보적 경쟁력은 기술이 아닙니다. 고객사에 들어가서 수개월간 온톨로지를 구축하는, 노동집약적이고 도메인 전문성이 필요한 작업을 해주는 것입니다.

Palantir Foundry의 핵심 구조

Ontology
Object Types + Link Types + Action Types
Patient라는 Object Type에 has_diagnosis라는 Link Type으로 Diagnosis에 연결. prescribe_medication이라는 Action이 정의됨.
Semantic
각 Object의 Property에 비즈니스 정의 부여
Patient.risk_score는 "지난 12개월 응급실 방문 횟수 × 만성질환 수"로 정의
Pipeline
원본 데이터 → 정제 → Object 매핑
EMR의 encounter 테이블 → 정제 → Patient Object의 visit_history property로 매핑
Application
온톨로지 위에 앱을 빌드
의사가 "고위험 환자 목록"을 보면 → Patient WHERE risk_score > 8 → 자동으로 데이터 소스 연결
Palantir의 진짜 비밀
기술적으로 특별한 것은 없습니다. YAML + 그래프 DB + 데이터 파이프라인의 조합입니다. Palantir의 진짜 해자는 (1) 고객 도메인에 맞는 온톨로지를 설계하는 컨설팅 역량, (2) 한번 구축하면 갈아타기 어려운 Lock-in, (3) AIP로 LLM이 온톨로지를 활용하게 만든 시너지입니다.
