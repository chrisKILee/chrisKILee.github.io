OpenTelemetry란 무엇인가?

OpenTelemetry(OTel)는 애플리케이션의 동작을 추적하기 위한 벤더 중립적 오픈소스 관찰성(Observability) 프레임워크입니다. CNCF(Cloud Native Computing Foundation)의 인큐베이팅 프로젝트로, OpenCensus와 OpenTracing이 통합되어 탄생했습니다.

쉽게 말해 — 서버에서 뭔가 느려지거나 에러가 났을 때 "왜 그랬는지"를 파악하기 위한 데이터를 수집하고 내보내는 표준 도구입니다. 90개 이상의 벤더가 지원하며 Datadog, Prometheus, Jaeger, Grafana 등 어느 도구와도 연결됩니다.

✦

Observability(관찰성)란 외부에서 시스템에 질문을 던져 내부 상태를 이해할 수 있는 능력입니다. "이 서비스가 왜 느린가?", "어느 마이크로서비스에서 에러가 났는가?"를 코드 수정 없이 파악할 수 있어야 진정한 관찰성입니다.

🏷️

벤더 중립

데이터 수집 방법은 OTel 표준으로 통일, 데이터를 보내는 백엔드(Jaeger, Datadog 등)는 자유롭게 선택.

🔌

업계 표준

CNCF 공식 프로젝트. AWS, Google Cloud, Azure, Datadog 등 90개 이상 벤더가 네이티브 지원.

🌐

12개 언어 지원

Java, Python, Go, JS/Node, .NET, Ruby, Rust, C++, Swift, PHP 등 주요 언어 공식 SDK 제공.

3대 신호 (Signals) — Traces · Metrics · Logs

OTel은 시스템 관찰을 위한 세 가지 핵심 신호(Signal)를 정의합니다. 이 세 가지를 함께 사용할 때 분산 시스템의 문제를 효과적으로 디버깅할 수 있습니다.

🔍

Traces

분산 추적. 요청이 여러 서비스를 거치는 전체 여정을 기록합니다.

흐름 추적
📈

Metrics

숫자 기반 측정값. CPU, 에러율, 처리량 등 시스템 건강도를 수치로 표현.

성능 측정
📝

Logs

타임스탬프가 있는 이벤트 기록. 트레이스와 연결하면 더욱 강력해집니다.

이벤트 기록
🎒

Baggage

서비스 간 컨텍스트 정보 전파. 사용자 ID, 세션 정보를 요청과 함께 전달.

컨텍스트 전파
⚡

Profiles

런타임 성능 프로파일링. CPU·메모리 사용을 코드 레벨에서 분석 (베타).

성능 분석
🔍 Traces 상세

분산 추적 — 요청의 여정을 지도로 그린다

하나의 HTTP 요청이 API Gateway → Auth Service → DB → Cache를 거치는 과정을 Span(작업 단위)들로 기록합니다. 각 Span은 부모-자식 관계로 연결되어 전체 Trace를 구성합니다. "어느 서비스에서 200ms가 낭비됐는가"를 한눈에 파악할 수 있습니다.

Trace 구조 개념도 
Trace ID: abc123
├── Span: API Gateway        [0ms → 5ms]
│   └── Span: Auth Service   [5ms → 30ms]
│       └── Span: DB Query   [10ms → 28ms]  ← 병목!
└── Span: Cache Lookup       [31ms → 35ms]
📈 Metrics 상세

메트릭 — 숫자로 보는 시스템 건강 상태

일정 기간의 집계 데이터입니다. Counter(요청 횟수 누적), Gauge(현재 CPU 사용률), Histogram(응답시간 분포) 세 가지 유형이 있습니다. Prometheus 등과 연동해 알림을 설정하는 데 주로 사용합니다.

📝 Logs 상세

로그 — 타임스탬프가 있는 이벤트 기록

기존 로그와 다른 점은 Trace ID와 자동으로 연결된다는 것입니다. "에러 로그가 발생했을 때 그 요청의 전체 Trace를 바로 볼 수 있다"는 것이 핵심 강점입니다. 기존 로그 라이브러리(log4j, winston 등)와도 통합 가능합니다.

🏗️

전체 아키텍처 — 데이터는 어디로 흐르는가

OTel의 데이터 흐름은 크게 세 단계입니다: 수집(Instrument) → 처리(Collect) → 내보내기(Export).

Your App
SDK로 계측
→
OTel Collector
수신 · 처리 · 라우팅
→
Jaeger / Prometheus
백엔드 저장
→
Grafana / Datadog
시각화 대시보드
💡

Collector 없이 앱에서 직접 백엔드로 내보낼 수도 있지만, Collector를 중간에 두면 백엔드를 나중에 교체해도 앱 코드를 수정할 필요가 없습니다. 운영 환경에서는 Collector 사용을 권장합니다.

🧩

핵심 구성요소

구성요소역할비고
API 텔레메트리 데이터를 생성하는 인터페이스. 라이브러리 개발자용. 핵심
SDK API의 실제 구현체. 앱 개발자가 설치해서 사용하는 언어별 라이브러리. 핵심
Collector 데이터 수신(Receiver) → 처리(Processor) → 내보내기(Exporter) 파이프라인. 벤더 중립 게이트웨이. 권장
Exporters 수집된 데이터를 Jaeger, Prometheus, Zipkin, OTLP 등 다양한 백엔드로 전송. 확장
OTLP OTel 자체 전송 프로토콜(gRPC/HTTP). 벤더들이 이 형식을 직접 지원하기 시작. 프로토콜
Auto Instrumentation Java Agent, .NET, Python 등 코드 수정 없이 자동으로 계측. 가장 빠른 도입 방법. Zero-code
✦

OTLP(OpenTelemetry Protocol)는 OTel이 만든 표준 전송 프로토콜입니다. AWS X-Ray, Google Cloud Trace, Datadog 등이 OTLP를 네이티브로 지원하기 시작해, 이제는 Collector 없이도 직접 연결이 가능해지고 있습니다.

⚡

계측(Instrumentation) 방법 3가지

OTel을 애플리케이션에 적용하는 방법은 코드 변경 여부에 따라 세 가지로 나뉩니다.

1

Zero-code (자동 계측) — 가장 빠른 방법

코드를 한 줄도 바꾸지 않고 계측합니다. Java Agent(-javaagent 옵션), .NET Auto Instrumentation, Python 등이 대표적입니다. 기존 프레임워크(Spring, Express, Django 등)의 HTTP 요청, DB 쿼리 등을 자동으로 감지합니다.

Java Agent 예시 
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=my-service \
     -Dotel.exporter.otlp.endpoint=http://collector:4317 \
     -jar myapp.jar
2

Library Instrumentation (라이브러리 계측)

OTel이 제공하는 라이브러리 통합 패키지를 설치합니다. Express, Django, Spring, gRPC 등 인기 프레임워크용 패키지가 이미 준비되어 있습니다. 약간의 설정 코드만 추가하면 됩니다.

Node.js 예시 
npm install @opentelemetry/sdk-node \
            @opentelemetry/auto-instrumentations-node

// instrumentation.js
const { NodeSDK } = require('@opentelemetry/sdk-node');
const sdk = new NodeSDK({
  serviceName: 'my-service',
  // Express, HTTP, gRPC 등 자동 계측
  instrumentations: [getNodeAutoInstrumentations()]
});
sdk.start();
3

Manual Instrumentation (수동 계측) — 최대 제어

OTel API를 직접 호출해 비즈니스 로직 단위로 커스텀 Span을 만듭니다. "결제 처리" 함수가 얼마나 걸리는지 등 프레임워크가 자동으로 잡지 못하는 부분을 추적할 때 사용합니다.

Python 수동 계측 예시 
from opentelemetry import trace

tracer = trace.get_tracer("my-service")

def process_payment(order_id):
    with tracer.start_as_current_span("process_payment") as span:
        span.set_attribute("order.id", order_id)
        # 비즈니스 로직
        result = charge_card(order_id)
        span.set_attribute("payment.success", result.success)
        return result

실전 활용 — 언제 왜 쓰나?

🐛

느린 API 디버깅

어느 마이크로서비스가 병목인지 Trace로 확인. DB 쿼리가 N+1 문제인지 즉시 파악 가능.

📟

에러 알림 & 추적

에러 발생 시 해당 요청의 전체 Trace를 바로 조회. 로그만 보는 것보다 원인 파악이 10배 빠름.

🔄

마이크로서비스 의존성

서비스 간 호출 관계 지도를 자동 생성. "A 서비스 배포 후 B 서비스가 느려졌다"를 증명.

📊

SLO/SLA 모니터링

p95, p99 응답시간을 Histogram으로 추적. 서비스 수준 목표 준수 여부 실시간 확인.

☁️

클라우드 비용 최적화

어느 함수가 CPU/메모리를 많이 쓰는지 Profiles로 파악. Lambda, Cloud Run 최적화에 활용.

🔀

벤더 마이그레이션

Datadog → Grafana로 교체할 때 앱 코드 수정 제로. Exporter만 바꾸면 됩니다.

OTel 도입 체크리스트

✅ 언어별 SDK 설치 (Java Agent / pip install / npm install)
✅ Service Name, 환경(prod/staging) 환경변수 설정
✅ OTel Collector 배포 (Docker/K8s)
✅ 백엔드 선택: Jaeger(오픈소스) or Datadog/Grafana(상용)
✅ 주요 API 엔드포인트 자동 계측 확인
✅ 핵심 비즈니스 로직에 수동 Span 추가
✅ 대시보드 구성 & 알림 설정

⚠️

모든 Trace를 저장하면 비용이 매우 높아집니다. Sampling(샘플링) 전략을 반드시 설정하세요. 일반적으로 프로덕션에서는 1~10%만 저장하고, 에러 요청은 100% 저장하는 Head/Tail Sampling을 조합합니다.

💡

Kubernetes 환경이라면 OTel Operator를 사용하면 사이드카 자동 주입으로 모든 파드를 코드 변경 없이 계측할 수 있습니다. 가장 빠른 대규모 도입 방법입니다.
