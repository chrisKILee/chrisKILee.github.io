01

RAG의 문제 — 매번 처음부터 시작한다

Karpathy Gist 원문: "LLM이 매번 질문마다 지식을 처음부터 다시 발견합니다. 축적이 없습니다."

기존 방식
RAG
  • 파일 업로드 → 질문마다 청크(조각) 검색
  • 매번 원본에서 처음부터 발견
  • 축적 없음, 정제 없음
  • 복잡한 질문은 조각 찾기부터 시작
  • NotebookLM, ChatGPT 파일 업로드 방식

아무것도 쌓이지 않습니다. 질문할수록 지식 베이스는 그대로입니다.

Karpathy 방식
LLM Wiki
  • 원본 자료 → LLM이 위키로 컴파일
  • 개념별 아티클, 역링크, 인덱스 생성
  • 에이전트가 Q&A하며 위키를 보강
  • 탐색할수록 지식 베이스가 강해짐
  • Obsidian + Claude Code 조합

탐색과 질문이 쌓일수록 위키가 점점 뚜렷해집니다.

02

코드 조작에서 지식 조작으로

"A large fraction of my recent token throughput is going less into manipulating code, and more into manipulating knowledge."

Andrej Karpathy · X (Twitter) · 2026-04-02

지금까지 대부분의 LLM 활용 경험은 코드를 조작하는 것이었습니다. Karpathy는 이제 자신의 토큰 사용량 상당 부분이 코드 조작이 아닌 지식 조작에 쓰인다고 밝혔습니다.

Gist 원문: "The idea of the idea file is that in this era of LLM agents, there is less of a point/need of sharing the specific code/app, you just share the idea, then the other person's agent customizes & builds it for your specific needs."

CORE INSIGHT

Karpathy는 이제 토큰의 상당 부분을 코드 조작이 아닌 지식 조작에 씁니다. LLM이 위키를 직접 쓰고 관리합니다. 사람은 방향만 잡으면 됩니다. 전체 아이디어 파일은 GitHub Gist에 공개됐고, 본인의 LLM 에이전트에 복붙하면 바로 시작할 수 있습니다.

03

LLM Wiki 파이프라인 — 5단계

원본 소스 → raw 저장 → Wiki 컴파일 → Q&A 에이전트 → 출력 귀환. STEP 3 WIKI가 핵심입니다.

STEP 3 WIKI — LLM이 소유하는 유일한 계층. 사람은 읽기만 합니다.

04

3계층 아키텍처

Karpathy Gist가 정의한 세 개의 계층. 계층마다 소유자가 다릅니다.

Layer 1 · 불변
Raw Sources
큐레이션된 원본 문서 모음. 아티클, 논문, 이미지, 데이터 파일. LLM이 읽지만 절대 수정하지 않습니다. 진실의 원천(source of truth).
human-owned · read-only
Layer 2 · 핵심
The Wiki
LLM이 생성하는 마크다운 파일 디렉토리. 요약, 엔티티 페이지, 개념 페이지, 비교, 개요, 합성. LLM이 이 계층 전체를 소유합니다. 사람은 읽기만 합니다.
llm-owned · always-current
Layer 3 · 설정
The Schema
LLM에게 위키 구조·규칙·워크플로우를 알려주는 설정 파일. Claude Code → CLAUDE.md, OpenAI Codex → AGENTS.md. LLM을 챗봇이 아닌 규율 있는 위키 관리자로 만듭니다.
config · CLAUDE.md / AGENTS.md
05

3가지 주요 작업 — Ingest · Query · Lint

Gist 원문이 정의한 위키 운영의 세 가지 핵심 작업입니다.

작업 트리거 LLM이 하는 일 결과
Ingest (수집) 새 소스 파일 추가 시 소스 읽기 → 핵심 추출 → 요약 페이지 생성 → 인덱스 업데이트 → 관련 엔티티/개념 페이지 10~15개 업데이트 → 로그 추가 위키가 새 지식을 흡수
Query (질의) 사용자가 질문 시 index.md로 관련 페이지 탐색 → 읽기 → 인용 포함 답변 합성. 좋은 답변은 새 위키 페이지로 저장됨 답변 + 위키 보강
Lint (건강 체크) 주기적으로 실행 모순 감지, 구식 정보 플래그, 고아 페이지(링크 없는 페이지) 탐지, 누락 역링크 추가, 데이터 공백 확인 위키 일관성 유지
06

특수 파일 — index.md & log.md

콘텐츠 지도
index.md
위키 내 모든 페이지 목록 + 한 줄 요약 + 링크. Q&A Agent가 질문을 받으면 index.md를 먼저 읽어 관련 페이지를 찾습니다. 적당한 규모(소스 ~100개, 페이지 수백 개)에서는 임베딩 기반 RAG 인프라 없이도 충분히 작동합니다.
타임라인 기록
log.md
언제 무엇을 했는지 추가 전용(append-only) 기록. 인제스트·쿼리·린트 이벤트가 쌓입니다. Gist 팁: 각 항목을 ## [2026-04-02] ingest | 제목 형식으로 시작하면 grep으로 파싱 가능합니다.
Obsidian 비유

Gist 원문: "In practice, I have the LLM agent open on one side and Obsidian open on the other. The LLM makes edits based on our conversation, and I browse the results in real time — following links, checking the graph view, reading the updated pages."

Obsidian = IDE  /  LLM = 프로그래머  /  Wiki = 코드베이스

08

왜 작동하는가

"Humans abandon wikis because the maintenance burden grows faster than the value. LLMs don't get bored, don't forget to update a cross-reference, and can touch 15 files in one pass."

Andrej Karpathy · GitHub Gist · 2026-04-04

지식 베이스 유지의 고통스러운 부분은 읽기나 생각이 아닙니다. 장부 정리(bookkeeping)입니다. 역링크 업데이트, 요약 최신화, 모순 플래그, 수십 페이지 일관성 유지. 사람은 이 비용이 증가하면 위키를 포기합니다. LLM은 지루해하지 않고, 역링크 업데이트를 잊지 않으며, 한 번에 15개 파일을 처리할 수 있습니다.

Karpathy는 1945년 Vannevar Bush의 Memex 개념도 언급합니다. "그가 해결하지 못한 부분은 누가 유지보수를 하느냐였습니다. LLM이 그것을 처리합니다."

RAG와 가장 큰 차이
컴파일 → 축적
원본을 한 번 컴파일하면 지식이 위키에 쌓입니다. 질문마다 다시 검색하지 않습니다. 위키는 영구적으로 복리처럼 성장하는 결과물입니다.
핵심 원칙
에이전트가 쓴다
사람이 위키를 직접 편집하지 않습니다. LLM 에이전트가 씁니다. 사람의 역할은 소스 큐레이션, 방향 설정, 좋은 질문하기.
복리 효과
출력이 귀환한다
Q&A 결과물을 다시 위키에 넣습니다. 비교 분석, 연결 발견, 합성 — 이것들이 채팅 기록에 사라지지 않고 위키에 남습니다.

한계 및 주의사항

커뮤니티와 Gist 자체에서 지적된 제한 사항입니다.

한계 내용
규모 한계 소스 ~100개, 페이지 수백 개까지는 index.md로 충분. 이후엔 qmd 같은 임베딩 검색 필요 → 결국 RAG로 회귀한다는 비판 있음
LLM 부정확성 LLM이 부정확한 크로스레퍼런스를 생성하거나 모순을 놓칠 수 있음. 인간 검증이 여전히 필요
협업 한계 DokuWiki 창업자 등의 비판: "진짜 위키가 아님" — 다중 사용자 권한·협업·버전 병합 메커니즘 부재
추상적 설계 Gist 원문: "이 문서는 의도적으로 추상적입니다. 특정 구현이 아닌 아이디어를 설명합니다." 도메인·도구·선호도에 따라 직접 구현 필요
