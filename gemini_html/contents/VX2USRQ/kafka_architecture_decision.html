지역 센터에 Kafka 서버를 배치하는 방식의 타당성과 명분을 정리합니다.

2026년 3월 13일 · 플랫폼인프라팀
핵심 결정: 군산·포항 등 VM이 있는 지역에는 지역 Kafka를 직접 배치하고, VM이 없는 순천·창원은 상암 Kafka를 경유하여 GCP로 전송한다. 이미 구성이 완료된 상태이며, 대체할 명확한 사유가 없어 현행 유지.
🎯 지역 Kafka 배치의 명분과 근거
단순히 이미 설치됐기 때문이 아닙니다. 지역 Kafka는 여러 운영 문제를 구조적으로 해결합니다.
🔔

회선 장애 시 알림 폭주 방지

지역 Kafka 없이 GCP에서 직접 모니터링할 경우, 회선 장애 시 해당 지역의 수십~수백 개 서버에서 각각 알람이 발생합니다.

지역 Kafka가 있으면 → Kafka 1개 알람만 발생. 장애 포인트 즉시 식별 가능.
🔀

GCP 경로 변경 시 단일 포인트 수정

수신처(GCP 엔드포인트 등)가 바뀔 때, 지역 Kafka 한 곳의 설정만 변경하면 하위 서버 전체에 반영됩니다.

말단 서버들의 개별 Config 수정 불필요 → 운영 공수 최소화.
🌐

도메인 기반 유연한 전환

각 지역 Kafka에 개별 도메인 URL이 할당되어 있습니다. 나중에 지역 Kafka를 없애야 할 경우, 해당 도메인을 GCP Kafka로 바라보도록 수정하면 됩니다.

하위 서버를 전혀 건드리지 않고도 전환 가능.
💾

회선 단절 시 데이터 버퍼

Kafka가 메시지 큐 역할을 수행하여, 회선이 일시적으로 끊기더라도 데이터가 손실되지 않고 버퍼에 보관됩니다.

GCP 직접 전송 방식은 회선 단절 시 데이터 유실 위험.
🔌

L2 계층 프록시 역할

로컬 Kafka 서버를 L2 계층의 프록시로 활용하여, ping/Port 체크 메트릭을 포함한 다양한 데이터를 한 곳에서 수집·전달합니다.

지역 내 모든 모니터링 데이터의 단일 집약점 역할.
⚙️

초기 구성 완료, 대체 이유 없음

이미 지역별 Kafka 세팅과 도메인 설정이 완료된 상태입니다. Alloy Aggregator 등 대안이 있으나, 현재 Kafka 효용성이 충분히 높아 굳이 전환 검토가 불필요합니다.

차선책을 찾는 실익이 없으며, 도입하지 않을 명확한 사유도 없음.
🗺️ 전체 아키텍처 다이어그램
지역별 VM 유무에 따라 Kafka 경유 경로가 달라집니다.
⚖️ 있을 때 vs 없을 때
지역 Kafka 유무에 따른 실질적인 차이입니다.
❌ 지역 Kafka 없이 GCP 직접 연결
  • 회선 장애 시 해당 지역 서버 수십~수백 개에서 각각 알람 발생
  • 장애 원인이 회선인지 서버인지 즉시 구분 불가
  • GCP 수신처 변경 시 모든 서버 Config를 일일이 수정해야 함
  • 회선 단절 시 데이터 유실 위험 (버퍼 없음)
  • ping/Port 체크 결과가 분산되어 집약 관제 어려움
✅ 지역 Kafka 배치 시
  • 회선 장애 시 Kafka 1개 알람만 발생, 즉시 장애 포인트 파악
  • 지역 내 모든 서버 데이터의 단일 집약·프록시 포인트
  • 수신처 변경은 Kafka 1대의 Config만 수정으로 완료
  • 메시지 큐 버퍼로 회선 단절 시에도 데이터 보존
  • 도메인 기반 구성으로 나중에 GCP Kafka로 전환도 용이
📍 지역별 구성 현황
VM 유무에 따라 데이터 전송 경로가 다르게 구성됩니다.
지역 VM 유무 데이터 경로 비고
제강 군산 ✅ VM 있음 서버 → 지역 Kafka → 상암 Kafka → GCP 지역 Kafka 직접 운영
제강 포항 ✅ VM 있음 서버 → 지역 Kafka → 상암 Kafka → GCP 지역 Kafka 직접 운영
제강 순천 ❌ VM 없음 서버 → 상암 Kafka → GCP 상암 Kafka 경유
제강 창원 ❌ VM 없음 서버 → 상암 Kafka → GCP 상암 Kafka 경유
상암 IDC ✅ 상암 Kafka 상암 Kafka → GCP 중앙 집약 포인트
※ 가용성 확보를 위해 홀수(3~5개) 구성이 권장되나, 현재는 지역별 1대로 운영 중. 향후 증설 검토.

지역 Kafka 존치 근거 정리

이미 지역별 Kafka 서버가 구성되어 있고 개별 도메인도 만들어져 있음. 회선 장애 시 수십~수백 개 알림 대신 Kafka 1개 알림으로 집약. GCP 업로드 경로가 바뀌면 지역 Kafka 한 군데 경로만 수정하면 됨. 지역 Kafka를 없애야 할 경우에도 해당 도메인만 GCP Kafka를 바라보도록 수정하면 됨.

현재로서는 지역 Kafka를 사용했을 때의 장점이 많은 상황. Alloy Aggregator 대안도 있지만 굳이 검토할 필요가 있나?

추가 정리 — Kafka의 핵심 역할

Kafka 큐 역할의 핵심은 회선이 끊겼을 때 버퍼로 작동한다는 것. 알람 측면에서는 반드시 Kafka일 필요는 없으나, 이미 구성된 Kafka가 이 역할을 함께 수행하므로 별도 대안 검토 실익이 없음.

버퍼 + 프록시 + 알람 집약 = Kafka 하나로 세 가지 역할 해결.

🎯 결론 요약

  • 지역 Kafka는 알람 집약·데이터 버퍼·경로 유연성의 세 가지 역할을 동시에 수행한다.

  • 향후 수신처 변경이나 Kafka 철수 시에도 도메인 단위 전환으로 유연하게 대응 가능하다.
