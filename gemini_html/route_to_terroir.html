01

왜 Route to Terroir인가?

현재 시스템은 세 가지 구조적 문제를 안고 있다. 이 문제들이 Route to Terroir 프로그램의 출발점이다.

🗄️
레거시 고착
.NET/SIS 기반 시스템이 현대화 없이 유지되고 있다. 기술 부채가 누적되고 새로운 역량 추가가 어렵다.
🔒
데이터 사일로
시스템 간 데이터가 단절되어 있어 AI 활용이 불가능하다. 데이터를 통합하거나 의미 있는 인사이트를 도출하기 어렵다.
⚙️
이중 운영 부담
신규 서비스와 레거시 시스템이 혼재해 운영 복잡도가 증가한다. 두 환경을 동시에 유지하는 비용이 크다.

"하나의 프로그램, 세 가지 경로. 모든 서비스가 Terroir를 거치되, 출발점에 따라 경로가 다르다."

Route to Terroir 핵심 원칙
02

세 가지 경로 개요

서비스의 출발 상태에 따라 세 가지 경로 중 하나를 선택한다. 경로가 달라도 최종 목적지는 Terroir 생태계다.

Nouvelle Cuvée
신규 프로젝트
  • 새 비즈니스 요구에서 시작
  • SDD SPEC → AI 코드 생성
  • Terroir 네이티브 Day 1
결과: Terroir-native 서비스
레거시: 해당 없음
Vinification
완전 재구축
  • 레거시 역추출 → SPEC 전환
  • 신규 서비스 재구축
  • 레거시 시스템 + 데이터 retire
결과: 현대화된 서비스
레거시: 완전 retire
Élevage
시맨틱 강화
  • 레거시 유지 상태에서 시작
  • Semantic Layer 구축
  • AI 활용 DX/AX 제공
결과: AI 활용 역량 추가
레거시: 그대로 운영
03

Track 1 · Nouvelle Cuvée

비즈니스 요구에서 시작해 Terroir 위에 처음부터 새로 만드는 경로. Terroir 5대 역량을 모두 Full로 활용한다.

04

Track 2 · Vinification

레거시를 해체 → SPEC 추출 → 새 시스템 구축 → 레거시 retire. Data to Semantic은 재구축을 위한 수단이다.

05

Track 3 · Élevage

레거시를 유지한 채 Semantic Layer를 씌워 DX/AX 역량을 확보한다. 팔란티어 Foundry/AIP 접근의 내재화.

06

Terroir 역량 활용 매트릭스

5개 Terroir Layer가 각 트랙에서 어느 수준으로 활용되는지 정리한다.

Terroir Layer Nouvelle Cuvée Vinification Élevage
Dev SDD 기반 SPEC → Claude Code 코드 생성. Coder IDE 전면 활용 Full 레거시 역추출 → SPEC 전환 → SDD 재구축. 전반부 역공학, 후반부 SDD Full Semantic Mapper, Adapter 개발. SDD는 connector 개발 시 부분 활용 Partial
Deploy Day 1 CI/CD + GitOps. 컨테이너 기반 배포 파이프라인 전체 Full 이중 환경 운영 후 점진적 전환 (Strangler Fig) Full Semantic Layer만 배포. 레거시 배포 기존 유지 Light
Infra GCP/IDC 하이브리드, K8s, VPN 풀 활용 Full 전환기 이중 인프라 → 완료 후 단일화 Full 최소 인프라. Semantic Layer 호스팅만 Light
Ops LGTM 전면 적용. OTel, Kafka Day 1 내장 Full 신규에 LGTM + 레거시 대비 비교 대시보드 Full 데이터 파이프라인 모니터링. 레거시 Ops 기존 유지 Partial
IDP Backstage 서비스 등록, API 문서, 온보딩 Full 마이그레이션 트래커(Cuvée Card), 전환 대시보드 Full Data Catalog, Semantic Registry 중심 Partial

Full 전면 활용    Partial 부분 활용    Light 최소 활용

07

Route 선택 의사결정 흐름

대상 서비스의 상태에 따라 세 가지 질문으로 경로를 결정한다.

재구축 리소스가 있는가? — YES →
Vinification
완전 재구축 진행
재구축 리소스가 있는가? — NO (유보) →
Élevage → Vinification
Élevage 선행 후 조건이 되면 Vinification 전환
08

경로 간 관계 — Élevage는 Vinification의 브리지

공유 역량 Data to Semantic은 세 트랙 모두에서 발생하지만 목적과 결과가 다르다.

Nouvelle Cuvée
Data to Semantic 역할

SDD Domain SPEC 작성 시 시맨틱이 자연 내장.
별도 작업 불필요.

Vinification
Data to Semantic 역할

재구축을 위한 수단. 역추출 → SPEC 전환 과정.
완료 후 레거시 데이터 retire.

Élevage
Data to Semantic 역할

그 자체가 목적. 영구적 시맨틱 인터페이스.
레거시 데이터 위에 영속.

Élevage → Vinification 브리지 패턴
재구축 리소스가 부족한 서비스는 Élevage로 시맨틱 가치를 먼저 확보한다.
이후 여건이 되면 Vinification으로 전환 — Élevage에서 만든 Ontology가 Crush 단계를 단축시킨다.
(이미 도메인의 의미 구조가 파악되어 있기 때문)
