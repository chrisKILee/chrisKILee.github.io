ADR-001

CI/CD 솔루션

GitHub Actions (CI) + ArgoCD (CD/GitOps)
✓ Accepted · 2025년 10월

하이브리드 인프라에서 여러 쿠버네티스 클러스터를 운영하며 일관된 CI/CD 파이프라인이 필요하다. 모노레포 전략과 자연스럽게 통합되는 도구를 선택한다.

결정 (Decision)

CI (지속적 통합): GitHub Actions를 채택한다.
CD (지속적 배포): GitOps 방식으로 ArgoCD를 채택한다.

GitHub Actions 채택 이유
모노레포와 긴밀한 통합
GitHub에 내장되어 있어 코드 저장소와 CI 파이프라인이 동일 플랫폼에 존재한다. 커뮤니티 액션이 풍부하여 구성 시 유연성이 높고, 관리 포인트가 단순화된다.
ArgoCD 채택 이유
멀티클러스터 GitOps
온프레미스 + GCP 여러 쿠버네티스 클러스터를 한 곳에서 관리한다. 웹 대시보드로 배포 상태를 확인할 수 있으며, CNCF 표준 GitOps 도구로 생태계가 활발하다.

고려했으나 채택하지 않은 옵션

  • GCP Cloud Build — GitHub Actions만으로 GCP 연동이 충분. CI 도구 이원화로 인한 운영 복잡도 증가 방지
  • Jenkins — 운영 부담과 학습 곡선이 크며, GitHub 기반 협업 환경에서 CI 이원화는 복잡도를 높임
  • FluxCD — ArgoCD의 웹 UI와 멀티클러스터 지원이 하이브리드 환경에 더 적합
2026-01-27
초안 작성 (Proposed) 후 즉시 Accepted 전환
ADR-002

Infrastructure as Code

Terraform (프로비저닝) + Ansible (설정 관리)
✓ Accepted · 2025년

온프레미스와 클라우드에 걸쳐 인프라를 코드로 관리한다. 휴먼 에러를 줄이고 감사/버전 관리를 용이하게 하며, 구성 드리프트(drift)를 방지한다.

결정 (Decision)

프로비저닝: Terraform — GCP 자원 프로비저닝
설정 관리: Ansible — 서버 설정 자동화
역할 분담 원칙: "프로비저닝은 Terraform, 설정은 Ansible"

Terraform
GCP 프로비저닝
멀티클라우드 IaC 도구로 GCP 프로바이더를 통해 VPC, Subnet, GKE, IAM, Cloud SQL 등 거의 모든 GCP 리소스를 기술한다. 원격 백엔드(GCS 버킷) + 상태 잠금으로 협업 시 충돌을 방지한다. GitHub Actions와 연계하여 코드리뷰 프로세스로 인프라 변경을 승인한다.
Ansible
OS 레벨 설정 관리
에이전트리스(SSH 기반) 구조로 온프레미스/클라우드를 가리지 않고 사용한다. OS 레벨 설정, 미들웨어 설치, 패치 적용 등 쿠버네티스 외부 VM/OS 레벨 작업에 적합하다. 방화벽·네트워크 스위치 설정에도 활용 가능하다.

고려했으나 채택하지 않은 옵션

  • HCP Terraform — 편의성은 높으나 비용 발생. 현재는 GitHub Actions에서 직접 실행하며, 향후 필요 시 재검토
  • Pulumi — TypeScript 시너지가 있으나 팀의 Terraform/HCL 숙련도와 생태계 성숙도 우선
  • CDKTF — 추상화 계층 추가와 운영 복잡도를 고려해 현 단계에서 불채택
  • 클라우드 전용 도구 (GCP Deployment Manager 등) — 하이브리드 환경에서 벤더 종속성 회피
2026-01-27
초안 작성 → 아키텍처 문서 기반으로 내용 업데이트 → Accepted
ADR-003

관측가능성 스택

Grafana 생태계 (Mimir · Loki · Tempo · Alloy)
✓ Accepted · 2025년

하이브리드 인프라 전반에서 메트릭·로그·트레이스를 하나의 플랫폼에서 통합 관리한다. GCP 관리형 서비스를 비활성화하여 장기적 비용을 절감한다.

결정 (Decision)

메트릭: Grafana Mimir · 로그: Loki · 트레이스: Tempo · 에이전트: Grafana Alloy · 시각화: Grafana · 경보: Alertmanager (1차 Google Chat, 2차 SMS)

고려했으나 채택하지 않은 옵션

  • GCP 관리형 서비스 (Cloud Monitoring, Cloud Logging) — 지속적 비용 발생, 온프레미스 통합 제한
  • Prometheus 단독 — 대규모 환경에서 고가용성·장기 보존·멀티클러스터 통합에 한계
  • Thanos — Grafana 스택과의 통합 경험 시너지를 위해 Mimir 선택
  • ELK Stack — 리소스 소비가 크고 운영 복잡도 높음
  • 상용 APM (Datadog, New Relic) — 높은 라이선스 비용과 벤더 종속성
2026-01-27
초안 작성 → Accepted 전환
ADR-004

클라우드 플랫폼

Google Cloud Platform (GCP) · asia-northeast3
✓ Accepted · 2025년

그룹사 정책상 퍼블릭 클라우드는 GCP를 기본으로 사용한다. 계열사 IDC와 GCP 간 전용선 연결이 이미 구축되어 있어 추가 비용 없이 하이브리드 환경을 구성한다.

결정 (Decision)

기본 리전: asia-northeast3 (Seoul)
GKE 역할: 공통 서비스(관측가능성 스택, ArgoCD 등) 배치
온프레미스 K8s 역할: 일반 애플리케이션·서비스 배치
주요 서비스: GKE Autopilot · Shared VPC · Cloud SQL · Artifact Registry

GKE Autopilot
노드 없는 Kubernetes
노드 관리 부담 없이 Pod 기반 자동 스케일링. 사용한 만큼만 과금되어 R&D 비용 최적화에 적합하다.
Shared VPC
네트워크 일원화
여러 프로젝트 간 네트워크를 공유하여 관리 포인트를 단일화한다. Interconnect를 통해 온프레미스와 단일 내부망처럼 운영한다.
Artifact Registry
컨테이너 이미지 저장소
온프레미스에서도 Interconnect를 통해 프라이빗 접근이 가능하다. 하이브리드 환경에서 단일 이미지 저장소를 유지한다.

"그룹사 전용선 기반 하이브리드 구조로 추가 네트워크 구축 비용 없이 온프레미스와 클라우드를 단일 내부망처럼 운영한다."

ADR-005

시크릿 관리

Sealed Secrets (단기) + HashiCorp Vault (장기 계획)
✓ Accepted · 2026-02-05

DB 패스워드, API 키 등 민감 정보를 GitOps 워크플로우에서 안전하게 관리한다. GKE와 온프레미스 K8s 클러스터 모두에서 동일한 메커니즘을 사용한다.

결정 (Decision)

단기 (현재): Sealed Secrets — K8s 매니페스트 시크릿 암호화, GitOps 통합
장기 (계획): HashiCorp Vault — 인프라 영역(IaC, Ansible, Terraform) 시크릿 중앙 관리

Sealed Secrets 작동 방식

단계별 로드맵

1
Sealed Secrets 도입 (현재)
K8s manifests 시크릿 암호화. GKE 및 온프레미스 K8s 클러스터에 동일 적용. ArgoCD와 자연스럽게 통합. 외부 인터넷 연결 불필요.
2
HashiCorp Vault 도입 — 인프라 영역 우선
IaC(Ansible, Terraform), 운영 스크립트 등 인프라 영역에 Vault를 먼저 도입. 시크릿 중앙 관리, 감사 로그, 접근 제어, 버전 관리 및 로테이션.
3
K8s–Vault 통합 검토 (선택적)
K8s 애플리케이션에서도 고급 시크릿 관리가 필요한 시점에 External Secrets Operator 또는 Vault Agent Injector 활용을 검토한다.

ADR-006

Dev/Test 리소스 최적화

GKE Autopilot Anti-affinity 비활성화 + Replica 축소
✓ Accepted · 2026-02-26

GKE Autopilot에서 Helm 차트 기본 설정(HA 다중 레플리카 + anti-affinity)은 CPU requests를 최소 500m으로 강제하여 비용이 크게 증가한다. Dev/Test 환경에서는 HA가 필수가 아니므로 최적화를 적용한다.

결정 (Decision) — Dev/Test 환경에만 적용

1. Anti-affinity 비활성화 (affinity: null, topologySpreadConstraints: []) → CPU 최소 500m → 50m
2. Replica 축소: Ingester/Store-gateway 3→1, Distributor/Querier 2→1
3. Zone-aware replication 비활성화 (cross-zone 트래픽 비용 절감)
4. 캐시 비활성화: Loki chunks/results cache, Tempo memcached
5. 부가 서비스 비활성화: Loki Canary, Mimir Alertmanager/Overrides Exporter/Rollout Operator

Prod 복원 시 필수 주의사항

  • affinity: null 제거 시 Helm 차트 기본 anti-affinity가 자동 적용됨
  • Anti-affinity 복원 시 CPU requests가 500m 미만이면 GKE Warden이 Pod 생성을 거부함
  • replication_factor 변경은 새로 쓰이는 데이터부터만 적용됨 (기존 데이터 replica 수 미변경)
  • 모든 최적화 지점에 [dev 환경] / [prod 환경] 인라인 주석을 추가하여 복원 시 참조

ADR-009

인프라 도구 역할 정의

Terroir 플랫폼 도구 경계 명확화 및 사용 가이드라인
◌ Proposed (검토 중)

Terraform, Helm, Kustomize, ArgoCD, KMM, Backstage, GitHub Actions, Sealed Secrets 등 다수의 인프라 도구가 도입되었으나 각 도구의 역할 경계가 불명확하여 팀 내 혼동이 발생한다. 도구별 명확한 역할 정의가 필요하다.

주요 혼란 포인트

  • Terraform과 Helm이 각각 어디까지 관리하는지 (둘 다 "선언적 인프라 관리"를 표방)
  • K8s 매니페스트가 3곳(RND-INFRA, RND-NX, terroir-manifests)에 존재하며 소유권 불명확
  • KMM, Backstage, ArgoCD 간 역할 경계
  • 시크릿 관리 도구의 현재 상태와 사용 방법
