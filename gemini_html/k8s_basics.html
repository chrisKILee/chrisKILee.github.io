쿠버네티스(k8s)란 무엇인가?

컨테이너로 만든 앱을 여러 서버에서 안정적으로 실행·관리해주는 오픈소스 플랫폼입니다. 구글이 만들고, 현재는 오픈소스 커뮤니티가 운영합니다.

💡 한 줄 요약: "컨테이너(도커)가 앱을 담는 그릇이라면, 쿠버네티스는 그 그릇들을 여러 서버에서 자동으로 배달하고 관리해주는 관제탑"입니다.

컨테이너를 쓰면 뭐가 좋나요?

쿠버네티스를 이해하려면 먼저 컨테이너의 장점을 알아야 합니다. 컨테이너는 앱과 그 앱이 필요한 모든 것(라이브러리, 설정 등)을 하나의 꾸러미로 포장한 것입니다.

⚡
빠른 배포 · 롤백
VM(가상머신)보다 훨씬 가벼워서 빠르게 앱을 올리고 내릴 수 있습니다. 문제가 생기면 이전 버전으로 즉시 되돌릴 수 있습니다.
🌍
어디서나 동일하게 실행
"내 PC에선 됐는데 서버에서는 안 돼요"를 없애줍니다. 개발 · 테스트 · 운영 환경이 동일하게 동작합니다.
🔒
앱 간 격리
각 컨테이너는 독립된 공간에서 실행되어 서로 간섭하지 않습니다. 한 앱이 죽어도 다른 앱에 영향을 주지 않습니다.
📊
자원 효율 극대화
VM처럼 OS 전체를 복사하지 않아서 훨씬 적은 CPU·메모리로 더 많은 앱을 실행할 수 있습니다.

그럼 쿠버네티스는 무엇을 해주나요?

컨테이너가 많아지면 문제가 생깁니다. "어떤 서버에서 실행하지?", "하나가 죽으면 누가 살리지?", "트래픽이 몰리면 어떻게 늘리지?". 쿠버네티스가 이 모든 것을 자동으로 처리합니다.

  1. 자동 배포 · 자동 복구
    앱이 죽으면 자동으로 다시 실행합니다. 항상 지정한 수만큼의 앱이 실행되도록 유지합니다.
  2. 자동 트래픽 분산 (로드밸런싱)
    들어오는 요청을 여러 앱 인스턴스에 골고루 분산합니다. 특정 서버에만 부하가 몰리지 않습니다.
  3. 자동 확장 · 축소 (스케일링)
    트래픽이 늘면 앱을 자동으로 더 띄우고, 줄면 다시 줄입니다. 자원 낭비를 막습니다.
  4. 시크릿 · 설정 관리
    DB 비밀번호, API 키 같은 민감 정보를 코드에 적지 않고 안전하게 관리합니다. 배포 시 컨테이너에 자동으로 주입합니다.

쿠버네티스가 하지 않는 것

쿠버네티스는 만능이 아닙니다. 아래 기능은 쿠버네티스가 직접 제공하지 않습니다.

항목설명대안
소스코드 빌드앱을 빌드하거나 배포 파이프라인을 만들지 않음Jenkins, GitHub Actions 등 CI/CD 도구 사용
DB 제공MySQL, Redis 등을 직접 제공하지 않음컨테이너로 띄우거나 외부 서비스 연동
로깅 · 모니터링로그 수집, 알림 시스템을 직접 제공하지 않음Grafana, Loki, Prometheus 등 연동
⚠️ 쿠버네티스는 강력하지만 복잡합니다. 앱이 소규모이거나 서버가 1~2대라면 오히려 과한 도구일 수 있습니다. 컨테이너 수가 많고 여러 서버에서 운영할 때 진가를 발휘합니다.
필수 용어

꼭 알아야 할 핵심 용어

쿠버네티스를 이해하려면 아래 5가지 용어를 먼저 파악해야 합니다. 문서를 읽을 때 항상 이 개념을 떠올리세요.

🎯 비유로 이해하기: 컨테이너 = 배송 박스, 파드(Pod) = 배송 카트, 노드 = 트럭, 클러스터 = 물류 센터, 컨트롤 플레인 = 관제탑

1. 파드(Pod) — 배포의 최소 단위

쿠버네티스에서 앱을 실행하는 가장 작은 단위입니다. 하나 이상의 컨테이너를 묶어서 하나의 파드로 만듭니다.

📦
파드 = 컨테이너 묶음
대부분은 컨테이너 1개 = 파드 1개입니다. 하지만 서로 의존하는 두 컨테이너(예: 앱 + 로그 수집기)는 하나의 파드로 묶을 수 있습니다.
🔄
파드는 일시적
파드는 죽으면 사라집니다. IP도 바뀝니다. 따라서 파드에 직접 접근하지 않고 서비스(Service)를 통해 접근합니다.

2. 노드(Node) — 파드가 실제로 실행되는 서버

파드가 실행되는 물리적 또는 가상 서버입니다. VM일 수도 있고, 물리 머신일 수도 있습니다. 노드 위에서 파드가 실행됩니다.

✅ 비유: 트럭(노드) 위에 배송 카트(파드)들을 실어서 운반하는 것처럼, 노드 위에서 파드들이 실행됩니다.

3. 클러스터(Cluster) — 노드들의 집합

여러 노드를 하나로 묶은 것이 클러스터입니다. 클러스터 단위로 쿠버네티스를 운영합니다. 노드가 1개여도 클러스터입니다.

4. 컨트롤 플레인 — 클러스터의 두뇌

클러스터 전체를 관리하고 결정을 내리는 컴포넌트들의 집합입니다. 보통 별도의 마스터 노드에서 실행됩니다. 사용자가 직접 건드릴 일은 거의 없지만, 모든 k8s 동작이 여기서 시작됩니다.

5. 네임스페이스(Namespace) — 클러스터 내 논리적 구역

하나의 클러스터를 여러 팀이나 환경(dev, prod 등)으로 나눌 때 사용합니다. 파드, 서비스 등 대부분의 리소스는 네임스페이스 안에 속합니다.

🏢
팀별 분리
팀A의 앱과 팀B의 앱이 같은 클러스터에 있어도 네임스페이스로 나누면 서로 간섭하지 않습니다.
🌱
환경별 분리
dev, staging, prod 네임스페이스를 따로 만들어 개발과 운영 환경을 한 클러스터에서 분리 운영할 수 있습니다.
내부 구조

클러스터 내부 컴포넌트

컨트롤 플레인과 워커 노드 안에서 실제로 어떤 프로그램들이 동작하는지 알아봅니다.

컨트롤 플레인 컴포넌트

클러스터를 관리하는 4가지 핵심 프로그램입니다. 모두 협력하여 클러스터 상태를 원하는 대로 유지합니다.

🚪
kube-apiserver
컨트롤 플레인의 문(프론트엔드). 모든 요청(kubectl 명령, 내부 컴포넌트 통신)이 여기를 통해 처리됩니다. HTTP API를 노출합니다.
🗄️
etcd
클러스터의 데이터베이스. 모든 클러스터 데이터(파드 상태, 노드 정보 등)를 저장하는 키-값 저장소입니다. 백업이 필수입니다.
📅
kube-scheduler
파드의 집(노드) 배정. 새 파드가 만들어지면 어느 노드에서 실행할지 결정합니다. CPU, 메모리 여유 공간 등을 고려합니다.
🎮
kube-controller-manager
상태 감시원. 파드 수가 맞는지, 노드가 살아있는지 등을 계속 감시하고 이상 시 복구 조치를 취합니다.

워커 노드 컴포넌트

실제로 파드가 실행되는 각 노드에는 2가지 핵심 컴포넌트가 항상 실행됩니다.

🔍
kubelet
파드 상태 감시자. 컨트롤 플레인의 지시를 받아 파드를 실행하고, 파드가 정상 동작하는지 계속 확인합니다. 쿠버네티스로 만든 컨테이너만 관리합니다.
🌐
kube-proxy
네트워크 중계자. 노드로 들어온 트래픽을 적절한 파드로 전달합니다. 쿠버네티스 서비스(Service) 개념의 실제 구현체입니다.

실행 흐름 요약

  1. 사용자가 kubectl로 파드 생성 요청
    예: kubectl apply -f pod.yaml
  2. kube-apiserver가 요청 수신 → etcd에 저장
    파드 명세(spec)를 etcd에 기록합니다.
  3. kube-scheduler가 파드를 실행할 노드 결정
    자원이 여유 있는 노드를 선택합니다.
  4. 선택된 노드의 kubelet이 파드를 실제 실행
    컨테이너 런타임(Docker 등)을 통해 파드를 시작합니다.
  5. kube-proxy가 네트워크 규칙 설정
    다른 파드나 외부에서 이 파드로 트래픽이 도달할 수 있도록 설정합니다.
오브젝트

오브젝트 & Spec이란?

쿠버네티스에서 무언가를 만들려면 "오브젝트"를 정의해야 합니다. 파드, 서비스, 디플로이먼트 모두 오브젝트입니다.

💡 오브젝트 = 의도서. "이런 상태로 유지해줘"라는 의도를 적은 문서입니다. 쿠버네티스는 이 의도에 맞게 클러스터를 계속 조정합니다.

Spec(명세)과 Status(상태)

오브젝트에는 두 가지 핵심 필드가 있습니다.

📝
spec (내가 원하는 상태)
내가 만들어 제출하는 부분입니다. "파드 2개를 nginx 이미지로 실행해줘"처럼 의도를 기술합니다.
📊
status (현재 실제 상태)
쿠버네티스가 자동으로 채우는 부분입니다. 현재 파드가 몇 개 실행 중인지 등 실제 상태를 나타냅니다.

쿠버네티스는 spec ≠ status이면 spec에 맞게 자동으로 조정합니다. 파드 2개를 원하는데 1개만 실행 중이라면 1개를 더 띄웁니다.

오브젝트 YAML 예시

오브젝트는 YAML 파일로 작성합니다. 아래는 nginx 웹서버 파드 2개를 실행하는 Deployment 예시입니다.

deployment.yaml
apiVersion: apps/v1 # 사용할 쿠버네티스 API 버전 kind: Deployment # 오브젝트 종류 (Deployment = 파드 묶음 관리자) metadata: name: nginx-deployment # 이 오브젝트의 이름 spec: replicas: 2 # 파드를 2개 실행해줘 selector: matchLabels: app: nginx # 'app=nginx' 라벨 붙은 파드를 관리 template: metadata: labels: app: nginx spec: containers: - name: nginx image: nginx:1.14.2 # 사용할 도커 이미지 ports: - containerPort: 80 # 80번 포트 오픈

오브젝트 필수 필드

필드역할예시
apiVersion사용할 API 버전 지정apps/v1, v1
kind오브젝트 종류Deployment, Pod, Service
metadata이름, 네임스페이스 등 식별 정보name: my-app
spec원하는 상태를 기술replicas: 2, image: nginx
kubectl

자주 쓰는 kubectl 명령어

kubectl은 쿠버네티스 클러스터를 조작하는 CLI 도구입니다. 마치 k8s의 리모컨과 같습니다.

조회 명령어

# 실행 중인 파드 목록 보기 kubectl get pods # 모든 네임스페이스의 파드 보기 kubectl get pods --all-namespaces # 파드 상세 정보 보기 kubectl describe pod <파드이름> # 디플로이먼트 목록 보기 kubectl get deployments # 서비스 목록 보기 kubectl get services # 노드 목록 보기 kubectl get nodes

생성 · 수정 · 삭제

# YAML 파일로 오브젝트 생성/수정 (권장) kubectl apply -f deployment.yaml # 오브젝트 삭제 kubectl delete -f deployment.yaml # 특정 오브젝트 삭제 kubectl delete pod <파드이름> kubectl delete deployment <디플로이먼트이름> # 레플리카 수 바꾸기 (스케일링) kubectl scale deployment nginx-deployment --replicas=3

디버깅 · 로그

# 파드 로그 보기 kubectl logs <파드이름> # 실시간 로그 스트리밍 kubectl logs -f <파드이름> # 실행 중인 파드에 쉘 접속 kubectl exec -it <파드이름> -- /bin/bash # 파드 이벤트 확인 (문제 원인 파악) kubectl describe pod <파드이름>
⚠️ 운영 환경에서는 kubectl delete를 신중하게 사용하세요. 파드를 지우면 k8s가 자동으로 다시 만들지만, Deployment 자체를 지우면 복구되지 않습니다.
관리 방법

오브젝트 관리 방법 3가지

쿠버네티스 오브젝트를 관리하는 방법은 3가지가 있습니다. 방법을 혼용하면 예상치 못한 동작이 생기니 한 가지만 일관되게 사용하세요.

세 가지 방법 비교

방법명령어 예시특징권장 상황
① 명령형 커맨드 kubectl create deployment nginx --image nginx 빠르고 간단. 파일 없이 즉시 생성 테스트, 일회성 작업
② 명령형 오브젝트 구성 kubectl create -f nginx.yaml 파일 기반이지만 create/replace로 관리 소규모 팀, 단순 프로젝트
③ 선언형 오브젝트 구성 kubectl apply -f nginx.yaml 파일 기반, 변경사항만 적용. GitOps에 최적 운영 환경 (권장)

왜 선언형(apply)이 권장되나요?

  1. 이미 있어도 안전하게 적용
    kubectl create는 이미 있으면 에러가 납니다. apply는 없으면 만들고, 있으면 변경된 부분만 업데이트합니다.
  2. Git으로 이력 관리 가능
    YAML 파일을 Git에 올려두면 누가 언제 무엇을 바꿨는지 추적할 수 있습니다. GitOps 방식의 기반입니다.
  3. 디렉토리 단위 일괄 적용
    kubectl apply -f ./k8s/ 처럼 폴더 전체를 한 번에 적용할 수 있습니다.
✅ 실무 팁: 운영 환경에서는 항상 YAML 파일을 Git에 관리하고 kubectl apply -f 를 사용하세요. 명령어로 직접 수정하면 파일과 실제 상태가 달라져 나중에 혼란이 생깁니다.

자주 쓰는 오브젝트 종류

🚀
Deployment
파드를 지정한 수만큼 유지해주는 관리자. 롤링 업데이트도 지원합니다.
🔗
Service
파드에 접근할 수 있는 고정된 주소를 제공합니다. 파드가 바뀌어도 주소는 유지됩니다.
⚙️
ConfigMap
환경변수나 설정 파일을 컨테이너에 주입할 때 사용합니다. 민감 정보가 아닌 일반 설정에 적합합니다.
🔑
Secret
DB 비밀번호, API 키 같은 민감 정보를 안전하게 저장하고 컨테이너에 주입합니다.
💾
PersistentVolume
파드가 삭제되어도 데이터를 유지하는 스토리지를 제공합니다. DB 데이터 보관에 필수입니다.
🌐
Ingress
외부 HTTP 트래픽을 클러스터 내 서비스로 라우팅합니다. 도메인별, 경로별 분기가 가능합니다.
