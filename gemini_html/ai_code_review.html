01

왜 코드 리뷰는 실패하는가

AI가 코드 작성 속도를 폭발적으로 높였지만, 리뷰 방식은 인간 속도에 머물러 있다.

원래부터 한계가 있었다
코드 리뷰는 2012~2014년에야 보편화됐다
많은 엔지니어링 조직이 이미 엉성한 리뷰를 운영하고 있었다. PR은 며칠씩 대기하고, 리뷰어는 형식적으로 승인(rubber stamp)하거나 500줄 diff를 대충 훑었다. 품질 게이트라 불렸지만 실질적 역할은 제한적이었다.
AI 도입이 폭발시킨 규모
변경의 수와 크기, 두 가지가 동시에 지수 증가
AI 도입 팀은 PR을 98% 더 많이 병합한다. 그런데 각 PR의 크기도 커졌다. 리뷰어가 소화해야 할 코드 총량이 기하급수적으로 늘어난 반면, 리뷰에 할당할 수 있는 인간의 시간은 늘지 않았다. 결과: 리뷰 시간 91% 증가.

"AI 생성 코드를 리뷰하는 것이 동료가 직접 작성한 코드를 리뷰하는 것보다 더 많은 노력이 필요하다."

— 개발자들의 공통된 체감
02

코드 리뷰에서 의도(Intent) 리뷰로

인간의 검증 지점을 상류(upstream)로 옮기자는 제안. 구현이 아닌 의도를 리뷰한다.

핵심 전환은 인간의 검증 시점을 '코드 작성 이후'에서 '코드 작성 이전'으로 옮기는 것이다. 스펙(Spec), 수용 기준(Acceptance Criteria), 행동 기반 시나리오(BDD)를 먼저 인간이 확정하고, 그 이후의 구현·검증은 에이전트와 자동화에 위임한다.

03

다층 신뢰 구조 — 스위스 치즈 모델

단일 리뷰 레이어 대신 여러 겹의 방어 계층으로 품질을 보장한다. 각 계층이 서로 다른 결함을 잡는다.

1
다중 에이전트 경쟁 (Multi-agent competition)
하나의 에이전트에게 완벽을 요구하는 대신, 세 개의 에이전트가 각각 다르게 구현을 시도한다. 검증 통과 수, diff 크기, 신규 의존성 추가 여부 등의 기준으로 최선을 선택한다.
2
결정론적 가드레일 (Deterministic guardrails)
테스트, 타입 체크, 계약 검증(contract validation) 같은 객관적 기준이 협상 불가능한 최저선을 만든다. 4가지 검증 계층: 코딩 가이드라인 린터 → 조직 전반 불변성 → 도메인 계약 → 수용 기준.
3
BDD 기반 수용 기준 (Behaviour-driven acceptance)
인간이 Given / When / Then 형식으로 기대 행동을 먼저 정의한다. 에이전트는 이 기준을 충족하는 구현을 만들고, 자동으로 테스트가 검증한다. 스펙을 신뢰하되, 에이전트가 스펙을 자동 검증하는 것도 맹신하지 않는다.
4
권한 시스템 (Permission architecture)
에이전트의 접근 범위를 최소화한다. 날짜 파싱 버그 수정 → utils/dates.py와 관련 테스트 파일만 접근 허용. 인증 로직 수정, DB 스키마 변경 등은 자동으로 에스컬레이션(인간 승인 요청).
5
적대적 검증 (Adversarial verification)
구현 에이전트와 검증 에이전트를 분리한다. 서로 신뢰하지 않도록 설계상 격리. 세 번째 에이전트는 엣지 케이스로 공격한다. 공모(collusion) 방지가 핵심이다.
04

기존 방식 vs 새로운 방식

두 패러다임의 핵심 차이를 직접 비교한다.

항목 기존 코드 리뷰 의도 기반 리뷰
인간 개입 시점 코드 작성 이후 (사후) 스펙·수용 기준 단계 (사전)
리뷰 대상 구현 코드 (500줄 diff) 의도, BDD 시나리오, 설계 결정
품질 보증 방법 리뷰어의 주관적 판단 결정론적 테스트 + 다중 에이전트
실패 대응 느린 리뷰 → 프로덕션 디버깅 빠른 배포 + 모든 것 관찰 + 빠른 롤백
AI 코드 스케일 리뷰 시간 91% 증가 (병목) 자동화 계층이 흡수
코드 가독성 중요도 높음 (인간이 읽어야 함) 낮음 (기계가 처리, 행동이 중요)
05

BDD로 보는 의도 명세 예시

행동 주도 개발(BDD, Behaviour-Driven Development)은 1990년대에 나온 방법론으로, AI 시대에 다시 주목받고 있다. 인간이 기대 행동을 먼저 정의하고 에이전트가 그것을 구현한다. 

// 인간이 작성하는 수용 기준 (BDD 형식)
Feature: 사용자 로그인

  Scenario: 유효한 자격증명으로 로그인
    Given 등록된 사용자 "user@example.com"이 있다
    When  비밀번호 "correct-password"로 로그인 시도한다
    Then  대시보드 페이지로 이동해야 한다
    And   세션 토큰이 발급되어야 한다

  Scenario: 잘못된 비밀번호로 로그인 시도
    Given 등록된 사용자 "user@example.com"이 있다
    When  비밀번호 "wrong-password"로 로그인 시도한다
    Then  "잘못된 자격증명" 에러 메시지가 표시되어야 한다
    And   세션 토큰이 발급되지 않아야 한다

이 명세서가 인간의 리뷰 대상이 된다. 에이전트는 이 기준을 충족하는 코드를 작성하고, 자동화 테스트가 통과 여부를 검증한다. 인간은 구현 세부사항이 아닌 의도의 정확성을 확인한다.

핵심 인사이트 정리

"기계를 능가하는 것은 불가능하다. 우리는 기계보다 앞에서 생각해야 한다 — 결정이 실제로 중요한 상류에서."

— Ankit Jain, Aviator CEO
유효한 주장
리뷰 병목은 실재하는 문제다
AI 도입으로 PR 수·크기가 폭발했는데 리뷰 방식이 그대로라면 병목은 필연적이다. 의도 상류화, BDD, 자동 가드레일은 방향성 있는 대안이다.
남은 과제
조직 문화와 전환 비용
BDD 작성 훈련, 에이전트 권한 설계, 적대적 검증 인프라 구축 모두 초기 투자가 필요하다. 기존 코드베이스와의 호환성, 규제 업종의 감사(audit) 요건도 해결 과제다.

이 논의의 진짜 가치는 "코드 리뷰를 없애야 하는가"가 아니라, AI 시대에 인간이 어느 지점에서 가장 효과적으로 개입할 수 있는가를 다시 묻게 만든다는 데 있다. 코드의 줄을 읽는 것이 아니라 의도의 정확성을 판단하는 쪽으로 인간의 역할이 이동하고 있다.
