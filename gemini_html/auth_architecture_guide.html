1 개요

본 문서는 웹 서비스의 인증 아키텍처를 세 단계로 정리하고, 2026년 기준 Keycloak1 26.5의 최신 보안 표준(PKCE2, DPoP3, Passkeys4, OpenTelemetry5)을 반영한 Production-Ready 가이드입니다.

단계 1: ID/PW 직접 인증

가장 단순한 인증 방식 · MVP 단계에 적합

가장 단순한 인증 방식으로, 서비스 서버가 직접 ID/PW를 수신하고 DB에서 검증한 후 인증 결과를 반환합니다.

2.1 인증 흐름

[그림 1: ID/PW 직접 인증 흐름]

단계FromTo설명
①BrowserService ServerID/PW 전송 (HTTPS POST)
②Service ServerUser DB사용자 조회 및 비밀번호 검증 (bcrypt10 비교)

2.2 특징 및 한계

단계 2: Google OpenID Connect + PKCE

인증을 Google에 위임 · 코드 탈취 공격 방어

Authorization Code Flow에 PKCE(Proof Key for Code Exchange)를 적용하여 코드 가로채기 공격을 방어합니다. 2026년 현재 모든 OIDC 클라이언트(SPA 포함)에서 PKCE(S256) 적용이 필수입니다.

3.1 인증 흐름 (PKCE 포함)

[그림 2: Google OIDC + PKCE 인증 흐름]

단계FromTo설명
①BrowserService Server로그인 요청
PKCEService Server—code_verifier 생성 → SHA256 해시로 code_challenge 생성
②Service ServerBrowserGoogle Auth URL redirect (code_challenge + S256 포함)
③BrowserGoogle AuthGoogle 로그인 화면에서 ID/PW 입력
④Google AuthBrowserAuthorization Code + redirect_uri로 리다이렉트
⑤BrowserService ServerAuthorization Code 전달
⑥Service ServerGoogle AuthCode + code_verifier로 Token 교환 (B2B)
⑦Google AuthService Servercode_verifier 검증 후 ID Token + Access Token 발급
⑧Service ServerBrowser사용자 확인/생성 후 서비스 자체 JWT 발급

3.2 PKCE가 필요한 이유

Authorization Code는 Browser의 redirect를 통해 전달되므로 중간자가 탈취할 수 있습니다. PKCE는 요청 시점에 code_challenge를 보내고, Token 교환 시점에 원본 code_verifier를 보내 두 값을 대조함으로써, 탈취된 코드로는 토큰을 발급받을 수 없게 만듭니다.

  • code_verifier: 클라이언트가 생성하는 임의의 문자열 (43~128자)
  • code_challenge: code_verifier의 SHA256 해시 (S256 방식)
  • 공격자가 Authorization Code를 탈취해도 code_verifier를 모르면 Token 교환 불가
핵심 포인트: PKCE는 코드 탈취 공격에 대한 방어막입니다. 2026년 현재 모든 OIDC 클라이언트(SPA 포함)에서 PKCE(S256) 적용이 필수화되었습니다.

단계 3: Keycloak + Google (Identity Brokering + SSO)

여러 서비스에서 한 번의 로그인으로 접근 · 토큰 바인딩

Keycloak이 중간에 위치하여 Google 인증을 중개(Identity Brokering)하고, 모든 서비스가 Keycloak의 토큰을 공유하여 SSO를 실현합니다. 모든 OIDC Client는 PKCE(S256)를 필수로 적용하며, DPoP를 통해 토큰 바인딩을 강화합니다.

4.1 전체 인증 흐름

[그림 3: Keycloak + Google SSO 전체 흐름 (PKCE + DPoP)]

단계FromTo설명
①BrowserService AService A 접근 (미인증 상태)
②Service AKeycloakKeycloak redirect + PKCE code_challenge(S256)
③KeycloakGoogle AuthGoogle 로그인으로 redirect (Identity Brokering)
④Google Auth—사용자가 Google에서 ID/PW 입력 및 인증
⑤Google AuthKeycloakAuthorization Code 반환
⑥KeycloakGoogle AuthCode → Token 교환 (B2B, server-to-server)
⑦Keycloak—Keycloak 내부에서 세션 생성 + 사용자 매핑 (Persistent Sessions)
⑧KeycloakService ACode + code_verifier → Keycloak Token 교환
⑨Service ABrowserKeycloak 발급 JWT + DPoP 바인딩으로 인증 완료

4.2 SSO 흐름 (Service B 접근)

Service A에서 이미 인증된 상태에서 Service B에 접근하는 경우입니다.

단계FromTo설명
⑩BrowserService BService B 접근 (미인증 상태)
⑪Service BKeycloakKeycloak으로 redirect
⑫Keycloak—기존 Persistent Session 확인 → 이미 인증됨!
⑬KeycloakBrowserGoogle 재인증 없이 즉시 Token 발급 → 인증 완료
핵심: ⑫번이 SSO의 핵심입니다. Keycloak 26.5의 Persistent Sessions(DB 기반 세션 유지)로 서버 재시작 시에도 세션이 유지됩니다.

5 Keycloak의 핵심 역할

5.1 Identity Brokering

Google OIDC 연동을 Keycloak이 한 번만 구현하면, 개별 서비스들은 Google을 알 필요가 없습니다. 서비스 입장에서 Keycloak이 곧 인증 서버입니다.

  • Apple, Kakao 등 새로운 IdP12 추가 시 Keycloak 설정만 변경, 서비스 코드 변경 불필요
  • IdP 추가/변경이 운영 설정 수준으로 단순화

5.2 Single Sign-On (SSO)

Keycloak에 세션 쿠키가 생성되면, 이후 다른 서비스 접근 시 Google 재인증 없이 즉시 토큰을 발급합니다. Keycloak 26.5의 Persistent Sessions로 서버 재시작/장애 시에도 세션이 유지됩니다.

5.3 토큰 흐름 구조

토큰 발행자소비자설명
GoogleKeycloakGoogle이 발급한 토큰은 Keycloak만 소비
KeycloakService A / B / ...Keycloak JWT + DPoP 바인딩으로 서비스에 전달
서비스 입장에서는 2단계와 거의 동일한 코드 구조이며, 인증 서버 URL만 Google에서 Keycloak으로 바뀌는 것입니다.

6 2026년 최신 보안 강화 사항 (Keycloak 26.5 기준)

6.1 PKCE (Proof Key for Code Exchange)

Authorization Code Flow 사용 시 모든 웹 서비스(SPA 포함)에서 PKCE(S256) 적용이 필수화되었습니다. 코드 가로채기 공격을 방어하는 핵심 보안 레이어입니다.

  • Keycloak 설정: Client → Settings → "PKCE Code Challenge Method" → S256 선택
  • 모든 Confidential/Public Client에 일괄 적용 권고
  • Keycloak Client Policy로 PKCE 강제 정책 설정 가능

6.2 DPoP (Demonstrating Proof-of-Possession)

DPoP는 토큰이 탈취되더라도 다른 클라이언트에서 사용할 수 없도록 토큰을 클라이언트의 공개키에 바인딩하는 메커니즘입니다. Keycloak 26.5에서 정식 지원됩니다.

  • Bearer Token 대비 토큰 탈취 시 재사용 불가 (Proof-of-Possession)
  • FAPI 2.013 컴플라이언스 요구사항
  • Keycloak의 Admin REST API, Account REST API에서도 DPoP 토큰 처리 가능

6.3 WebAuthn / Passkeys

Keycloak 26.5는 로그인 폼에 Passkeys를 네이티브로 통합합니다. 비밀번호 없는(Passwordless) 환경을 구축하여 사용자 경험을 극대화합니다.

  • Authentication → Policies → Webauthn Passwordless Policy → Enable Passkeys 활성화
  • Conditional UI와 Modal UI 모두 지원 — 사용자 디바이스의 생체 인증 활용
  • Google 소셜 로그인과 병행 운용 가능 — 사용자가 선택

6.4 Keycloak Organizations (B2B/SaaS)

Keycloak 26.x의 Native Organizations 기능은 기업 고객 대상 SaaS 서비스에서 조직별 독립된 인증 정책을 설정할 수 있게 해줍니다.

  • 각 Organization별 고유한 IdP, 로그인 방식, 관리자 지정
  • Organization 초대 및 멤버십 관리 (Admin Console + REST API)
  • 테넌트 격리와 사용자 권한 정책의 중앙화에 유용

6.5 Quarkus14 기반 런타임

Keycloak은 기존 Wildfly에서 Quarkus 기반으로 완전히 전환되었습니다. 컨테이너 환경(Kubernetes)에서의 배포에 최적화되어 있습니다.

  • 빠른 기동 속도 + 낮은 메모리 점유율 — K8s HPA15 스케일링에 적합
  • Rolling Update 시 동일 버전 이미지 간 무중단 배포 지원
  • Optimized Image 빌드로 프로덕션 성능 최적화

6.6 OpenTelemetry 모니터링

Keycloak 26.5는 OpenTelemetry를 통해 Metrics, Traces, Logs를 통합 관측할 수 있습니다. 인증 단계별 병목, 토큰 발급 실패, 세션 만료 등을 실시간으로 모니터링할 수 있습니다.

  • telemetry-endpoint, telemetry-protocol, telemetry-service-name으로 중앙 설정
  • Jaeger, Grafana Tempo 등 보편적인 APM 툴과 연동
  • 인증 흐름 전체를 trace로 추적하여 병목 구간 식별 가능

7 각 서비스의 구현 사항

7.1 서비스 측 설정

  1. OIDC Client 등록: Keycloak을 OIDC Provider로 등록, PKCE(S256) 필수 설정
  2. Redirect URI 설정: 각 서비스의 callback URL을 Keycloak에 등록
  3. Token 검증: JWKS16 endpoint에서 공개키 캐싱 + DPoP 토큰 검증 구현
  4. DPoP 적용: API 요청 시 DPoP Proof JWT를 함께 전송, 서버에서 바인딩 검증

7.2 Keycloak 측 설정

  1. Realm17 생성: 조직/환경 단위로 Realm 구성
  2. Identity Provider: Google을 IdP로 등록 (client_id, client_secret)
  3. Client 등록: 각 서비스를 Client로 등록, PKCE(S256) 강제
  4. Client Policy: PKCE + DPoP 강제 정책 설정 (fapi-2-dpop-security-profile)
  5. Passkeys: Authentication → Policies → Webauthn Passwordless → Enable Passkeys
  6. Organizations: B2B 서비스 시 조직별 IdP/정책 설정
  7. OpenTelemetry: telemetry-endpoint 설정으로 Jaeger/Tempo 연동
  8. Persistent Sessions: DB 기반 세션 저장으로 장애 시 세션 유지

9 결론

세 가지 인증 방식은 서비스의 규모와 요구사항에 따라 선택할 수 있습니다.

  • 단일 서비스, 빠른 MVP: ID/PW 직접 인증으로 충분
  • 단일 서비스, 소셜 로그인: Google OIDC + PKCE 직접 연동
  • 다중 서비스, SSO + 보안 강화: Keycloak + PKCE + DPoP + Passkeys + OpenTelemetry
Keycloak 26.5를 도입하면 인증 제공자 추가, 사용자 관리, 권한 정책, 세션 관리, 토큰 보안, 모니터링까지 중앙에서 통제할 수 있으며, 각 서비스는 Keycloak의 OIDC 클라이언트로서만 동작하면 됩니다. PKCE와 DPoP를 통해 FAPI 2.0 수준의 보안을 확보하고, Passkeys로 사용자 경험을 극대화하며, OpenTelemetry로 인증 흐름 전체를 가시화할 수 있습니다.

? 각주 — 용어 설명

  • 1 Keycloak: Red Hat이 개발한 오픈소스 Identity and Access Management(IAM) 솔루션. SSO, OIDC, SAML 등을 지원하며 기업 환경에서 널리 사용됩니다.
  • 2 PKCE (Proof Key for Code Exchange): Authorization Code를 브라우저에서 주고받을 때 중간 탈취를 막기 위한 보안 메커니즘. 먼저 code_verifier 해시(challenge)를 서버에 보내고, 나중에 원본(verifier)을 검증합니다.
  • 3 DPoP (Demonstrating Proof-of-Possession): 토큰을 특정 클라이언트의 공개키에 묶어두는 메커니즘. Bearer Token과 달리, 탈취된 토큰은 원래 클라이언트의 개인키 없이는 사용할 수 없습니다.
  • 4 Passkeys: 비밀번호 없이 생체 인증(지문, 얼굴 인식)이나 디바이스 PIN으로 로그인하는 기술. WebAuthn 표준 기반이며 피싱 공격에 면역입니다.
  • 5 OpenTelemetry: 애플리케이션의 로그, 메트릭, 트레이스를 수집·관측하는 오픈소스 표준. Jaeger, Grafana 등과 연동됩니다.
  • 6 OIDC (OpenID Connect): OAuth 2.0 위에 사용자 인증 레이어를 추가한 프로토콜. "이 사용자가 누구인지" 확인하는 표준 방법입니다.
  • 7 Identity Brokering: Keycloak이 외부 IdP(Google 등)와의 인증을 대신 처리해주는 기능. 서비스는 Keycloak만 알면 됩니다.
  • 8 SSO (Single Sign-On): 한 번 로그인하면 여러 서비스에 추가 인증 없이 접근할 수 있는 방식입니다.
  • 9 WebAuthn: W3C 표준 웹 인증 API. 하드웨어 보안 키나 생체 인증으로 로그인하는 기술의 기반입니다.
  • 10 bcrypt: 비밀번호를 안전하게 해시하는 알고리즘. 단방향(복호화 불가)이며 무차별 대입 공격에 강합니다.
  • 11 JWT (JSON Web Token): JSON 형식으로 사용자 정보를 담아 서명한 토큰. 서버가 세션을 저장하지 않아도 되는 Stateless 인증에 사용됩니다.
  • 12 IdP (Identity Provider): 사용자 신원을 확인하고 인증 정보를 제공하는 서비스. Google, Apple, Kakao 등이 대표적입니다.
  • 13 FAPI 2.0: Financial-grade API Security Profile. 금융 등 높은 보안이 요구되는 API를 위한 OAuth 2.0 보안 프로파일입니다.
  • 14 Quarkus: Red Hat이 만든 Kubernetes-Native Java 프레임워크. 빠른 기동 시간과 낮은 메모리 사용량이 특징입니다.
  • 15 HPA (Horizontal Pod Autoscaler): Kubernetes에서 부하에 따라 자동으로 Pod 수를 늘리거나 줄이는 기능입니다.
  • 16 JWKS (JSON Web Key Set): JWT 서명 검증에 사용하는 공개키 묶음. 서버가 공개적으로 제공하며, 클라이언트는 이를 캐싱하여 토큰을 검증합니다.
  • 17 Realm: Keycloak에서 독립된 인증 도메인. 다른 Realm 간에는 사용자, 세션, 설정이 분리됩니다.
