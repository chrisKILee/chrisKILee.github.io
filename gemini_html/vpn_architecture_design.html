1 Executive Summary

본 문서는 VNTG의 IDC에서 GCP1(Google Cloud Platform)로의 네트워크 연결 아키텍처를 설계하기 위한 제안서이다. 핵심 결정 사항은 VPN 구성을 Dev/Prod로 분리할 것인지, 단일 VPN으로 통합할 것인지에 대한 것이며, 다양한 관점에서의 분석을 통해 최적의 아키텍처를 제안한다.

GCP 측 K8s2 클러스터는 서비스용 Dev/Prod 클러스터와 인프라용(IDP, ArgoCD3, LGTM4 Stack) 클러스터의 3개로 구성되며, Infra 클러스터가 Dev/Prod 양쪽에 접근해야 하는 Cross-Cutting 특성을 가진다.

✅ 최종 결론

단일 HA VPN5 + Infra VPC6 Hub-and-Spoke7 구조를 권장한다.
Infra 클러스터의 Cross-Cutting 성격, 운영 복잡도, 비용 효율성, 그리고 보안 관제의 중앙화 관점에서 가장 합리적인 선택이다.

3 Architecture Design

3.1 VPC Topology: Hub-and-Spoke

GCP 측 VPC는 3개로 분리하되, Infra VPC를 Hub로 두고 Dev/Prod VPC를 Spoke로 연결하는 Hub-and-Spoke 구조를 채택한다. IDC에서의 VPN은 Infra VPC에 단일 랜딩하며, Dev/Prod VPC로의 접근은 Infra VPC를 경유한다.

[Figure 1] GCP VPC Topology — Hub-and-Spoke Architecture

VPC 간 연결 방식: Peering + Custom Route Export

GCP VPC Peering8은 기본적으로 transitive routing9을 지원하지 않으나, Custom Routes Export/Import 옵션을 활성화하면 Peering만으로 transitive routing이 가능해진다. Infra VPC의 Peering 설정에서 'Export custom routes'를 켜고, Dev/Prod VPC의 Peering 설정에서 'Import custom routes'를 켜면, Infra VPC가 VPN을 통해 학습한 IDC 대역 경로가 Dev/Prod VPC로 전파된다.

이 구성에서 VPC 간 별도의 HA VPN 터널은 불필요하며, Peering + Custom Route Export만으로 IDC → Infra VPC → Dev/Prod VPC 경로가 완성된다. Dev VPC와 Prod VPC 사이에는 Peering을 생성하지 않아 상호 격리를 보장한다.

3.2 Traffic Flow Patterns

IDC에서 GCP로 향하는 트래픽은 크게 4가지 유형으로 분류되며, 모든 트래픽은 Infra VPC를 관문으로 통과한다. GCP 내부 트래픽(ArgoCD 배포 등)은 VPN을 경유하지 않는다.

4 VPN Design: Single HA VPN

4.1 HA VPN 구성

IDC ↔ GCP 간 VPN은 GCP HA VPN을 사용하며, IDC 측 VPN 장비 2대와 GCP HA VPN Gateway의 2개 인터페이스를 Full Mesh로 연결하여 총 4개 터널을 구성한다. BGP10(Border Gateway Protocol)를 통한 동적 라우팅으로 자동 failover를 보장한다.

4.2 VPC Peering 구성 (GCP 내부)

Infra VPC에서 Dev/Prod VPC로의 연결은 VPC Peering에 Custom Routes Export/Import를 활성화하여 구성한다. 별도의 VPC 간 HA VPN 터널은 불필요하며, Peering만으로 IDC에서 출발한 트래픽이 Infra VPC를 경유하여 Dev/Prod VPC까지 도달할 수 있다.

PeeringInfra VPC SideTarget VPC SideRoute Behavior
Infra → DevExport custom routes: ONImport custom routes: ONIDC routes propagated to Dev VPC
Infra → ProdExport custom routes: ONImport custom routes: ONIDC routes propagated to Prod VPC
Dev ↔ ProdN/AN/ANo Peering (Isolated)

4.3 VPN 분리 vs 단일 VPN 비교

아래 표는 두 옵션의 상세 비교이다. Infra 클러스터의 Cross-Cutting 성격을 고려하면, VPN 분리 시 사실상 3개의 VPN이 필요하게 되어 운영 복잡도가 크게 증가한다.

CriteriaOption A: VPN SeparationOption B: Single HA VPN 권장
VPN Tunnels3 sets (Infra, Dev, Prod)1 set (IDC ↔ Infra VPC)
Operational ComplexityHigh (3x monitoring, routing tables)Medium (single management point)
Network IsolationPhysical separationLogical separation (firewall-enforced)
Infra AccessRequires additional VPN or complex routingDirect (natural Hub connectivity)
Cost3 VPN Gateways + tunnel costs1 VPN Gateway + VPC Peering
Failure Blast RadiusIsolated per VPNInfra VPC as SPOF12 (mitigated by VPN HA)
Security AuditPhysical separation evidenceLogical separation + centralized logging
Central Monitoring3 monitoring pointsSingle gateway (Cloud IDS13, VPC Flow Logs)

5 LGTM Observability Traffic Analysis

IDC에서 GCP Infra 클러스터의 LGTM Stack(Loki, Grafana, Tempo, Mimir)으로 전송되는 Observability 트래픽은 주요 VPN 사용 트래픽 중 하나이다. 이 트래픽은 Infra VPC로 직접 도달하므로 Hub 구조와 완벽히 부합한다.

5.1 트래픽 볼륨 추정

Metrics (Mimir14)Prometheus remote_write~Mbps~MbpsMinimal
Logs (Loki15)Alloy / Promtail13~67 Mbps5~35 MbpsLow
Traces (Tempo16)Alloy (1~5% sampling)~Mbps~MbpsMinimal
전체 LGTM 트래픽을 합산해도 수십 Mbps 수준이며, HA VPN 6Gbps 대비 1~2%에 불과하다. 장애 시 에러 로그 폭증으로 순간 버스트(10~50배)가 발생할 수 있으나, 이 경우에도 HA VPN 대역폭 내에서 충분히 수용 가능하다.

5.2 안정성 확보 방안

LGTM 트래픽의 안정성은 VPN 이중화보다 에이전트 레벨의 내구성이 더 중요하다. Grafana Alloy17는 WAL(Write-Ahead Log)18을 지원하여 네트워크 단절 시 로컬 버퍼링 후 복구 시 재전송한다. Promtail19은 positions 파일로 마지막 읽기 위치를 기록하여 재시작 시 이어서 전송한다.

로그/메트릭은 실시간 API 호출이 아닌 배치성 push이므로 VPN 레이턴시 변동에 민감하지 않으며, Dev 트래픽과의 QoS 경합도 실질적 우려 사항이 아니다.

6 Kafka Data Pipeline Traffic Analysis

향후 IDC Kafka에서 GCP로의 데이터 파이프라인이 구성될 예정이다. Kafka 파이프라인은 로그/메트릭과 달리 비즈니스 데이터를 전송하며, 볼륨 예측이 어렵고 서비스 성장에 비례하여 증가하는 특성이 있다.

6.2 권장 아키텍처

GCP Infra 클러스터에 Kafka Connect를 배치하고 IDC Kafka를 Source로 consume하는 패턴을 권장한다. 트래픽 방향은 IDC → GCP이며, Infra VPC로 직접 들어오므로 Hub 구조와 자연스럽게 맞는다.

데이터 최종 적재지가 BigQuery, GCS 등 GCP 매니지드 서비스인 경우, Infra VPC의 Kafka Connect에서 GCP 내부 네트워크로 직접 쓰므로 VPN 부하와 무관하다. VPN을 타는 구간은 IDC Kafka → GCP Infra VPC 한 구간뿐이다.

7 Security Considerations

7.1 중앙 관문 보안

단일 VPN + Hub 구조에서는 모든 IDC ↔ GCP 트래픽이 Infra VPC를 통과하므로, 이 지점에 보안 관제를 집중할 수 있다. Cloud IDS(Intrusion Detection System)와 VPC Flow Logs22를 Infra VPC에 배치하여 전체 트래픽에 대한 가시성을 확보한다.

7.2 환경 격리

Dev VPC와 Prod VPC 간 직접 Peering을 두지 않아 상호 접근이 원천 차단된다. Infra VPC에서 Dev/Prod VPC로의 접근은 VPC Peering을 통해 이루어지며, 각 VPC의 방화벽 규칙으로 필요한 포트/프로토콜만 허용한다.

개발 환경의 misconfiguration이나 보안 사고가 운영 환경으로 전파되는 것을 원천 차단합니다.

7.3 규제 요건 확인

VNTG의 사업 도메인에 따라 물리적 네트워크 분리를 요구하는 규제가 있는지 확인이 필요하다. 금융권 일부 규정에서는 운영망과 개발망의 물리적 분리를 명시하는 경우가 있으며, 이 경우에는 VPN 분리가 필수적일 수 있다.

현재 구조에서는 논리적 분리 + 방화벽 정책으로 충분한 보안 수준을 제공하며, 대부분의 보안 감사 기준을 충족하지만, 규제 요건 확인은 별도로 필요합니다.

8 Conclusion & Recommendations

✅ 8.1 Architecture Decision

Single HA VPN + Infra VPC Hub-and-Spoke 구조를 최종 권장한다.

8.2 근거 요약

  1. Infra 클러스터의 Cross-Cutting 성격: ArgoCD, IDP, LGTM이 Dev/Prod 모두에 접근하는 구조에서 Hub가 자연스럽다.
  2. 운영 복잡도: VPN 분리 시 3개 터널 세트 운영이 필요하며, 복잡한 네트워크는 그 자체가 보안 리스크이다.
  3. 대역폭 충분: LGTM + Kafka 초기/중기 트래픽 합산이 HA VPN 6Gbps 대비 충분한 여유가 있다.
  4. 보안 관제 중앙화: 단일 관문에 Cloud IDS, VPC Flow Logs 집중 배치로 효과적 모니터링이 가능하다.
  5. 확장 경로 명확: 대역폭 한계 도달 시 VPN 분리가 아닌 Cloud Interconnect 전환으로 대응한다.

8.3 필수 후속 조치

  • IDC 측 VPN 장비 이중화 확인 및 구성
  • VPN 터널 throughput 모니터링 대시보드 구축 (70% threshold alert)
  • Infra VPC 방화벽 규칙 및 VPC Peering Custom Route Export/Import 설정
  • Grafana Alloy WAL 설정 및 버퍼 크기 산정
  • VNTG 사업 도메인 기반 규제 요건 확인 (물리적 분리 요구 여부)
  • Cloud Interconnect 전환 시점 사전 계획 수립 (Kafka 볼륨 성장 추이 기반)

? 각주 — 용어 설명

  • 1 GCP (Google Cloud Platform): Google이 제공하는 클라우드 컴퓨팅 서비스. Compute Engine, GKE, BigQuery 등 다양한 서비스를 포함합니다.
  • 2 K8s (Kubernetes): 컨테이너 오케스트레이션 시스템. 컨테이너화된 애플리케이션의 배포, 확장, 관리를 자동화합니다.
  • 3 ArgoCD: Kubernetes용 GitOps 기반 지속적 배포(CD) 도구. Git 저장소를 단일 진실 공급원으로 사용하여 앱을 배포합니다.
  • 4 LGTM Stack: Loki(로그), Grafana(시각화), Tempo(트레이스), Mimir(메트릭)을 합친 통합 관측 스택입니다.
  • 5 HA VPN (High Availability VPN): Google Cloud의 고가용성 VPN 서비스. 2개의 VPN 게이트웨이 인터페이스와 4개 터널로 99.99% SLA를 보장합니다.
  • 6 VPC (Virtual Private Cloud): 클라우드 내에서 논리적으로 격리된 가상 네트워크입니다.
  • 7 Hub-and-Spoke: 중앙 허브(Hub)를 통해 여러 스포크(Spoke)가 연결되는 네트워크 토폴로지. 모든 트래픽이 Hub를 경유합니다.
  • 8 VPC Peering: 서로 다른 VPC 네트워크 간에 내부 IP 주소로 통신할 수 있도록 하는 GCP 기능입니다.
  • 9 Transitive Routing: A → B → C로 경유하는 라우팅. GCP Peering은 기본적으로 지원하지 않지만, Custom Route Export/Import로 가능하게 할 수 있습니다.
  • 10 BGP (Border Gateway Protocol): 인터넷에서 라우팅 정보를 교환하는 동적 라우팅 프로토콜. VPN 장애 시 자동으로 다른 경로로 전환합니다.
  • 11 IPsec IKEv2: VPN 터널을 암호화하는 인터넷 보안 프로토콜의 최신 버전. 빠른 연결 복구가 특징입니다.
  • 12 SPOF (Single Point of Failure): 장애 발생 시 전체 시스템에 영향을 주는 단일 취약점. HA VPN으로 이 위험을 완화합니다.
  • 13 Cloud IDS: Google Cloud의 네트워크 침입 탐지 서비스. 네트워크 트래픽에서 위협을 자동으로 감지합니다.
  • 14 Mimir: Grafana Labs의 오픈소스 Prometheus 메트릭 장기 저장 및 쿼리 시스템입니다.
  • 15 Loki: Grafana Labs의 로그 집계 시스템. Prometheus에서 영감받은 레이블 기반 로그 저장 방식을 사용합니다.
  • 16 Tempo: Grafana Labs의 분산 트레이싱 백엔드. 저렴한 비용으로 대규모 트레이스를 저장합니다.
  • 17 Grafana Alloy: Grafana Labs의 OpenTelemetry 기반 통합 수집 에이전트. 로그, 메트릭, 트레이스를 한 번에 수집합니다.
  • 18 WAL (Write-Ahead Log): 데이터를 실제 저장하기 전에 로컬에 먼저 기록하는 방식. 네트워크 단절 시에도 데이터를 잃지 않습니다.
  • 19 Promtail: Loki용 로그 수집 에이전트. 파일 시스템의 로그를 읽어 Loki로 전송합니다.
  • 20 MirrorMaker2: Kafka 클러스터 간 토픽을 복제하는 도구. 데이터센터 간 재해 복구에 사용됩니다.
  • 21 Cloud Interconnect: IDC와 GCP를 전용 물리 회선으로 연결하는 서비스. 10Gbps 또는 100Gbps의 고대역폭을 제공합니다.
  • 22 VPC Flow Logs: VPC 네트워크의 모든 트래픽 흐름을 기록하는 GCP 기능. 보안 분석 및 이상 탐지에 활용됩니다.
