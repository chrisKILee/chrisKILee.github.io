Claude 세션 간 Context Handoff
맥락을 잃지 않는 4계층 전략

Context rot, Auto-compact 비대칭성, Context amnesia — 세션이 끝날 때마다 증발하는 맥락을 체계적으로 보존하는 4계층 전략.

출처 · Toby's Codex 원문 작성 · 2026-04-23 조회 · 1,800

개요

어제 두 시간에 걸쳐 OAuth refresh 로직을 뜯어봤다. 세 가지 접근을 시도해서 두 개는 폐기하고, 세 번째로 방향을 잡은 참이었다. 오늘 아침 새 세션을 열고 "어제 이어서 하자"고 말했더니 Claude는 당연히 아무것도 모른다. 폐기했던 첫 번째 접근을 다시 제안한다.

Context window가 200K에서 1M으로 늘어났지만 이 문제는 사라지지 않았다. 오히려 한 세션 안에 더 많은 것을 쌓을 수 있게 되면서 세션이 끝났을 때 잃는 것도 더 많아졌다. 어제의 결정, 실패한 가설, 미묘한 제약 조건이 모두 증발한다.

이 글의 목적 Claude Code 공식 문서, Anthropic 엔지니어링 블로그, 커뮤니티 실전 사례를 종합해 언제 무엇을 써야 하는가를 네 계층으로 정리한다. 단일 세션 내 품질 유지 → 세션 전환 시 상태 보존 → 결정과 근거의 영구화까지 세 문제를 동시에 다룬다.

문제의 3층위

Handoff 전략이 왜 필요한지는 세 가지 서로 다른 현상에서 출발한다.

📉

Context rot

컨텍스트가 길어질수록 중간 정보가 덜 참조되는 "lost in the middle" 현상. 커뮤니티 경험칙 기준 60% 사용률 근처에서 품질 저하를 체감한다고 보고.

⚡

Auto-compact 비대칭성

auto-compact는 모델이 가장 덜 똑똑해진 순간에 발동된다. Anthropic 공식 블로그도 이 구조적 문제를 인정. 요약 과정에서 다음 턴에 필요한 맥락이 잘려나간다.

🫥

Context amnesia

새 세션은 백지로 시작. CLAUDE.md는 불변 규약을 이어주지만 "어제 어떤 접근을 시도했고 왜 폐기했는지"는 이어주지 못한다.

중요 수치 출처 "60%" 임계점은 Anthropic의 공식 권고가 아닌 커뮤니티의 경험칙이다. 정확한 임계점은 작업 성격에 따라 달라진다.

전환 시나리오 분류

Handoff를 한 가지 방법으로 처리하려는 시도는 대부분 실패한다. 상황에 맞는 도구가 따로 있다.

시나리오특징기본 전략
In-session 연속 같은 task 계속 계속 이어가기
실패 후 재시도 방금 시도가 틀림 /rewind + 학습 반영
같은 task, 새 세션 컨텍스트 오염/포화 Document & Clear
관련 task, 새 세션 구현 → 문서화 등 /clear + brief prompt
무관한 task 완전한 전환 /clear
며칠 뒤 재개 시간 간격 큼 Handoff 문서 → 새 세션
Multi-agent 조율 여러 Claude 인스턴스 Registry + report 구조
Anthropic 공식 휴리스틱 "새로운 task를 시작할 때는 새로운 세션을 시작하라." 유혹은 "이 세션이 이미 많이 알고 있으니 계속 쓰자"이지만, 대부분의 경우 오염된 컨텍스트로 인한 품질 저하가 재시작 비용을 넘는다.

Tier 1 — 세션 내 컨텍스트 관리

Tier 1 · In-Session

가장 먼저 손댈 수 있는 레이어는 현재 세션 자체의 관리다.

/rewind — 가장 저평가된 도구

Esc Esc 두 번으로 발동. Claude가 5개 파일을 읽고 접근 A를 시도해 실패했다면, 본능적으로는 "그 방식 말고 B로 해줘"라고 이어 쓴다. 그러나 파일 read 직후로 돌아가서 "A는 foo 모듈이 해당 API를 노출하지 않으니 B로 바로 가자"라고 다시 프롬프트하는 편이 깔끔하다.

효과 실패한 시도는 컨텍스트에서 사라지고, 학습은 다음 프롬프트에 녹아든다. 불필요한 컨텍스트 오염 없이 재시도 가능.

/compact — Focus 없이는 쓰지 않는다

지시 없이 쓰면 결과가 예측 불가능하다. 항상 아래처럼 focus를 명시한다:

/compact focus on auth refactor decisions, drop debug logs
커뮤니티 관찰 Shrivu Shankar 같은 시니어 사용자들은 아예 /compact를 회피하고 후술할 Document & Clear로 간다. 자동 compact도 불투명해서 신뢰하지 말라는 것이 공통된 감상이다.

Subagent — main context를 더럽히지 않는 탐색

✦

언제 쓰나

"authentication 시스템이 토큰 갱신을 어떻게 처리하는지, OAuth 유틸이 있는지 subagent로 조사해줘"라고 요청하면 수십 파일을 읽지만 main context에 돌아오는 건 요약 몇 단락뿐이다.

⚠

남용 주의 (Tier 4에서 자세히)

Custom subagent를 많이 만들면 main agent가 컨텍스트를 빼앗겨서, 자기 코드의 테스트 방법조차 subagent를 호출해야 아는 상태가 된다.

Tier 2 — 단기 핸드오프 (Document & Clear)

Tier 2 · Short-Term Handoff

같은 프로젝트에서 세션만 새로 시작해야 할 때 가장 신뢰할 만한 패턴이다.

1

현재 상태를 .md로 dump

Claude에게 현재 상태를 Handoff 문서(.md)로 정리하도록 지시한다.

2

/clear로 세션 초기화

오염된 컨텍스트를 완전히 비운다.

3

새 세션에서 재개

"X.md를 읽고 이어서 작업해"라고 시작한다.

Handoff 문서 구조 (오픈소스 /transfer-context 기준)

  • Summary 이번 세션에 완료된 것 (1-3문장)
  • Key Decisions 결정과 근거
  • Traps to Avoid 실패한 접근, 다음 세션이 빠지기 쉬운 함정
  • Working Agreements 사용자 선호 (예: "review before committing")
  • Relevant Files path:L10-L45 — 왜 중요한지
  • Open Work 상태로만 서술. "X is not yet implemented"는 OK, "Implement X next"는 금지
  • Prompt for New Chat 새 세션에 붙여넣을 프롬프트. 마지막에 검증 지시 포함 필수
Open Work — 명령형 금지 "Implement X next"라고 쓰면 새 세션이 맹목적으로 실행한다. "X is not yet implemented; it depends on the backoff util being finalized first"처럼 상태 서술형으로 쓴다. 세션이 현재 상황을 이해하고 다음 행동을 스스로 결정하게 해야 한다.
Handoff = Hypothesis 검증 지시가 중요한 이유: Handoff 문서의 주장이 틀릴 수 있다. 이전 세션이 혼동 상태에서 문서를 썼다면 새 세션이 그 오류를 그대로 이어받는다. "나열된 파일을 실제로 Read 도구로 읽어. 요약본이라고 주장하지 말고, 이 문서의 주장을 코드와 대조해 검증하고, 내 지시를 기다려" 식의 검증 지시를 마지막에 포함한다.
토큰 절감 효과 (Black Dog Labs 측정) 이 패턴은 10,000+ 토큰의 지식 전달을 1,000-2,000 토큰으로 줄인다. 주 3-5회 세션 전환 시 주간 30-50K 토큰 절감 효과.

Tier 3 — 영구 메모리 계층

Tier 3 · Persistent Context

Handoff 문서는 개별 전환의 해결책이지만, 반복되는 컨텍스트는 영구화해야 매번 다시 쓰지 않는다.

CLAUDE.md 계층

Repo root, 서브디렉토리, 사용자 홈(~/.claude/CLAUDE.md)까지 계층적으로 로드된다.

# CLAUDE.md 담을 것 (변하지 않는 것)
아키텍처 규약, 빌드 명령, 코딩 스타일
도메인 용어집, 핵심 원칙

# CLAUDE.md에 넣지 말 것 (변하는 것)
현재 작업 상태, 이번 주 진행 사항
→ 매 세션마다 토큰 낭비 + 정기적 prune 필수

Report registry 패턴

Ilyas Ibrahim이 제안한 구조로, multi-agent나 long-term 프로젝트에 특히 잘 맞는다.

.claude/reports/
├── _registry.md          # 50줄짜리 index
├── analysis/             # 조사/리서치
├── arch/                 # 아키텍처 결정, ADR, spec
├── bugs/                 # 버그 리포트, 근본 원인
├── commits/              # 커밋 문서
├── design/               # UI/UX 결정
├── handoff/              # 세션 간 전달
├── impl/                 # 구현 상세
├── review/               # 코드 리뷰 결과
├── tests/                # 테스트 결과
└── archive/              # 완료/대체된 리포트
핵심 원리 main agent가 5,000줄의 전체 리포트가 아닌 50줄의 registry만 읽는다. 필요한 리포트만 on-demand로 컨텍스트에 들어간다. Multi-agent 조율 시 agent A가 만든 리포트를 agent B가 무시하는 "context amnesia" 현상을 구조적으로 차단한다.

Tier 4 — 크로스 세션 조율

Tier 4 · Cross-Session Orchestration

여러 세션, 여러 에이전트가 같은 프로젝트에서 공존할 때 필요한 상위 구조다.

Spec-Driven Development

PRD나 spec 문서 자체가 handoff 매체가 된다. 어느 세션이 spec을 쓰면 다른 세션은 그 spec을 읽고 구현한다. Claude는 자유 대화보다 명시적인 문서를 기반으로 작업할 때 훨씬 일관적이다. Spec은 의도적인 "외부 메모리"이며, 인간의 리뷰와 Git 버전 관리가 함께 작동한다.

ADR로 결정 기록

Handoff 문서의 "Key Decisions" 섹션이 반복적으로 같은 주제를 다룬다면 ADR(Architecture Decision Record)로 승격시켜야 한다. ADR은 세션 수명을 넘어서고, CLAUDE.md에서 참조되고, 코드 리뷰 시 기준이 된다.

Git commit message를 handoff 매체로

feat: add OAuth refresh (ADR-0012)

다음 세션이 git log --oneline만 읽어도 맥락의 상당 부분을 복원한다. 단, commit message의 명확한 한계가 있다 — "왜 그 결정을 내렸는지, 어떤 대안을 배제했는지"는 담기지 않는다.

해법 commit message와 ADR/handoff 문서의 이중 기록. 성공 정보는 코드에 남지만 실패·배제 정보는 따로 기록하지 않으면 소실된다.

Master-Clone vs Lead-Specialist

Custom subagent(Lead-Specialist)를 많이 만들면 main agent가 컨텍스트를 빼앗겨서, 자기 코드의 테스트 방법조차 subagent를 호출해야 알 수 있는 상태가 된다. Shrivu Shankar는 CLAUDE.md에 모든 맥락을 놓고, main agent가 동적으로 Task/Explore로 자기 복제본에 위임하는 Master-Clone 구조를 선호한다. Handoff 관점에서도 전달할 "특화 에이전트 상태"가 따로 없어 단순하다.

Handoff 문서 작성 실전 규칙

구조보다 더 중요한 것은 작성 방식이다. 같은 섹션을 써도 뉘앙스 하나가 다음 세션의 품질을 가른다.

1

명령형 금지 → 상태 서술형

"Implement the retry logic" ❌
"Retry logic is not yet implemented; it depends on the backoff util being finalized first" ✅

2

파일 참조는 라인 번호까지

src/auth/TokenService.kt:L45-L72 — refresh 로직, race condition 의심됨
단순히 "TokenService를 봐"보다 훨씬 강력하다. 새 세션이 정확히 어디서부터 시작할지 안다.

3

CLAUDE.md 중복 절대 금지

Handoff 프롬프트 끝에 "Read CLAUDE.md first. Do NOT restate anything already covered there" 지시를 포함한다. 그렇지 않으면 토큰 낭비 + 첫 응답이 불필요하게 길어진다.

4

실패를 명시적으로 기록

"Traps to Avoid" 섹션이 handoff의 가치를 가장 많이 올린다. 성공 정보는 코드에 남지만 실패 정보는 handoff에 남기지 않으면 소실된다.

5

토큰 예산 의식 — 2,000 토큰 이내

Handoff 문서가 커지면 그 자체로 컨텍스트 부담이 된다. 상세 내용은 .claude/reports/의 개별 리포트로 분리하고, handoff는 registry 수준에서 참조만 한다.

/catchup 커스텀 슬래시 명령 (Shrivu Shankar) /clear 직후에 "현재 git branch의 변경 파일을 전부 읽어라" 한 줄 프롬프트를 /catchup으로 단축하면 코드 수준의 현재 상태를 빠르게 복원할 수 있다. Claude Code v2.1.101+부터 커스텀 슬래시 명령은 .claude/skills/<name>/SKILL.md 경로가 권장 형태. (기존 .claude/commands/도 동작)
