Grafana 운영 표준
community helm + PVC + GitOps + 베이스/사용자 하이브리드

GKE Autopilot→Standard 마이그레이션, Helm chart EOL, OIDC 인증 도입이 동시에 압박하는 시점에, 신규 Grafana 인스턴스 배포 표준을 확립한다. chart 선택·DB 영속성·백업 정책·dashboard 관리 모델을 한 번에 결정하여 이후 모든 Grafana 운영이 같은 기준을 따르도록 한다.

배경

동시에 압박하는 4가지 변화

회사는 R&D 인프라 모니터링용 Grafana 1대를 운영 중이다. GKE 마이그레이션·chart EOL·인증 정상화·dashboard 관리 모델 변화라는 네 가지 결정 압박이 같은 사이클에 집중되었고, 신규 Grafana를 세우는 이 시점이 운영 표준을 재정립할 유일한 자연스러운 기회이다.

압박 01
인증 정상화 (RDDP-456)
익명 접근 차단 → dex OIDC (generic_oauth) 로그인으로 전환. 사용자·role·org가 Grafana 내부 DB에 저장되며, DB 영속성이 본질 문제로 부상.
압박 02
GKE 마이그레이션 (ADR-008)
GKE Autopilot → Standard 전환. test-infra-gke-cluster 폐기 후 새 Standard 클러스터에 Grafana를 신규 배포 + blue-green swap으로 이전.
압박 03
Helm chart community 이관
2026-01-30부로 grafana/helm-charts가 grafana-community/helm-charts로 이관. 기존 v8.15.0은 EOL repo의 EOL 직전 버전.
압박 04
Dashboard 관리 모델
기존 sidecar + ConfigMap 패턴 + 사용자 UI 직접 편집이 혼재. 베이스(코드)와 사용자(UI)의 경계를 명확히 정할 시점.

"이번에 결정해 박지 않으면 다음 마이그레이션 사이클까지 운영 부담·재작업 부담이 누적된다."

결정 1

Chart = grafana-community/grafana helm chart

신규 Grafana 인스턴스 표준은 community helm chart로 한다. 매니페스트 모델은 표준 helm + GitOps 조합이며, custom resource(CRD)는 명시적으로 회피한다.

결정 내용
grafana-community/helm-charts — 기존 운영 노하우 그대로 활용
grafana/grafana(EOL) → grafana-community/grafana로 이관. values schema 100% 호환이므로 기존 8.15.0 운영 자산을 그대로 사용 가능하다. 모든 신규 Grafana 인스턴스는 이 chart로 ArgoCD Application(multi-source 가능)으로 배포한다.

Operator(옵션 2) 거부 사유

  • R-01회사 전체 컴포넌트(dex, ArgoCD, ExternalDNS)가 standard k8s primitives 사용 — 9개 CRD 도입 시 일관성 파괴
  • R-02Operator의 강점(multi-instance, 팀별 분산 선언)이 "1대 중앙 관리" 시나리오에서 실효 미미
  • R-03helm sidecar도 ConfigMap delete → dashboard 자동 제거 지원 — operator 고유 가치 아님
  • R-04community helm chart는 기존 운영 경험 있음, operator는 첫 도입으로 troubleshooting 노하우 없음
  • R-055개 dashboard 변환 부담이 위 단점을 압도하지 않음
결정 2

DB 영속성 = PVC

Grafana 내부 DB(사용자·role·org·API key 등)의 영속성은 chart의 PVC로 보장한다. Cloud SQL Postgres는 본 ADR 시점에서 채택하지 않는다.

검증 단계 (Lab)
PVC 5Gi / pd-standard
· persistence.enabled=true
· persistence.size=5Gi
· persistence.storageClassName=pd-standard
· access mode: ReadWriteOnce
운영 단계
PVC 30Gi / pd-balanced
· persistence.size=30Gi
· persistence.storageClassName=pd-balanced
· dashboard·history 누적 고려
· PD Snapshot Schedule 정식 적용
Cloud SQL 거부 사유: 현재 사용자 <50명, dashboard ~수십 개. Cloud SQL 인스턴스 신규 생성·VPC peering·IAM·백업 설정은 본 ADR 범위 외 과투자. PVC + PD snapshot으로 영속성·복구가 충분히 보장된다.
결정 3

백업 정책 = 2 레이어 방향 정의 (구체 구현은 후속)

PVC 단독으로는 노드 장애·DB 손상·blue-green 신규 배포 시 빈 PVC 문제가 있다. 두 레이어 백업이 의무임을 정의하고, 구체 구현은 별도 후속 작업으로 진행한다.

레이어대상방향구체화
인프라 레이어 Grafana DB (PVC → Persistent Disk) GCE PD Snapshot Schedule · Terraform 코드화 빈도·retention·복구 절차는 후속 결정
Application 레이어 사용자 dashboard (Grafana DB 내 application 자산) Grafana API 주기 export 또는 사용자 자율 export 자동화 도구(cronjob/GHA 등) 선정은 후속 결정
결정 4

Dashboard 관리 모델 = 베이스 / 사용자 하이브리드

Dashboard는 플랫폼팀이 관리하는 베이스 영역과 사용자가 자율 관리하는 영역으로 명확히 분리한다.

구분베이스 Dashboard사용자 Dashboard
관리 주체 플랫폼 엔지니어 사용자(Dashboard 작성자)
저장 위치 git repo infra/k8s/<cluster>/grafana/dashboards/*.json Grafana DB (사용자 UI에서 직접 생성)
변경 절차 git PR → ArgoCD sync → sidecar reconcile → Grafana API push Grafana UI Edit → Save → DB 즉시 반영
Grafana Folder Platform (또는 Base) User (또는 사용자별 sub-folder)
UI 수정 시 다음 sidecar reconcile에 코드 버전으로 덮어씀 (provisioned) 자유롭게 수정 가능
백업 책임 git PR history 결정 3의 Application 레이어 백업 + 사용자 자율
결정 5

Lab 검증 단계 vs 운영 단계 차이

본 ADR은 신규 배포 표준이지만, 검증(Lab)과 운영 단계는 일부 다른 설정을 가진다.

항목Lab 검증 (infra/k8s/lab/grafana/)운영 단계
DB PVC5Gi · pd-standard30Gi · pd-balanced
PD Snapshot검증 기간만 적용 (빈도는 후속 결정)정식 적용
베이스 Dashboard0개 (검증용 임시)5개 이상 (현행 grafana-dashboards/)
호스트grafana-lab.nfw.vntgcorp.com정식 호스트 (Terraform record 또는 wildcard)

결정 6 · 7 · 8

거부 사유 · 재평가 트리거

결정 6 — Operator 거부 / 결정 7 — PVC 채택 사유

결정 6 — Operator 거부
현재 시나리오에서 operator의 가치가 약함
· 회사: 1대 중앙 관리 모델 → multi-instance 강점 불필요
· sidecar도 dashboard 자동 lifecycle 지원
· 전사 CRD 도입 일관성 파괴
· 운영 노하우 없음 → troubleshooting 부담
결정 7 — Cloud SQL 거부
현재 규모에서 PVC + PD Snapshot으로 충분
· 사용자 <50명, dashboard ~수십 개
· Cloud SQL 도입 비용(~$25~50/월 + VPC + IAM) 은 과투자
· ReadWriteOnce 제약 = 단일 인스턴스에서 무관
· blue-green + PD snapshot으로 복구 가능

결정 8 — 재평가 트리거

트리거재평가 대상
Grafana 인스턴스 2대 이상으로 증가chart 결정 (operator 검토) + DB 결정 (Cloud SQL 검토)
사용자 수 200명 이상으로 증가DB 결정 (Cloud SQL 검토)
Dashboard 100개 이상 + 팀별 분산 선언 니즈chart 결정 (operator의 dashboard CR 가치 재평가)
grafana-community/helm-charts 거버넌스 붕괴 또는 EOLchart 결정 (operator 또는 다른 fork 검토)
사용자 dashboard 손실 사고 발생백업 정책 (자동화 강화)
사용자 dashboard 동시 편집 충돌 빈번DB 결정 (외부 DB 트랜잭션 격리 검토)
